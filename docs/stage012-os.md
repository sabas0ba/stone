# Stage 12: 簡易 OS と POSIX 風実行環境 設計文書

## 1. 目的と位置づけ

### 1.1 目的

Stage 11 までの処理系はベアメタル QEMU virt 上で動き，外界との接点は
UART (getc / putc) と test finisher (exit) しかない。ファイルが無いので
「複数の入力を開く」ことすらできず，リンカへはオブジェクトを連結して
標準入力から与えている ([stage008-elf-ld.md](stage008-elf-ld.md) 2.3)。
この形は入力が大きくなるほど成立しなくなる。

Stage 12 の目的は **自作の簡易 OS (カーネル) を作り，その上に POSIX 風の
実行環境を用意する** ことである。これで次が可能になる。

- ファイル I/O (`open` / `read` / `write` / `close`)。`stdio.h` の土台
- 記憶域の動的な要求 (`brk`)。malloc の固定領域 (1 MiB) の上限が外れる
- コマンドライン引数 (`argc` / `argv`) と終了コード。cc や ld を
  「コマンド」として起動できるようになり，Stage 13 (自立したビルド道具・
  シェル相当・テキストエディタ) の前提になる
- ホストとのファイル交換を UART の逐次転送ではなく **QEMU 起動時の
  イメージ注入** で行う (4 章)

[roadmap.md](roadmap.md) Phase B の 2 段目である。

### 1.2 非目標

- アドレス変換 (ページング / Sv32)。保護は特権レベルの分離のみ
- マルチタスク・スケジューラ。プロセスは一度に 1 つ (逐次実行)。
  プログラムからのプログラム起動 (spawn) は Stage 13 で扱う
- ネットワーク・永続デバイス (ブロックデバイス経由のディスク)。
  ファイルシステムはメモリ上に置き，ホストとの授受は共有領域で行う
- 動的リンク・スレッド・シグナル・浮動小数点 (従来どおり)
- ベアメタル環境の廃止。**既存 Stage の生成物とテストは一切変えない** (7.1)

## 2. 決定: 案 Y (自作の簡易 OS)

[roadmap.md](roadmap.md) 2.2 の 2 案について，当初は案 X (Linux
ユーザランド) を検討したが，**案 Y (自作 OS) に決定した**。

| 案 | 内容 | 判断 |
|---|---|---|
| X | Linux ユーザランドを実行環境とする (qemu-user 等の上で syscall を叩く) | 見送り |
| Y | 自作の簡易 OS と，その上の POSIX 風環境 | **採用** |

理由:

1. **成果物の純度。** 案 X はビルド経路の実行環境に他者の実行系
   (qemu-user なり実 Linux なり) を組み込むことになる。本計画の価値は
   「すべての世代成果物が自作の鎖の上にある」ことであり，実行環境も
   その一部である。L1 / L2 (GCC / Linux のビルド) は **処理系を鍛える
   ベンチマーク指標としての目標** であって，外部のソースや生成物を
   stone の世代成果物に混ぜてよい理由にはならない
2. **入力転送の現実性。** 大量のソースを UART で流し込むのは非現実的で
   あり，案 X でもファイル注入の仕組みは別途要る。ならば注入の仕組み
   (4 章) と自作 OS を組み合わせるほうが一貫する
3. **開発効率の向上が目的に含まれる。** OS の上にシェル相当・テキスト
   エディタ等の最低限の道具 (Stage 13) を揃え，ゲスト内で効率よく開発
   できる環境そのものを成果物とする

### 2.1 syscall ABI は RV32 Linux 互換にする

自作カーネルの syscall は，**番号・呼出し規約とも RV32 Linux と同じ**
にする (`a7` に番号，`a0`〜`a5` に引数，`ecall`，戻り値は `a0`。負値は
-errno)。

- 独自 ABI を発明しても値打ちがない。番号表は仕様であって実装ではなく，
  これを合わせることは純度ポリシーに反しない
- libc の環境部とユーザプログラムは，将来 (L2 で Linux が起動した時点で)
  無改変でそのまま実 Linux の上でも動く。ベンチマーク指標としての
  L1 / L2 への経路を保つ

カーネルが実装するのは表 (5.4) の数個だけであり，それ以外の番号は
-ENOSYS を返す。

## 3. 全体像

```
QEMU virt (RV32)
├── 共有領域 (memory-backend-file)     ... ホストと授受する FS イメージ (4 章)
├── カーネル (M モード, フラット形式)   ... trap 入口, syscall, ローダ (5 章)
└── ユーザプロセス (U モード, ELF)      ... cc/ld が作る普通のプログラム (5.5)
      └── libc (純粋部 + 環境部)
```

- カーネルは従来どおり `-bios` で 0x8000_0000 に置かれ，M モードで走る
- ユーザプログラムは **ELF 実行形式** で FS イメージ内に置かれ，カーネルが
  ロードして U モードで実行する。syscall は `ecall` で M モードへ戻る
- コンパイラ (cc) と言語・ABI は **変えない**。特権命令や ecall の実体は
  すべてリンカの前置部が持つ (5.2)

## 4. ホストとのファイル交換 (共有領域と FS イメージ)

### 4.1 注入の方法

QEMU の `memory-backend-file` (share=on) で，ホスト上のイメージファイルを
ゲスト物理アドレス空間の固定位置へマップする。ゲストの書込みはホスト側の
ファイルへそのまま現れるので，**入力の注入と成果物の回収が同じ 1 枚で
済む**。UART は従来どおり標準入出力 (端末) に使う。

ホスト側の道具 (`tools/mkfs.sh` / `tools/lsfs.sh` 相当) が
「ディレクトリ → イメージ」「イメージ → ディレクトリ」の変換を行う。
ホスト側 sh スクリプトの使用は現行の作法の範囲であり，ゲスト内での
自立は Stage 13 の課題である。

### 4.2 FS イメージの形式 (sfs)

単純な読み書き両用の形式を自作する。設計方針は bundle 形式
([stage009-pp.md](stage009-pp.md) 2.2) と同じ「名前と長さを並べるだけ」。

```
スーパーブロック: マジック 'sfs1', 領域全体の大きさ, ファイル表の位置と件数
ファイル表:       (名前 [パス文字列, NUL 終端], データ位置, 長さ, 有効フラグ) の列
データ:           追記割付け (削除は有効フラグを落とすだけ。詰め直しはしない)
```

- 名前空間はフラットで，`stage011/src/mal.c` のような **パス文字列を
  そのまま名前とする** (ディレクトリという実体は持たない)。ホスト側の
  変換道具がパスとの対応を取る
- カーネルの `open` / `read` / `write` はこの表を直接操作する。
  メモリ上の操作なのでキャッシュも同期も不要である
- 上限 (領域の大きさ・ファイル数) はイメージ作成時に決める

## 5. カーネルの設計

### 5.1 特権構成

M モードのカーネルと U モードのユーザプロセスの 2 段だけを使う。
アドレス変換は行わない (物理アドレス直)。この段階での特権分離の目的は
「ユーザの誤りからカーネルを守る」ことよりも，**`ecall` による制御の
移転をアーキテクチャの作法どおりに行う** ことにある (PMP による保護は
将来の裁量とし，当面は設定しない)。

### 5.2 カーネルの書き方: 特権命令は前置部に閉じる

カーネル本体は自作 cc の C89 で書く。ただし C では書けない箇所が 2 つある。

| 箇所 | 内容 |
|---|---|
| ブート入口 | レジスタ初期化，mtvec の設定，ユーザプロセスへの mret |
| trap 入口 | レジスタの退避・復帰，C のハンドラ呼出し，mret |

これらは **ld12 の「カーネル前置部」が機械語で持つ** (5.3)。ベアメタルの
「実行環境が提供するものはリンカの前置部が実体を持つ」という既存の作法
([stage008-elf-ld.md](stage008-elf-ld.md) 2.2) の延長であり，**cc に
inline asm や組込み関数を足さない**。

### 5.3 ld12: リンカの新世代

stage012/ に置き，前段の成果物 (stage008 の ld) でビルドする。従来の
フラット出力に加え，**入力の先頭 1 バイトで出力形式を選ぶ**。

| 形式 | 内容 |
|---|---|
| `'F'` | フラット (従来どおり。ベアメタルの前置部) |
| `'K'` | カーネル: フラット + カーネル前置部 (ブート入口・trap 入口。trap フレームを C のハンドラへ渡す) |
| `'E'` | ELF 実行形式 (ET_EXEC + プログラムヘッダ 2 本。`.bss` は `p_filesz = 0`)。ユーザプログラム用の前置部 (5.5) を持つ |

ベアメタルの ld.bin (stage008) は変更しないので，既存 Stage の SHA-256 は
すべて維持される。

### 5.4 syscall (第 1 弾)

RV32 Linux の番号で実装する。

| シンボル | 番号 | 内容 |
|---|---|---|
| `read` | 63 | fd 0 は UART RX，それ以外は sfs |
| `write` | 64 | fd 1 / 2 は UART TX，それ以外は sfs |
| `openat` | 56 | sfs の表を引く。作成 (O_CREAT) は表への追加 |
| `close` | 57 | |
| `brk` | 214 | ユーザ領域の末尾を伸ばす。戻り値は新しいブレーク (Linux 生の仕様) |
| `exit` | 93 | ユーザプロセスを終え，終了コードをカーネルへ返す |

それ以外の番号は -ENOSYS。エラーは負値 (-errno) で返し，libc 環境部が
`errno` へ写す。

### 5.5 ユーザプロセス

- カーネルは sfs から ELF 実行形式を読み，プログラムヘッダどおりに
  固定のユーザ領域 (カーネルより上位の物理アドレス) へ配置して，
  U モードへ mret する
- ユーザ側の前置部 ('E') が 2 本のスタックを整える。フレームスタック
  (x2) はカーネルが与えた初期 sp，データスタック (x9) は `.bss` 上に
  リンカが割り付けた領域の末尾である。argc / argv を本処理系の呼出し規約
  (データスタック渡し) で `main(argc, argv)` へ渡し，返却値を `exit` へ
  渡す。引数を使わない既存の `main()` もそのまま動く (取り出す個数は
  仮引数の個数で決まる。[stage010-c89.md](stage010-c89.md) 16 章)
- syscall スタブ (read / write / openat / close / brk / exit) と
  getc / putc の互換シンボル (read / write の 1 バイト版) も 'E' の
  前置部が提供する。**Stage 11 までの libc とテスト資産は無改変で
  OS 上でも動く**
- 起動するプログラムと引数は，当面 sfs 内の固定名 `boot` に書かれた
  1 行で与える。対話的な起動 (シェル) は Stage 13

## 6. libc の再編: 純粋部と環境部

### 6.1 分け方

```
lib/            純粋部 (環境に依存しない。従来どおり)
  string.c ctype.c stdlib.c
lib/posix/      環境部 (POSIX 風 syscall の上に立つ)
  sys.c         open (openat の包み) / errno / sbrk 相当
  morecore.c    malloc の供給源 (brk 版)
  stdio.c       FILE と stdio (第 4 部)
```

syscall ABI が Linux 互換 (2.1) なので，環境部は「自作 OS 用」と
「実 Linux 用」を分ける必要がない。1 種類で両方に通じる。

### 6.2 malloc の下回りの差し替え

Stage 11 第 2 部の設計どおり，差し替えるのは `morecore` 1 関数である
([stage011-libc.md](stage011-libc.md) 7.1)。固定領域版はベアメタル用に
残し，brk 版を環境部に置く。利用者はどちらか一方を stdlib.o と並べて
リンクする。「必要なオブジェクトだけ並べる」リンクの単位の設計が
そのまま環境の選択になる。

### 6.3 errno と errno.h

syscall の失敗 (-errno) を環境部が大域変数 `errno` へ写し，関数は C の
慣例どおりの値 (-1 や NULL) を返す。`errno.h` には当面必要な値
(ENOENT, EBADF, ENOMEM, EINVAL, ENOSYS など) だけを定義する。
Stage 11 で保留した `strtol` の ERANGE もここで導入できる。

### 6.4 stdio.h (第 4 部)

- `FILE` は fd と 1 バイトの押し戻し (ungetc 用) を持つ構造体。
  バッファリングはしない (正しさが先。速度は測ってから)
- `stdin` / `stdout` / `stderr` は fd 0 / 1 / 2 に固定で結ばれた実体
- 第 1 弾: `fopen` `fclose` `fgetc` `fputc` `fread` `fwrite` `fgets`
  `fputs` `feof` `ferror` `fflush` (無バッファなので何もしない)
- `printf` / `fprintf` は `%d` `%u` `%x` `%c` `%s` `%%` と最小の幅指定
  だけを実装する (可変長引数は実装済み)

## 7. 既存資産との関係

### 7.1 ベアメタルは凍結して残す

Stage 2〜11 の生成物・テスト・SHA-256 は一切変えない。ブートストラップ鎖
(hex0 → … → cc10l) はベアメタル上で動き続け，Stage 12 の成果物
(ld12・カーネル・環境部) はその鎖の先に足される。cc / ld 自身を OS 上へ
移す (自身を ELF 実行形式でリンクし直す) のは Stage 13 の課題である。

### 7.2 テスト実行系

`tools/run-os.sh` を足す: カーネルと sfs イメージ (テスト素材入り) を
組んで QEMU を起動し，UART を標準入出力に接続し，終了コードを回収する。
イメージの生成・回収はホスト側の変換道具 (4.1) が行う。環境 (パッケージ)
の追加は不要である (qemu-system-riscv32 のみで完結する)。

## 8. 部割りと検証計画

| 部 | 内容 | 検証 |
|---|---|---|
| 第 1 部 | 共有領域と sfs: イメージ形式，ホスト側変換道具，ベアメタルのテストプログラムによる読み書き | ディレクトリ → イメージ → ディレクトリの往復が同一。ゲストからの読取り・書込み・追加がホスト側で見える |
| 第 2 部 | ld12 ('K' / 'E') とカーネル: trap・syscall・ELF ローダ・単一プロセス | hello (putc) が OS の上で動き終了コードが返る。readelf でプログラムヘッダを検査。argc/argv を写すプログラム。未実装番号が -ENOSYS |
| 第 3 部 | libc 環境部: open/read/write/close の包み，errno，brk 版 morecore | ファイルの読み書きと内容照合。存在しないファイルで errno = ENOENT。malloc が 1 MiB を超えて確保できる。Stage 11 の libc テスト (str/cty/mal/srt/num/word) を OS 上でも実行して同値 |
| 第 4 部 | stdio (FILE / fopen 系 / printf 最小) | 書式の境界 (0, 負数, INT_MIN, %x, 幅)。ファイル経由の往復。cat 相当・wc 相当の自己適用 |

各部とも従来どおり: 設計は本書へ追記し，生成物の SHA-256 を記録し，
tests/stage012 で照合する。

## 9. Stage 13 への接続

第 4 部まで終えると「ファイルを開き，読み書きし，引数を受け取り，
終了コードを返す」コマンドが OS の上で書ける。Stage 13 では

- spawn / wait 相当の syscall を足し，シェル相当を作る
- 最低限のテキストエディタ (ed 風の行エディタから始める) を作る
- cc / ld / pp を ELF 実行形式でリンクし直して OS 上へ移し，
  ホスト側の sh スクリプトなしでチェーン全体を再ビルドする

を行い，ゲスト内で開発が完結する環境を整える。
