# Stage 9: プリプロセッサ 設計文書

## 1. 目的と位置づけ

### 1.1 目的

Stage 8 で翻訳単位を分割できるようになったが，翻訳単位のあいだで宣言を
共有する手段がない。定数は各ファイルに書き写すほかなく，構造体定義は
複製するしかない。これは分割コンパイルの利点を大きく損なう。

Stage 9 の目的は **プリプロセッサ (pp)** を用意することである。
[roadmap.md](roadmap.md) Phase A の 2 段目にあたり，完了条件は
「`#include` `#define` (関数形式マクロ・可変長マクロ) `#if/#ifdef/#elif/#else/#endif`
`#undef` `##` `#` が動作し，ヘッダを共有した分割ソースがビルドできること」である。

外部の C 資産はほぼ例外なくプリプロセッサに依存しているため，
Phase C (外部資産の取り込み) の前提でもある。

### 1.2 名称

名称は **pp** とする。Unix の慣例に従えば `cpp` (C PreProcessor) だが，
`.cpp` が C++ のソース拡張子として広く使われており，本プロジェクトでも
将来 C++ を扱う可能性がある ([roadmap.md](roadmap.md) 2.1 案 A) 以上，
その名前は空けておく。`pp` なら 2 文字で `cc` / `ld` と揃い，
言語を含意しないので取り違えの余地がない。

### 1.3 独立した処理系にする理由

プリプロセッサをコンパイラ内部の一段として組み込む実装もあるが，本 Stage では
**独立した実行像 `pp`** とし，テキストからテキストへの変換器とする。

```
pp(bundle)  -> prog.i    (前処理済みソース)
cc(prog.i)  -> prog.o
ld(prog.o)  -> prog.bin
```

理由は 3 つある。

1. **単体で検証できる。** 入力テキストと出力テキストを直接比較できるので，
   マクロ展開の細かい規則を「生成バイナリを介さずに」試験できる
2. **cc を変更しないで済む。** cc.bin は Stage 8 のまま据え置けるため，
   Stage 9 の変更が既存の固定点検査を壊さない
3. 古典的な C ツールチェインの構成に一致する

### 1.4 非目標

- `#include` のディレクトリ探索・`-I` 相当。実行環境にファイルシステムがない
  (2.1 節) ため，探索対象は入力の束ねに限る
- `#line` によるトークン位置の追跡と，コンパイラへの位置情報の伝達
  (`#line` 指令自体は読み飛ばす)
- `_Pragma` 演算子，`#pragma` の解釈 (読み飛ばす)
- 三重字 (trigraph)，`\` による行連結を除く translation phase の厳密な順序
- GNU 拡張の `, ## __VA_ARGS__` (可変引数が空のときのカンマ削除)

## 2. 入力の与え方: 束ね (bundle)

### 2.1 問題

`#include "util.h"` は「名前で別のソースを開く」操作である。しかし
実行環境は UART のみで，ファイルを開く手段がない。Stage 8 のリンカが
複数のオブジェクトを連結して標準入力から受け取ったのと同じ問題である。

### 2.2 形式

ソース群を **名前つきで連結したもの** を標準入力から与える。これを
束ね (bundle) と呼ぶ。ld の「オブジェクトの連結」と違い，メンバに
名前が要る (`#include` が名前で引くため) 点だけが異なる。

```
bundle := "#!stone-bundle\n" member* EOT
member := "@" name " " size "\n" content
```

- `name` は空白を含まない 1..31 バイト。`size` は `content` の
  バイト数を 10 進で書いたもの
- **最後のメンバが前処理対象の翻訳単位**である。それ以外は `#include`
  で参照できる。`cat util.h main.c` と同じ並び (依存が先，本体が後) になる
- マジック `#!stone-bundle\n` で始まらない入力は，全体を 1 個の
  無名メンバ (名前 `-`) とみなす。この場合 `#include` は必ず失敗する。
  束ねを作らずに `printf '...' | pp` と書けるようにするための規定である

束ねは `tools/bundle.sh` が生成する。

```
sh tools/bundle.sh util.h main.c | qemu pp.bin > main.i
```

### 2.3 出力

前処理済みのテキストを標準出力へ書き，末尾に EOT (0x04) を置く。
cc の入力終端が EOT なので，そのまま `pp | cc` と繋げられる。

## 3. 仕様

### 3.1 字句とテキストの扱い

- **行連結**: `\` の直後が改行なら，両方を取り除く。文字列・コメントの
  内側を含め，あらゆる位置で先に処理する
- **コメント**: `/* */` と `//` を空白 1 個に置き換える。文字列・文字
  リテラルの内側では解釈しない。**cc は `//` しか解さないので，
  `/* */` が使えるようになるのは本 Stage の副次的な成果である**
- **識別子**: `[A-Za-z_][A-Za-z0-9_]*`，31 バイト以下。sc 言語の識別子は
  英小文字のみだが，マクロ名は慣習的に大文字であり，取り込む外部ヘッダも
  大文字を使う。**pp は入力言語より広い字句を受け付ける**
  (前処理後のソースが cc の制限に収まるかどうかは利用者の責任である)
- 数 (pp-number) は途中に現れる `e+` `e-` を含めて 1 個の字句として素通しする。
  マクロ名の誤検出 (`0x1e` の `e`) を防ぐため
- 文字列・文字リテラルは逐語で素通しする。中にマクロ名があっても展開しない

### 3.2 指令

行頭 (空白のみが先行する位置) の `#` から始まる行を指令として処理する。
指令行は出力に残さず，代わりに改行 1 個を出力する。

| 指令 | 動作 |
|---|---|
| `#define N body` | オブジェクト形式マクロ |
| `#define N(a,b) body` | 関数形式マクロ。`N` の直後に空白なしで `(` |
| `#define N(a,...) body` | 可変長マクロ。`__VA_ARGS__` で参照する |
| `#undef N` | 定義を取り消す |
| `#include "n"` / `#include <n>` | 束ねの中から名前 `n` のメンバを差し込む。両形式とも探索先は同じ |
| `#if expr` | 定数式が非 0 なら以下を採用 |
| `#ifdef N` / `#ifndef N` | 定義の有無で分岐 |
| `#elif expr` / `#else` / `#endif` | 分岐の継続・既定・終了 |
| `#error` | 終了コード 5 で停止 |
| `#warning` `#pragma` `#line` | 読み飛ばす |
| `#` のみ | 何もしない (空指令) |

抑止されている区間 (`#if` が偽の枝) では，`#if` 系の指令だけを処理して
入れ子を数え，他の指令と本文は捨てる。

### 3.3 マクロ展開

置換の規則は C89 に従う。

- **引数の事前展開**: `#` `##` の作用対象でない仮引数は，実引数を
  展開しきってから置き換える
- **文字列化 `#`**: 直後の仮引数の実引数を，展開せずに文字列リテラルへ変える。
  内部の `"` と `\` は逃がす。実引数の内部の空白列は空白 1 個に畳む
- **連結 `##`**: 左右の字句を隙間なく繋ぐ。作用対象の仮引数は展開しない。
  オブジェクト形式マクロの本体でも働く
- **再帰の抑止**: マクロ M の置換結果を走査しているあいだ，M は展開しない
  (入力フレームの積みに M の印を持たせ，印のあるマクロは名前のまま出力する)
- **関数形式マクロの呼出し**: 名前の後に空白・改行を跨いで `(` が続く場合のみ
  展開する。続かなければ名前をそのまま出力する
- 展開結果の末尾には空白 1 個を補う。`-A` のように，展開結果と後続の文字が
  意図せず 1 個の字句へ繋がるのを避けるため
- 定義済みマクロ: `__STDC__` = 1, `__STONE__` = 1。`__FILE__` は現在の
  メンバ名の文字列，`__LINE__` は現在の行番号 (どちらも表を引かずに直接処理する)

### 3.4 `#if` の定数式

`defined N` / `defined(N)` を先に 1 / 0 へ置き換え，次にマクロを展開し，
最後に評価する。展開後に残った識別子は 0 とみなす。

演算子は優先順位の低い順に
`?:` `||` `&&` `|` `^` `&` `==` `!=` `<` `>` `<=` `>=` `<<` `>>` `+` `-`
`*` `/` `%`，単項 `+` `-` `!` `~`。すべて 32 bit 符号つきで計算する。
数は 10 進・`0x` 16 進・文字リテラルを解し，`u` `l` の接尾辞は読み飛ばす。

`||` `&&` `?:` は短絡しない (両辺を評価する)。これは実装を小さく保つための
割切りである。ただし短絡を期待する `defined(N) && N > 3` のような式で
0 除算が起きないよう，**0 による除算・剰余の結果は 0 と定める**。

### 3.5 エラー

| 終了コード | 条件 |
|---|---|
| 0 | 正常終了 |
| 1 | 字句・指令の誤り (未終端のコメント，未知の指令，束ねの破損) |
| 2 | `#include` の対象が束ねに無い |
| 3 | マクロ呼出しの誤り (実引数の個数不一致，`)` が来ないまま入力終端) |
| 4 | 条件指令の誤り (対応しない `#else` / `#endif`，未終了の `#if`，式の誤り) |
| 5 | `#error` に到達 |
| 6 | 容量超過 (表・緩衝域・入れ子の深さ) |

### 3.6 容量

| 対象 | 上限 |
|---|---|
| 入力全体 | 256 KiB |
| 束ねのメンバ数 | 64 |
| マクロ定義数 | 512 |
| マクロ本体の総量 | 128 KiB |
| 仮引数・実引数の個数 | 31 |
| 入力フレームの深さ (`#include` とマクロ展開の合計) | 64 |
| 識別子・メンバ名 | 31 バイト |
| 指令 1 行 | 8 KiB |

## 4. 実装の構造

### 4.1 入力フレームの積み

pp の中核は **文字を 1 個ずつ引き出す積み (スタック)** である。
底が翻訳単位で，`#include` はファイルのフレームを，マクロ展開は
置換結果のフレームを積む。フレームが尽きれば自動的に下へ戻る。

```
  +----------------------+
  | 展開: BAR の置換結果 |  <- 現在ここから読んでいる
  +----------------------+
  | 展開: FOO の置換結果 |     (FOO の中から BAR が現れた)
  +----------------------+
  | ファイル: util.h     |
  +----------------------+
  | ファイル: main.c     |  <- 底 (翻訳単位)
  +----------------------+
```

この構造にすると，走査の本体 (`scan1`) は「1 個の字句を処理する」だけの
関数になり，再走査・入れ子の展開・include の復帰がすべて同じ仕組みで片づく。
再帰抑止も「積みの中に自分の印があるか」で判定できる。

### 4.2 2 本のアリーナ

置換結果の文字列を置く領域が要る。フレームの寿命は後入れ先出しなので，
**スタック割付けのアリーナ** で足りる。フレームを積むときに割付け位置を
記録しておき，降ろすときにそこまで戻す。

アリーナは 2 本ある。

- `xb`: フレームが参照するテキスト (実引数の生テキスト，置換結果)
- `eb`: 実引数の事前展開の結果と，`#if` の式の展開結果

分ける理由は，事前展開の最中に「出力先 (`eb`) と，展開のために積む
フレームのテキスト (`xb`)」が同時に伸びるためである。1 本だと互いの
領域を跨いでしまう。

### 4.3 出力先の切替え

`emit` の行き先は 3 通りある。

| 条件 | 行き先 |
|---|---|
| 事前展開・`#if` の評価中 (`edep > 0`) | `eb` |
| `#if` が偽の区間 (`nfalse > 0`) | 捨てる |
| それ以外 | 標準出力 (`putc`) |

出力は前から順に書くだけで後戻りしないので，出力用の緩衝域は持たない。

### 4.4 sc 言語の制約に由来する書き方

pp.sc は cc (Stage 8) がコンパイルできる範囲で書く必要がある。
[stage005-sc.md](stage005-sc.md) 2 章のとおり，sc には
`for` `do` `switch` `break` `continue` `++` `+=` `sizeof` キャスト
初期化子・定数構文・列挙型が無い。したがって

- ループの途中脱出は完了フラグ (`done`) で表す
- 種別定数は大域変数として `init()` で設定する
- 表はすべて添字を共有する並行配列で表現する
- 再入する関数 (`subst` は実引数の事前展開を通じて自分自身に戻ってくる)
  が使う作業領域は，大域ではなくローカル配列に置く

## 6. 検証計画 (tests/stage009)

1. **ビルド再現**: `pp.bin` の SHA-256 が `stage009/pp.md` の記載値と一致する
2. **素通し**: 指令を含まない実在のソース (`cc.sc`, `ld.sc`, `pp.sc`) を
   pp に通してから cc + ld でビルドした結果が，通さずにビルドした結果と
   一致する。コメントの除去と行連結が意味を変えないことの検査でもある
3. **ヘッダの共有**: 共通ヘッダ (定数マクロ・関数形式マクロ・構造体定義) を
   `#include` する 2 つの翻訳単位を個別に前処理・コンパイルし，
   リンクして動作する
4. **マクロ**: オブジェクト形式・関数形式・入れ子・再帰抑止・`#`・`##`・
   可変長・`#undef` の展開結果をテキストで照合する
5. **条件**: `#if` の算術と優先順位，`defined`，`#ifdef` / `#ifndef`，
   `#elif` / `#else`，入れ子，抑止区間の中の指令が無視されること
6. **include**: 入れ子の `#include`，インクルードガード，`<>` 形式
7. **コメント**: `/* */` と `//` が空白になること，文字列の中では
   解釈されないこと
8. **エラー系**: 対象なし → 2，実引数の個数不一致 → 3，
   対応しない `#endif` → 4，`#error` → 5

## 7. Stage 10 への接続

本 Stage の時点では，ヘッダに書けるのはマクロと構造体定義に限られる。
大域変数の宣言を共有できないのは，sc に `extern` が無く，各翻訳単位の
宣言がそのまま `.bss` の定義になってしまうためである
(同じ名前が 2 つのオブジェクトで定義されるとリンカが多重定義とみなす)。
関数プロトタイプも無いため，他の翻訳単位の関数は未定義シンボルとして
暗黙に参照される。

`extern` / `static` によるリンケージの区別と関数プロトタイプは，
言語仕様の完成 (Stage 10) で扱う。ヘッダが「宣言を共有する場所」に
なるのはその時点である。
