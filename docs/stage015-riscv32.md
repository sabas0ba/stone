# Stage 15 第 5 部: tcc に RV32 の backend を足す

[stage015-tcc.md](stage015-tcc.md) 8.5 で採った道 (案 A) の作業記録。

## 1. なぜ要るのか

第 1 部の実測で **tcc には RV32 のコード生成が無い**と判った
(stage015-tcc.md 8.1)。開発枝 (mob) には `riscv64-gen.c` があるが，
RV64 であって RV32 ではない。本計画の鎖は Stage 1 から一貫して RV32 で
ある。

このままだと，我々の処理系が tcc をビルドできても，その tcc は RV32 の
コードを吐けない。**自分自身を作り直せない**ので，完了条件
(T2 == T3) が成り立たない。だから書く。

**この部は我々の処理系に依らない。** ホストの gcc で作った交差 tcc に
RV32 のコードを吐かせ，我々の QEMU と OS の上で走らせれば正しさは
確かめられる。第 2〜4 部 (処理系側の 64 bit 整数・浮動小数点・libc) と
並行して進められる。

## 2. 形: ファイルを写さず patch にする

素直な案は `riscv64-gen.c` (1496 行) を `riscv32-gen.c` へ写して直す
ことだった。**採らない。**

- 1496 行のうち RV32 で変わるのはごく一部である (4 章)。写すと
  「同じものが 2 つある」状態になり，上流の直しを追う手間が倍になる
- 我々の repo に他人のコードの複製が 1 本増える。tcc は LGPL 2.1 で
  あり複製・改変は認められているが，**複製せずに済むならそのほうが
  素性がはっきりする**

代わりに **同じファイルを `XLEN` で切り替える**。RV32 と RV64 の違いは
語長であって命令体系ではないので，これは無理のない形である。tcc 自身も
ARM の変種 (fpa / vfp / eabi / hardfloat) を 1 つの `arm-gen.c` で
切り替えている。

したがって第 5 部の成果物は **[stage015/tcc/riscv32.patch](../stage015/tcc/riscv32.patch) 1 枚**である。
差分がそのまま「RV32 に要る違い」の一覧になる。

## 3. 対象の選び方

新しい対象を足すと，普通は core (`tccgen.c` `tccelf.c` `tccasm.c`
`tccdbg.c` `libtcc.c`) に散らばる `#ifdef TCC_TARGET_RISCV64` を
すべて書き換えることになる。**40 箇所あまりある。**

| ファイル | `TCC_TARGET_RISCV64` の出現数 |
|---|---|
| tccgen.c | 16 |
| tccelf.c | 9 |
| tccasm.c | 5 |
| tccdbg.c | 5 |
| tcc.h | 8 |
| tcctok.h | 6 |
| libtcc.c | 2 |
| tcc.c / tccrun.c / conftest.c | 各 1 |

そこで **2 つのマクロを両方定義する**。

```
DEF-riscv32 = -DTCC_TARGET_RISCV64 -DTCC_TARGET_RISCV32
```

- `TCC_TARGET_RISCV64` … 「**RISC-V であること**」を表す
- `TCC_TARGET_RISCV32` … 「**語長が 32 bit であること**」を絞り込む

こうすると，上の 40 箇所あまりは 1 つも書き換えずに済む。RV32 と RV64 で
本当に違うところだけを `#ifdef TCC_TARGET_RISCV32` で分ければよい。

名前が実態とずれる (RV32 なのに `RISCV64` が定義されている) のは
確かに読みにくい。それでも採ったのは，**上流への差分を小さく保つことが
そのまま「上流の版を上げ直す手間」を決める**からである。差分が小さければ
commit を進めるときに壊れにくい。

## 4. その 1 の実測 (2026-08-11)

まず**語長だけ**を 32 bit に切り替えた状態を作り，何が動いて何が止まるかを
実測した。

### 4.1 通ったところ

`sh tools/tcc.sh riscv32` で **`riscv32-tcc` (交差コンパイラ) は出来る**。
そして ELF32 の RISC-V オブジェクトを吐く。

```
$ tmp/tcc/build/riscv32-tcc -c t.c -o t.o && file t.o
t.o: ELF 32-bit LSB relocatable, UCB RISC-V, double-float ABI, ...
```

`file` が「32-bit」「RISC-V」と読めているのが要点である。ELF の作りと
再配置の枠組み，`EM_RISCV`，オブジェクトの入出力は**そのまま使える**。

### 4.2 止まったところ (実物)

`int add(int a, int b) { return a + b; }` を吐かせて逆アセンブルすると，
RV32 に無い命令がそのまま並ぶ (`.insn` と表示されているものが不正)。

```
   0:	fe010113          	addi	sp,sp,-32
   4:	00113c23          	.insn	4, 0x00113c23     ← sd ra,24(sp)
   8:	00813823          	.insn	4, 0x00813823     ← sd s0,16(sp)
   c:	02010413          	addi	s0,sp,32
  10:	00000013          	nop
  14:	fea43423          	.insn	4, 0xfea43423     ← sd a0,-24(s0)
  18:	feb43023          	.insn	4, 0xfeb43023     ← sd a1,-32(s0)
  1c:	fe842503          	lw	a0,-24(s0)            ← これは合っている
  20:	fe042583          	lw	a1,-32(s0)
  24:	00b5053b          	.insn	4, 0x00b5053b     ← addw a0,a0,a1
  28:	00040113          	mv	sp,s0
  2c:	ff843083          	.insn	4, 0xff843083     ← ld ra,-8(s0)
  30:	ff043403          	.insn	4, 0xff043403     ← ld s0,-16(s0)
  34:	00008067          	ret
```

**間違いが「不正命令」として出る**のは良い性質である。黙って別の意味に
なる (Stage 14 の台帳でいう bad) のではなく，走らせれば必ず落ちる。

また libtcc1.a (実行時支援) のビルドは呼出し規約で止まる。

```
riscv32-tcc: riscv64-gen.c:750: gfunc_call: Assertion `r2' failed.
```

これも同じで，**未対応の経路は表明で落ちる**。我々の cc が未対応の型を
終了コード 5 で拒むのと同じ考え方である。

### 4.3 直すものの一覧

実測から，RV32 で手を入れる先は 4 つに分かれる。

| # | 直すもの | 中身 |
|---|---|---|
| 1 | 語幅の載せ替え | `ld`/`sd` (funct3 = 3) を `lw`/`sw` (funct3 = 2) へ。枠の退避位置 8 の倍数 → 4 の倍数 |
| 2 | 32 bit 幅演算命令 | `addw` `subw` `sllw` `addiw` … (opcode 0x1b / 0x3b) は RV64 だけの命令。RV32 では素の `add` `sub` `sll` `addi` (0x13 / 0x33) |
| 3 | 呼出し規約 (ilp32) | 引数レジスタは a0-a7 で同じだが，**64 bit の値がレジスタ 2 本にまたがる**。偶数番から使う規則，スタックへの積み方，構造体の渡し方，可変長引数 |
| 4 | 浮動小数点 | `fcvt.l.d` など「64 bit 整数と浮動小数点の変換」は RV32 に無い。`long double` は 16 バイト → 8 バイト (double と同じ) |

**64 bit 整数の演算そのものは書かなくてよい。** tcc は 32 bit 対象の
ために `tccgen.c` に `gen_opl()` を持っており，64 bit 演算を 32 bit の
組合せへ分解してくれる (i386 と arm がそうしている)。backend が
`gen_opl` を自前で持つのは RV64 のように 1 命令で足りるときだけである。
patch では RV32 のときに backend 側の `gen_opl` を外し，`tccgen.c` の
ものを使わせている。

> これは我々の cc の第 2 部と同じ結論に，別の道から辿り着いたことになる
> (stage015-tcc.md 6.1「案 2: 前段で上位・下位へ分解する」)。32 bit の
> 機械で 64 bit を扱う方法は結局そう多くない。

### 4.4 再配置は 32 bit でも RELA

tcc は `PTR_SIZE` で再配置の形を決めており，32 bit なら `Elf32_Rel`
(加数を項目に持たない) を使う。i386 と arm がそうだからである。

**RISC-V は 32 bit でも RELA (加数を項目に持つ) である。**
`riscv64-link.c` は `rel->r_addend` を読み書きするので，そのままでは
コンパイルが通らない。

```
riscv64-link.c:324: error: 'Elf32_Rel' has no member named 'r_addend'
```

`tcc.h` で RISCV32 のときだけ `ElfW_Rel` を `Elf32_Rela`，`SHT_RELX` を
`SHT_RELA`，節の名前を `.rela%s` にする。tccelf.c 側は
`#if SHT_RELX == SHT_RELA` で既に分かれているので，これで通る。

## 5. まだ決めていないこと: 浮動小数点

RV32 で浮動小数点をどう出すかは**まだ決めていない**。道は 2 つある。

| 案 | 中身 | 気になる点 |
|---|---|---|
| ハード (RV32D) | `f` レジスタと `fadd.d` などをそのまま使う | 我々の QEMU の CPU が D 拡張を持つか。我々の OS が例外や文脈切替で f レジスタを扱えるか |
| ソフト | 浮動小数点を整数演算の関数呼出しに落とす | libtcc1 に一式が要る。tcc の他の対象に前例が無い |

決めるのは第 5 部その 4 で，**先に我々の QEMU と OS が何を許すかを測る**。
なお**これは我々の cc の第 3 部 (処理系側の浮動小数点) とは別の話**で
ある。第 3 部は「cc が double を含む C を読めるか」，ここは「tcc が
double の計算をどんな命令で吐くか」であり，層が違う。

## 7. 検証

- **その場で見る**: `riscv32-tcc` が吐いたオブジェクトを逆アセンブルし，
  不正命令 (`.insn`) が無いことを見る。これは機械的に数えられる
- **走らせて見る**: 吐いたものを我々の QEMU と OS で実行し，結果を
  ホストの tcc (x86_64) が同じソースから作ったものの結果と突き合わせる
  (その 3 から。理由は 9.3)
- **RV64 を壊していないこと**: `riscv64-tcc` がビルドできるだけでなく，
  **patch を当てない素の tcc とバイト単位で同じオブジェクトを吐く**ことを
  見る。共通のファイルを触るので，ここがいちばん効く検査である

素材 (`docs/external/tcc`) が要る検査なので，**素材があるときだけ走らせる**
([stage014-external.md](stage014-external.md) 2.2 と同じ扱い)。

## 8. 「上流は無改変」の掟について

stage015-tcc.md 8.5 に「上流の tcc は無改変である。足すのは新しい
ファイルと設定であり，既存のソースは書き換えない」と書いた。
**これは守れない。訂正する。**

コンパイラに新しい対象を足す作業は，性質上，対象を選ぶ仕掛け
(`Makefile`・`tcc.h`・`libtcc.c`) と backend 本体に手が入る。「新しい
ファイルを足すだけ」で済ませる道は無い。

Stage 14 (bzip2 / zlib) の「無改変」は，**我々の処理系が他人のコードを
そのまま扱えることの証明**として意味があった。第 5 部はそれとは目的が
違う。ここでやっているのは**上流に無い機能を我々が書く**ことであり，
素材を改変するのは当たり前である。

守るものは残る。

- 素材の取得は commit で固定し，**当てる前に照合する** (tools/fetch.sh)
- 改変は **patch 1 枚に閉じ**，repo に置いて読めるようにする
- 我々の処理系が扱う C の側 (第 2〜4 部) では，**tcc のソースは 1 行も
  書き換えない**。書き換えたら「他人のコードを扱えた」ことにならない

## 9. その 2 の結果 (2026-08-11)

4.3 の 1 (語幅の載せ替え) と 2 (32 bit 幅演算命令) を入れた。

### 9.1 入れたもの

いずれも `XLEN` から導いた定数に置き換えただけで，場合分けの枝を増やして
いない。**RV32 と RV64 の違いは「語が何バイトか」に尽きる**というのが
この部の見立てであり，それがそのまま形に出た。

| 足した定数 | 意味 |
|---|---|
| `XBITS` | 語の bit 数 (`XLEN * 8`)。幅の狭い型への詰め直しの桁数に使う |
| `F3_LX` | 語 1 本の読み書きの funct3。RV64 は 3 (`ld`/`sd`)，RV32 は 2 (`lw`/`sw`) |
| `OP32` | opcode に足すと 32 bit 幅の演算になる値。RV64 は 8，**RV32 は 0** |

`OP32` が要点である。RV64 は 32 bit の演算に `addw` `sllw` などの専用命令を
使うので opcode に 8 を足していた。RV32 では語がもともと 32 bit なので，
足す値を 0 にすれば素の命令がそのまま正しい。演算の組立て
(`gen_opil`) は 1 箇所直すだけで済んだ。

| 直した先 | 内容 |
|---|---|
| 語の読み書き 20 箇所 | `EI(0x03, 3, …)` / `ES(0x23, 3, …)` を `F3_LX` へ |
| 枠の退避位置 | ra と s0 を置く `-8` / `-16` を `-XLEN` / `-2*XLEN` へ。可変長引数の退避も同様 |
| `gen_opil` | 32 bit 幅への足し込みを `OP32` に。シフト桁数の切り出しを 63 でなく 31 に |
| `load` の定数生成 | `addiw` を `addi` に |
| `gen_cvt_csti` | char / short への詰め直しの桁数を `XBITS - 8` / `XBITS - 16` に |
| `gen_cvt_sxtw` | int から語への符号拡張。**RV32 では何もしない** |

### 9.2 確かめたこと

`tests/stage015/tccprobe/int32.c` (乗除算・シフト・比較・幅の狭い型・
ポインタ演算・配列・分岐・繰返し・関数呼出し・大きな定数) を吐かせて
逆アセンブルすると，**RV32 に無い命令は 0 個**になった。その 1 の 4.2 で
並んでいた不正な語がすべて消えている。

```
   0:	fe010113          	addi	sp,sp,-32
   4:	00112e23          	sw	ra,28(sp)
   8:	00812c23          	sw	s0,24(sp)
   c:	02010413          	addi	s0,sp,32
  ...
  24:	00b50533          	add	a0,a0,a1
  2c:	ffc42083          	lw	ra,-4(s0)
  30:	ff842403          	lw	s0,-8(s0)
  34:	00008067          	ret
```

**RV64 側は 1 bit も変わっていない。** patch を当てない素の tcc で作った
`riscv64-tcc` と，patch を当てたもので作った `riscv64-tcc` に，同じ
ソース 7 本 (tcc 自身の実行時支援と上の検査ソース) を食わせて，出来た
オブジェクトがバイト単位で一致することを検査に入れた。`XLEN` が 8 の
ときはすべて元と同じ定数に畳まれる，という設計がそのとおりであることの
証拠である。

### 9.3 まだ走らせていない

生成コードは**まだ我々の QEMU で走らせていない**。理由は 2 つある。

1. 関数呼出しの規約 (4.3 の 3) が未着手なので，引数が語をまたぐ場合に
   `gfunc_call` の表明で止まる。実行時支援 (`riscv32-libtcc1.a`) が
   まだ作れない
2. tcc が吐く ELF は節ごとに 0x1000 境界へ揃うので，そのまま平らな
   バイト列に落としても番地が合わない。我々の QEMU は 0x8000_0000 に
   置いた平らな像を実行するので，**ELF の program header を読んで像を
   組む小さな道具**が要る

どちらもその 3 の仕事である。それまでの正しさの根拠は「不正命令が無い
こと」と「RV64 が変わっていないこと」に留まる。**これは弱い**ので，
その 3 で必ず実走に上げる。
