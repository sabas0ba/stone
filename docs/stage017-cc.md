# Stage 17 第 1 部: コンパイラをコマンドとして持つ

## 1. なぜここから始めるか

Stage 16 で「実物の `configure` が通る Unix」に到達した
([stage016-os.md](stage016-os.md) 12 章)。そのとき測って判ったことが
1 つある。

**`configure` が外部のプログラムを起動した 6 回は，すべてコンパイラ
関係だった。**

```
gcc -o ./conftest <src>/conftest.c
./conftest              (素 / compiler / version / minor の 4 回)
gcc -Wdeclaration-after-statement -Wunused-result -o a.out -c -xc -
```

道具 (`cat` / `grep` / `uname` …) の側はもう外を必要としていない。
残っているのは **`cc` と書けば動くもの**だけである。

これは [roadmap.md](roadmap.md) 2.1 の 3 案 (A: C++ 処理系 / B: x86-64
backend / C: GCC 4.7 に RV backend) の**どれを採っても等しく要る**。
Stage 16 を挟んだときと同じ理屈で，分岐の判断より先に済ませられる。
**案の決定はまだ行わない。**

## 2. 何が足りなかったか

鎖には `pp16` / `cc15p` / `ld16` があり，どれも完成している。
足りないのは 2 つだけだった。

### 2.1 平らな像しか無かった

`tmp/build/pp16.bin` などは**平らな像**である。QEMU に `-bios` で
0x8000_0000 へ置いて走らせる形で，我々の OS の上の実行形式ではない。

直し方は既にある。**リンカに `'E'` を前置して .o を組み直すだけ**で
ELF になる (Stage 13 の `pp13cmd` / `cc13cmd` / `ld13cmd` と同じ手。
[stage013-tools.md](stage013-tools.md) 7 章)。ソースは要らない。

| | 平らな像 (`-bios`) | OS のコマンド (ELF) |
|---|---|---|
| `pp16` | 53,432 | 53,892 |
| `cc15p` | 248,224 | 248,684 |
| `ld16` | 35,140 | 35,600 |

差はどれも 460 バイトちょうどだが，**中身が同じで包みだけが違う
わけではない**。実際に比べると本体も食い違う。`ld16` は前置部
(`'E'` あり / なし) で入口の作りを変えるからである ——

- 前置部なし: 0x8000_0000 に置かれ M モードで走る。`getc` / `putc` は
  UART を直に叩く
- `'E'` あり: OS の上の U モードで走る。`getc` / `putc` は
  `read(0)` / `write(1)` の 1 バイト版になる ([stage013-tools.md](stage013-tools.md) 7 章)

**同じ `.o` から出るが，同じバイト列にはならない。** 460 という差が
揃っているのは，どちらの前置部も大きさが同じで，ELF の頭のぶんだけ
増えているためである。

### 2.2 3 段を順に呼ぶものが無かった

ホストでは `tools/build.sh` が

```
bundle.sh ヘッダ... src | pp16 > x.i
cc15p < x.i > x.o
{ printf 'E'; cat x.o libc の .o...; printf '\0'; } | ld16 > out
```

と書いている。これを OS の側でやるものが要る。それが `cc17` である。

## 3. 駆動役の作り (`stage017/cc17.c`)

```
cc [-c] [-o OUT] [-W...] [-x c] [FILE | -]
```

段取りは 4 つで，`spawn` するのは 3 回だけである。

1. `/include` の下を読んで束ねを作る (最後に翻訳単位を置く)
2. `pp16` で前処理
3. `cc15p` で翻訳 (`-c` ならここまで)
4. `'E'` + `.o` の連結 + `'\0'` を組んで `ld16` へ流す

### 3.1 束ねは駆動役が自分で書く

ホストの `tools/bundle.sh` もゲストの `stage013/bundle.c` も
**「引数の綴りをそのまま名前にする」**。

```
bundle /include/stdio.h main.c
  -> @/include/stdio.h 1234
```

`#include <stdio.h>` はこれを引けない。sfs が平らだった頃は
「置いてある場所 = 名乗る名前」でよかったが，**sfs2 に階層が
できた今，束ねる側は 2 つを別に持つ必要がある**。

駆動役は「`/include` に置いてあって `stdio.h` と名乗る」ことを
知っているので，ここで組むのが素直である。`bundle` の世代を
足すより呼び出しが 1 つ減る。

### 3.2 `/lib` には 1 揃いだけ置く

駆動役は `/lib` の `.o` を**全部**並べて `ld16` へ渡す。したがって
`/lib` は「1 つのプログラムに対して過不足のない 1 揃い」でなければ
ならない。

最初これで落とした。`src/morecore.o` と `posix/morecore.o` の
両方を置いたところ，`ld` が多重定義で落ちた (終了コード 3)。
2 つは同じものの別実装 (フリースタンディング版と POSIX 版) である。

正しい 1 揃いは `tools/build.sh` が `sh2` を組むときに並べている
10 個である。`tools/build/stage017.sh` の `cc17_run` と
`tests/stage017/test.sh` の `mkroot` は**同じ並びを書いている**ので，
片方を触ったら両方を直す。

### 3.3 警告の選択肢は黙って受ける

`configure` は

```
$cc $OPT1 $OPT2 -o a.out -c -xc - < /dev/null > cc_msg.txt 2>&1
for o in $OPT1; do
  if ! grep -q -- $o cc_msg.txt; then CFLAGS="$CFLAGS $o"; fi
done
```

と書く。**「警告文に選択肢の名前が出てこなければ，その選択肢は
使える」**という判定である。したがって駆動役は `-W...` を受けても
**何も言ってはいけない**。「知らない選択肢だ」と文句を言うと，
`configure` はそれを「使えない」と読む。

`< /dev/null` から読むことにも注意がいる。ここで空装置が要る
([stage016-os.md](stage016-os.md) 11.5)。

## 4. 到達点

`tests/stage017/test.sh` が 5 件を見る。

### 4.1 我々の OS が自分だけで C を翻訳して走らせる

```
hello-build 0
hello from cc on stone
hello-run 0
selfhost-build 0
struct 25
fib 144
sort 1 2 3 4 5
sprintf fmt-42-ff
malloc ok
strlen 10
selfhost-run 0
```

`selfhost.c` は構造体・再帰・`qsort`・`sprintf`・`malloc`・`strlen` を
通す。**`/lib` の 1 揃いが正しく引けているか**が主な狙いで，1 つでも
欠ければリンクで落ちる。期待値はホストの `cc` の出力とも突き合わせる ——
我々の処理系とホストで答えが違うなら，どちらかが間違っている。

### 4.2 `configure` が我々のコンパイラを見つける

```
conftest-build 0
unknown / 0 / 0 / no
C compiler          cc (0.0)
configure-rc 0
CC=cc
CC_NAME=unknown
```

**`CC_NAME=unknown` が要点である。** `configure` はコンパイラを
見つけられなかったとき `cc_name` を空のままにし，`config.mak` には
`gcc` と書く。Stage 16 で `--cc=false` を渡したときはそうなっていた。
`unknown` と書かれているということは，**`conftest.c` を実際に組んで
走らせ，その答えを読んだ**ということである。

`unknown` なのは我々の `cc` が `__GNUC__` も `__TINYC__` も
定義しないからで，故障ではない。`conftest.c` は前処理の定義済み
マクロで相手を見分ける。

所要は 6 秒である (kernel22 の上で `hello` / `selfhost` / `conftest` を
組み，`configure` を 1 回通して)。

### 4.3 CI では走らない部分がある

4.2 は `docs/external/tcc` を要る。外部ソースは repo に取り込まない
決まりなので (`tools/fetch.sh` の頭)，**CI では飛ばす**。
Stage 16 の `configure` の節と同じ扱いである。飛ばしたことは
はっきり出す。

## 5. まだ無いもの

| | 状態 |
|---|---|
| `-I` / `-D` を `pp16` へ渡す | 無い。束ねに何を入れるかは `/include` 決め打ち |
| 複数の翻訳単位 (`cc a.o b.o -o x`) | 無い。1 本だけ |
| `-l` / ライブラリの選択 | 無い。`/lib` を丸ごと並べる |
| `ar` | 無い。`configure` の `AR=ar` はまだ嘘である |
| `__GNUC__` などの定義済みマクロ | 無い。`conftest` は `unknown` と答える |

このうち **`ar` と複数翻訳単位は tcc の `Makefile` を回すのに要る**
ので，次に来る。`-I` / `-D` も同じ理由で要る。

## 6. 次

`configure` が通り，コンパイラが見つかるところまで来た。次は
`make` である。tcc の `Makefile` を我々の OS の上で回せれば，
**外部の実物を我々の OS だけでビルドする**ところまで届く。

[roadmap.md](roadmap.md) 2.1 の 3 案の判断は，そこまで見てから行う。

## 7. 第 2 部の設計: 複数の翻訳単位と書庫 (`ar`)

### 7.1 何が要るかを実測で決める

tcc の `Makefile` が `ar` を呼ぶのは**1 箇所だけ**である。

```make
libtcc.a: $(LIBTCC_OBJ)
	$S$(AR) rcs $@ $^
```

`lib/Makefile` の `XAR` も同じ `$(AR)` を指す。`configure` は
`AR=ar` と書く (我々の `cc` は `tcc` と名乗らないので `$cc -ar` の枝には
落ちない。4.2)。

`CC` の側は各 `.c` を `-c` で `.o` にし，最後にまとめてリンクする。
つまり第 1 部で作った「1 本の `.c` から 1 つの実行形式」では足りない。

### 7.2 リンカには手を入れない

これが設計の要である。

`ld16` の入力は `'E'` + `.o` の連結 + `'\0'` である (第 1 部 2.2)。
**書庫は `cc` が展開して並べればよい。** リンカは書庫という概念を
知らないままでよく，**凍結済みの世代に手が入らない**。

Stage 16 で記憶域を広げたとき「0x86000000 より下は 1 バイトも動かさない」
と決めたのと同じ考え方である (stage016-os.md 8 章)。**世代を刻まずに
済む形があるなら，そちらを選ぶ。**

### 7.3 `ar` の形式は本物に合わせる

独自形式にする手もあるが，**本物の `ar` に合わせる**。理由は 1 つで，
**検査に本物を使えるから**である。

- 我々の `ar` が作った書庫を host の `ar t` が並べられる
- host の `ar x` が取り出した中身が元の `.o` と一致する

Stage 16 で「期待値は本物で作る」と決めたのと同じ筋である
(stage016-os.md 12.2)。身代わりを自分で書くと，自分の思い違いを
そのまま固定してしまう。

形式は `!<arch>\n` に続けて 60 バイトのヘッダと中身の繰り返しである。

| 位置 | 幅 | 中身 |
|---|---|---|
| 0 | 16 | 名前 (`/` 終端，空白詰め) |
| 16 | 12 | 更新時刻 |
| 28 | 6 | uid |
| 34 | 6 | gid |
| 40 | 8 | 権限 (8 進) |
| 48 | 10 | 大きさ (10 進) |
| 58 | 2 | `` `\n `` |

中身は偶数境界へ `\n` で詰める。

**バイト一致は狙わない。** 時刻・uid・gid をどう書くかは実装ごとに
違い，そこを揃えることに意味は無い。狙うのは相互運用である
(bzip2 / zlib で host 側実装と突き合わせたのと同じ水準。
stage014-external.md)。

### 7.4 符号の索引 (`s`) は書かない

`rcs` の `s` は符号の索引 (`/` という名前の先頭メンバ) を書けという
指示である。**我々は書かない。**

- 我々の `cc` は書庫の中身を**全員**並べるので索引を引かない
- 索引を書くには各メンバの ELF 符号表を読む必要があり，**本題
  (複数の翻訳単位を扱う) から遠い**

`s` は受け取って黙って無視する。**無視することを文書に書き，検査で
「索引が無い」ことを確かめる。** 黙って何かを書いたことにするのが
一番悪い。host の `ar t` / `ar x` は索引が無くても動く。

将来 tcc 自身のリンカに読ませるなど索引が要る場面が来たら，
`ranlib` 相当を足す。

### 7.5 `-I` と `-D` は駆動役が束ねで表現する

`pp16` は**引数を取らない**。標準入力から束ねを読むだけである
(第 1 部 3.1)。したがって選択肢は駆動役が束ねの側で表現する。

| 選択肢 | どう表現するか |
|---|---|
| `-I dir` | `dir` の下のヘッダを束ねの員に足す。名乗る名前は `#include` の綴り |
| `-D NAME=VAL` | 翻訳単位の**頭に `#define NAME VAL` を挿む** |
| `-U NAME` | 同じく `#undef NAME` を挿む |

`-D` を前置きで表す形は，`pp16` に手を入れずに済むという点で 7.2 と
同じ判断である。**順序が意味を持つ** (`-D` は `-U` より先に書かれても
コマンド行の順に効く) ので，与えられた順に並べる。

### 7.6 完了条件

**我々の OS が，複数のファイルからなるプログラムを書庫経由でビルドする。**

材料は手元にある —— libc の第 18 世代は 10 個の `.c` に分かれている。

```
cc -c src/string.c -o string.o     (10 個ぶん)
ar rcs libc.a string.o stdlib.o ...
cc -o prog prog.c libc.a
```

これが通り，出来た `prog` が我々の OS で正しく走ること。あわせて

- host の `ar t` が我々の書庫の並びを列挙できる
- host の `ar x` が取り出した `.o` が元と**バイト一致**する

を見る。

### 7.7 tcc の `Makefile` を回すことは目標に含めない

第 2 部の完了条件に `Makefile` を入れないのは，**GNU make の言語が
別物だから**である。tcc の `Makefile` は `ifeq` / `$(subst)` /
パターン規則 / `$(if ...)` を使う。Stage 13 の `mk` は依存と命令を
並べるだけのもので，これらを解釈しない。

「`make` をどこまで作るか」は独立した大きさを持つ問題なので，
第 2 部の中に混ぜない。**第 2 部が済めば，材料 (`cc` / `ar`) の側は
揃う。** 残るのは駆動する側だけになる。

## 8. 第 2 部の到達点

**我々の OS が，自分の libc を自分のコンパイラで翻訳し，自分の `ar` で
書庫にまとめ，その書庫だけを頼りにプログラムをリンクして走らせる。**
7.6 に書いた完了条件そのものである。

OS の中で走る手順はこうである。

```
for f in src/string src/stdlib src/misc15 posix/sys \
         posix/morecore posix/stdio posix/assert posix/dir
do
  cc18 -c $f.c -o $f.o
done
ar rcs libc.a src/string.o ... posix/dir.o
cc18 -o uselibc uselibc.c libc.a
uselibc                         -> linked against libc.a (6)
```

`/lib` に置くのは走り時の下働き (`rt64.o` / `rtfp.o`) だけにしてある。
libc の `.o` を置いたままだと書庫の員と `/lib` の員が同じ符号を二重に
定義してリンカが落ちるので，**この配置でリンクが通ること自体が
「書庫から本当に引けている」証拠**になる。`printf` は `posix/stdio`，
`strcpy` / `strlen` は `src/string`，`malloc` は `posix/morecore` と，
別々の翻訳単位に散った関数を意図して並べてある。

相互運用も見た。ホストの `ar t` が我々の書庫の 8 員をすべて列挙し，
`ar x` が取り出した `.o` は元と**バイト一致**する。符号の索引は
7.4 のとおり書いていない (書いたことにしていないかを，`ar t` の出力に
`/` で始まる員が無いことで確かめている)。

### 8.1 `cc18` の別名の穴 —— 束ねが 2 件目から壊れていた

`-I` を足すために，第 1 部で書き下していたヘッダ集めを `adddir` として
括り出した。`adddir` は大域の `path` に経路を建てる。ところが呼ぶ側が

```c
strcpy(path, INC);
strcat(path, "/sys");
adddir(fd, path, "sys/");       /* dir == path である */
```

と，**`path` 自身を `dir` として渡していた**。`adddir` の中の
`strcpy(path, dir)` は 1 件目こそ無害だが，その直後に `path` へ
`"/stat.h"` を継ぎ足すので，2 件目では `dir` の指す先が既に
`"/include/sys/stat.h"` になっている。結果として

```
/include/sys/stat.h/time.h
```

を開こうとして落ちる。`adddir` の入口で `dir` の控えを取って直した。

第 1 部の `cc17` に同じ穴が無いのは，あちらが 2 つの階層を別々に
書き下していて `dir` という変数を持たなかったからである。**括り出しが
持ち込んだ誤りである。**

この穴は検査が捕まえた。`-I` を使う道は第 2 部で初めて増えたので，
第 2 部の検査を書いた時点で必ず踏む位置にあった。

### 8.2 `kernel22` が引数を黙って捨てていた

`libc.a` を作ろうとして見つかった。`ar rcs libc.a` に 8 員を並べると
語数は 11 になるが，出来た書庫には**員が 5 つしか入っていない**のに
`ar` は 0 を返して終わる。

原因はカーネルにあった。`kernel22` の `sys_spawn` は

```c
while (kargc < 8) {
  p = ld4(argvp + kargc * 4);
  if (p == 0) break;
  ...
}
```

と書いていて，**9 語目から先を黙って捨てて成功を返していた**。
`ar` は受け取った 8 語 (= 5 員) だけを見て正しく仕事をしており，
`ar` 側には誤りが無い。呼んだ側からは成功に見えるのに中身が足りない，
台帳でいう bad である (`docs/stage016-os.md` 9.4)。

`kernel23` で上限を 64 語 / 4095 バイトへ広げ，あわせて**溢れたら
`E2BIG` で落とす**ようにした。数を増やすだけでは同じ罠が先へ動く
だけである。検査でも 2 つの向きから見ている —— 32 語が 1 語も欠けずに
届くことと，96 語の呼び出しが**成功を返さず，そもそも走らない**こと。

`kernel22` は Stage 16 第 4 部で記録済みなので書き換えず世代を刻んだ
(`roadmap.md` 4 章)。`kernel22` との差はこの 1 点だけである。

**8 という上限は Stage 13 で `spawn` を入れたときのまま，一度も
見直されていなかった。** それまでの呼び出しはどれも語数が少なく，
上限に触れなかったので気づきようが無かった。書庫という「引数の数が
入力の数に比例する」道具を作って初めて表に出た。

### 8.3 まだ無いもの

- **符号の索引 (`ranlib`)。** 7.4 のとおり書いていない。我々のリンカは
  書庫の員を全部並べるので索引を要らないが，本物のリンカに我々の書庫を
  食わせるときは `ranlib` が要る。
- **員の名前は 15 バイトまで。** 長い名前を持つ書庫の形式 (`//` の
  文字列表) は実装していない。超えたら `ar` がはっきり落ちる。
- **`make`。** 7.7 のとおり第 2 部の目標に含めていない。材料
  (`cc` / `ar`) の側は揃ったので，残るのは駆動する側だけである。

## 9. 第 3 部の設計: `make`

第 2 部で材料 (`cc` / `ar`) が揃った。残るのは駆動する側である。
目標は **tcc の `Makefile` を我々の OS の上で回すこと**で，そこまで
届けば「外部の実物を我々の OS だけでビルドする」ことになる。

### 9.1 何が要るかを実測で決める

tcc の `Makefile` (537 行) が実際に使っている機能を数えた。**推測では
なく，このファイルに対する `grep` の結果である。**

| 機能 | 出現数 |
|---|---|
| `$(call ...)` (利用者定義の関数) | 32 |
| `$(if ...)` | 15 |
| `$(wildcard ...)` | 7 |
| `$(shell ...)` | 7 |
| `$(findstring ...)` | 6 |
| `$(foreach ...)` | 5 |
| `$(or ...)` | 3 |

### 9.2 変数の指標 `$($T_FILES)` が効く

数だけ見ると関数が多いが，作りの上でいちばん重いのは表に出ない 1 行で
ある。

```make
LIBTCC_SRC = $(filter-out tcc.c tcctools.c,$(filter %.c,$($T_FILES)))
```

`$($T_FILES)` は**変数名を変数から作っている**。`T` が `x86_64` なら
`$(x86_64_FILES)` を引く。展開器が「名前を先に展開してから引く」形で
書かれていないと通らない。同じ理由で

```make
TCCDEFS_H$(subst yes,,$(CONFIG_predefs)) = tccdefs_.h
```

は**代入の左辺にも展開が要る**ことを示す。

### 9.3 命令はシェルへ渡す

`mk` は命令行を自分で切っていた (空白で分割し `<` `>` を見るだけ)。
第 3 部ではやめて，**1 行ずつ `sh2` に渡す**。tcc の `Makefile` の
命令行は `&&`・`||`・`$(...)` の入った合成命令を含むので，切り直すのは
シェルを二度書くことになる。

`sh2` には `-c` が無く，引数があればそれをファイルとして開く
(`stage016/sh2.c` の `main`)。そこで命令行を一時ファイルへ書いて
`sh2 その一時ファイル` を `spawn2` する。`sh2` に `-c` を足す案は採らない
—— `sh2` は Stage 16 で記録済みであり，世代を刻む値打ちがこの一点には
無い。

命令行の頭の `@` (表示しない) と `-` (失敗を無視) は `make` の側で
解釈してから渡す。

### 9.4 作り直しの判定は**しない**。そう書く

`make` の中核は「依存より古ければ作り直す」である。**我々にはそれが
できない。** sfs2 の項目は名前・親・位置・長さ・印しか持たず，時刻を
持たないからである (`docs/stage012-os.md` 4.3)。

採り得た道は 3 つあった。

1. **常に作る。** Stage 13 の `mk` と同じ。遅いが，嘘はつかない。
2. **sfs に時刻を足す (sfs3)。** 項目は 64 バイトぴったりで空きが無い
   ので，形式・カーネル・ホスト側の道具がすべて動く。独立した大きさを
   持つ。
3. **内容の SHA-256 で判定する。** 我々の `tools/build.sh` が実際に
   採っている手である (`docs/dev-notes.md` 1.5)。時刻より強い判定に
   なるが，`make` の意味とは別物になる。

**第 3 部の 1 では 1 を採る。** 遅いことと嘘をつくことは違う。
「作り直しの判定をしない `make`」であることを help にも文書にも書き，
`まだ無いもの` に残す。2 と 3 は，回るようになってから速さが問題に
なった時点で判断する材料が揃う。

### 9.5 部の切り方

一度に作らない。**それぞれが単体で完結し，検査を持つ**ように切る。

- **第 3 部の 1 (`mk17`)** —— 骨格。変数 (`=` `:=` `+=` `?=`)・展開
  (`$(V)` `${V}` `$V`，および 9.2 の指標)・条件 (`ifeq` `ifneq`
  `ifdef` `ifndef` `else` `endif`，入れ子)・`include` / `-include`・
  規則と依存・パターン規則 (`%.o : %.c`)・自動変数 (`$@` `$<` `$^`
  `$*`)・`.PHONY`・命令の `@` と `-`・命令は `sh2` へ渡す。
- **第 3 部の 2** —— 関数群。9.1 の表に出た 12 個。
- **第 3 部の 3** —— tcc の `Makefile` を実際に回す。ここで初めて
  `$(MAKE)` の再帰・目標特有の変数・`VPATH` が要るかどうかが判る。

**第 3 部の 1 の完了条件**は tcc ではない。**我々自身の libc を
`Makefile` でビルドすること**である —— 第 2 部で書庫まで通した 8 本を，
パターン規則と自動変数で書き直せること。材料は既に手元にあり，
外部の素材を要らないので CI でも走る。

## 10. 第 3 部の 1 の到達点

**我々の OS が，自分の libc を `Makefile` から組む。**

```make
CC = cc18

OBJS  = src/string.o src/stdlib.o src/misc15.o
OBJS += posix/sys.o posix/morecore.o posix/stdio.o
OBJS += posix/assert.o posix/dir.o

all: uselibc

```

第 2 部では同じことを `go.sh` に 8 行並べて書いていた。**同じことを
1 つの型規則で言えることが，`make` を持った意味である。**

検査は 3 つの向きから見る。

1. OS の上で `mk` が `libc.a` を組み，それに繋いだものが走ること
2. **同じ記述を本物の `make` に食わせたとき，命令の並びが一致する**
   こと —— 出来上がりだけ見ていると，別の順で別のものを作っても
   気づけない
3. 未実装の関数が空に展開されず落ちること

2 のために，`spawn2` を `system()` へ回す殻 (`tests/stage017/host/
mkhost.c`) を置いて **`mk17.c` そのものを**ホストで取り込んでいる。
`mk17.c` の側に検査用の分岐は無い —— 入れると，ホストで通る道と OS で
通る道が分かれてしまう。

### 10.1 ホストで一巡して出た 4 件

本物の `make` と突き合わせて見つけた。**4 件のうち 3 件は
「黙って違うことをする」型である。**

| | 何が起きたか |
|---|---|
| `include` が外側の器を上書き | `parse` が `static` な器を 1 つ使い回していたので，`include` を読むと外側の `parselines` が読んでいる最中の中身が消え，千切れた行で落ちた |
| 複数目標の命令が最初の 1 つにしか付かない | `m1 m2:` と書くと **`m1` だけが作られ，`m2` は何もせず「作った」ことになる** |
| 継続行の空白が二重になる | `a \` + `   b` が `"a  b"` |
| 失敗を無視したことを黙る | `-false` で本物は `(ignored)` と告げるが，こちらは何も言わなかった |

1 件目は **`cc18` の `adddir` と同じ型**である (8.1) —— 大域の器を
指す名前を，その器を書き換える関数へ渡していた。同じ誤りを 2 部
続けて持ち込んだので，「大域の作業領域を関数の引数にしない」は
書いておく値打ちがある。

### 10.2 `cc15p` のフレームの上限 (器の都合)

鎖の上で組んだら `cc15p` が終了コード 6 で落ち，0 バイトの `.o` が
出た。`build.sh` の空検査が止めた (`docs/dev-notes.md` 1.2.1)。

**1 つの関数のフレームがおよそ 32 KB を超えると通らない。**
`parselines` が `tg[NEXP]` と `dp[NEXP]` を並べて持つので，`NEXP` が
32768 だと 64 KB になる。実測すると 16384 は通り 32768 は落ちる。

`NEXP` を 16384 にした。tcc の `Makefile` のどの展開よりも十分に
大きく，溢れたときは黙って切らず落ちる。記述の置き場 (`NTXT`) は
大域なのでこの上限に掛からない。

### 10.3 まだ無いもの

- **関数**。9.1 の 12 個。第 3 部の 2 である。見つけたら落ちる。
- **作り直しの判定**。9.4 のとおり，しない。規則のある目標は毎回作る。
- **`$(MAKE)` の再帰**・**目標特有の変数**・**`VPATH`**。tcc の
  `Makefile` を実際に回す第 3 部の 3 で，要るかどうかが判る。
- **`else if`**。落ちる。tcc の `Makefile` には無い。
- **型規則の選び方**。合った最初のものを使う。「依存が作れるものを
  選ぶ」ところまではやらない。

## 11. 第 4 部の設計: 時刻を持つファイル系 (`sfs3`)

9.4 で「作り直しの判定はしない」と決めた。**それを覆す。**

理由は所有者からの一言である —— 「差分ビルドする機会は今後デバッグ時に
発生すると考えられ，都度破棄するのは都合が悪い」。9.4 で挙げた 3 案の
うち 2 (sfs に時刻を足す) を採る。

### 11.1 時計はあった

9.4 では「sfs2 の項目が時刻を持たない」ことだけを見て，**時計そのものが
あるかを調べていなかった**。調べたらあった。

QEMU の `virt` の device tree を出すと

```
rtc@101000        google,goldfish-rtc
clint@2000000     sifive,clint0
```

カーネルは M モードで走るので，`0x101000` を直に読める。実際に読んで
確かめた。

```
RTC 18ce57b6:a183bb98   ->  1787462544018095000 ns  =  1787462544 秒
ホストの date +%s        ->  1787462543 秒
```

差 1 秒は 2 つの読みの間に経った時間である。**通し番号で代用する必要は
なく，ホストと同じ土俵の時刻が持てる。**

### 11.2 ナノ秒を u32 2 本で持つ —— 除算を要らなくするため

goldfish RTC は epoch からのナノ秒を `TIME_LOW` (+0) / `TIME_HIGH` (+4)
で返す。**秒に直さず，64 bit のまま 2 語で格納する。**

- **カーネルに 64 bit の除算が要らない。** 我々の C は 32 bit であり，
  `1e9` で割るのは書けなくはないが，書かずに済むなら書かない
- 比較は上位語 → 下位語の 2 段で済む。`make` が要るのはこれだけである
- ホスト側の `pack` が実ファイルの mtime をそのまま書き，`unpack` が
  復元できる。**OS が書いた時刻とホストが詰めた時刻が同じ土俵に乗る**
- 秒より細かいので，1 秒以内に 2 つ作ったときの取り違えが起きない
  (我々の OS は遅いが，`.o` を 8 個作る間に秒が跨がらない場面はある)

`TIME_LOW` を読むと `TIME_HIGH` が固定される仕様なので，**必ず下位から
読む**。

### 11.3 バイト配置 (sfs3)

sfs2 の項目は 64 バイトぴったりで**空きが 1 バイトも無い**。名前を削る
案は採らない —— 静かに切れる危険があり，我々が何度も踏んだ型である。
**項目を 72 バイトに広げる。**

```
スーパーブロック (32 バイト):
  0   'sfs3' (4 バイト)
  4   u32 total    イメージ全体の大きさ
  8   u32 tbloff   表の位置 (= 32)
  12  u32 tblcnt   表の件数 (容量)
  16  u32 cursor   次にデータを置く位置 (追記割付け。4 バイト境界)
  20  予約 (0)

表項目 (72 バイト / 件。未使用の項目は全 0):
  0   name[48]     そのディレクトリ内での名前，NUL 終端 (最長 47 バイト)
  48  u32 parent   親のエントリ番号
  52  u32 dataoff
  56  u32 len
  60  u32 flags    bit0 有効, bit1 ディレクトリ, bit2 削除済, bit3 空装置
  64  u32 mtlo     更新時刻 (epoch からのナノ秒) の下位 32 bit
  68  u32 mthi     同 上位 32 bit
```

sfs2 との差は**末尾の 2 語と項目の大きさだけ**である。上位ヘッダは
`'sfs2'` → `'sfs3'` の 4 バイトしか変わらない。

**sfs2 は残す。** Stage 16 の検査がすべてそれに依っている
(`tools/sfs2.sh` と `tools/sfs.sh` を残したのと同じ理由)。

### 11.4 時刻を立てる場所

- **作成時** —— `sfsmk` が今の時刻を書く
- **書込み時** —— `sfswrite` が今の時刻に更新する。**0 バイトの書込みでも
  更新する** (`> file` で切り詰めるのも変更である)
- **読み出しでは触らない。** atime は持たない

ホストの `sfs3.sh pack` は実ファイルの mtime を書く。`unpack` は
`touch -d` で復元する。**詰めて展開して元と時刻が一致すること**を検査で
見る。

### 11.5 `stat` を持つ

`libc18` の `sys/stat.h` にはこう書いてある。

> **stat / fstat は無い。** sfs2 に許可・所有者・時刻が無く，返せる欄が
> ほとんど 0 になる。「あるのに嘘の値を返す」より「無い」ほうが呼び手に
> とって安全である

時刻ができたので，この判断の前提が変わった。**`libc19` で `stat` を
持つ。** ただし返すのは**本当に持っている欄だけ**である。

```c
struct stat {
  long st_size;                 /* 長さ */
  unsigned st_mtime_lo;         /* 更新時刻 (ns) の下位 32 bit */
  unsigned st_mtime_hi;         /* 同 上位 */
  int st_mode;                  /* S_IFDIR か S_IFREG だけ。許可は無い */
};
```

**`st_uid` / `st_gid` / 許可ビットは置かない。** 持っていない欄を 0 で
埋めて名前だけ揃えると，呼び手が「見た」つもりになる。無い欄は
**構造体に無い**のがいちばん安全である。

### 11.6 部の切り方

- **第 4 部の 1** —— `sfs3` + `kernel24` + `tools/sfs3.sh` + `libc19`。
  **完了条件は「ホストが詰めたファイルの時刻を，我々の OS の上の
  プログラムが読んで，ホストの値と一致すること」。** 時刻が本物である
  ことをここで確かめる
- **第 4 部の 2** —— `mk18` が時刻を見て作り直しの要否を決める。
  **完了条件は「2 度目の `mk` が，変わっていないものを作り直さない
  こと」。**

第 4 部の 2 が済んだ時点で 9.4 と 10.3 の「まだ無いもの」から
「作り直しの判定」が消える。

## 12. 第 4 部の到達点

**我々の OS が，変わったものだけを作り直す。**

```
--1--                       1 回目。全部作る
cat a.src > a.cp
cat b.src > b.cp
cat a.cp b.cp > prog
--2--                       2 回目。何も作らない
mk: nothing to be done for 'all'.
--3--                       b.src を触ったあと
cat b.src > b.cp
cat a.cp b.cp > prog        **a.cp は作り直さない**
--4--                       -B は古さを見ない
cat a.src > a.cp
cat b.src > b.cp
cat a.cp b.cp > prog
```

触るのに使うのは `sh2` の `>` である。**ホストで触ってから詰め直すと，
カーネルが時刻を立てているのか，ホストが立てた時刻を読んでいるだけ
なのか区別が付かない。**

9.4 で「作り直しの判定はしない」と書いた。**その判断は覆した。**
覆した理由は所有者の一言だが，**覆せた理由は「時計を調べていなかった」
という自分の落ち度である** (11.1)。「sfs2 の項目が時刻を持たない」まで
は正しく，そこで止めた。持たせられるかを調べていなかった。

### 12.1 時刻が本物であることをどう確かめたか

「時刻がある」は「時刻が正しい」ではない。3 つの向きから見た。

1. **ホストが詰めた時刻を OS が読む。** わざと「ありえない過去」
   (1700000000.123456789 など) を与える。**今の時刻を使うと，読んだ
   のか立て直したのか区別が付かない**
2. **触っていないファイルの時刻が変わらない。** 読むだけで時刻が動く
   なら差分ビルドは成り立たない
3. **OS が書いたファイルには今の時刻が立つ。** ホストの `date` で
   前後を挟んで，その間に入ることを見る

さらにホスト側だけで，詰めて展開して**中身と時刻の両方**が元と一致する
ことを見る。

### 12.2 時刻を立てる場所は 6 箇所あった

`sfsmk` (作成) と `sfswrite` (書込み) の 2 箇所だと思って書き始めたが，
**`sfswrite` を通らない切詰めが 3 つあった。**

- `open` の `O_TRUNC`
- `spawn` の出力つなぎ替え
- `spawn` の標準エラーつなぎ替え

どれも「中身を空にする」もので，落とすと**切り詰めたのに古いまま**に
なる。`mk` はそれを「新しくない」と読んで作り直しを飛ばす。
書込みは **0 バイトでも立てる** —— `> file` は変更である。

### 12.3 「作ると決めたか」ではなく「命令が走ったか」

最初，`mk18` は「作ると決めた」時点で「作った」と数えていた。
`all: prog` のような**命令を持たない目標**は，作ると決めても何もしない。
そのため何もしなかった走りが「作った」ことになり，`nothing to be done`
が出なかった。数えるのは命令が走ったときにした。

### 12.4 番地を出さないと切り分けに時間がかかる

検査を新しく書いたとき，記憶を 512M ではなく 256M と書いた。
`kernel19` 以降はユーザのフレームスタックの上端を `USP = 0x9700_0000`
に置いているので，256M では届かない。**何も出さずに落ちた。**

カーネルが出したのは `!00000007 80000344` (mcause と PC) だけである。
QEMU の `-d int` で `tval = 0x96ffeef0` を取り，それが `setupstack` の
書く `USP - 4368` だと判って初めて切り分けられた。

**落ちたときに番地を出していれば一目で済んだ。** 出すには前置部に手を
入れる必要があり，`ld16` は凍結済みなので今回は見送る。次にリンカの
世代を刻むときの持ち物にする。

### 12.5 これで「まだ無いもの」から消えるもの

9.4 と 10.3 に挙げた**「作り直しの判定」は無くなった**。残るのは

- **関数** (9.1 の 12 個)。第 3 部の 2
- **`$(MAKE)` の再帰**・**目標特有の変数**・**`VPATH`**。第 3 部の 3 で
  要るかどうかが判る
- **`else if`**・**型規則の選び方**は 10.3 のまま

## 13. 第 3 部の 2 の到達点

**関数が通る。** 9.1 で数えた 12 種を入れた。

```make
SRC  = src/string.c src/stdlib.c src/misc15.c
SRC += posix/sys.c posix/morecore.c posix/stdio.c
SRC += posix/assert.c posix/dir.c

OBJS  = $(patsubst %.c,%.o,$(SRC))
POSIX = $(filter posix/%,$(SRC))
tagged = <$(1)>
TAGS  = $(foreach f,$(POSIX),$(call tagged,$(f)))
```

第 3 部の 1 では目的ファイルを 8 個手で並べていた。**同じことを言うのに
手で並べ直さなくてよくなるのが，関数を持った意味である。**

### 13.1 評価の順が種類で違う

ほとんどの関数は**引数を先に展開してから**呼ぶ。しかし
`if` / `or` / `foreach` / `call` は**呼んでから中で展開する**。

```make
$(if $(X),$(BOOM))
```

先に全部展開すると，`X` が空でも `BOOM` が展開されてしまう。`foreach` は
語ごとに変数を立て直すので，そもそも先に展開してはいけない。

引数は**深さ 0 の `,` でだけ**切る。切らないと

```make
$(if $(filter a,b),y)
```

の内側の `,` で切れて壊れる。

`foreach` の変数と `call` の `$(1)`〜`$(9)` は，**元の値を退避して戻す**。
入れ子の `call` があるからである。

### 13.2 扱えないものは扱えるふりをしない

- **`$(wildcard)` に `*` や `?` が来たら落とす。** 我々の OS に glob が
  無い。空に展開すると，ファイルが 1 つも無かったのと区別が付かない
- **知らない関数は落とす。** 変数名として引くと静かに空になる。
  `$(notdir a/b.c)` は `mk: unknown function: notdir` で止まる

どちらも mk17 からの決まりである (9.5)。

### 13.3 `cc15p` のフレームの上限に**また**掛かった

鎖の上で組んだら 0 バイトの `.o` が出た。`callfn` が `NEXP` の器を
3 つ局所に持っていたので 48 KB になる。**10.2 で `mk17` が踏んだのと
同じ上限である。**

深さで分けた大域の池に移した。関数は入れ子になるので 1 組では潰れる。
戻り道が多いので，深さの上げ下げは包みを 1 つかぶせてそこ 1 箇所に
集めた。

**2 度目なので書いておく: `cc15p` で書くものは，大きな器を局所に
置かない。** 大域なら掛からない (BSS なので像も太らない)。

### 13.4 検査

3 つの向きから見る。

1. OS の上で `mk` が関数を展開し，`libc` を組み，繋いだものが走る
2. **同じ記述を本物の `make` に食わせて，関数の展開と命令の並びが
   一致する。** 関数は結果が静かに空になる形の誤りが出やすいので，
   出来上がりだけでなく並びそのものを見る
3. 知らない関数は空に展開せず落ちる

ホストでは 21 通りの関数を個別に本物と突き合わせてある。

### 13.5 残るのは第 3 部の 3 だけ

9.5 の 3 分割のうち，1 と 2 が済んだ。残るのは **tcc の `Makefile` を
実際に回すこと**である。そこで初めて `$(MAKE)` の再帰・目標特有の
変数・`VPATH` が要るかどうかが判る。

## 14. 第 3 部の 3 の実測: tcc の `Makefile` に何が足りないか

`mk19` に tcc の `Makefile` を `-n` で食わせ，**足りないものだけを
数えた**。9.5 で「第 3 部の 3 で判る」と書いた問いへの答えである。

足りないものを黙って空にした写しで通すと，**18 個の命令が出た**。
本物の `make -n` は 34 個である。差は 4 種類しか無い。

| | 要るか | 出現 |
|---|---|---|
| `$(wildcard)` の `*` | **要る** | `$(wildcard *-libtcc1.a)` 1 箇所 |
| 目標特有の変数 | **要る** | 5 箇所 |
| 命令の無い追加の依存行 | **要る** | `$(X)tcc.o : tcctools.c` など |
| `$(MAKE)` の再帰 | **要る** | `lib/` へ降りる 1 箇所 |
| `VPATH` | **要らなかった** | 変数としては在るが使われない |
| `else if` | **要らなかった** | 0 |
| 知らない関数 | **無かった** | 0 |

**関数はもう足りている。** 第 3 部の 2 で入れた 12 種で，537 行の
`Makefile` が最後まで読める。

### 14.1 いちばん効くのは「命令の無い追加の依存行」

```make
$(X)tcc.o : tcctools.c
$(X)tccpp.o : $(TCCDEFS_H)
```

本物の `make` はこれを**既にある規則への依存の追加**と読む。`tcc.o` を
どう作るかは型規則 `$(X)%.o : %.c` が持ったままである。

`mk19` は目標行を見るたびに新しい規則を立てるので，命令を持たない
規則が型規則より先に見つかり，**何も作らずに「作った」ことになる**。
実際 `tcc.o` と `tccpp.o` の翻訳が出力から丸ごと落ちた。

これは我々が繰り返し踏んでいる型 —— **黙って何もしない** である。

### 14.2 部の切り方

第 3 部の 3 を 2 つに分ける。

- **第 3 部の 3 の 1 (`mk20`)** —— 上の 4 種。**完了条件は
  「tcc の `Makefile` から出る命令の並びが，本物の `make -n` と
  一致すること」**。読めることと，正しく読めることは違う
- **第 3 部の 3 の 2** —— 我々の OS の上で実際に回す。ここは
  `cc18` が tcc の C を翻訳できるかという別の問題に当たるので，
  分けておく

## 15. 第 3 部の 3 の 1 の到達点 (`mk20`)

### 15.1 完了条件と，その置き方

14.2 で置いた完了条件はこれである。

> tcc の `Makefile` から出る命令の並びが，本物の `make -n` と一致すること

**「読める」を条件にしなかったのが要点である。** 読めるだけなら
`mk19` でも読めた —— 途中で止まらずに最後まで走り，それらしい命令を
並べた。だがその並びは本物と違っていて，違っているところは全部
「黙って何かを落とす」形をしていた。

一致した。

```
$ sh tools/mkref.sh tcc
make: 34 行 / mk20: 34 行
一致した (tmp/mkref/tcc)
```

34 行には `lib/` へ降りる再帰も含む。

### 15.2 再現の仕方

`tools/mkref.sh` に置いた。

```
sh tools/fetch.sh tcc      # 素材を取る (docs/external/tcc)
sh tools/mkref.sh tcc      # ./configure して両方に -n で読ませ diff する
```

**この突き合わせは CI では走らない。** 素材を repo に入れない決まり
(`tools/fetch.sh` の頭) があり，CI は取得しないからである。CI で
走るのは `tests/stage017/mk/tccish.mk` —— tcc の `Makefile` が使う
6 つの形だけを自前で並べた記述で，これは本物の `make` と突き合わせる。

つまり **CI が見ているのは「同じ形が同じに読めること」で，完了条件
そのものではない**。ここは正直に書いておく。完了条件そのものを見る
には上の 2 手が要る。

### 15.3 一致させる過程で出た誤り

14 章で数えた不足 4 種を入れたあと，まだ 3 つ違っていた。**どれも
「読めてはいた」**ので，一致を条件にしなければ見付からなかった。

**その 1: `$<` が別のファイルを指す。**

```
%.o : %.c        # 型規則。ここが命令を持つ
	$(CC) -c $< -o $@
tcc.o : tcctools.c   # 別の行で足した依存
```

`mk20` は「合った規則の依存を全部集める」ようにしてあったが，集めた
順が記述の順だった。`tcc.o` の依存は `tcctools.c`, `tcc.c` の順に
並び，`$<` (最初の依存) が `tcctools.c` になった。**命令を出す規則の
依存を先頭へ移す**ようにして直した。

出た命令は `cc -c tcctools.c -o tcc.o` である。止まらない。**別の
ファイルを翻訳して，正しい名前を付ける。**

**その 2: 目標特有の変数の `+=` が値を凍らせる。**

```
DEFS = -DBASE            # 遅延 (= なので使うときに展開する)
EXTRA-DEFS = -DEXTRA
main.o : DEFS += $(EXTRA-DEFS)
```

`+=` を入れたとき，`vset(..., V_SIMP)` で即時にしていた。即時にすると
その場で展開されるので一見正しいが，**元の側 (`-DBASE`) に入っていた
参照まで一緒に凍る**。元が遅延ならこちらも遅延で継がなければならない。

出た命令には `$(EXTRA-DEFS)` がそのまま載った。**文字列として。**

**その 3: `$(wildcard)` が名前の順に並ばない。**

`readdir` の順は作った順である。本物の `make` は `glob(3)` を通すので
名前の順に並ぶ。並びが違えば，同じ記述から違う命令列が出る。
`stage017/mk20.c` の `globinto` で挿入して名前の順に入れるようにした。

これは tcc の `Makefile` では表に出なかった (たまたま順が合っていた)。
`tests/stage017/mk/tccish.mk` に **わざと順の合わない名前** (`zmain.c`)
を置いて捕まえてある。

### 15.4 併せて入れたもの

14 章で数えた 4 種の他に，一致のために要ったもの。

- **型規則は依存が揃えられるものを選ぶ。** tcc の `lib/` には
  `%.o : %.c` と `%.o : %.S` が並ぶ。`atomic.o` は `.S` のほうである。
  「先に合ったもの」で済ませると `atomic.c` が無いと言って止まる。
  依存が在るか，作る規則があるものを先に探す 2 巡にした。
  **1 段しか見ない** —— 全部辿ると輪に入りうるし，1 段で足りることは
  実測で判っている
- **`t: dep ; cmd` の形。** 深さ 0 の最初の `;` から後ろが命令である。
  **中身が空でも「命令を持つ規則」になる**のが要点で，型規則より
  こちらが選ばれて「何もしない」が実現する (tcc の `cross-libtcc1` 他)
- **`-C dir`** と `--no-print-directory` (受けて捨てる)
- **`$(MAKE)` は自分自身** (`argv[0]`)。`-n` のときも走らせる ——
  走らせないと下の階層の命令が 1 行も見えない

### 15.5 本物と綴りが違う唯一の点

本物の `make` は `-n` を `MAKEFLAGS` (環境変数) で下へ継ぐ。**我々には
環境変数が無い**ので，`$(MAKE)` の値のほうに入れて継ぐ。

したがって下へ降りる行はこうなる。

```
make -C lib      本物
mk -n -C lib     我々
```

`tools/mkref.sh` はこの 1 点だけを揃えてから `diff` する。それ以外に
差は無い。

### 15.6 我々の OS の上

`tests/stage017/mk/tccish-os.mk` を `kernel24` の上で走らせる
(`tests/stage017/test.sh` の「第 3 部の 3 の 1」の節)。翻訳器は使わない
—— 見たいのは **`mk` がどの命令をどの順で出すか**であって，翻訳では
ないからである。6 つの形を全部通し，`$(MAKE)` の再帰と，11 章の
差分ビルド (触った依存に繋がる分だけ作り直す) までを 1 続きで見る。

変数の値が凍っていないことは，**`DEFS` に実在するファイル名を入れて
`cat` の引数にする**ことで見ている。凍っていれば `$(EXTRA-DEFS)` の
まま渡り，`cat` が開けずに落ちる。

### 15.7 残り

**第 3 部の 3 の 2 —— 実際に tcc の build を我々の OS の上で回すこと**
は手付かずである。`mk20` が出す命令は正しくなったが，その命令の中身
(`cc18` が tcc の C を翻訳できるか) はまた別の問題で，14.2 で分けた
通りそちらは別に当たる。

## 16. 第 3 部の 3 の 2 の実測: 命令が正しくても走らない

15 章で命令の並びは本物と一致した。**その命令が通るかどうかは別**である。
14 章と同じやり方で，まず数える。

### 16.1 我々向けの `config.mak` で何が出るか

上流の `configure` はホスト専用の shell script なので走らせない。
`ARCH=riscv32` / `CC=cc18` / `CFLAGS=` を書いた `config.mak` を与えて
`mk20 -n` に読ませると，こうなる。

```
cc18 -o tcc.o -c tcc.c -I. -DONE_SOURCE=0
cc18 -o libtcc.o -c libtcc.c -I. -DONE_SOURCE=0
cc18 -DC2STR conftest.c -o c2str.exe
./c2str.exe include/tccdefs.h tccdefs_.h
cc18 -o tccpp.o -c tccpp.c -I.
   ... (riscv64-gen.o / riscv64-link.o / riscv64-asm.o まで 8 本)
ar rcs libtcc.a libtcc.o tccpp.o ... riscv64-asm.o
cc18 -o tcc tcc.o libtcc.a -lm -ldl -lpthread
mk -C lib
   ... (../tcc に libtcc1.a を作らせる 14 行)
perl ./texi2pod.pl tcc-doc.texi tcc-doc.pod
pod2man ... >tcc.1
```

`ARCH` を替えると規則の選び方まで正しく替わる (`riscv64-gen.o` が出て
`x86_64-gen.o` が出ない)。**読む側は足りている。**

### 16.2 止まるところ その 1: `-I.` が階層ごと束ねる

これが一番大きい。

`cc18` の `-I dir` は「**その階層のファイルを全部，束ねの員に足す**」
という意味である (`stage017/cc18.c` の `adddir`)。`pp16` が引数を取らず
標準入力から束ねを読むだけなので，7.2 でそう決めた。ヘッダが十数個
置いてある `/include` ならこれで足りる。

tcc の木に `-I.` を与えるとこうなる。

| | 数 |
|---|---|
| `.` 直下のファイル | 63 |
| うち `.h` | 16 |
| うち `.c` | **30** |
| その他 (`configure`・`COPYING`・`.texi` など) | 17 |
| 合計 | **約 2.3 MB** |

`tccpp.c` が実際に要るのは `tcc.h` `tccdefs_.h` `tcctok.h` の 3 つである。
**要らない 60 個と 2.3 MB を毎回束ねる。** しかも 30 個の `.c` が
「ヘッダ」として員に入る。

**しかもこれは「無駄」で済まない。そもそも通らない。**

`pp16` の束ねの員は **64 個が上限**である (`stage015/pp16.sc` の
`if (mbcnt >= 64) exit(6)`)。`cc18 -c tccpp.c -I.` が組む束ねは

| 出どころ | 員 |
|---|---|
| `/include` (libc19 のヘッダ) | 16 |
| `/include/sys` | 2 |
| `-I.` (tcc の木) | 63 |
| 翻訳単位 | 1 |
| **合計** | **82** |

で 64 を超える。実測した。

```
b64: 員=64 rc=0 out=24 バイト
b65: 員=65 rc=6 out=0 バイト
```

65 員で容量超過の 6 で落ちる。**黙って切り詰めない**のは正しい
(それが我々の決まりである) が，落ちることに変わりはない。

上限を上げれば済む話ではない。上げても 2.3 MB を毎回前処理する
ことになるし，`src` の器 (4 MB) にも当たる。**入れる員を減らすのが
筋である。**

つまり `-I` を**探す道**として持つ世代が要る。`pp16` は凍っている
(引数を取らない) ので，`#include` の解決を `cc` の側でやるか，`pp` に
世代を足すかの選択になる。

**数えたら決まった。** `cc` の側でやるなら，翻訳単位の字面を走査して
`#include "..."` を辿るしかない。`cc` は `#if` を評価しないので，
**通らない枝の `#include` まで辿ってしまう**。tcc はこれが効く形をして
いる —— `libtcc.c` は各対象の実装を `#include "arm-gen.c"` のように
`#ifdef TCC_TARGET_*` で選ぶ。

`tccpp.c` を `-I.` で翻訳するとき，3 つの方法で束ねに入る量:

| 方法 | 員の数 | 大きさ |
|---|---|---|
| いまの `cc18` (`-I` は階層ごと) | 63 | 2,358,626 |
| `cc` の側で字面を走査 (`#if` を見ない) | 31 | 1,104,869 |
| **本当に要るもの** | **13** | **481,816** |

> **訂正。** ここに最初「9 個 / 290,384」と書いた。それは既存の束ね
> (`tools/tcc-stone.sh` が ONE_SOURCE 用に並べている `.h`) を数えた
> もので，**分割翻訳の閉包ではない**。実際に `cc19 -c tccpp.c -I t` を
> 通して測り直した値が上の 13 個である (19.4)。
>
> 増えた 4 つは `riscv64-gen.c` `riscv64-link.c` `riscv64-asm.c` と
> `config.h` である。前の 3 つは `tcc.h` が `TARGET_DEFS_ONLY` を
> 定義して**無条件に**取り込む —— ONE_SOURCE とは関係がない。
> 「`.c` を `#include` するのは ONE_SOURCE のときだけ」という思い込みが
> あった。

字面の走査では 4 倍のままで，しかも入ってくるのは**全対象の
`.c`** (`arm-gen.c` `arm64-gen.c` `c67-gen.c` …) である。ヘッダですら
ない。

どの枝が生きているかを知っているのは前処理器だけである。したがって
**`pp` に世代を足して，`-I` を辿らせるのが正しい**。凍結済みの
`pp16` には手を入れず，世代を刻む (roadmap 4 章)。

もう 1 つ考えられる手 —— **`cc` が `pp16` を繰り返し呼び，「無い」と
言われた分だけ員に足していく**——も消えた。`pp16` は見つからない
`#include` の**名前を言わない**からである。

```
$ printf '#include "nope.h"\nint main(){return 0;}\n' | bundle | pp16
rc=2   (標準出力・標準エラーとも空)
```

止まるのは正しい (9.5 の決まり) が，何が無いのかが判らないので，
呼ぶ側は次に何を足せばよいか決められない。**新しい世代で名前を
出すようにする**のは，この意味でも要る。

なお `"..."` の綴りはすべて**同じ階層の平らな名前**だった (`../` も
下位ディレクトリも無い)。`<...>` は他の環境向けの枝の中にしか無い。
探す道の実装は素直で済む。

### 16.3 止まるところ その 2: 途中で道具を作って走らせる

```
cc18 -DC2STR conftest.c -o c2str.exe
./c2str.exe include/tccdefs.h tccdefs_.h
```

build の途中で**実行形式を作り，それを走らせて，その出力を次の入力に
する**。**`./名前` は走る。**確かめた —— `kernel24` の `walk` は `.` の段を
そのまま扱い，`sh2` は `argv[0]` を作業ディレクトリからの相対で
`spawn2` に渡す。実際に `./mk` と `sub/mk` の両方で走った。

```
--dot--          ./mk -n
echo hi
--sub--          sub/mk -h
usage: mk [-f makefile] [-C dir] [-n] [-s] [-B] [target...]
```

**ただし探す道 (PATH) は無い。** 素の名前は作業ディレクトリからの
相対でしか見つからない。`mk -C lib` で下へ降りたあと素の名前で
道具を呼ぶ形は通らない —— tcc の `lib/Makefile` は `../tcc` と書いて
いるので今回は当たらないが，**上の階層に置いた道具は下から名前だけ
では呼べない**ことは覚えておく。

残るのは `cc18` が `-c` 無しで翻訳から結合まで 1 度にやること (これは
在る) と，出来た実行形式が `include/tccdefs.h` を読んで `tccdefs_.h` を
書けることだけである。

今の鎖はこの段を避けて，ホストの tcc が作った `tccdefs_.h` を持ち込んで
いる (`tools/tcc-stone.sh` の `bundle`)。**Makefile どおりに回すなら
避けられない。**

### 16.4 止まるところ その 3: `lib/` は作った tcc を使う

`lib/` の 14 行は `../tcc` —— **今作ったばかりの tcc** で `libtcc1.a` を
作る。しかも `atomic.S` `alloca.S` `alloca-bt.S` の 3 つは**アセンブラ
の入力**で，tcc 自身のアセンブラを通る。

ここは Stage 15 第 6 部 (T1/T2/T3) と地続きの話であって，`make` の話
ではない。

### 16.5 止まるところ その 4: doc の的

`perl ./texi2pod.pl` と `pod2man` がある。どちらも我々の OS には無い。
`all` ではなく `tcc` を的にすれば出ない。**これは config で避けられる**
唯一のものである。

### 16.6 数えた結果

読む側 (`mk20`) は足りている。足りないのは**読んだ命令を通す側**で，
大きさの順に

1. `-I` を探す道として持つ **`pp` の世代** と，それを渡す `cc` の世代
   (16.2)。**ここが本体**で，ほとんどこれしか無い
2. build の途中で作った実行形式を走らせる段 (16.3)。**土台は既に
   在る**ことを確かめた。残るのは `c2str` が通るかだけ
3. `lib/` —— Stage 15 第 6 部と地続き (16.4)
4. doc の的 —— config で避ける (16.5)

第 3 部の 3 の 2 は 1 と 2 までとし，`tcc` 本体 (`libtcc.a` と `tcc`)
が我々の OS の上で `Makefile` から出来ることを完了条件にする。
3 は第 3 部の 3 の 3 へ回す。

## 17. 第 3 部の 3 の 2 の設計: `-I` を探す道にする (`pp17` / `cc19`)

16 章で数えた結果，足りないものはほぼ 1 つ ——「`-I` を**探す道**として
持つこと」——である。ここではその形を決める。

### 17.1 なぜ `pp` の側なのか (16.2 の再掲)

`cc` の側で `#include` を辿ると，`#if` を見ないので通らない枝まで
辿ってしまう。tcc はこれが効く形をしている。**どの枝が生きているかを
知っているのは前処理器だけ**である。

`pp16` は凍っている (roadmap 4 章) ので世代を刻む。**`pp17` である。**

### 17.2 `pp17` は `.sc` のままでよい (実測)

`pp16.sc` は入出力に `getc` / `putc` しか持たない。ファイルを開けない。
そこで「C へ書き直して libc19 と繋ぐ」ことを考えたが，**要らなかった。**

`ld16` の `'E'` 前置部が既に持っている (`stage015/ld16.sc` 24〜28 行と
817〜822 行):

- `sys_openat` / `sys_read` / `sys_close` / `sys_write` / `sys_brk`
- 汎用の `sys_ecall(n, a, b, c)`
- **`sp` 上の `argc` / `argv` を `main` へ渡す** (511 行)

両方とも実際に確かめた。`.sc` を `cc15p` -> `ld16 'E'` で組み，
`kernel24` の上で走らせた。

```
$ av one two three          # int main(int argc, char **argv)
4
one
two
three

$ op sub/data.txt           # sys_openat(-100, argv[1], 0, 0) -> sys_read
HELLO FROM FILE
```

**土台だけでなく，本体が載ることも確かめた。** `pp16.sc` の `main()` を
`main(int argc, char **argv)` に替え，3 つの `sys_*` の宣言を足した
ものを `cc15p` に通すと**そのまま通る** (82,612 バイトの `.o`)。
`'E'` で組んで `kernel24` の上で `pp16cmd` と同じ束ねを食わせると，
**出力がバイト一致した**。

```
pp16 0          # 同じ入力を pp16cmd と
pp17 0          # 手を入れた側に食わせ
OS 上で出力一致  # 出た 24 バイトが一致
```

つまり **`pp17` は `pp16.sc` の続きとして `.sc` で書ける。** libc も
要らず，1769 行を書き直す必要も無い。足すのは

1. `main(argc, argv)` —— `-I <dir>` と入力ファイルを受ける
2. `#include` を辿るときに `sys_openat` で開く
3. 見つからないときに**名前を出して**止まる (16.2 の最後)

の 3 つである。

**ただし `pp17` は OS の上でしか走らない。** `sys_*` のスタブは
`'E'` 前置部にしか無いので，フラット (`'F'`) で組もうとすると
未定義で落ちる (実測: `rc=7`)。

これは困らない。`pp17` を使うのは我々の OS の上の `cc19` だけであり，
ホスト側の道 (`tools/build.sh` の `tool1` が `pp16.bin` をベアメタルで
回す経路) は**これまでどおり `pp16` を使う**。`cc18` / `mk20` /
`ar17` と同じで，OS の道具は OS の道具である。

### 17.3 束ねはどうなるか

`pp17` が自分で開けるなら，束ね (`#!stone-bundle`) は要らなくなる ——
ように見えるが，**捨てない**。

- 既存の道 (`cc17` / `cc18`・`tools/bundle.sh`・`tools/tcc-stone.sh` の
  ONE_SOURCE) が全部これで動いている
- 束ねのままのほうが良い場合がある。ホストから流し込む経路
  (`build.sh` の `tool1` など) はファイル系を持たない

したがって `pp17` は**両方受ける**。標準入力が束ねならこれまでどおり，
`-I` が与えられていればそちらも探す。**64 員の上限に当たらなくなる**
のは，`-I` の階層を員に入れなくなるからである。

### 17.4 `cc19`

`cc18` の `-I` の扱い (`adddir` で階層ごと員に足す) を，`pp17` へ
`-I` をそのまま渡す形に替える。`/include` は今までどおり束ねに入れる
—— 我々のもので 18 個しかなく，既存のプログラムがそこに載っている
ことを前提にしている (7.2)。

**`-I` だけを探す道にする**のが，いちばん小さい変更で 16 章の 4 つの
うち 1 番目を片付ける形である。

### 17.5 完了条件

第 3 部の 3 の 2 の完了条件は

> tcc の `Makefile` から `libtcc.a` と `tcc` が我々の OS の上で出来ること

とする。`lib/` (`libtcc1.a`) は 16.4 のとおり Stage 15 第 6 部と地続き
なので，**第 3 部の 3 の 3** へ回す。

## 18. `pp17` の到達点

17 章で決めたとおりに作った (`stage017/pp17.sc`)。`pp16.sc` からの差は
`-I` だけで，本体には手を入れていない。

### 18.1 何を確かめたか

`kernel24` の上で 6 つを見た。**「新しくできること」だけでなく，
「これまでできていたことが変わっていないこと」も見る**。

| | 与えたもの | 結果 |
|---|---|---|
| A | 束ねに無いヘッダ・`pp16` | `2` で落ちる (これが出発点) |
| B | 同じ束ね・`pp17 -I inc` | `0`。`int v = 42 ;` |
| C | 入れ子 (`nest.h` → `sub.h`)・`pp17 -Iinc` | `0`。`int v = 42 + 7 ;` |
| D | **員に在る束ね**・`pp16` と `pp17` | 両方 `0` で**出力がバイト一致** |
| E | 束ねに無い・`-I` を与えない | `pp: cannot find include: greet.h` / `2` |
| G | `-I inc` にも無い名前 | `pp: cannot find include: absent.h` / `2` |

D が要である。**`-I` を使わない道は 1 バイトも変わっていない。**
これが「上乗せであって置き換えではない」ことの中身である。

E と G は，pp16 が黙って `2` で落ちていたところである。終了コードは
`2` のままで，名前だけを足した —— `stage009` の「`#include` の対象が
無い (終了コード 2)」がそのまま通る。

`-Z` のような知らない選択肢は `pp: unknown option: -Z` で `1`。
**受けて捨てない。** 受けて捨てると，効いているつもりの指定が効かない
まま通る。

### 18.2 中の作り

`#include` の解決はこうなった。

1. これまでどおり**束ねの員**を探す
2. 無ければ `-I` の階層を**与えられた順**に見る
3. 開けたら中身を `src` の末尾へ読み，**員として足す**

3 が肝で，読み込んだ後の扱いが束ねの員とまったく同じになる。
フレームの積みも `__FILE__` も入れ子の復帰も，既存の道をそのまま
通る。足したのは入口だけである。

員の上限は 64 から 256 へ上げた。`-I` で足す分がここに入るためである。

### 18.3 まだやっていないこと

**鎖にも検査にも繋いでいない。** `pp17` を使う `cc19` (`-I` を束ねへ
展開するのをやめ，`pp17` へ渡す駆動役) がまだ無い。そこまで揃って
はじめて 16 章で数えた `tccpp.c` の翻訳が通る。

## 19. `cc19` の到達点と，見つかった破壊

### 19.1 何をしたか

`cc18` からの差は `-I` の扱いだけである。`/include` と `/include/sys`
は**これまでどおり束ねる** —— 我々のもので数が知れており，既存の
プログラムがこの形に乗っているからである。変えたのは `-I` だけ。

### 19.2 確かめたこと

ヘッダを `inc/` にだけ置き，束ねには入れない。`kernel24` の上で。

| | 与えたもの | 結果 |
|---|---|---|
| A | `cc18 -c main.c -o m18.o -I inc` | `0` |
| B | `cc19 -c main.c -o m19.o -I inc` | `0` |
| C | `m18.o` と `m19.o` | **バイト一致** (1340 バイト) |
| D | `cc19 -o prog main.c -I inc` → `prog` | `total 42` |
| E | `-I` を与えない | `pp: cannot find include: extra.h` / `2` |

**C が要点である。** 道は変えたが，出るものは変わっていない。
D は入れ子 (`extra.h` → `conf.h`) を探す道で辿り，マクロが正しく
展開されている。

### 19.3 その途中で見つけた破壊 (`cc18` にある)

E の終了コードが，先に D を走らせたときだけ `2` ではなく `1` になり，
`pp17` が出すはずの名前も出なかった。**同じ命令の答が違う**ので
1.6 の作法で自己再現を見たところ，**再現した** —— 環境ではなく，
D が何かを壊していた。

`_cc.b` を取り出すと 20,613 バイトのはずが 21,647 バイトあり，員
`sys/time.h` の中身が **1,340 バイトの ELF** になっていた。像の中の
`/include/sys/time.h` を見ると，本当に ELF で上書きされていた。

原因は `path` が**大域**であることである。

```c
sprintf(path, "_t%d.o", i);   /* 大域 path に出力名を作り */
compile1(ins[i], path);       /* そのまま渡す */
```

`compile1` は中で `addheaders()` → `adddir()` を呼び，`adddir` は
**同じ大域 `path`** を経路の組み立てに使う。したがって `compile1` が
出力を書く時点で，`out` は「最後に走査したファイルの経路」を指す。

- `cc18` は `-I` の階層を最後に走査する → **`inc/extra.h` を潰す**
- `cc19` は `/include/sys` が最後 → **`/include/sys/time.h` を潰す**

**症状が出ないのが最悪である。** 壊した先の名前をそのままリンカへ
渡すので辻褄が合い，リンクは通り，出来た `prog` は `total 42` を
正しく出す。**ビルドは成功したと言う。** 気づけるのは後でその
ヘッダを読んだときで，そのころには原因から遠い。

`cc19` では名前を局所に作って直した。**`cc18` にはこの誤りが残って
いる** —— 記録対象の世代なので書き換えず，ここに記す (roadmap 4 章)。
`cc18` を使うときは `-o` を付けた結合を避けるか，`-c` で `.o` を
明示的に作ってから繋ぐこと。

これで**同じ型を 3 度踏んだ** (`cc18` の `adddir` の `dir` 引数・
`mk17` の `parse()` の静的バッファ・ここ)。`docs/dev-notes.md` 4 章に
「大域の器は跨いで渡さない」として足した。

### 19.4 tcc の `tccpp.c` が我々の OS の上で通った

第 3 部の 3 の 2 で一番見たかったことである。

```
--cc19 -c t/tccpp.c -I t--
cc19 0
```

出たもの:

```
Class:    ELF32          Type:     REL (Relocatable file)
Machine:  RISC-V
.text  0x1b078 (110,712)   .bss  0x105a8 (66,984)   .rela.text 有り
記号 269
```

**tcc の前処理器を，我々のコンパイラが，我々の OS の上で訳した。**
`-I` は探す道として働き，`pp17` が要るものだけを開いている。

同じ命令を `cc18` に与えることはできない。`-I t` は `t/` の 14 個を
すべて員にするので，`/include` の 18 個と合わせて 33 個 —— 上限には
届かないが，`tcc` の木全体 (`-I.`) では 82 個で落ちる (16.2)。
`cc19` は開いた 13 個だけを員にする。

`t/` の 14 ファイルは**すべて無傷**である (19.3 の破壊が戻っていない
ことの，実物での確認)。

**必要なものは pp17 が名前で教えた。** 最初の試みは

```
pp: cannot find include: riscv64-gen.c
```

で止まった。`pp16` ならここは無言の `2` で，何が足りないのか判らない
まま止まる。名前を出すようにした甲斐がここで出た。

### 19.5 残り

`tccpp.c` 1 本が通っただけである。`Makefile` の 34 行を通しで回すには

- 残り 10 本の翻訳単位 (`tcc.c` `libtcc.c` `tccgen.c` …) も通ること
- `ar` で `libtcc.a` にまとめ，`ld16` で `tcc` に繋ぐこと
- build の途中で `c2str` を作って走らせること (16.3)

が要る。`lib/` は 16.4 のとおり第 3 部の 3 の 3 へ回す。

## 20. tcc が我々の OS の上で組み上がった (第 3 部の 3 の 2)

### 20.1 何ができたか

`tools/tcc17.sh` で，16.1 が数えた 34 行のうち **`tcc` 本体を作る分**を
我々の OS の上で通した。

```
$ sh tools/tcc17.sh all

built tccdbg (116532 バイト)     built tccelf (139476 バイト)

`hello.o` は ELF32 / REL / RISC-V である。**`-v` が通っただけでは
動くと言えない**ので，実際に翻訳させるところまでを `check` に入れた。

使ったものはすべて我々のものである —— `pp17` `cc15p` `ar17` `ld16`
を `cc19` が呼び，`sh2` が回し，`kernel24` の上で走る。

### 20.2 何を**していない**か

ここははっきり書く。

- ~~**`mk20` に tcc の `Makefile` を読ませて回してはいない。**~~
  → **21 章で回した。** ここは片付いた
- **`libtcc1.a` (`lib/`) は作っていない。** 16.4 のとおり，出来た
  `tcc` 自身と `.S` のアセンブラが要るので第 3 部の 3 の 3 へ回す
- ~~**`tccdefs_.h` はホストの tcc が作ったものを使っている。**~~
  → **21 章で我々の OS の上で作った。** ここも片付いた
- **`longjmp` が本物でない。** 途中で `tccdefs.h` が見つからなかった
  とき，`longjmp: not supported (compile error path)` と出て止まった。
  **これは我々の libc19 が出している** —— `stage017/libc19/include/setjmp.h`
  に書いてあるとおり，`setjmp` は 0 を返し `longjmp` は報告して
  `exit(1)` する**意図した割り切り**である (黙って続けて「通るが誤り」を
  作らないため)。

  実害は小さい。tcc は誤りの本文
  (`<command line>:20: error: include file 'tccdefs.h' not found`) を
  **先に出してから** `longjmp` を呼ぶので，誤りの内容は伝わる。
  終了コードもどちらも 1 である。後ろに我々の 1 行が付くだけ。

  ただし `setjmp.h` の註は「本物が要ることが**実測で判ったら**，`ld` の
  前置部にレジスタ退避のスタブを足す形で入れ直す」と書いている。
  **その実測がこれである。** 入れ直すかどうかは，tcc に誤りのある
  ソースを食わせる使い方をするかで決める

### 20.3 1 本ずつ別の起動にした理由

11 本を 1 度の起動でやると，途中で殺されたときに全部やり直しになる
(1.5)。1 本ごとに起動を分け，出来た `.o` をホスト側へ取り出して
スタンプを置く。**殺されても失うのは高々 1 本**である。実測では
1 本あたり 20〜60 秒だった。

### 20.4 自分のスクリプトで踏んだ誤り

2 つとも同じ形だったので書いておく。

1. `root` に `lib/` を作っただけで libc の `.o` を入れていなかった。
   リンクが未定義シンボルの `2` で落ちた
2. それを直したのに落ち続けた。`do_link` が「`root` が在れば使う」
   だったので，**古い `root` が使われていた**

「在れば使う」は速いが，**作り方を直したときに効かない**。組み直しは
写すだけで数秒なので，毎回組み直すことにした。手順を直したのに古い
成果物が使われるのは，このリポジトリで繰り返し出ている形である
(1.2.1 の系統)。

`ld16` が**どの記号が未定義なのかを言わない**ことも足を引っ張った
(`exit(2)` のみ)。`symnm[]` という診断用の配列を持っているのに使って
いない。`pp17` で同じことをしたので，`ld` にも世代を刻むときは名前を
出すようにする。

## 21. `mk20` が tcc の `Makefile` を回した (第 3 部の 3 の 2 の完了)

### 21.1 完了条件

第 3 部の 3 の 2 で言いたかったのはこれである。

> tcc の**本物の `Makefile`** を，我々の `make` が，我々の OS の上で
> 読んで回し，`tcc` が出来ること

回った。

```

cc19 -o libtcc.o -c libtcc.c -I. -DONE_SOURCE=0

ので手で固定した) と `config.h` だけである。

### 21.2 突き合わせ

出たものを 2 つ突き合わせた。

| | |
|---|---|
| `Makefile` から出た `tcc` と，20 章で手で回した `tcc` | **バイト一致** (985,216) |

途中で実行形式 (`c2str.exe` 98,540 バイト) を作り，走らせ，その出力を
次の入力にする，という段が我々の OS の上で通った。

`tcc` が同じバイト列なので，20.1 の `check` (実際に `hello.c` を
翻訳させる) はそのまま当てはまる。

### 21.3 木を `t/` の中に置いた理由

像の根に置くと，tcc の `include/` が我々の `/include` を隠す。`cc19` は
`/include/*.h` を束ねるので，そこが tcc のものに替わると**自分の libc の
ヘッダを見失う**。`tools/tcc-stone.sh` の「平らな名前空間」の註と同じ話
である。

`t/` で走らせる以上，素の名前は `t/` からしか引けない (探す道は無い。
16.3)。`cc19` / `ar` / `mk` を `t/` にも置いてある。

### 21.4 出た雑音

```

```

`Makefile` が `TCC_GITHASH` を `$(shell git ...)` で作ろうとする。
我々の OS に `git` は無い。`mk20` は落ちた `$(shell)` を空として扱い，
**本物の `make` と同じように**先へ進む。`-DTCC_GITHASH=...` が命令行に
