# Stage 6: scc (セルフホスト) 設計文書

## 1. 目的と位置づけ

### 1.1 目的

Stage 5 までで sc 言語のコンパイラ (sol 言語で実装) が得られたが，
処理系の実装言語 (sol) と処理対象の言語 (sc) が異なるため，
ビルドチェーンは依然として下位の言語に依存している。

Stage 6 の目的はセルフホストである。sc コンパイラを sc 言語自身で再記述し
(scc = self-hosted sc compiler)，固定点検証によって「sc 言語だけで
sc 言語の処理系を維持できる」ことを機械的に示す。以降の開発 (Stage 7 の
現代化) は scc.sc の改訂のみで進められる。

### 1.2 固定点検証 ([plan.md](plan.md) 4 章 Stage 6 の完了条件)

scc.sc を S，Stage 5 の sc コンパイラを C0 と書く。

```
B1 = C0(S)     # 下位チェーンで bootstrap した scc
B2 = B1(S)     # scc が自分自身をコンパイルしたもの
B3 = B2(S)     # さらにもう一段
```

完了条件は B2 と B3 のビット一致である (B2 以降は「S を S 自身の定める
コード生成で処理した結果」であり，正しくセルフホストできていれば不動点に達する)。
さらに scc のコード生成は C0 と同一のテンプレート・規約を踏襲するため，
実装が正しければ B1 == B2 も成立する (テストでは B2 == B3 を完了条件とし，
B1 == B2 は追加の一致検査として確認する)。

### 1.3 非目標

- sc 言語仕様の拡張は行わない。scc は [stage005-sc.md](stage005-sc.md) 2 章の
  仕様の範囲内で記述し，同仕様を実装する。
- 最適化・エラーメッセージの改善は行わない (Stage 7 以降)。

## 2. 実装方針

### 2.1 構成

scc.sc は Stage 5 実装 (sc.sol) の構成を sc 言語へ移植したものである:
字句解析，再帰下降構文解析，単一パスコード生成 + 出力バッファへの
バックパッチ，同一のコード生成テンプレート，同一のランタイム前置部 (32 語)，
同一のエラーコード (0..6)。

sc 言語の制約に合わせた再構成:

- 記号表は「構造体の配列」が書けないため，並行配列 (名前 16 バイト × N の
  char 配列 + int 配列群) で表す。エントリの参照は添字で行い，
  未発見は -1 で表す。
- 定数構文がないため，トークン種別等の定数は大域変数として `init()` で
  設定する (値は Stage 5 実装と同一)。
- 出力バッファへの語アクセスは，char 配列のアドレスを int ポインタ変数へ
  代入して行う (sc の代入は型変換を検査しない)。
- break/continue がないため，探索ループは関数化して return で脱出する。

### 2.2 領域 (すべて大域配列。生成プログラムの BSS 0x8010_0000 から確保される)

| 配列 | 用途 |
|---|---|
| src (256 KiB) | 入力ソース (EOT まで読込み) |
| outb (512 KiB) | 生成バイナリ (バックパッチ対象) |
| gname/gkind/gty/gval/gdef/garr/gna (2048 エントリ) | 大域記号表 |
| lname/lty/loff/larr (256) | ローカル記号表 |
| sname/ssize (256) | 構造体表 |
| mname/msid/mty/moff/marr (2048) | メンバ表 |
| sbuf (256) / tname (16) / snam (16) | 文字列リテラル / トークン名 / struct 名退避 |

### 2.3 検証で用いる同値性

B2 の正しさは固定点だけでなく，Stage 5 の仕様テストスイート
(tests/stage005/*.sc) を B2 でコンパイルして実行し，Stage 5 と同じ
出力・終了コードになることでも確認する (言語仕様に対する同値性)。

## 3. 成果物と管理形態

| ファイル | 内容 |
|---|---|
| stage006/scc.sc | scc のソース (sc 言語)。以降の正本 |
| stage006/scc.md | 説明文書: ビルド手順，B1/B2 の期待 SHA-256，構造表 |

scc1.bin (= C0(S)) と scc.bin (= B2。以降の実行に用いる正本) は
ビルドで再現される生成物であり，git 管理しない。

```
sh tools/build.sh stage006   # hex0 -> hex1 -> asm -> sol -> sc -> scc1 -> scc の順でビルド
```

## 4. 検証計画 (tests/stage006)

1. ビルド再現: B1 (scc1.bin)・B2 (scc.bin) の SHA-256 が scc.md 記載値と一致すること
2. 固定点: B3 = B2(scc.sc) が B2 とビット一致すること (完了条件)。
   併せて B1 == B2 (コード生成の同一性) を確認する
3. 同値性: Stage 5 仕様スイート (arith/fib/ptr/struct/upper) を B2 で
   コンパイル・実行し，Stage 5 と同じ出力・終了コードになること
4. エラー系: B2 が Stage 5 と同じエラーコード (1..6) を返すこと
5. verify 層: B2 の逆アセンブルとランタイム・テンプレートの照合

## 5. Stage 7 への接続

Stage 7 (現代化: SSA IR・最適化・レジスタ割付) は scc.sc の改訂として行う。
コード生成が変わるため B1 == B2 は以降維持されないが，固定点 B2 == B3 は
維持し続ける (完了条件)。
