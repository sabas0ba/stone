# stone: コンパイラ実装 Bootstrap 計画

## 1. 目的

QEMU RISC-V (RV32IM, bare-metal) 上で，人手エンコードした機械語 seed から出発し，
段階的に言語処理系を構築し，最終的にセルフホストする現代的なコンパイラへ到達する。
各段階は前段の成果物のみでビルド可能であることを機械的に検証し，全過程を再現可能に保つ。

## 2. 方針・制約

### 2.1 純度ポリシー（ビルド経路）

- seed (Stage 1) をはじめとする人手エンコードの成果物は，生のバイナリファイルとして
  直接 git 管理する。変換ツールは介在させない。各バイナリには全命令の注釈付き listing と
  照合用 SHA-256 を記載した説明文書を添付する。
- Stage 2 以降の成果物は，すべて前段の成果物のみでビルドする。
- 既存のアセンブラ (as) およびリンカ (ld) は，ビルド経路・検証経路を問わず一切使用しない。
- 既存 bootstrap 系プロジェクトのコードは参照・流用しない。設計は概念レベルで独自に行う。

### 2.2 検証ポリシー (verify 層)

- `verify/` 配下に限定して，参照用逆アセンブラ (riscv64-unknown-elf-objdump) の使用を許可する。
  用途は，手書きエンコードおよび自作処理系の出力バイナリを逆アセンブルし，意図したエンコードと
  照合することに限定する。ビルド成果物には影響しない。
- `verify/audit/` には，仕様書から独立に書き起こした参照実装 (ホスト側 Python) による
  再導出検査を置く (`verify/audit/README.md`)。逆アセンブラと同じく読取り専用の検証であり，
  ビルド経路には使用しない。
- コンテナイメージからは as / ld の実体を削除し，ポリシーを機械的に強制する。

### 2.3 再現性

- 開発環境はコンテナ (podman) で固定する。ベースイメージは digest 固定，
  パッケージは snapshot.debian.org のアーカイブ時点指定で固定する。
- パッケージのバージョンはアーカイブ時点指定により一意に定まる。`env/packages.lock` に
  全導入パッケージのバージョンを固定し，イメージビルド時に導入結果と照合する。
  不一致の場合はビルドを失敗とする。
- 各 Stage のビルドはビット再現可能とし，期待バイナリのハッシュをテストで固定する。

### 2.4 開発運用

- git 管理下で開発し，機能追加は branch で行う。Commit message は Conventional Commits に従う。
- テンポラリファイルは repo 内の git ignore された `tmp/` 配下で扱う。
- 一次資料 (ISA 仕様書等) は `docs/external/` (git ignore) に保存し,
  URL と SHA-256 を [SOURCES.md](SOURCES.md) に記録する。
- 実務上の手順 (コンテナが使えない環境での代替，デバッグ手法，検証レシピ) は
  [dev-notes.md](dev-notes.md) に記録する。

## 3. 実行環境

| 項目 | 内容 |
|---|---|
| エミュレータ | qemu-system-riscv32 (Debian bookworm, qemu-system-misc) |
| マシン | `-M virt` |
| ISA | RV32IM (virt デフォルト CPU のサブセットとして使用) |
| ロード方式 | `-bios <flat.bin>`: フラットバイナリを RAM 先頭 0x8000_0000 に配置し，そこから実行。ELF 等のコンテナ形式は使わない |
| I/O | 16550 互換 UART (virt: 0x1000_0000) のみ。ホスト側で stdin → UART RX, UART TX → stdout をパイプする |
| 終了通知 | virt の test finisher (0x0010_0000)。成功 0x5555 / 失敗 (code<<16)\|0x3333 の書込みで QEMU が終了コード付きで停止 |
| 永続化 | ストレージデバイスは導入しない。ファイルの保存・受け渡しはすべてホスト側で行う |

各 Stage の処理系は「UART からソーステキストを読み，UART へ成果物バイナリを書き出すフィルタ」
として動作する。ホスト側は

```
podman run ... qemu-system-riscv32 ... -bios stageN.bin < input.src > output.bin
```

の形式で実行し，入出力はホスト側でファイルとして保存する。

デバッグ・トレースには QEMU の GDB stub および実行トレース機能を使用する
(`tools/run-qemu.sh` 参照)。いずれも観測専用であり，成果物の生成には影響させない。

## 4. 段階計画

| Stage | 成果物 | ビルド手段 | 完了条件 |
|---|---|---|---|
| 0 | コンテナ環境，QEMU 実行スクリプト，テストハーネス，本計画書 | ホスト | 人手エンコードした最小プログラムが QEMU 上で動作し，UART 出力と終了コードを CI で判定できる |
| 1 | seed (hex0): hex テキスト → バイナリ変換フィルタ | 人手エンコードした生バイナリ (説明文書を添付) | 自分自身の hex listing を入力すると自分自身のバイナリを出力する（自己再生成の一致） |
| 2 | hex1/2: ラベル定義・参照 (分岐オフセット自動計算)，コメント対応 | Stage 1 | ラベル付き hex で書いたテストケース群が期待バイナリと一致する |
| 3 | アセンブラ: RV32IM ニーモニック，疑似命令，2 パスラベル解決 | Stage 2 | RV32IM 全命令のエンコードテストが通り，verify 層での逆アセンブル結果と一致する |
| 4 | 低級構造化言語 (スタック指向の小言語を想定) の処理系 | Stage 3 | 制御構造・サブルーチン・変数を備え，Stage 5 の記述に十分な表現力を持つ |
| 5 | 高級言語サブセット (C サブセット相当: 関数・ポインタ・構造体程度) のコンパイラ | Stage 4 | 言語仕様書に対するテストスイートが通る |
| 6 | セルフホスト: Stage 5 言語による自己再記述 | Stage 5 | 固定点検証: A(A) と A(A(A)) の出力バイナリがビット一致する |
| 7 | 現代化: IR 導入 (SSA)，最適化パス，レジスタ割付の再設計 | Stage 6 | 各最適化パスの単体テストと，固定点検証の維持 |

横断ルール:

- 各 Stage は「前段の成果物のみでビルドできること」を make ターゲットとして表現し，
  チェーン全体の再ビルドを CI で検証する。
- 各 Stage の設計文書を `docs/stageN-*.md` として残す（入出力仕様，文法，エンコード規約）。
- 設計文書は単独で判断できる状態を保つ。前段から継承する前提（言語仕様・実行モデル等）は
  参照だけで済ませず，判断に必要な範囲の要約を文書内に含める。
- 文書間の参照は相対パスの markdown リンクで記述する。

## 5. リポジトリ構成

```
stone/
├── docs/            # 計画・設計文書，SOURCES.md，external/ (git ignore, 一次資料)
├── env/             # Containerfile, packages.lock
├── tools/           # ホスト側・コンテナ内スクリプト (QEMU 起動，seed 初回変換，テスト実行)
├── stage001/ …      # 各 Stage のソースと期待出力・テスト (番号は 3 桁ゼロ埋め)
├── tests/           # リグレッションテスト (tools/test.sh から実行)
├── verify/          # 検証専用レイヤ (objdump による照合のみ)
└── tmp/             # git ignore 対象の作業領域
```
