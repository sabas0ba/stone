# Stage 14: 外部の C プログラムのビルド 設計文書

## 1. 目的と位置づけ

Stage 13 までで，処理系は自分で作った OS の上で自分自身を作り直せる
ようになった ([stage013-tools.md](stage013-tools.md) 7.4)。しかし
**これまでの入力はすべて自分たちが書いた C である。**

[roadmap.md](roadmap.md) Phase C の狙いは，ここで入力を「他人の C」へ
切り替えることである。自作コードだけを入力にしてきた処理系は，自分が
使わない書き方を実装しないまま通ってしまう。その差は，実際に他人の
コードを読ませるまで見えない。

Stage 14 の完了条件は「無改変の外部ソースをビルドし，正しく動作する」で
ある。本書はそこへ至る道筋を定める。

## 2. 先に決めておくこと

### 2.1 外部ソースを repo に取り込まない

外部のソースは **repo に含めず，取得して SHA-256 で固定する**。
既に一次資料 (ISA 仕様書) で使っている仕組みをそのまま流用する
([plan.md](plan.md) 2.4)。

- 実体は `docs/external/` (git ignore) に置く
- URL と SHA-256 は [SOURCES.md](SOURCES.md) に記録する

理由は 2 つある。

1. **他人の著作物を抱え込まない。** ライセンスの管理と再配布の判断が
   必要になり，本計画の関心から外れる
2. **純度ポリシーとの区別を保つ。** [roadmap.md](roadmap.md) 2.3 の
   とおり，他人のソースを**入力として**読むことは目標そのものであり，
   ビルド経路へ他人の**成果物**を差し込むこととは別である。repo の中に
   置かないことで，この区別が配置として現れる

### 2.2 取得できない環境でどうするか

外部ソースの取得には外向きの通信が要る。本計画の CI はコンテナを
`snapshot.debian.org` に固定して作っており，それ以外への通信を前提に
していない。実際，本書を書いた作業環境では外向きの HTTPS が
プロキシに拒まれた (403)。

したがって **外部ソースを使う検査は「素材があるときだけ走る」形にする**。
素材が無ければその検査は飛ばし，理由を出す。素材の有無で結果が変わる
検査を必須にすると，環境の差でチェーン全体が赤くなる。

素材に依存しない検査 (4 章の適合台帳) は常に走る。

### 2.3 最初の 1 本をどう選ぶか

いきなり大きなものを当てても，落ちた箇所の数だけが判って前に進めない。
選定の条件を先に決める。

| 条件 | 理由 |
|---|---|
| 単一ファイル規模 (数千行まで) | 落ちた箇所を 1 つずつ潰せる |
| C89 で書かれている | C99 以降の機能は Stage 14 の範囲を広げすぎる |
| 浮動小数点を使わない | 処理系に浮動小数点が無い (4.2) |
| OS への要求が小さい | 自作 OS が持つのは open/read/write/close/brk/exit だけ |
| 正解が自明 | 既知の入力に対する既知の出力で正しさを確かめられる |
| ライセンスが寛容 | 取得と利用に条件が少ない |

圧縮・ハッシュ・簡易なインタプリタの類が当てはまる。**選定は素材を
実際に取得できる環境で行う。**

## 4. 第 1 部: 適合台帳

### 4.1 何をしたか

現実の C が使う書き方を 1 つずつ切り出した小さなプログラム
([../tests/stage014/probe/](../tests/stage014/probe/)) を 26 本書き，
本処理系に通して結果を記録した。記録は
[../tests/stage014/ledger.txt](../tests/stage014/ledger.txt) にあり，
[../tests/stage014/test.sh](../tests/stage014/test.sh) が毎回照合する。

状態は 3 つに分ける。

| 状態 | 意味 |
|---|---|
| `ok` | 通って，期待どおりの出力になる |
| `gap` | cc がその終了コードで拒む (未対応。**拒むこと自体は正しい**) |
| `bad` | 通ってしまうが結果が誤っている |

**台帳と実測が食い違えば検査は失敗する。** 直したのに表がそのままでも，
壊したのに気づかなくても，等しく捕まえるためである。`gap` が `ok` に
変わるのは前進なので，表を直して commit する。

この形にしたのは，Stage 10 で「仕様が揃った」と判断した後に実装漏れが
見つかった経験による ([dev-notes.md](dev-notes.md) 4 章)。**未対応を
「まだ無い」と明示して数える**ほうが，目次を追って揃ったと言うより
確かである。

### 4.2 結果

通ったのは 13 件である。符号なしの比較・剰余・シフト，負数の算術右
シフト，`sizeof` の各形，多次元配列の受渡し，`switch` の落下，共用体，
`goto`，文字エスケープ，ポインタの差と比較と `void *`，文字列ポインタの
表，`const` / `volatile`，前処理の `defined` / `#elif` / `##` / `#`，
そして **可変長引数を別の関数へ渡すこと** (`vfprintf` 相当) が動く。

未対応は 12 件である。影響の大きい順に並べる。

| 未対応 | cc | なぜ重いか |
|---|---|---|
| 1 つの宣言に複数の宣言子 (`int a, b;`) | 1 | **現実の C ではほぼ全てのファイルに現れる。** これだけで大半のソースが通らない |
| 隣接する文字列リテラルの連結 (`"a" "b"`) | 1 | 長いメッセージや書式を行に分けて書くのに常用される |
| 整数定数の接尾辞 (`U` / `L`) | 1 | 境界値の定義に現れる |
| 入れ子の初期化子 (`{{1,2},{3,4}}`) | 1 | 静的な表を持つ書き方が通らない |
| 関数名を初期化子に使う | 1 | 関数ポインタの表 (手書きの仮想表) が作れない |
| 関数内 `static` | 1 | 状態を隠す常套手段 |
| K&R 形式の関数定義 | 1 | 1989 年より前に書かれた C はこの形 |
| ビットフィールド | 1 | ヘッダやプロトコル定義に現れる |
| `register` 記憶域クラス | 2 | 古い C では頻出する |
| 不完全型への `typedef` の前方参照 | 2 | 連結リスト・木の定義で使う |
| 浮動小数点 (`float` / `double`) | 2 | 範囲が大きい。当面は「使わないものを選ぶ」で回避する (2.3) |
| 引数リストが空の宣言へ実引数を渡す | 5 | 古い C の書き方 |

**通るが誤っているものが 1 件ある。**

- `long long` が **32 bit として扱われる** (`sizeof` が 4 を返す)。
  拒まれないので，使っているソースは静かに壊れる。
  [dev-notes.md](dev-notes.md) の「型エラーとして拒否するより，静かに
  値が壊れるほうが悪い」に照らすと，**まず拒むように直すべきもの**である

### 4.3 この結果から言えること

1. **止まっているのは言語の中心ではなく，書き方の幅である。** 式・文・
   型の仕組みはあらかた動く。足りないのは「同じことを別の書き方で書く」
   経路で，宣言の構文まわりに集中している
2. **最優先は複数宣言子である。** これ 1 つで通らないソースの数がまるで
   違う。第 2 部はここから始める
3. **浮動小数点は別格に大きい。** 型・定数・演算・書式・ソフトウェア
   実装 (RV32IM に浮動小数点命令は無い) が一式で要る。第 2 部には
   含めず，必要になった段で独立して扱う
4. **`long long` は先に拒むように直す。** 直せるまでは通してはいけない

## 5. 第 2 部: 宣言と字句の幅 (cc14a)

### 5.1 何を直したか

台帳の判断 (4.3) どおり，宣言の構文まわりから潰した。cc の新世代
[../stage014/cc14.sc](../stage014/cc14.sc) である。

| 直したもの | 台帳 | 手当て |
|---|---|---|
| 1 つの宣言に複数の宣言子 | multidecl | 大域 (`dcont`)・局所 (`plocal`) の両方を，基底型を保ったまま `,` で回す形にした |
| 隣接する文字列リテラルの連結 | strcat_lit | `lexstr` が閉じ引用符の後ろの空白と行コメントを飛ばし，次も引用符なら続けて同じ緩衝へ読む |
| 整数定数の接尾辞 (`U` / `L`) | usuffix | `lexnum` が末尾の `u U l L` を読み捨てる。長さの区別は付けない (`long` は `int` と同じ幅) |
| `register` / `auto` | registerkw | 予約語として受け，記憶域の割付けは変えずに読み捨てる |

**コード生成には触れていない。** 触れたのは字句解析と宣言の構文だけで
ある。したがってブートストラップ 1 段目と正本が一致するはず……ではなく，
ここは一致しない。宣言子ごとに型を取り直す形へ変えたことで局所変数の
割付け順序が変わりうるためである。健全性は固定点 (B2 == B3) で確かめる
([dev-notes.md](dev-notes.md) 4 章)。

### 5.2 `long long` は「通す」から「拒む」へ

第 1 部で見つけた唯一の `bad` である。cc10l は `long long` を受け付け，
`long` と同じ 32 bit として扱っていた。**拒まれないので，使っている
ソースは静かに壊れる。**

cc14a は型指定子の中で `long` の個数を数え，2 個以上なら終了コード 2 で
拒む。64 bit 整数そのものは実装していないので，これは「正しく動くように
した」のではなく「**誤った答えを出すのをやめた**」変更である。

[dev-notes.md](dev-notes.md) の「型エラーとして拒否するより，静かに値が
壊れるほうが悪い」に従った。台帳の `bad` は 0 件になった。

### 5.3 `cc.bin` は差し替えない

これまで「`cc.bin` は常に最新世代を指す」という約束で来た
([stage010-c89.md](stage010-c89.md) 2.1)。Stage 14 ではこれを**行わない**。

`cc.bin` を cc14a へ向けると，Stage 11・12・13 の記録済み成果物が
すべて別のバイト列になる。それらは cc10l が作ったものとして凍結されて
おり ([artifacts.md](artifacts.md))，作り直しは過去の世代を書き換える
ことにあたる。

したがって cc14a は別名で置き，差し替えは必要になった時点で判断する。
適合台帳だけは最前線の世代で測る意味があるので，cc14a を使う。

### 5.4 結果

台帳は「通る 17 件 / 未対応 9 件 / 通るが誤り 0 件」になった
(第 1 部は 13 / 12 / 1)。最も影響の大きい複数宣言子が通るように
なったので，現実の C を読ませたときに **最初の 1 行で落ちる** ことは
なくなったはずである。

## 6. 次の一歩

第 3 部は残る未対応のうち，初期化子まわり (入れ子の初期化子・関数名を
初期化子に使う) と関数内 `static` を扱う。どれも「静的な表を持つ」
書き方に効くもので，現実の C で次に多く現れる形である。

K&R 形式の関数定義とビットフィールドはその後に置く。前者は古いソース
だけに現れ，後者は構造体の配置そのものに手を入れるためである。
