# Stage 14: 外部の C プログラムのビルド 設計文書

## 1. 目的と位置づけ

Stage 13 までで，処理系は自分で作った OS の上で自分自身を作り直せる
ようになった ([stage013-tools.md](stage013-tools.md) 7.4)。しかし
**これまでの入力はすべて自分たちが書いた C である。**

[roadmap.md](roadmap.md) Phase C の狙いは，ここで入力を「他人の C」へ
切り替えることである。自作コードだけを入力にしてきた処理系は，自分が
使わない書き方を実装しないまま通ってしまう。その差は，実際に他人の
コードを読ませるまで見えない。

Stage 14 の完了条件は「無改変の外部ソースをビルドし，正しく動作する」で
ある。本書はそこへ至る道筋を定める。

## 2. 先に決めておくこと

### 2.1 外部ソースを repo に取り込まない

外部のソースは **repo に含めず，取得して SHA-256 で固定する**。
既に一次資料 (ISA 仕様書) で使っている仕組みをそのまま流用する
([plan.md](plan.md) 2.4)。

- 実体は `docs/external/` (git ignore) に置く
- URL と SHA-256 は [SOURCES.md](SOURCES.md) に記録する

理由は 2 つある。

1. **他人の著作物を抱え込まない。** ライセンスの管理と再配布の判断が
   必要になり，本計画の関心から外れる
2. **純度ポリシーとの区別を保つ。** [roadmap.md](roadmap.md) 2.3 の
   とおり，他人のソースを**入力として**読むことは目標そのものであり，
   ビルド経路へ他人の**成果物**を差し込むこととは別である。repo の中に
   置かないことで，この区別が配置として現れる

### 2.2 取得できない環境でどうするか

外部ソースの取得には外向きの通信が要る。本計画の CI はコンテナを
`snapshot.debian.org` に固定して作っており，それ以外への通信を前提に
していない。実際，本書を書いた作業環境では外向きの HTTPS が
プロキシに拒まれた (403)。

したがって **外部ソースを使う検査は「素材があるときだけ走る」形にする**。
素材が無ければその検査は飛ばし，理由を出す。素材の有無で結果が変わる
検査を必須にすると，環境の差でチェーン全体が赤くなる。

素材に依存しない検査 (4 章の適合台帳) は常に走る。

### 2.3 最初の 1 本をどう選ぶか

いきなり大きなものを当てても，落ちた箇所の数だけが判って前に進めない。
選定の条件を先に決める。

| 条件 | 理由 |
|---|---|
| 単一ファイル規模 (数千行まで) | 落ちた箇所を 1 つずつ潰せる |
| C89 で書かれている | C99 以降の機能は Stage 14 の範囲を広げすぎる |
| 浮動小数点を使わない | 処理系に浮動小数点が無い (4.2) |
| OS への要求が小さい | 自作 OS が持つのは open/read/write/close/brk/exit だけ |
| 正解が自明 | 既知の入力に対する既知の出力で正しさを確かめられる |
| ライセンスが寛容 | 取得と利用に条件が少ない |

圧縮・ハッシュ・簡易なインタプリタの類が当てはまる。**選定は素材を
実際に取得できる環境で行う。**

## 4. 第 1 部: 適合台帳

### 4.1 何をしたか

現実の C が使う書き方を 1 つずつ切り出した小さなプログラム
([../tests/stage014/probe/](../tests/stage014/probe/)) を 26 本書き，
本処理系に通して結果を記録した。記録は
[../tests/stage014/ledger.txt](../tests/stage014/ledger.txt) にあり，
[../tests/stage014/test.sh](../tests/stage014/test.sh) が毎回照合する。

状態は 3 つに分ける。

| 状態 | 意味 |
|---|---|
| `ok` | 通って，期待どおりの出力になる |
| `gap` | cc がその終了コードで拒む (未対応。**拒むこと自体は正しい**) |
| `bad` | 通ってしまうが結果が誤っている |

**台帳と実測が食い違えば検査は失敗する。** 直したのに表がそのままでも，
壊したのに気づかなくても，等しく捕まえるためである。`gap` が `ok` に
変わるのは前進なので，表を直して commit する。

この形にしたのは，Stage 10 で「仕様が揃った」と判断した後に実装漏れが
見つかった経験による ([dev-notes.md](dev-notes.md) 4 章)。**未対応を
「まだ無い」と明示して数える**ほうが，目次を追って揃ったと言うより
確かである。

### 4.2 結果

通ったのは 13 件である。符号なしの比較・剰余・シフト，負数の算術右
シフト，`sizeof` の各形，多次元配列の受渡し，`switch` の落下，共用体，
`goto`，文字エスケープ，ポインタの差と比較と `void *`，文字列ポインタの
表，`const` / `volatile`，前処理の `defined` / `#elif` / `##` / `#`，
そして **可変長引数を別の関数へ渡すこと** (`vfprintf` 相当) が動く。

未対応は 12 件である。影響の大きい順に並べる。

| 未対応 | cc | なぜ重いか |
|---|---|---|
| 1 つの宣言に複数の宣言子 (`int a, b;`) | 1 | **現実の C ではほぼ全てのファイルに現れる。** これだけで大半のソースが通らない |
| 隣接する文字列リテラルの連結 (`"a" "b"`) | 1 | 長いメッセージや書式を行に分けて書くのに常用される |
| 整数定数の接尾辞 (`U` / `L`) | 1 | 境界値の定義に現れる |
| 入れ子の初期化子 (`{{1,2},{3,4}}`) | 1 | 静的な表を持つ書き方が通らない |
| 関数名を初期化子に使う | 1 | 関数ポインタの表 (手書きの仮想表) が作れない |
| 関数内 `static` | 1 | 状態を隠す常套手段 |
| K&R 形式の関数定義 | 1 | 1989 年より前に書かれた C はこの形 |
| ビットフィールド | 1 | ヘッダやプロトコル定義に現れる |
| `register` 記憶域クラス | 2 | 古い C では頻出する |
| 不完全型への `typedef` の前方参照 | 2 | 連結リスト・木の定義で使う |
| 浮動小数点 (`float` / `double`) | 2 | 範囲が大きい。当面は「使わないものを選ぶ」で回避する (2.3) |
| 引数リストが空の宣言へ実引数を渡す | 5 | 古い C の書き方 |

**通るが誤っているものが 1 件ある。**

- `long long` が **32 bit として扱われる** (`sizeof` が 4 を返す)。
  拒まれないので，使っているソースは静かに壊れる。
  [dev-notes.md](dev-notes.md) の「型エラーとして拒否するより，静かに
  値が壊れるほうが悪い」に照らすと，**まず拒むように直すべきもの**である

### 4.3 この結果から言えること

1. **止まっているのは言語の中心ではなく，書き方の幅である。** 式・文・
   型の仕組みはあらかた動く。足りないのは「同じことを別の書き方で書く」
   経路で，宣言の構文まわりに集中している
2. **最優先は複数宣言子である。** これ 1 つで通らないソースの数がまるで
   違う。第 2 部はここから始める
3. **浮動小数点は別格に大きい。** 型・定数・演算・書式・ソフトウェア
   実装 (RV32IM に浮動小数点命令は無い) が一式で要る。第 2 部には
   含めず，必要になった段で独立して扱う
4. **`long long` は先に拒むように直す。** 直せるまでは通してはいけない

## 5. 第 2 部: 宣言と字句の幅 (cc14a)

### 5.1 何を直したか

台帳の判断 (4.3) どおり，宣言の構文まわりから潰した。cc の新世代
[../stage014/cc14.sc](../stage014/cc14.sc) である。

| 直したもの | 台帳 | 手当て |
|---|---|---|
| 1 つの宣言に複数の宣言子 | multidecl | 大域 (`dcont`)・局所 (`plocal`) の両方を，基底型を保ったまま `,` で回す形にした |
| 隣接する文字列リテラルの連結 | strcat_lit | `lexstr` が閉じ引用符の後ろの空白と行コメントを飛ばし，次も引用符なら続けて同じ緩衝へ読む |
| 整数定数の接尾辞 (`U` / `L`) | usuffix | `lexnum` が末尾の `u U l L` を読み捨てる。長さの区別は付けない (`long` は `int` と同じ幅) |
| `register` / `auto` | registerkw | 予約語として受け，記憶域の割付けは変えずに読み捨てる |

**コード生成には触れていない。** 触れたのは字句解析と宣言の構文だけで
ある。したがってブートストラップ 1 段目と正本が一致するはず……ではなく，
ここは一致しない。宣言子ごとに型を取り直す形へ変えたことで局所変数の
割付け順序が変わりうるためである。健全性は固定点 (B2 == B3) で確かめる
([dev-notes.md](dev-notes.md) 4 章)。

### 5.2 `long long` は「通す」から「拒む」へ

第 1 部で見つけた唯一の `bad` である。cc10l は `long long` を受け付け，
`long` と同じ 32 bit として扱っていた。**拒まれないので，使っている
ソースは静かに壊れる。**

cc14a は型指定子の中で `long` の個数を数え，2 個以上なら終了コード 2 で
拒む。64 bit 整数そのものは実装していないので，これは「正しく動くように
した」のではなく「**誤った答えを出すのをやめた**」変更である。

[dev-notes.md](dev-notes.md) の「型エラーとして拒否するより，静かに値が
壊れるほうが悪い」に従った。台帳の `bad` は 0 件になった。

### 5.3 `cc.bin` は差し替えない

これまで「`cc.bin` は常に最新世代を指す」という約束で来た
([stage010-c89.md](stage010-c89.md) 2.1)。Stage 14 ではこれを**行わない**。

`cc.bin` を cc14a へ向けると，Stage 11・12・13 の記録済み成果物が
すべて別のバイト列になる。それらは cc10l が作ったものとして凍結されて
おり ([artifacts.md](artifacts.md))，作り直しは過去の世代を書き換える
ことにあたる。

したがって cc14a は別名で置き，差し替えは必要になった時点で判断する。
適合台帳だけは最前線の世代で測る意味があるので，cc14a を使う。

### 5.4 結果

台帳は「通る 17 件 / 未対応 9 件 / 通るが誤り 0 件」になった
(第 1 部は 13 / 12 / 1)。最も影響の大きい複数宣言子が通るように
なったので，現実の C を読ませたときに **最初の 1 行で落ちる** ことは
なくなったはずである。

## 6. 第 3 部: 入れ子の初期化子 (cc14b)

### 6.1 2 件の未対応は同じ原因だった

台帳の `nestinit` (`{{1,2},{3,4}}`) と `fptab` (関数ポインタの表) は，
別々の機能に見えて **原因が同じ**だった。大域の初期化子を 1 個読む
`ginit1` が `{` を受けなかったのである。

`ginit1` に次を足した。

- 要素が **構造体** なら，メンバを登録順に埋める。メンバ間の隙間と
  末尾の余りは 0 で埋める (`moff` と `tsize` を見る)
- それ以外なら，`{ ... }` を **透過的な括り** として読む。多次元配列は
  `ginit` が既に要素型を平らに畳んでいるので，内側の括りは「平らな列の
  一部」として読めばよい

あわせて `ginit` の配列ループが要素数を **出力バイト数から** 求めるように
した。入れ子の初期化子は 1 回の `ginit1` で複数の要素を出すので，
呼出し回数では数えられない。ここを直さないと，読み終えた後の 0 埋めが
既に出した領域を上書きする。

### 6.2 直しても通らなかったほう

`nestinit` は通るようになったが，`fptab` は通らなかった。**残っていたのは
初期化子ではなく，`struct op { int (*fn)(void); };` という
構造体メンバの関数ポインタ**である。台帳の説明をそのように直した。

台帳の項目名は「症状」で付けるので，直してみるまで原因が 1 つとは限らない。
2 件が 1 つの原因だったのと同じくらい，1 件が 2 つの原因を持つこともある。

### 6.3 世代を足すときは，凍結した世代を書き換えない

第 3 部の作業では最初，第 2 部の `stage014/cc14.sc` をその場で編集して
しまった。これは [artifacts.md](artifacts.md) の凍結の規則に反する
(cc14a の SHA-256 は記録済みで，その入力を書き換えると記録どおりに
再生成できなくなる)。気づいた時点で `cc14.sc` を戻し，差分を新世代
`cc14b.sc` へ移した。**世代を足すときは必ず複製から始める。**

### 6.4 結果

台帳は「通る 18 件 / 未対応 8 件 / 通るが誤り 0 件」になった。

## 7. 第 4 部: 関数内 `static` と構造体メンバの関数ポインタ (cc14c)

### 7.1 構造体メンバの関数ポインタは宣言側だけの穴だった

第 3 部で判ったとおり，`fptab` の残りは `struct op { int (*fn)(void); };`
というメンバ宣言そのものだった。`strudef` がメンバの宣言子で `isfnp()` を
見て `fnpdec` へ回すようにしただけで，呼出し (`ops[i].fn()`) は既存の
「関数へのポインタを通した呼出し」がそのまま効いた。**コード生成には
触れていない。**

### 7.2 関数内 `static` は「別名を付けた大域」である

実体をフレームではなく `.bss` に取り，呼出しをまたいで値が残るように
した。

- 大域表へ「元の名前 + `.` + 通し番号」の別名で登録する。`.` は識別子に
  使えないので利用者の大域と衝突せず，**一意性は通し番号だけで決まる**
  (関数が違っても同じ名前の `static` を持てる)。ELF にはローカル
  シンボルとして出る
- 局所表には元の名前で載り，対応表 (`lsg`) が別名の大域記号を指す。
  参照 (`eident`) は大域と同じ形 (`c_gaddr`) を出す
- **初期化子は拒む** (終了コード 1)。関数の途中で `.text` へ初期値を
  書き出す経路が無く，通すと初期値が付かないまま静かに壊れるためである。
  `.bss` なので値は 0 で始まり，`static int n;` は C の意味どおりになる

### 7.3 結果

台帳は「通る 20 件 / 未対応 6 件 / 通るが誤り 0 件」になった。

## 8. 第 5 部: タグの前方参照と K&R 形式 (cc14d)

### 8.1 不完全型は「大きさ 0」で表す

`typedef struct node Node;` は，本体が出る前のタグを使う。`ptype` が
タグを引けなければ**不完全型** (大きさ 0) として登録し，本体は後の
`struct node { ... }` が同じ項目を埋める形にした。

- 大きさ 0 を「不完全」の印に使う。メンバの無い定義が紛れないよう，
  完成時の大きさは最小 4 にする
- **不完全のまま値で使うことは拒む** (メンバ・局所・大域とも終了
  コード 5)。通せるのはポインタだけである。ここを黙って通すと
  大きさ 0 の実体が割り付き，隣の変数を静かに壊す

### 8.2 K&R 形式は仮引数の「名前と型を分けて読む」だけ

`int add(a, b) int a; int b; { ... }` は，`(` の直後が「typedef 名で
ない識別子」なら K&R の並びとみなし，名前だけを int として登録する。
`)` と `{` の間の宣言が型を上書きし，宣言の無い名前は int のまま
(C の既定)。呼出し規約は変わらないので，コード生成には触れていない。

### 8.3 結果

台帳は「通る 22 件 / 未対応 4 件 / 通るが誤り 0 件」になった。残るのは
ビットフィールド・浮動小数点・空の引数リストへの実引数・`long long`
(拒否で正しい) である。

## 9. 第 6 部: ビットフィールド (cc14e)

### 9.1 命令種別を足さずに済ませる

ビットフィールドの読み書きは，**IR の既存演算だけで組んだ**。

- 配置: 語 (32 bit) の中へ下位ビットから詰める。連続するビット
  フィールドは同じ語に収まる限り続け，収まらない幅は次の語へ送る。
  普通のメンバを挟むと次の語からやり直す
- 取り出し (`rv`): 語を読み，右へ寄せ (`srl`)，幅でマスクする (`and`)。
  マスクが上位を落とすので，右シフトの種類 (算術/論理) に依存しない
- 代入 (`assign`): 読み・修正・書き。語を読み，そのフィールドの
  ビットを消し，値をはめて書き戻す (`and` / `sll` / `or`)

命令種別を増やさないので，IR の 4 箇所ルール
([dev-notes.md](dev-notes.md) 4 章) を踏まずに済む。式の状態には
「左辺値がビットフィールドである」印 (`ebfw` / `ebfo`) を足し，
`emember` が立てて `rv` と `assign` が消費する。左辺値を作る他の経路
(変数・添字・間接参照) は印を消す。

### 9.2 未対応の操作は拒む

複合代入 (`v.a |= 1`) と `++` / `--` は読み・修正・書きの経路を
まだ持たないので，**黙って語ごと動かして隣のフィールドを壊す前に拒む**
(終了コード 5)。`&` (アドレス取得) は C でも不正なので拒む。
値は符号なしとして取り出す (plain `int` の符号は C89 でも処理系定義)。
無名ビットフィールド (`unsigned : 3;` の詰め物) は未対応である。

### 9.3 結果

台帳は「通る 23 件 / 未対応 3 件 / 通るが誤り 0 件」になった。残るのは
浮動小数点・空の引数リストへの実引数・`long long` (拒否で正しい) だけで，
**言語側の対応はここで一区切りである**。いずれも外部ソースの選定 (2.3)
で回避できる見込みが高い。

## 10. 第 7 部: libc 第 14 世代

外部の C が前提にする libc の不足を埋めた。
[../stage013/libc](../stage013/libc) を全文複製した第 14 世代
([../stage014/libc](../stage014/libc)) である。詳細は
[../stage014/libc.md](../stage014/libc.md)。

- **assert.h** (新規)。不成立なら式の文字列を stderr へ出して exit(1)。
  `NDEBUG` で無効化できる。abort (シグナル) は無いので exit で表す
- **printf の拡張**: `l` 修飾 (`long` は int と同じ幅なので読み捨てる)，
  `-` (左詰め)，`%s` の幅
- **sprintf / vsprintf / vfprintf**。書式化の書込み先を FILE か緩衝かで
  切り替える 1 点 (`emitc`) を入れただけで，書式の実装は 1 本のまま
- libc は**最前線の cc でコンパイルする** (l13 までは cc10l)。
  外部ソースと同じ経路に載せるためである (第 8 部で cc14f へ更新した。
  cc14f は既存コードに対し cc14e と同一のコードを出すので，オブジェクトは
  変わらない)

## 11. 第 8 部 (前半): 取得の仕組み

外部ソースは repo に取り込まず，取得して SHA-256 で固定する (2.1)。

- [../tools/fetch.sh](../tools/fetch.sh): manifest (名前・URL・SHA-256)
  駆動の取得スクリプト。取得 -> 照合 -> `docs/external/<名前>/` へ展開。
  照合に失敗したら取得物を消して失敗する
- 記録は [SOURCES.md](SOURCES.md)。bzip2 1.0.8 と zlib 1.3.1 を登録し，
  最初の取得 (2026-08-10) で照合が成立して確定した

最初の 1 本は **bzip2 1.0.8 の libbz2** (2.3 の条件で選定):

| 条件 | bzip2 の実際 |
|---|---|
| 規模 | libbz2 相当 7 ファイル・約 4800 行 (単一ファイルではないが 1 ファイルずつ潰せる) |
| C89 | ANSI C。処理系拡張なし |
| 浮動小数点 | `BZ_NO_STDIO` を定義すると verbosity 出力のマクロが空になり，**前処理後に浮動小数点が消える** |

| 正解が自明 | 圧縮 -> 伸長の往復一致。加えて出力は正規の bzip2 ストリームなのでホストの bzip2 でも検証できる |

## 12. 第 8 部 (後半): 落ちた箇所と cc14f / ld14

libbz2 を実際に当てて，落ちた箇所を 1 つずつ特定した。すべて本処理系の
gap であり，bzip2 側の問題は 1 つも無かった。

| # | 落ちた箇所 | 症状 | 直し |
|---|---|---|---|
| 1 | 16 進リテラルの大文字 (`0xF`) | cc 終了 1 | 字句 (ishex / hexv) を大文字対応に |
| 2 | 単項 `~` | cc 終了 1 | `x ^ -1` へ落とす (命令種別を足さない) |
| 3 | 宣言子の定数式 (`[(2+(900000/50))]`) | cc 終了 1 | 畳込み評価器 (ccond) を宣言子に足す |
| 4 | 2040 バイト超のローカル配列 | cc 終了 6 | 大フレームは liw+add の 3 語でアドレス生成 (上限 65528) |
| 5 | IR 命令数 > 8191 (手動アンロールの巨大関数) | cc 終了 6 | 表を 16384 へ (ラベル・後埋めも倍に) |
| 6 | 15 バイト超のシンボル名 (`BZ2_bzBuffToBuffCompress`) | ld 終了 2 | ld14: 大域シンボル表を 32 バイト幅へ |

2 と 6 は台帳の発想 (4 章) だけでは出てこない類のものである。
2 はブートストラップ鎖自身が `~` を使わず `^ -1` で書いてきたため，
6 は鎖のソースが短い名前しか使わないため，**外部ソースを当てるまで
残っていた**。「他人のソースを入力にする」ことが検査になっている。

成果は cc14f ([../stage014/cc14f.md](../stage014/cc14f.md)) と
ld14 ([../stage014/ld14.md](../stage014/ld14.md))。cc14f は
2048 バイト未満のフレームの関数に対して cc14e と同一のコードを出す
(回帰テストで sh / ed / mk が cc10l と同じ .o になることを確認)。

### 実走 (検査ドライバ bzt)

[../tests/stage014/user/bzt.c](../tests/stage014/user/bzt.c) が
libbz2 + libc14 とリンクされ (ld14 の 'E')，kernel13 の上で走る:

1. 既知の 4096 バイト (繰返しテキスト + 擬似乱数) を
   `BZ2_bzBuffToBuffCompress` で圧縮 (blockSize100k=1) -> 2555 バイト
2. `BZ2_bzBuffToBuffDecompress` で伸長し，往復一致を確認
3. 圧縮結果を sfs へ書き出し，**ホストの bzip2 -d でも伸長して原文と
   一致**することを確認 (形式の相互運用。ホストに bzip2 が無ければ飛ばす)

検査は素材があるときだけ走る (2.2)。tests/stage014/test.sh 参照。

## 13. 第 9 部: カーネルの第 14 世代 (kernel14)

2026-08 の監査が挙げた 2 つの穴を塞ぐ。**機能は足していない**——
どちらも「踏むと原因の判りにくい壊れ方をする」ものである。

### 13.1 sfs の上書きが隣接ファイルを壊した

`sfswrite` (kernel13) は表項目に割付け容量を持たず，`off + pos` へ
無条件に書き，伸長時はカーソルを `off + pos + n` へ無条件に置いていた。
`O_TRUNC` (`openat` と spawn の出力切詰め) は `dataoff` をそのまま
再利用するので，次の 2 つが起きた。

1. 既存ファイルを元の割付けより長く書き直すと，**直後に割り付けられた
   ファイルのデータを上書きする**
2. 末尾でない項目を伸ばすと**カーソルが巻き戻り**，以後の新規作成が
   既存データに重なる

現行のテストは毎回イメージをゼロから作り直し，出力が常に新規ファイルに
なるため露見しなかった。しかし「同一セッションで mk を 2 回走らせる」
「シェルの `> 既存ファイル`」という通常の運用で起き，**ゲスト内で
作り直した成果物が記録 SHA-256 と食い違う**形で現れる。

**直し方**は追記割付けの設計を保ったまま，不変条件を 1 つ立てる:

```
各項目は [off, off + rup4(len)) を占め，カーソルは常に使用済みの末尾を指す
  ⇒  off + rup4(len) == カーソル   ⇔   その項目が最後の割付け
```

`sfsgrow` はこれを見て分岐する。最後の割付けならその場で伸ばし，
そうでなければ**中身を末尾へ引っ越してから**伸ばす。カーソルは決して
巻き戻さない。`O_TRUNC` は `len = 0` にするだけでよい——次の書込みが
`rup4(0) = 0` に収まらないので自動的に末尾へ移る。容量が尽きたときは
`-ENOSPC` を返し，`sys_write` は fd の位置を進めない。

引っ越しは旧領域を捨てるので，同じファイルを何度も書き直すとイメージが
やせる。回収 (`sfs.sh unpack`) は表を見るので中身は正しく，ゲスト内での
1 セッションぶんには十分である。詰め直しが要るなら，イメージを
ホストで pack し直すのがいちばん安い。

### 13.2 loadelf に境界検査がなかった

`loadelf` はマジック 2 バイトだけを見て `p_vaddr` / `p_filesz` /
`p_memsz` をそのまま信じて複写していた。壊れた ELF を spawn すると
ユーザ領域 (0x8600_0000〜) の外——カーネル本体や spawn の退避領域——を
書き潰せた。セキュリティは本プロジェクトの目標外だが，「壊れた ELF で
黙ってカーネルが壊れる」のは再現性のデバッグを著しく難しくする。

`elfok` を分け，載せる前に確かめる:

- `ELF` の 4 バイト，ファイル長が ELF ヘッダぶんあること
- プログラムヘッダと中身が**ファイルの中に収まる**こと
- `fsz <= msz`
- 載せ先が `[UBASE, UBRKMAX]` に収まること

引き算はすべて「引かれる側が大きいこと」を確かめてから行う。unsigned
なので `pva + msz > UBRKMAX` の形は桁あふれで通ってしまう。

併せて spawn の**順序**を直した。退避領域の資源検査 (ENOMEM) が
つなぎ替えの解決より後にあり，起動に失敗しても出力ファイルだけが
切り詰められていた。検査を前へ移し，`elfok` も親を壊す前に済ませる。
