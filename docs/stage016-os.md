# Stage 16: 実行環境の拡張

本書は Stage 16 の設計文書である。1〜4 章は**この段を挟むと決めた
経緯** (GCC へ直行しない理由) で，5 章以降が設計である。

[roadmap.md](roadmap.md) 2.1 は分岐点を 3 案として提示し，「その時の
実装体力を見て決める」として保留していた。Stage 15 が終わった今が
その時である。

## 1. 前提が変わった: tcc が鎖の成果物になった

roadmap 2.1 を書いた時点で我々が持っていた処理系は cc だけだった
(C89。GNU 拡張は持たない)。**Stage 15 で tcc が加わった**
([stage015-tcc.md](stage015-tcc.md) 13 章)。

- T2 == T3 == tccH。tcc が我々の OS の上で自分自身を作り，その出力が
  動かない
- T2 は**参照実装が作る tcc とバイト一致**する
- tcc は鎖の成果物である。**Stage 16 の入力に使ってよい**
  ([artifacts.md](artifacts.md) の凍結規則の対象であり，外部バイナリの
  持ち込みには当たらない)

tcc は GNU C 拡張を相当量サポートする (statement expression・
`__attribute__`・`typeof`・computed goto・inline asm など)。**3 案の
どれを採るにせよ，「コンパイラ側」の負担は roadmap 執筆時より大幅に
軽い。**

## 2. しかし律速はコンパイラではなく OS である

GCC 4.7 系のビルドが要求するものと，我々の OS が今持っているものを
並べる。**左は実測値**である。

| | 我々の OS (実測) | GCC 4.7 のビルドが要るもの |
|---|---|---|
| ユーザ空間 | **14 MB** (`UBASE` 0x8600_0000 〜 `UBRKMAX` 0x86e0_0000) | cc1 が自分自身を翻訳するのに数百 MB |
| ファイル系 | sfs。既定 4 MiB (第 6 部で 8 MiB) | 展開後で数百 MB |
| 名前空間 | **平ら** (ディレクトリという実体を持たない) | 深いディレクトリ木を前提にする |
| 道具 | sh / ed / mk / bundle / ldin / eot | make・sh・awk・sed・tar，そして `configure` |
| シェル | 1 行 9 語・引数 8 個 | `configure` は数万行のシェルスクリプト |
| 依存ライブラリ | 無し | GMP・MPFR・MPC の 3 つが要る |

**桁が違う。** Stage 14 で bzip2 / zlib，Stage 15 で tcc を通せたのは，
どれも「単一ディレクトリ・数十ファイル・数 MB」に収まったからである。
GCC はそこから 2 桁上にある。

なお GCC 4.7.4 の実物はこの環境から取得できなかった
(`ftp.gnu.org` / `gcc.gnu.org` ともネットワークポリシーで拒否)。
上表の右列は構造的に確かな要求 (GMP/MPFR/MPC が要る，`configure` が
シェルスクリプトである，等) に留め，**数値の実測は取得できる環境で
行う**。

## 3. 3 案の再評価

roadmap 2.1 の 3 案を，1 と 2 を踏まえて評価し直す。

| 案 | 内容 | コンパイラ側 | OS 側 | RISC-V |
|---|---|---|---|---|
| A | C++ サブセット処理系を作り GCC 7 をビルド | **特大** (C++ を自作) | 特大 | 保てる |

| C | GCC 4.7 に RISC-V backend を自作して載せる | 中 (tcc がある) | 特大 | 保てる |

**どの案でも OS 側の負担は変わらない。** つまり 2 の差は分岐点の前に

コンパイラ側だけを見れば，Stage 15 の成果により **B と C の差は
「backend を書く対象が x86-64 か RISC-V か」だけ**に縮んでいる。
そして我々は第 5 部で **tcc に RV32 backend を書いた実績**がある
([stage015-riscv32.md](stage015-riscv32.md))。GCC の machine

## 4. 提案: 分岐の前に OS を育てる段を挟む

2 の表から出る結論は「**GCC の前に，大きなビルドが成立する OS が要る**」
である。具体的に足りないものは次のとおりで，どれも A/B/C と独立に要る。

1. **記憶域**: ユーザ空間 14 MB → 数百 MB。ページングか，少なくとも
   もっと広い平坦空間
2. **ファイル系**: 平らな sfs → ディレクトリを持つもの。数百 MB
3. **道具**: awk 相当・sed 相当・本物の make。`configure` を通すなら
   POSIX シェルに近いものも
4. **依存ライブラリ**: GMP・MPFR・MPC (これ自体が Stage 14 規模の
   外部ソース 3 本である)

Stage 14 (bzip2 / zlib) と Stage 15 (tcc) が「外部ソースを 1 本ずつ
当てて処理系を鍛える」やり方で成功しているので，同じやり方を OS 側に
当てるのが素直である。**GCC より小さく，かつ上の 1〜4 を要求する
外部ソース**を次の標的に選ぶ。

## 5. 決めたこと

**OS を育てる段を Stage 16 として挟む。** 案 A/B/C の判断はその後へ
持ち越す (4 のとおり，どの案でも等しく要る作業だから，先延ばしの損が
無い)。GCC は Stage 17 になる。

手当ての順は**ファイル系 (ディレクトリ) を先**にする。理由は 3 つ。

1. 外部ソースは例外なく深いディレクトリ木を前提にする。平らなままでは
   **展開すらできない**。Stage 14 / 15 が通ったのは，どれも単一
   ディレクトリに収まったからである
2. 記憶域の不足は「容量が足りない」という分かりやすい症状で出る。
   第 6 部で何度も当たって都度広げてきた実績があり，後追いできる
3. ファイル系は自作の範囲で完結する。外部ソースの取得を要さない

## 6. 第 1 部の設計: ディレクトリを持つファイル系 (sfs2)

### 6.1 いまの sfs とその限界

[stage012-os.md](stage012-os.md) 4.3 の sfs は次の形である。

- 先頭に表 (エントリの配列)，その後ろにデータ
- エントリは「名前・オフセット・長さ」だけ
- **名前は平ら**。ホスト側の `find . -type f` が出す `a/b/c.h` という
  文字列を，そのまま 1 個の名前として持つ (ディレクトリという実体は
  無い)

平らでも「`a/b/c.h` を開く」ことはできる。実際 Stage 15 第 6 部では
`sys/time.h` をこの形で置いた。**足りないのは次の 3 つ**である。

| 足りないもの | なぜ要るか |
|---|---|
| 相対パスの解決 | `#include "../foo.h"` や，作業ディレクトリを持つビルド |
| 一覧 (readdir) | `configure` や make が「そこに何があるか」を訊く |
| 作成・削除 | ビルドは中間ディレクトリを掘る |

### 6.2 方針

**平らな表は残し，その上に木を載せる。** エントリに「親」と「種別」を
足すだけにする。sfs の「表 + データ」という単純さは，カーネルが
数百行で読めることの理由なので崩さない。

- エントリに **種別** (ファイル / ディレクトリ) と **親のエントリ番号**
  を足す
- 名前は**そのディレクトリ内での名前**にする (`c.h`)。全体の経路は
  親を辿って組み立てる
- ルートはエントリ 0 とし，親を自分自身にする

これで readdir は「親が n のエントリを並べる」，パス解決は「/ で切って
1 段ずつ引く」で済む。

### 6.3 バイト配置 (sfs2)

sfs1 の表項目はちょうど 64 バイトで隙間が無い。**名前を 52 → 48 に
縮めて，空いた 4 バイトを親に充てる。** 名前はそのディレクトリ内での
名前になるので，47 バイトあれば実用上足りる (sfs1 は経路まるごとを
名前にしていたので 51 バイトでも足りないことがあった)。項目が 64 バイト
のままなので，カーネル側の算術は変わらない。

すべてリトルエンディアン。

```
スーパーブロック (32 バイト):
  0   'sfs2' (4 バイト)
  4   u32 total    イメージ全体の大きさ
  8   u32 tbloff   表の位置 (= 32)
  12  u32 tblcnt   表の件数 (容量)
  16  u32 cursor   次にデータを置く位置 (追記割付け。4 バイト境界)
  20  予約 (0)

表項目 (64 バイト / 件。未使用の項目は全 0):
  0   name[48]     そのディレクトリ内での名前，NUL 終端 (最長 47 バイト)
  48  u32 parent   親のエントリ番号
  52  u32 dataoff
  56  u32 len
  60  u32 flags    bit0 = 有効, bit1 = ディレクトリ
```

- **エントリ 0 は必ずルート**である。名前は空，親は自分自身 (0)，
  flags = 3 (有効 + ディレクトリ)
- ディレクトリのエントリは `dataoff` / `len` を使わない (0)
- 経路の解決は「`/` で切り，1 段ずつ『親が n で名前が一致する項目』を
  引く」。一覧 (readdir) は「親が n の項目を並べる」

### 6.4 進め方

**ホスト側から先に作る。** `tools/sfs2.sh` (pack / unpack / list) と
その往復検査は QEMU を要さないので速く回せる。形式が固まってから
カーネルへ持ち込む。

sfs1 (`tools/sfs.sh`) は**そのまま残す**。Stage 12〜15 の検査がすべて
それに依っており，凍結済みの成果物の再現に要るからである。

### 6.5 カーネル側 (kernel17)

`stage016/kernel17.c` は kernel16 の写しに sfs2 の経路解決を入れたもの
である。触ったのは 3 関数だけで，残りは kernel16 のままである。

| 関数 | kernel16 | kernel17 |
|---|---|---|
| `nameeq` → `nameeqn` | 項目の名前と文字列全体を比べる | 項目の名前が `s[0, n)` と一致し**そこで終わる**か |
| (新設) `childof` | — | 親 `par` の中から名前 `s[0, n)` を引く |
| (新設) `walk` | — | 経路を `/` で切って 1 段ずつ辿る |
| `sfsfind` | 表を線形に走査して名前で引く | `walk(path, 0, ...)` |
| `sfsnew` → `sfsmk` | 空き項目に名前を書く | 親を `walk(path, 1, ...)` で出してから書く。ディレクトリも作れる |

`nameeqn` が「切り出さずに比べる」形なのは，**カーネルに経路の一時
領域を持たせないため**である。`a/b/c.h` の `b` を比べるのに `b` を
どこかへ複製する必要がない。

`walk` の `stop` 引数が 2 つの用途を 1 つの関数にまとめている。

- `stop = 0` (引く): 最後の段まで辿り，その項目番号を返す
- `stop = 1` (作る): 最後の段の**手前**まで辿り，その親を返す。最後の
  段の名前と長さを `*lastp` / `*lastn` で返す

**ファイルを途中に挟む経路は失敗させる** (`/top.txt/x`)。`walk` は
1 段進むごとに「まだ後ろが残っているのに今の項目がディレクトリでない」
かを見る。これが無いと `/top.txt/x` が `/top.txt` として開けてしまい，
「無いはずのものが開ける」という一番たちの悪い壊れ方をする。

連続する `/` と先頭の `/` は読み飛ばす (`//src///one.c` は
`/src/one.c` と同じ)。`.` と `..` はまだ扱わない —— 作業ディレクトリを
持つのは第 2 部の課題である。

検査は `tests/stage016/user/pathprobe.c` を OS の上で走らせて，10 件の
経路の引き方を期待と突き合わせる。中身をその経路の名札にしてあるので，
取り違えれば**どれとどれを取り違えたか**が出力に出る。

### 6.6 実測

`kernel17.bin` は 26,020 バイト (kernel16 との差は経路解決のぶんだけ)。
`pathprobe` を kernel17 の上で走らせた結果は下のとおりで，10 件すべてが
期待と一致した。

| 名札 | 経路 | 期待 |
|---|---|---|
| `abs` | `/top.txt` | `TOP` |
| `rel` | `top.txt` | `TOP` |
| `deep` | `/src/a/b/three.c` | `THREE` |
| `dup-inc` | `/inc/one.c` | `INC-ONE` |
| `dup-src` | `/src/one.c` | `SRC-ONE` |
| `slashes` | `//src///one.c` | `SRC-ONE` |
| `miss-top` | `/nosuch.txt` | 開けない |
| `miss-deep` | `/src/nosuch.c` | 開けない |
| `thru-file` | `/top.txt/x` | 開けない |
| `miss-dir` | `/nodir/one.c` | 開けない |

`dup-inc` と `dup-src` が別物として引けたことが第 1 部の目的そのもので
ある。sfs1 では**この 2 つは同じ名前を持てなかった**ので，木の中に
同名のファイルを置くこと自体ができなかった。

第 1 部の検査は sfs2 のホスト側 9 件と合わせて 11 件で，すべて通っている。

## 7. 第 2 部の設計: ディレクトリを操作する

第 1 部で経路は引けるようになったが，**木を見る手段も，木を作る手段も，
木の中で位置を持つ手段も無い**。`configure` と make はこの 3 つを前提に
している。第 2 部でそれを入れる。

### 7.1 何が足りないか

| 足りないもの | 誰が要求するか |
|---|---|
| 一覧 (`opendir` / `readdir`) | `configure` が「そこに何があるか」を訊く。make のワイルドカード |
| 作成 (`mkdir`) | ビルドが中間ディレクトリを掘る |
| 作業ディレクトリ (`chdir` / `getcwd`) | `cd src && make` の形。相対経路のすべて |
| `.` と `..` | 相対経路の中に必ず現れる (`../include`) |

### 7.2 syscall

番号は引き続き RV32 Linux 互換にする。ここも実 Linux でそのまま通じる
形にしておくと，L2 (Linux をビルドする) への経路が保てる。

| 番号 | 名前 | 用途 |
|---|---|---|
| 17 | `getcwd` | 作業ディレクトリの経路を書き出す |
| 34 | `mkdirat` | ディレクトリを作る (RV32 に `mkdir` は無い) |
| 49 | `chdir` | 作業ディレクトリを移す |
| 61 | `getdents64` | ディレクトリの項目を読み出す |

`getdents64` が返す 1 件の形も Linux に合わせる。可変長で，`d_reclen`
だけ進めば次の件に着く。

```
  0   u64 d_ino      項目の索引 (sfs2 のエントリ番号)
  8   s64 d_off      次の件の読み出し位置
  16  u16 d_reclen   この件の全長 (8 バイト境界へ切上げ)
  18  u8  d_type     4 = ディレクトリ, 8 = ふつうのファイル
  19  char d_name[]  NUL 終端の名前
```

64 bit の欄は 32 bit の語 2 本として書く。カーネルは 32 bit なので，
上位は常に 0 である。

### 7.3 作業ディレクトリ

カーネルは `cwd` を 1 つだけ持つ (エントリ番号。初期値 0 = ルート)。
プロセスは一度に 1 つしか走らないので，これで足りる。

経路の解決は第 1 部の `walk` をそのまま使い，**出発点だけを変える**。

- `/` で始まる → ルート (エントリ 0) から
- そうでない → `cwd` から

段の名前が `.` なら動かず，`..` なら親へ上がる。**ルートの親はルート
自身**なので `/..` は `/` になる (Linux と同じ)。`..` はディレクトリ
以外には現れないので，`walk` の「ファイルを途中に挟む経路は失敗」の
検査はそのまま効く。

`getcwd` は逆向きに辿る。`cwd` から親を辿ってエントリ番号を積み，
逆順に名前を並べる。sfs2 は親を持っているのでこれができる
(sfs1 にはそもそも親が無かった)。

### 7.4 libc が邪魔をしていた箇所

libc15 の `open` は**先頭の `/` の並びを全部剥がしていた**。

```c
  /* ルート直下しか無いので，先頭の '/' の並びは剥がして裸の名前にする */
  while (*path == '/')
    path = path + 1;
```

平らな名前空間では正しかった。しかし**作業ディレクトリを持った瞬間に
これは重大な誤りになる** —— `/inc/one.c` が `inc/one.c` になり，
ルートからではなく `cwd` から引かれてしまう。「絶対経路を渡したのに
今いる場所によって別のファイルが開く」という，第 1 部の
`thru-file` と同じ種類の (黙って間違う) 壊れ方である。

剥がす処理は**要らなくなっている**。この処理が入った理由は tcc が
`-I/` から `//tccdefs.h` の形の経路を作ることだったが，第 1 部の
`walk` は先頭と連続の `/` を読み飛ばすので，そのまま渡して正しく
引ける (`slashes` の検査がそれを見ている)。libc16 では削る。

### 7.5 世代

[artifacts.md](artifacts.md) 4 章の手順どおり，直前の世代を全文複製して
から編集する。

| 新しい世代 | 複製元 | 変えるところ |
|---|---|---|
| `stage016/kernel18.c` | `stage016/kernel17.c` | `cwd`・`.` / `..`・4 つの syscall・ディレクトリを `open` できるようにする |
| `stage016/libc/` | `stage015/libc/` | `dirent.h`・`sys/stat.h`・`chdir` / `getcwd`・7.4 の削除 |

kernel17 は第 1 部の成果物として残す。第 1 部の検査 (`pathprobe`) は
kernel17 の上で走り続けるので，**第 2 部の変更が第 1 部を壊していない
ことが常に見える**。

### 7.6 実測

`dirprobe` を kernel18 の上で走らせた結果は 31 件すべて期待と一致した。
第 1 部と合わせて Stage 16 の検査は 13 件 (sfs2 のホスト側 9・kernel17
の経路解決 2・kernel18 のディレクトリ操作 2) で，すべて通っている。

要点は次の 3 つである。

| 名札 | 見ていること |
|---|---|
| `abs-from-src` | cwd が `/src` のときに `/inc/one.c` が `INC-ONE` を返す。**libc が絶対経路を相対に変えていない**こと (7.4) |
| `dotdot2` | `/src/a` から `../../inc/one.c` が引ける。`..` が 2 段続けて上がれること |
| `read-dir` | ディレクトリの fd への `read` が `-1` になる。fdpos の意味が二重になっているのを黙って通さないこと |

### 7.7 見つかった「黙って間違う」実装 2 件

第 2 部の作業の中身は，syscall を足すことよりも**平らな名前空間の
時代に正しかった実装が，木を持った途端に嘘になる**箇所を見つけて
潰すことだった。2 件あり，どちらも同じ形をしている。

| 場所 | 平らなときは | 木を持つと |
|---|---|---|
| `posix/sys.c` の `open` が先頭の `/` を剥がす | ルート直下しか無いので正しい | 絶対経路が `cwd` から引かれる |
| `src/misc15.c` の `getcwd` が常に `"/"` を返す | 常にルートにいるので正しい | どこにいても `/` と答える |

`getcwd` のほうは**リンクの多重定義 (ld の終了コード 3) で偶然見つかった**。
本物を `posix/sys.c` に置いたら，純粋部に同じ名前の偽物が残っていた
のである。検査で見つけたのではない点は記録しておく価値がある ——
**「値を返すが嘘である」実装は，呼び手が正しく動いてしまうので
検査を書かない限り永久に見つからない。**

### 7.8 残した穴

`src/misc15.c` の `unlink` / `remove` は「何もせず 0 を返す」ままである。
これも上の 2 件と同じ *bad* の形だが，直すには sfs2 に削除が要る。
第 3 部の課題とする。

削除を入れるときは追記割付け (6.3 のカーソル) との折り合いが要る。
項目を消しても穴が空くだけで詰まらないので，「消した項目を再利用する」
か「詰め直す」かを決めることになる。

## 8. 第 3 部の設計: 記憶域を広げる

### 8.1 いまの壁は 14 MB である

ユーザプログラムが `malloc` で取れる上限は

```
UBRKMAX - UBASE = 0x86e0_0000 - 0x8600_0000 = 14 MB
```

から像の大きさを引いたぶんである。tcc の自己ホスト (Stage 15) はここに
収まったが，GCC のビルドは数百 MB を要る。**これは工夫で回避できる
種類の不足ではない。**

### 8.2 何が動かせて，何が動かせないか

配置定数はカーネルの `#define` だけにあるわけではない。**リンカの
前置部に機械語として焼き込まれているものがある** (`stage015/ld16.sc`)。

| 値 | どこに焼かれているか | 動かせるか |
|---|---|---|
| トラップフレーム `0x8370_0000` | `prologuek` の `lui t6, 0x83700` | **不可** (ld の世代が要る) |
| カーネルスタック `0x8380_0000` / `0x83f0_0000` | `prologuek` の `lui sp` / `lui s1` | **不可** (同上) |
| ユーザ像のロード先 `0x8600_0000` | `ld` の `base`。`'E'` 形式の既定 | **不可** (同上) |
| `UBRKMAX` / `USP` | カーネルの `#define` のみ | 可 |
| `SAVEA` / `SAVETOP` | カーネルの `#define` のみ | 可 |
| QEMU の RAM 量 | `tools/run-qemu.sh` の `-m` | 可 |

したがって **`0x8600_0000` より下は 1 バイトも動かさない**方針を採る。
そうすればリンカの世代を刻まずに済み，凍結済みの `.sc` と，そこから
出る全成果物の SHA-256 がそのまま生きる。**広げるのは上だけである。**

### 8.3 新しい配置 (RAM を 512 MB にする)

```
  0x8000_0000  カーネル                       ← 変えない
  0x8370_0000  トラップフレーム               ← 変えない (ld16 が持つ)
  0x8380_0000  カーネルスタック               ← 変えない (ld16 が持つ)
  0x8400_0000  sfs2 イメージ (32 MB)          ← 変えない
  0x8600_0000  ユーザ像 (UBASE)               ← 変えない (ld16 の 'E' base)
       …       .text/.data/.bss + データスタック 256 KiB
       …       ヒープ (brk がここから上へ伸びる)
  0x9600_0000  UBRKMAX                        ← 0x86e0_0000 から移す
       …       フレームスタック (16 MB)
  0x9700_0000  USP                            ← 0x8700_0000 から移す
  0x9700_0000  spawn の退避領域 (144 MB)      ← 0x8100_0000 から移す
  0xa000_0000  RAM の終わり (-m 512M)
```

ヒープの上限は **0x9600_0000 - 0x8600_0000 = 256 MB** になる (像と
データスタックのぶんを引く)。14 MB から 18 倍である。

`0x8100_0000`〜`0x8370_0000` は退避領域を移した跡が空く。**当面は
使わない**。sfs2 を 32 MB より大きくしたくなったときの行き先にする。

### 8.4 退避領域と釣り合い

`spawn` は親の像とフレームスタックを丸ごと退避領域へ写す
([stage013-tools.md](stage013-tools.md) 3.2)。したがって

```
退避領域の大きさ ≧ 親が使っている記憶域 × 入れ子の深さ
```

でなければ `spawn` が通らない。上の配置では**ヒープが 256 MB 取れる
のに退避領域は 144 MB** なので，記憶域を大きく使った親からの `spawn`
は失敗する。

これは意図した釣り合いである。理由は 2 つ。

- カーネルは既に `savecur + 296 + imgsz + stksz > SAVETOP` を検査して
  `ENOMEM` を返す。**黙って壊れるのではなく，はっきり失敗する** ——
  台帳でいう gap であって bad ではない
- 記憶域を最も使うのはコンパイラ本体であり，それは `make` から
  `spawn` される**子**の側である。子は入れ子の末端なので，退避される
  ことがない

親 (シェルや make) が数百 MB を使い始めたら，そのときに配置を見直す。

### 8.5 世代

カーネルだけが変わる。[artifacts.md](artifacts.md) 4 章のとおり
`stage016/kernel18.c` を全文複製して `stage016/kernel19.c` を作り，
`#define` の 4 つを変える。**リンカも libc も変えない。**

`tools/run-qemu.sh` の `-m` と，検査が作る RAM ファイルの大きさも
128 MB から 512 MB へ揃える。RAM ファイルは疎ファイルなので，実際に
消費するのは QEMU が触れたページのぶんだけである。

### 8.6 実測

同じ `memprobe` を 2 つのカーネルで走らせて対にした。**片方だけを
見ても「広がった」ことは言えない**ので，検査は必ず両方を出す。

| カーネル | RAM | 取れた量 |
|---|---|---|
| kernel18 (第 2 部) | 128 MB | **13 MiB** |
| kernel19 (第 3 部) | 512 MB | **255 MiB** |

13 MiB は `UBRKMAX - UBASE = 14 MB` から像とデータスタック (256 KiB)
を引いた値で，計算と合う。255 MiB も同様である。

`memprobe` は `sbrk` の返り値を信じない。**1 MiB 取るごとにその先頭と
末尾へ印を書き，最後にもう一度なめて読み戻す。** カーネルの `UBRKMAX`
だけを上げて QEMU の RAM が足りていなければ「確保は成功するのに書いた
瞬間に落ちる」ことになり，それは台帳でいう bad だからである。
`verify ok` はその 2 度目のなめが通ったことを表す。

### 8.7 既定の RAM 量は変えていない

`tools/run-qemu.sh` に `STONE_QEMU_RAM` を足したが，**既定は 128M の
ままにした**。kernel15〜18 は 128 MB を前提にした配置を持っており，
それらの検査は当時と同じ大きさで再現できるほうがよい。広い記憶域を
要るのは kernel19 以降だけなので，**要る側が明示的に指定する**形にした。


## 9. 第 4 部の設計: 道具立て (configure が通る Unix)

### 9.1 完了条件を実物で決める

「道具立て」は際限なく広げられるので，**具体的なスクリプト 1 本が
そのまま走ること**を完了条件にする。対象は tcc の `configure`
(768 行) にした。理由は 3 つ。

- **既に手元にある。** 作業環境の網は制限されており，新しい tarball を
  取ってこられない (`ftp.gnu.org` は 403)。鎖が既に読んでいる資産の中
  から選ぶしかない
- **他人が書いた本物の POSIX シェルスクリプトである。** 我々が
  「通るように」書いたものではない
- **答え合わせができる。** ホストの `sh` で走らせた結果 (`config.h` /
  `config.mak`) と突き合わせれば，通ったかどうかが機械的に決まる

### 9.2 何が要るか (数えた結果)

`configure` が使っている機能を数えた。

| 機能 | 回数 | 機能 | 回数 |
|---|---|---|---|
| パイプ `\|` | 74 | `case` | 19 |
| `test` / `[` | 72 | `for` | 11 |
| `if` | 51 | `tr` | 9 |
| `echo` | 31 | `grep` / `cat` | 4 / 4 |
| `$(...)` / `` ` `` | 22 / 8 | `eval` | 3 |
| | | `rm` / `sed` / `mkdir` / `while` | 2 / 1 / 1 / 1 |

**`awk` は 1 度も出てこない。** text 処理系のうち最も重いものが要件から
外れる。`sed` も 1 箇所だけである。

いまの `sh` (`stage013/sh.c`，73 行) が持っているのは「語に分割して
`spawn`」と `<` `>` だけなので，上の表はほぼ全部が不足である。

### 9.3 パイプをどう作るか (プロセスが 1 つしかない)

カーネルは**プロセスを一度に 1 つしか走らせない**。`spawn` は子の
終わりを待つ逐次実行である ([stage013-tools.md](stage013-tools.md) 3.2)。
本物のパイプは 2 つのプロセスが同時に走ることを要求するので，このまま
では作れない。

選べるのは 2 つ。

| 案 | 内容 | 得失 |
|---|---|---|
| P1 | カーネルに並行実行を入れる | 本物。スケジューラ・待ち行列・fd の共有が要る。**カーネルの作り直しに近い** |
| P2 | 一時ファイルで中継する | 左を一時ファイルへ流し切ってから右を走らせる。逐次実行のまま作れる |

**P2 を採る。** 違いが出るのは「無限に流れる左」と「早く打ち切る右」
(`yes | head -1`) だけで，`configure` にはどちらも現れない。P1 は
それ自体が Stage 1 つぶんの仕事であり，**`configure` を通すという
目的に対して釣り合わない**。

代償ははっきり書いておく。**P2 のパイプは左を全部走らせてから右を
始めるので，左が終わらなければ右は始まらない。** これは gap であって
bad ではない (黙って違う答えを出すのではなく，単に止まる)。

`$(...)` と `` ` `` も同じ仕掛けで作れる —— 中身を一時ファイルへ流し，
読み戻して末尾の改行を落とす。

### 9.4 一時ファイルには削除が要る (第 2 部で残した穴)

P2 は一時ファイルを大量に作る。したがって **sfs2 に削除を入れる**
必要がある。7.8 で第 3 部送りにした `unlink` / `remove` の穴が，ここで
塞がれることになる。

削除は追記割付け (6.3 のカーソル) と噛み合わせる必要がある。項目を
消しても穴が空くだけで詰まらないからである。決め方は 2 つある。

| 案 | 内容 |
|---|---|
| D1 | 項目を未使用に戻すだけ。データの穴は放置し，カーソルは進む一方 |
| D2 | 消すたびに後ろを詰める |

**D1 を採る。** D2 は全項目の `dataoff` を書き換えることになり，開いて
いる fd が指す位置がずれる。D1 の代償は「作っては消すを繰り返すと
イメージを使い切る」ことだが，これも**はっきり `ENOSPC` で失敗する**
ので bad ではない。`configure` 1 回ぶんの一時ファイルは 32 MB の
イメージに十分収まる。

### 9.5 分け方

1 本の PR には大きすぎるので 3 つに割る。

| 部 | 中身 |
|---|---|
| 第 4 部の 1 | sfs2 の削除 (`unlink`)。カーネルと libc。**一時ファイルの土台** |
| 第 4 部の 2 | シェル (`sh2`)。引用符・変数・`test`・`if`/`while`/`for`/`case`・`&&`/`\|\|`・パイプ・`$(...)`・`eval` |
| 第 4 部の 3 | 中核の道具 (`echo` / `cat` / `rm` / `mkdir` / `tr` / `grep` / `sed`) と，`configure` を実際に走らせた突き合わせ |

順序に意味がある。**削除が無いとパイプが作れず，パイプが無いと
`configure` は 1 行目から進まない。**

### 9.6 数え直し: シェルの要件はもう一段深い

9.2 は「1 行に現れる字面」を数えたものだったので，**構文の深いところを
数え落としていた**。実装に入る前に数え直した結果を残す。

| 要る機能 | 回数 | 9.2 で見えていたか |
|---|---|---|
| **シェル関数の定義** | 11 | 見落とし |
| `${V#*=}` `${V%%=*}` `${V%eabi}` (接頭・接尾の切り落とし) | 8 | 見落とし |
| `${V:-既定}` `${V:=既定}` (既定値) | 3 | 見落とし |
| **here-doc** (`cat << EOF`) | 3 | 見落とし |
| `set --` (位置パラメータの置き換え) | 2 | 見落とし |
| `${V}` (素の展開) | 32 | ○ |
| `$1` `$2` `$3` `$#` `$?` | 46 | ○ |
| `unset` / `local` | 1 / 1 | 見落とし |

関数名は `assign_opt` / `good_split` / `confvars_has` / `confvars_set` /
`show_help` / `default` / `default_conf` / `fcho` / `print_str` /

**とくに重いのは関数とパラメータ展開の演算子**で，どちらも「あれば

字面を数えると「パイプ 74・test 72」のような目立つものは拾えるが，
関数定義や `${V#...}` のような**構文そのもの**は落ちる。要件を数える
ときは字面と構文を別々に数える必要がある。
