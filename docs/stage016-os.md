# Stage 16: 実行環境の拡張

本書は Stage 16 の設計文書である。1〜4 章は**この段を挟むと決めた
経緯** (GCC へ直行しない理由) で，5 章以降が設計である。

[roadmap.md](roadmap.md) 2.1 は分岐点を 3 案として提示し，「その時の
実装体力を見て決める」として保留していた。Stage 15 が終わった今が
その時である。

## 1. 前提が変わった: tcc が鎖の成果物になった

roadmap 2.1 を書いた時点で我々が持っていた処理系は cc だけだった
(C89。GNU 拡張は持たない)。**Stage 15 で tcc が加わった**
([stage015-tcc.md](stage015-tcc.md) 13 章)。

- T2 == T3 == tccH。tcc が我々の OS の上で自分自身を作り，その出力が
  動かない
- T2 は**参照実装が作る tcc とバイト一致**する
- tcc は鎖の成果物である。**Stage 16 の入力に使ってよい**
  ([artifacts.md](artifacts.md) の凍結規則の対象であり，外部バイナリの
  持ち込みには当たらない)

tcc は GNU C 拡張を相当量サポートする (statement expression・
`__attribute__`・`typeof`・computed goto・inline asm など)。**3 案の
どれを採るにせよ，「コンパイラ側」の負担は roadmap 執筆時より大幅に
軽い。**

## 2. しかし律速はコンパイラではなく OS である

GCC 4.7 系のビルドが要求するものと，我々の OS が今持っているものを
並べる。**左は実測値**である。

| | 我々の OS (実測) | GCC 4.7 のビルドが要るもの |
|---|---|---|
| ユーザ空間 | **14 MB** (`UBASE` 0x8600_0000 〜 `UBRKMAX` 0x86e0_0000) | cc1 が自分自身を翻訳するのに数百 MB |
| ファイル系 | sfs。既定 4 MiB (第 6 部で 8 MiB) | 展開後で数百 MB |
| 名前空間 | **平ら** (ディレクトリという実体を持たない) | 深いディレクトリ木を前提にする |
| 道具 | sh / ed / mk / bundle / ldin / eot | make・sh・awk・sed・tar，そして `configure` |
| シェル | 1 行 9 語・引数 8 個 | `configure` は数万行のシェルスクリプト |
| 依存ライブラリ | 無し | GMP・MPFR・MPC の 3 つが要る |

**桁が違う。** Stage 14 で bzip2 / zlib，Stage 15 で tcc を通せたのは，
どれも「単一ディレクトリ・数十ファイル・数 MB」に収まったからである。
GCC はそこから 2 桁上にある。

なお GCC 4.7.4 の実物はこの環境から取得できなかった
(`ftp.gnu.org` / `gcc.gnu.org` ともネットワークポリシーで拒否)。
上表の右列は構造的に確かな要求 (GMP/MPFR/MPC が要る，`configure` が
シェルスクリプトである，等) に留め，**数値の実測は取得できる環境で
行う**。

## 3. 3 案の再評価

roadmap 2.1 の 3 案を，1 と 2 を踏まえて評価し直す。

| 案 | 内容 | コンパイラ側 | OS 側 | RISC-V |
|---|---|---|---|---|
| A | C++ サブセット処理系を作り GCC 7 をビルド | **特大** (C++ を自作) | 特大 | 保てる |
| B | x86-64 backend を足し GCC 4.7 → 新しい GCC と登る | 中 (tcc がある) | 特大 | **主対象でなくなる** |
| C | GCC 4.7 に RISC-V backend を自作して載せる | 中 (tcc がある) | 特大 | 保てる |

**どの案でも OS 側の負担は変わらない。** つまり 2 の差は分岐点の前に
ある共通の作業であり，roadmap 2.1 が「どの案でもクリティカルパスは
共通」と書いたのと同じ構図が，もう一段先で繰り返されている。

コンパイラ側だけを見れば，Stage 15 の成果により **B と C の差は
「backend を書く対象が x86-64 か RISC-V か」だけ**に縮んでいる。
そして我々は第 5 部で **tcc に RV32 backend を書いた実績**がある
([stage015-riscv32.md](stage015-riscv32.md))。GCC の machine
description は tcc の backend より遥かに大きいが，「backend を書く」
という作業自体は未知ではない。

## 4. 提案: 分岐の前に OS を育てる段を挟む

2 の表から出る結論は「**GCC の前に，大きなビルドが成立する OS が要る**」
である。具体的に足りないものは次のとおりで，どれも A/B/C と独立に要る。

1. **記憶域**: ユーザ空間 14 MB → 数百 MB。ページングか，少なくとも
   もっと広い平坦空間
2. **ファイル系**: 平らな sfs → ディレクトリを持つもの。数百 MB
3. **道具**: awk 相当・sed 相当・本物の make。`configure` を通すなら
   POSIX シェルに近いものも
4. **依存ライブラリ**: GMP・MPFR・MPC (これ自体が Stage 14 規模の
   外部ソース 3 本である)

Stage 14 (bzip2 / zlib) と Stage 15 (tcc) が「外部ソースを 1 本ずつ
当てて処理系を鍛える」やり方で成功しているので，同じやり方を OS 側に
当てるのが素直である。**GCC より小さく，かつ上の 1〜4 を要求する
外部ソース**を次の標的に選ぶ。

## 5. 決めたこと

**OS を育てる段を Stage 16 として挟む。** 案 A/B/C の判断はその後へ
持ち越す (4 のとおり，どの案でも等しく要る作業だから，先延ばしの損が
無い)。GCC は Stage 17 になる。

手当ての順は**ファイル系 (ディレクトリ) を先**にする。理由は 3 つ。

1. 外部ソースは例外なく深いディレクトリ木を前提にする。平らなままでは
   **展開すらできない**。Stage 14 / 15 が通ったのは，どれも単一
   ディレクトリに収まったからである
2. 記憶域の不足は「容量が足りない」という分かりやすい症状で出る。
   第 6 部で何度も当たって都度広げてきた実績があり，後追いできる
3. ファイル系は自作の範囲で完結する。外部ソースの取得を要さない

## 6. 第 1 部の設計: ディレクトリを持つファイル系 (sfs2)

### 6.1 いまの sfs とその限界

[stage012-os.md](stage012-os.md) 4.3 の sfs は次の形である。

- 先頭に表 (エントリの配列)，その後ろにデータ
- エントリは「名前・オフセット・長さ」だけ
- **名前は平ら**。ホスト側の `find . -type f` が出す `a/b/c.h` という
  文字列を，そのまま 1 個の名前として持つ (ディレクトリという実体は
  無い)

平らでも「`a/b/c.h` を開く」ことはできる。実際 Stage 15 第 6 部では
`sys/time.h` をこの形で置いた。**足りないのは次の 3 つ**である。

| 足りないもの | なぜ要るか |
|---|---|
| 相対パスの解決 | `#include "../foo.h"` や，作業ディレクトリを持つビルド |
| 一覧 (readdir) | `configure` や make が「そこに何があるか」を訊く |
| 作成・削除 | ビルドは中間ディレクトリを掘る |

### 6.2 方針

**平らな表は残し，その上に木を載せる。** エントリに「親」と「種別」を
足すだけにする。sfs の「表 + データ」という単純さは，カーネルが
数百行で読めることの理由なので崩さない。

- エントリに **種別** (ファイル / ディレクトリ) と **親のエントリ番号**
  を足す
- 名前は**そのディレクトリ内での名前**にする (`c.h`)。全体の経路は
  親を辿って組み立てる
- ルートはエントリ 0 とし，親を自分自身にする

これで readdir は「親が n のエントリを並べる」，パス解決は「/ で切って
1 段ずつ引く」で済む。

### 6.3 バイト配置 (sfs2)

sfs1 の表項目はちょうど 64 バイトで隙間が無い。**名前を 52 → 48 に
縮めて，空いた 4 バイトを親に充てる。** 名前はそのディレクトリ内での
名前になるので，47 バイトあれば実用上足りる (sfs1 は経路まるごとを
名前にしていたので 51 バイトでも足りないことがあった)。項目が 64 バイト
のままなので，カーネル側の算術は変わらない。

すべてリトルエンディアン。

```
スーパーブロック (32 バイト):
  0   'sfs2' (4 バイト)
  4   u32 total    イメージ全体の大きさ
  8   u32 tbloff   表の位置 (= 32)
  12  u32 tblcnt   表の件数 (容量)
  16  u32 cursor   次にデータを置く位置 (追記割付け。4 バイト境界)
  20  予約 (0)

表項目 (64 バイト / 件。未使用の項目は全 0):
  0   name[48]     そのディレクトリ内での名前，NUL 終端 (最長 47 バイト)
  48  u32 parent   親のエントリ番号
  52  u32 dataoff
  56  u32 len
  60  u32 flags    bit0 = 有効, bit1 = ディレクトリ
```

- **エントリ 0 は必ずルート**である。名前は空，親は自分自身 (0)，
  flags = 3 (有効 + ディレクトリ)
- ディレクトリのエントリは `dataoff` / `len` を使わない (0)
- 経路の解決は「`/` で切り，1 段ずつ『親が n で名前が一致する項目』を
  引く」。一覧 (readdir) は「親が n の項目を並べる」

### 6.4 進め方

**ホスト側から先に作る。** `tools/sfs2.sh` (pack / unpack / list) と
その往復検査は QEMU を要さないので速く回せる。形式が固まってから
カーネルへ持ち込む。

sfs1 (`tools/sfs.sh`) は**そのまま残す**。Stage 12〜15 の検査がすべて
それに依っており，凍結済みの成果物の再現に要るからである。

### 6.5 カーネル側 (kernel17)

`stage016/kernel17.c` は kernel16 の写しに sfs2 の経路解決を入れたもの
である。触ったのは 3 関数だけで，残りは kernel16 のままである。

| 関数 | kernel16 | kernel17 |
|---|---|---|
| `nameeq` → `nameeqn` | 項目の名前と文字列全体を比べる | 項目の名前が `s[0, n)` と一致し**そこで終わる**か |
| (新設) `childof` | — | 親 `par` の中から名前 `s[0, n)` を引く |
| (新設) `walk` | — | 経路を `/` で切って 1 段ずつ辿る |
| `sfsfind` | 表を線形に走査して名前で引く | `walk(path, 0, ...)` |
| `sfsnew` → `sfsmk` | 空き項目に名前を書く | 親を `walk(path, 1, ...)` で出してから書く。ディレクトリも作れる |

`nameeqn` が「切り出さずに比べる」形なのは，**カーネルに経路の一時
領域を持たせないため**である。`a/b/c.h` の `b` を比べるのに `b` を
どこかへ複製する必要がない。

`walk` の `stop` 引数が 2 つの用途を 1 つの関数にまとめている。

- `stop = 0` (引く): 最後の段まで辿り，その項目番号を返す
- `stop = 1` (作る): 最後の段の**手前**まで辿り，その親を返す。最後の
  段の名前と長さを `*lastp` / `*lastn` で返す

**ファイルを途中に挟む経路は失敗させる** (`/top.txt/x`)。`walk` は
1 段進むごとに「まだ後ろが残っているのに今の項目がディレクトリでない」
かを見る。これが無いと `/top.txt/x` が `/top.txt` として開けてしまい，
「無いはずのものが開ける」という一番たちの悪い壊れ方をする。

連続する `/` と先頭の `/` は読み飛ばす (`//src///one.c` は
`/src/one.c` と同じ)。`.` と `..` はまだ扱わない —— 作業ディレクトリを
持つのは第 2 部の課題である。

検査は `tests/stage016/user/pathprobe.c` を OS の上で走らせて，10 件の
経路の引き方を期待と突き合わせる。中身をその経路の名札にしてあるので，
取り違えれば**どれとどれを取り違えたか**が出力に出る。
