# 成果物の分類と配置

本書は「どのファイルが凍結され，どのファイルが書き換わるのか」を定める。
[roadmap.md](roadmap.md) 4 章 (進め方の原則) の細則である。

## 1. 規則

**記録対象の成果物の入力になるものは，すべて世代ごとに凍結する。**

`stageNNN/` に置いたソースは，一度その世代の成果物を作ったら **二度と
書き換えない**。変更は新しい世代のファイルを足す形で行う。

| 例 | 世代 |
|---|---|
| `stage010/cc.sc` … `cc12.sc` | C コンパイラの各世代 |
| `stage008/ld.sc` / `stage012/ld12.sc` | リンカの各世代 |
| `stage011/libc/` / `stage012/libc/` | libc の各世代 |

## 2. なぜ凍結するのか

各 Stage の `.md` に記録した SHA-256 を CI が照合する。この照合が意味を
持つのは，**その成果物を作る入力がすべて固定されているとき** だけである。

`cc10a` が `cc2.sc` をコンパイルして `cc10b` を作る、という依存関係があるので，
`cc.sc` を後から書き換えると `cc10b` 以降を記録どおりに再生成できなくなる。

libc も同じ立場にある。Stage 13 以降，OS 上の道具 (シェル・エディタ) が
libc をリンクすると **libc はそれらの入力になる**。libc を 1 つだけ持って
書き換える形にすると，後の世代で libc を触ったときに前の世代の道具の
SHA-256 が変わってしまう。だから libc も世代ごとに凍結する。

当初は libc を他の世代成果物の入力として使わないと考え，凍結不要と判断した。
しかし Stage 13 以降ではツールのリンク入力になるため，この判断を訂正した。

## 3. 外部ソース・外部処理系の生成物を世代成果物に含めない

[roadmap.md](roadmap.md) 2.3 の制約を，以下の適用例で明確にする。
過去の違反と修正内容は [stage017-cc.md](stage017-cc.md) 34 章に記録している。

> L1 / L2 は処理系を鍛えるベンチマーク指標としての目標であり，
> 外部のソースや生成物を stone の世代成果物 (実行環境を含む) に
> 混ぜないことを優先する

tcc・GCC・Linux のソースは，stone の処理系が対応する言語機能や規模を
検証するための入力である。これらを stone の標準処理系や実行環境に採用しない。

| | 可否 | なぜ |
|---|---|---|
| 外部のソースを検証用の入力として読む (stone の cc が tcc をコンパイルする) | 可 | stone の処理系の対応状況を測定できる (2.3) |
| 測定で判明した stone の未実装機能・不具合を修正する (`cc15q` … `cc15u`) | 可 | stone の実装を修正するため |
| 外部の**実行形式**を stone の OS に置く | 不可 | 外部の生成物である |
| **外部の処理系に我々のソースを訳させた出力**を stone の OS に置く | **不可** | 入力が我々のものでも，**出力は外部の生成物**である |
| 外部の処理系を我々の `cc` に据える | 不可 | 以降の成果物すべてが外部由来になる |
| 外部の処理系で zlib 等をビルドし，stone の処理系の検証結果とする | 不可 | stone の処理系でコンパイルできることを確認していないため |

stone のソースであっても，外部の処理系でコンパイルした `.o` は外部由来の
生成物として扱う。ソースの著者だけでなく，生成に使用した処理系も判定対象になる。

L1 は stone の処理系で GCC をコンパイルできることを目標とする。
外部の処理系でビルドに成功しても，stone の処理系の対応状況を示す結果にはならない。

## 4. 凍結しないもの

`tools/` (ホスト側のビルド・テスト駆動) と `docs/` `tests/` は世代を持たない。
これらは **成果物の入力ではなく，成果物を作る手順と検査**だからである。
`tools/build.sh` を変えれば全 Stage が作り直されるが，作られる生成物の
バイト列は変わらない (変わったら SHA-256 の照合で落ちる)。

## 5. 世代を追加するときの手順

1. 直前の世代のディレクトリを **全文複製** して新しい世代を作る
   (`cp -r stage011/libc stage012/libc`)
2. 新しい世代だけを編集する
3. `tools/build.sh` に新しい世代のビルドを足す。生成物の名前は世代で
   分ける (`l11_string.o` / `l12_src_string.o`)
4. 新しい世代の `.md` に SHA-256 を記録する。**古い世代の `.md` は触らない**

全文複製は重複を生むが，`cc.sc` … `cc12.sc` で既に採っている作法であり，
「過去の世代を読めば，その時点の全体像がそこにある」という利点を取る。
