# 開発ノート (環境・デバッグ手順)

本書は [plan.md](plan.md) を補う実務メモである。計画・仕様ではなく，
「作業を再開する人が知らないと調査に時間を浪費する」種類の情報を集めている。

- 1 章: コンテナが使えない環境での作業手順
- 2 章: デバッグ手法 (実際にバグを見つけた手順を残す)
- 3 章: 検証レシピ (固定点・コメントのみ変更の証明)
- 4 章: 落とし穴

## 1. 実行環境

### 1.1 標準はコンテナ

[plan.md](plan.md) 2.3 のとおり，再現性の基準はコンテナ (`env/Containerfile`) である。
CI は毎回このイメージを構築し，全 Stage のテストを実行する。
**各 `.md` に記録した SHA-256 の正当性を保証するのは CI である。**

```
sh tools/env.sh build      # イメージ構築と packages.lock の照合
bash tools/test.sh         # 全 Stage のテスト
```

### 1.2 コンテナが使えない場合 (egress 制限のある環境)

作業環境によっては `env.sh build` が失敗する。これまでに確認した例:

| 症状 | 原因 |
|---|---|
| `Cannot connect to the Docker daemon` | dockerd が起動していない。`dockerd &` で起動する |
| ベースイメージ取得が 403 | `production.cloudfront.docker.com` が egress ポリシーで拒否されている |
| `apt-get update` が 403 (`x-deny-reason: host_not_allowed`) | `snapshot.debian.org` が拒否されている。**ポート 80 のみ拒否**という例もある (443 は許可でも Containerfile は `http://` を使うため失敗する) |

`snapshot.debian.org` は迂回できない。plan.md 2.3 でパッケージをアーカイブ時点に
固定しており，`deb.debian.org` 等へ差し替えると版が動いて `env/packages.lock` との
照合が壊れる。HTTPS へ切り替える案も，ベースイメージ (`debian:bookworm-slim`) が
`ca-certificates` を持たないため成立しない (それを入れるには apt が要る，という循環)。
**egress を許可してもらうか，本節の手順でホスト実行に切り替えるかの二択である。**

#### ホストでの実行

```
apt-get install -y qemu-system-misc binutils-riscv64-unknown-elf
```

`tools/env.sh` に以下の分岐を一時的に入れると，既存のテスト・ビルドスクリプトを
そのまま `STONE_ENGINE=host` で流用できる。

```sh
if [ "${STONE_ENGINE:-}" = host ]; then
    repo_root=$(CDPATH= cd -- "$(dirname -- "$0")/.." && pwd)
    cmd=${1:-}; shift || true
    case "$cmd" in
    qemu) exec sh "$repo_root/tools/run-qemu.sh" "$@" ;;
    run)  cd "$repo_root" && exec "$@" ;;
    build) exit 0 ;;
    esac
fi
```

> **このパッチは絶対に commit しないこと。** ローカルの便宜であり，
> コンテナを基準とする再現性ポリシーを迂回する。作業後は元に戻し，
> commit 前に `git diff tools/env.sh` が空であることを確認する。
>
> (恒久的にサポートする案もあるが，`env.sh` の契約を変えることは
> 再現性ポリシーの変更にあたるため，plan.md の改訂とセットで判断する。)

**一度入ってしまった。** Stage 15 の作業中 (`bbb95b8`) に他の変更と
一緒にステージされ，PR 2 本ぶん main に載ったまま気づかれなかった。
見つかったのは 2 日後，別件で `git status` を見たときである。

見逃した理由が 2 つあり，どちらも「注意する」では防げない性質のもの
だった。

- **CI では分岐に入らない。** パッチは `STONE_ENGINE=host` のときしか
  通らず，コンテナで走る CI は通らない。**動作としては完全に無害**な
  ので，緑の CI を 3 回すり抜けた。動作を壊さない違反は，動作の検査
  では見つからない
- **警告が止んだことを「片付いた」と読んだ。** それまで毎回出ていた
  「未コミットの変更がある」がステージされた時点で出なくなり，
  消えたこと自体が解決の合図に見えた

そこで `tools/test.sh` に検査を 1 つ置いた。**作業中の `tools/env.sh`
に当たっているかは見ない** (それが本来の使い方である)。見るのは
`git show HEAD:tools/env.sh` の側で，「リポジトリに入っていないこと」
だけを確かめる。

#### パッチを当てたまま commit する (外してはいけない)

`git update-index --skip-worktree tools/env.sh` を一度掛けておけば，
**当てたまま commit してよい**。

```
worktree:1  index:0  HEAD:0
```

`git commit` が見るのは索引であって作業ツリーではない。skip-worktree
が掛かっていると索引は綺麗なままなので，commit される `env.sh` にも
パッチは入らない。`git add -A` も拾わない。

**commit のたびにパッチを外して戻す，をやってはいけない。** 一見
安全に見えるが 2 つの事故を起こした。

- **外したまま戻し忘れる。** ビルドが黙って進み，`kernel20.bin` が
  0 バイトで出来上がる。検査が 9 件落ちて初めて気づいた
- **走行中のビルドの足元で外す。** ビルドは `env.sh` を何度も起動
  するので，外れている間に起動したものだけが失敗する。**stage014 以降
  の生成物が全部 0 バイトになった**。1 回のビルドの中で成功と失敗が
  混ざるので，原因が見えにくい

外す必要が無いのだから，外さないのが正しい。

なお当て直すときは，パッチ本文を**ファイルに置いてから**流し込むこと。
シェルの引用を通すと `$` や `&&` が化けて `env.sh` が壊れる (これも
実際にやった)。

ホスト実行の妥当性: Stage 2 以降のすべての `.md` 記載 SHA-256 は，
ホスト QEMU で算出した値をコンテナ上の CI が照合する形で運用してきた。
これまで両者が食い違ったことはない。ただしホストの QEMU は
`env/packages.lock` で固定した版とは限らないため，**最終的な正当性は
常に CI 側に置く**こと。

### 1.3 ビルドのキャッシュ (スタンプ)

ブートストラップ鎖の再ビルドは QEMU 上の実行を多数含むため時間がかかる。
`tools/build.sh` は Stage ごとに `tmp/build/<stage>.stamp` を書き，
**「入力 (ソースと前段のスタンプ) のハッシュ」と「生成物の sha256sum」の
両方が前回と一致する Stage を省略する**。健全性の根拠はビルドの決定性で
ある (同じ入力からは常に同じバイト列が生成される。各 Stage のテストが
SHA-256 の照合と固定点で保証している)。

- 入力に前段のスタンプを含めるので，上流の変更は下流全体へ伝播する
- 生成物側も照合するので，キャッシュの破損や部分的な復元は検出される
- `STONE_FORCE_BUILD=1` を立てるとスタンプを無視して作り直す
- `tools/test.sh` は引数で Stage を絞れる
  (`bash tools/test.sh stage010 stage011`)
- `tools/test.sh` は各 Stage のテストを並列に走らせる (出力は Stage の順の
  まま)。`STONE_TEST_SERIAL=1` で従来どおり 1 つずつ実行する
- `tools/build.sh` は stage011 以降 (依存が stage010 までで分かれる) を
  並列に作る。生成物は逐次と同じバイト列になる

CI は `tmp/build/` を actions/cache で持ち回し，変更のあった Stage だけを
作り直す。1.1 の「SHA-256 の正当性を保証するのは CI である」は次の
2 本立てになる。

| 実行 | 内容 |
|---|---|
| push / pull_request | キャッシュを復元し，変更のあった Stage だけ再ビルド。生成物と `.md` の SHA-256 照合は毎回全 Stage で行う |
| 週次 (schedule) | `STONE_FORCE_BUILD=1` でキャッシュを使わずゼロから全段を再ビルドし，再現性そのものを検証する |

### 1.4 スタンプの粒度 (Stage 15 の 3 分割)

スタンプの入力にはその Stage の手順のファイル (`tools/build/<stage>.sh`)
自身が入る。手順を直せばその Stage を作り直す，という当然の帰結だが，
**1 つの Stage が長いとこれが効かなくなる**。Stage 15 は cc の世代が
14 あり，1 枚のときはカーネルの 1 行を直しても 14 世代を作り直した
(30 分以上)。

そこで Stage 15 を 3 つに分けてある。

| 手順 | 中身 | 直す回数 |
|---|---|---|
| `stage015a.sh` | 第 1〜4 部で封じた cc の世代 (cc15a〜cc15k) | ほぼ無い |
| `stage015b.sh` | 第 6 部の最前線 (cc15l〜cc15n・pp15・pp16・ld15) | 世代を足すとき |
| `stage015c.sh` | OS の側 (実行時支援・カーネル・libc15) | いちばん多い |

依存は a → b → c の 1 本道で，`do_stage015` が順に呼ぶ。カーネルや
libc を直したときに作り直されるのは c だけになる。

**新しい Stage を足すときの目安**: 「封じて以後変わらないもの」と
「これから何度も直すもの」は別の手順ファイルに分ける。

### 1.5 途中で殺されても続きから (再開の単位)

長い作業は必ず途中で死ぬ。コンテナの再起動・CI のタイムアウト・
Ctrl-C のどれでも起きる。**再開の単位が粗いと，そのたびに全部を
捨てることになる。** 第 6 部の作業中に 5 回起きて，毎回 30〜45 分を
捨てた。そこで 3 つの層すべてに細かいスタンプを入れた。

| 層 | 再開の単位 | 仕掛け |
|---|---|---|
| 鎖のビルド | 世代 1 つ (2〜3 分) | `tools/build.sh` の `step` / `ccgen` / `tool1` |
| 検査 | Stage 1 つ | `tools/test.sh` の `tmp/test/<stage>.stamp` |
| tcc の自己ホスト | 段 1 つ (T1 / T2 / T3) | `tools/tcc-stone.sh` の `stamped` |

考え方はどれも 1.3 と同じである。**入力のハッシュが前回と一致し，
生成物が残っていれば飛ばす。** 健全性の根拠はビルドの決定性である。

- ビルド: `step <名前> <生成物...> -- <入力...> -- <コマンド...>`。
  cc の世代は `ccgen <名前> <前段> <ソース>` で 1 行になる
- 検査: 入力は「その Stage の検査一式」「`tests/lib.sh`」「**その Stage
  以下の番号**の鎖のソース」「生成物のスタンプ (`tmp/build/*.stamp`)」。
  生成物のスタンプには全成果物の SHA-256 が入っているので，成果物が
  1 バイトでも変われば鍵が変わる。**落ちた Stage はスタンプを書かない**
  ので次回も走る

  ソースを「その Stage 以下」に絞ってあるのは，当初のように全部入れると
  **新しい Stage を 1 つ足すだけで全 Stage のキャッシュが外れる**ため
  である (Stage 16 を足したとき実際に 000〜015 が全部走り直した)。
  各 Stage の検査が参照する `stage` ディレクトリは自分以下の番号に
  収まっている (最大は stage013 → stage009 / 010 / 012) ので，後ろの
  Stage のソースが前の Stage の検査結果を変えることはない
- 自己ホスト: T1 / T2 / T3 は各 25〜30 分。ここが最も効く

無視して全部やり直す口も要る。

| 変数 | 効果 |
|---|---|
| `STONE_FORCE_BUILD=1` | ビルドのスタンプを無視する |
| `STONE_FORCE_TEST=1` | 検査のスタンプを無視する |
| `STONE_FORCE_TCC=1` | 自己ホストのスタンプを無視する |

CI の週次 (schedule) は前 2 つを立て，キャッシュも使わずゼロから作る。
**「速い経路」と「正しさを保証する経路」を分ける**のが要点で，
push / PR は前者，週次は後者である。

## 2. デバッグ手法

生成物は裸の RV32 バイナリで，デバッガから見える名前も型もない。
以下は実際にバグを特定した手順である。

### 2.1 固有エラーコードの注入 (どの検査で落ちたかを知る)

処理系は異常時に `exit(N)` で停止するが，同じコード N を返す箇所が多数あるため
「どの検査に引っかかったか」が判らない。ソースを機械変換して，各 `exit` 箇所に
互いに異なるコードを振ったデバッグ版を作ると，終了コードがそのまま発生位置になる。

```sh
python3 - <<'EOF'
lines = open('stage005/sc.sol').read().splitlines()
n, out, mapping = [10], [], []
for i, ln in enumerate(lines):
    while '1 exit' in ln:
        code = n[0]; n[0] += 1
        ln = ln.replace('1 exit', f'{code} exit', 1)
        mapping.append((code, i + 1))
    out.append(ln)
open('tmp/sc-debug.sol', 'w').write('\n'.join(out) + '\n')
for c, l in mapping: print(c, 'line', l)
EOF
```

これで `stage005/sc.sol` の「引数個数の検査漏れ」を特定した。

### 2.2 実行トレースと PC 周期 (無限ループの原因を知る)

```sh
qemu-system-riscv32 -M virt -bios tmp/x.bin -display none -monitor none \
    -serial stdio -singlestep -d exec 2> tmp/trace.log
```

- `-singlestep` が必要 (これがないと翻訳ブロック単位でしか記録されない)
- `-one-insn-per-tb` は本バージョンの QEMU には**存在しない**

PC 列を抽出して繰り返しを見つける:

```sh
grep -o '/00000000800[0-9a-f]*/' tmp/trace.log | sed 's|/00000000||;s|/||' > tmp/pcs.txt
tail -600 tmp/pcs.txt | sort | uniq -c | sort -rn | head    # 周回している範囲
```

得られたアドレスを `verify/disasm.sh` の逆アセンブル結果と突き合わせる。
この手順で「B-type 分岐の ±4KiB 制限による silent 誤コンパイル」を特定した
([stage007-occ.md](stage007-occ.md) 3 章)。

### 2.3 大域アドレスから変数名への逆引き

生成コードに現れる `lui`/`addi` の即値は大域変数の絶対アドレスである。
ソースの大域宣言を順に読んで割付けを再現すれば，どの変数かが判る。

```sh
python3 - <<'EOF'
import re
addr = 0x80100000     # 生成プログラムの BSS 先頭
target = 0x801e7168   # 逆アセンブルに現れたアドレス
head = open('stage007/occ.sc').read().split('int init()')[0]
for m in re.finditer(r'(char|int)\s+(\*?)(\w+)(\[(\d+)\])?;', head):
    ty, star, name, _, n = m.groups()
    size = ((int(n) * (1 if (ty == 'char' and not star) else 4)) + 3) & ~3 if n else 4
    if addr <= target < addr + size:
        print(f'{name} + {target - addr}')
    addr += size
EOF
```

これで「ポインタ演算のスケーリングが効いていない」箇所を特定した。

## 3. 検証レシピ

### 3.1 固定点の確認

セルフホストした処理系 (Stage 6 以降) を触ったら必ず実行する。

```sh
sh tools/build.sh stage007          # B1, B2 を生成
{ cat stage007/occ.sc; printf '\004'; } \
    | sh tools/env.sh qemu tmp/build/occ.bin > tmp/b3.bin
cmp tmp/build/occ.bin tmp/b3.bin    # B2 == B3 が完了条件
```

sc 系の入力終端は **EOT (0x04)** である (`.` ではない)。`printf '\004'` の付加を忘れると
入力待ちのまま止まる。

### 3.2 「コメントのみの変更」の証明

コメントを増やしたときは，コードに触れていないことを機械的に示す。

```sh
strip() { sed 's|//.*||' "$1" | sed 's/[[:space:]]\+/ /g; s/^ //; s/ $//' | grep -v '^$'; }
git show HEAD:stage007/occ.sc > tmp/old.sc
diff <(strip tmp/old.sc) <(strip stage007/occ.sc) && echo "code identical"
```

sol (`stage005/sc.sol`) はコメントが `#` なので `sed 's|#.*||'` に読み替える。
併せて全チェーンを再ビルドし，各 `.md` の SHA-256 と一致することを確認する。

### 3.3 信頼根の独立監査 (Stage 1〜3)

seed・hex1・asm を，仕様書から独立に書き起こした参照実装 (Python) で
再導出し，記録 SHA-256・ゴールデン・自己再生成の裏を鎖の外から取る。
QEMU もコンテナも要らない。

```sh
bash verify/audit/audit.sh
```

検査の一覧・信頼モデル・全段監査の手順は
[verify/audit/README.md](../verify/audit/README.md) を参照。

## 4. 落とし穴

- **`xxd` が入っていない。** バイナリを見るときは `od -A x -t x1` を使う。
- **ビルドの完了待ちに `pgrep -f build.sh` を使ってはいけない。** 待つ側の
  シェル自身のコマンド行にもその文字列が含まれるため，自分にマッチして
  永遠に抜けられない (`pkill -f` も同様で，逆に自分を撃つ)。生成物の
  ファイルができたかどうかで待つ (`until [ -s tmp/build/xxx.bin ]`)。
- **実行中の `tools/build.sh` を編集しない。** sh はスクリプトを逐次読む
  ので，走っている最中に編集すると，どの版が実行されるかが決まらない。
  さらに 2 つのビルドを同じ `tmp/build/` で並走させると生成物が混ざる。
  編集は完了を待ってから行い，走らせるビルドは常に 1 本にする。
- **全 Stage のテストは 10 分を超える。** フォアグラウンドで実行すると打ち切られる
  ことがある。バックグラウンド実行するか Stage 単位で流す。
- **`stage007/occ.sc` は scc がコンパイルできる形を保つ必要がある。**
  ブートストラップ 1 段目 (`B1 = scc(occ.sc)`) は旧コード生成を通るため，
  `if`/`while` の本体が 4KiB を超えると B1 が壊れる。大きなループ本体は
  関数に切り出す (`fold` に対する `foldins` がその例)。
- **文書化コメントの形式は言語で異なる。** sc 系 (`scc.sc` / `occ.sc`) は Doxygen の
  `///` がそのまま使える。sol (`sc.sol`) は行コメントが `#` のため `#/` を
  文書化コメントとする規約を用いる (Doxygen へ掛けるなら `FILTER_PATTERNS` で
  `#/` → `///`)。sol はスタック指向で名前付き引数がないため `@param` は使わず，
  スタック効果を `@stack ( 引数 -- 結果 )` で記す。
- **生成物 `cc.bin` は常に最新世代の C コンパイラを指す。** 過去世代は
  世代番号を付けて呼ぶ (`cc8.bin` = Stage 8)。各 Stage の成果物は前段の
  成果物のみでビルドするので，Stage 9 の `pp` は `cc8.bin` でビルドする。
  ここを取り違えると `pp.bin` の SHA-256 が記載値と食い違う。
- **構文だけを足したコンパイラは，ブートストラップ 1 段目と正本が一致する。**
  前段のコンパイラが作った `cc1.bin` と，それが自分自身を再コンパイルした
  `cc.bin` がバイト単位で一致すれば，コード生成規則に触れていないことの
  機械的な証明になる。一致しなければ，意図せずコード生成を変えている。
- **トークン種別の番号は範囲が重ならないようにする。** cc の `k_*` (予約語) は
  10 番台から，`o_*` (演算子) は 30 番台から始まる。予約語を足すときに
  安易に続きの番号を振ると演算子と衝突し，**構文エラーではなく「別の
  トークンとして解釈される」形で壊れる** ので原因が見えにくい。
  Stage 10 第 2 部では 80 番台へ逃がした。
- **cc の識別子は Stage 10 第 2 部まで英小文字のみだった。** 大文字を含む
  テストを書くと，字句解析器が識別子と認識せず演算子として扱い，
  「未知の演算子」で終了コード 1 になる。原因が指令や宣言の側に見えるので
  紛らわしい。lexop の失敗地点で文字コードと位置を出力させると早い。
- **IR に命令種別を足したら，触る場所は 4 箇所ある。** 出力段 (emitins)，
  dce の「根から辿る被演算子」，レジスタ割付けの「被演算子の表」，そして
  レジスタ割付けの **「値を定義する命令の表」**。どれを忘れても
  コンパイルは通り，生成物が静かに壊れる。
  Stage 10 第 2 部の 4 で `sh` / `lb` / `lh` / `lhu` を足したとき前の 3 つで，
  第 2 部の 5 で `jalr` の呼出しを足したとき最後の 1 つを見落とした
  (呼出しの結果にレジスタが割り当てられず，別の値が返った)。
- **コンパイラ自身の演算子の意味を変えると，定数畳み込みの結果が世代で
  食い違う。** `>>` を算術シフトへ変えた段で，畳み込みの `>>` も一緒に
  変わってしまった。畳み込みの式は「新旧どちらの意味で解釈しても同じ値に
  なる」書き方にするか，その演算を畳まないことにする。
- **hex0/hex1/asm/sol の入力終端は `.`，sc 系は EOT (0x04)。** Stage 5 で変わっている。
  Stage 9 の pp は入力・出力ともに EOT で，`pp | cc` と繋げられる。
- **pp の 1 文字先読み (押し戻し) はフレームごとに区切る。** マクロ名の次の
  文字を読んでから展開フレームを積むため，押し戻しを共有すると展開結果より
  先にその文字が出てしまう (`return A;` が `return ;1` になる)。フレームを
  積むときに押し戻しの床を上げ，降ろすときに戻す。あわせて，フレームを
  降ろした直後は押し戻しを再確認してから次のフレームを読む必要がある。
- **pp で `#if` の式を評価すると行頭性が落ちる。** 式の展開はフレームからの
  読取りなので，`atbol` が 0 になったまま指令処理を抜けてしまう。抜ける際に
  必ず立て直す。怠ると次の行の指令が本文として素通しされ，`#if` の入れ子が
  合わなくなる。
- **番兵フレームは自分では降ろさない。** 展開しきりの終端で `ungc(-1)` を
  受け止める先が要るため，番兵は終端に達しても積んだままにし，読み終えた側が
  明示的に降ろす。先に降ろすと -1 が一段下の押し戻しへ紛れ込む。
- **記号表の鍵 `tname` を書き換える処理は，先読みの前に済ませる。** cc の
  `lfind` / `lnew` / `gfind` は「直近に読んだ識別子」を鍵にする。
  コンパイラが自前でローカルを登録するとき (Stage 10 第 3 部の 2 の
  `__va_ptr`) に `tname` を書き換えるので，**次のトークンを読んだ後で
  登録すると，そのトークンの名前が消える**。`va_list ap;` の `va_list` が
  `typedef` 名と認識されず，宣言が宣言に見えなくなるという壊れ方をした。
  構文エラー (1) にはなるが，出るのはずっと後ろの位置である。
- **大域の初期化子で，文字列の実体をその場に書いてはいけない。** 記号の値を
  先に確定させてから初期化子を読むので，途中で文字列の実体を出すと
  ポインタ語がその後ろへずれ，記号が文字列の先頭を指す。関数本体の
  文字列プールと同じく，番号だけ予約して実体は後ろへ回す
  (Stage 10 第 3 部の 1)。
- **実引数の「評価順」と「積む順」を分けると，コード生成規則が変わる。**
  可変長引数のために `ARG` を出す順序を並べ替えた段で，値の計算をすべて
  済ませてから `ARG` を出す形になり，IR の並びとレジスタ割付けの結果が
  変わった。ブートストラップ 1 段目と正本が一致しなくなるのは想定内で，
  固定点 (B2 == B3) で健全性を確かめる。
- **「型エラーとして拒否する」より「静かに値が壊れる」ほうが悪い。** 構造体の代入と
  値渡しは，第 3 部の 2 までコンパイルが通るのに先頭 1 語しか複写されて
  いなかった。先頭メンバだけ合っているので，テストの書き方によっては
  素通りする。**4 バイトを超える構造体だけを使い，先頭以外のメンバの値を
  必ず出力に混ぜる** テストでないと捕まらない。
  同じ理由で，まだ実装していない機能 (構造体の返却) は「通るが壊れる」まま
  にせず，明示的にエラーへ倒しておく。
- **IR から触れないものは，出力段に埋め込むしかない。** 構造体の返却では，
  呼んだ側が呼出しの直後にデータスタック (x9) から値を引き取る必要がある。
  IR が知っているのは「フレーム上の位置」と「値番号」だけなので，この操作は
  IR では書けない。命令種別を増やす代わりに **呼出し命令へ側情報を持たせ**
  (iret)，出力段が呼出しの直後に複写を出す形にした。こうすると IR の
  4 箇所ルール (出力段・dce・割付けの被演算子・割付けの値定義) を踏まずに済む。
- **左辺値かどうかと，アドレスがあるかどうかは別である。** 構造体の値は
  どれも実体のアドレスで表すので，呼出しの返却値でもメンバは取れる
  (`mk().x`)。しかしその実体は一時領域なので代入先にはできない。
  `elv` (左辺値) だけで判定すると `mk().x = 5` が黙って通り，捨てられる
  領域へ書くだけになる。一時領域であることを別の印 (`erv`) で持つ。
- **CI の runner は実行系の版が混在する。** コンテナ像キャッシュの鍵に
  podman / crun の版を含めたことで，版の違う runner に当たるとキャッシュ
  ミスになり像を作り直す。このとき base image の取得が docker.io の
  無認証 rate limit で即座に失敗することがある (`requested access to the
  resource is denied`)。`env.sh build` は間を置いて 3 回まで試し，
  `tools/test.sh` は環境が用意できなければログを表示して早期に中止する
  (像なしで続行すると qemu を使う全テストが連鎖失敗し，原因が読めなくなる)。
  それでも失敗が続く場合は，base image の取得元をミラー
  (mirror.gcr.io など。digest は同一) へ切り替えるか registry への認証を
  検討する。
- **キャッシュしたコンテナ像の tar は，実行系の更新で使えなくなることがある。**
  CI が保存した `stone-env.tar` を runner 側の podman / crun の更新後に
  復元すると，`podman run` が一律に
  `OCI runtime error: crun: unknown version specified` で失敗した
  (像そのものは load できるので気づきにくい)。像キャッシュの鍵には
  Containerfile のハッシュだけでなく実行系の版も含める (ci.yml)。
- **リンカの前置部が提供する関数も，cc の呼出し規約に従わなければならない。**
  cc はレジスタ割付けで x13..x27 を使い，これらを callee-saved として扱う
  (呼ばれた側が退避する)。Stage 12 の syscall スタブは引数と番号に
  `a3` (x13) と `a7` (x17) を使うので，退避を忘れると **呼出しを跨いで
  生きている変数が静かに壊れる**。症状は「ユーザプログラムが無関係な
  ストアで例外を出す」で，原因の場所からは遠い。逆アセンブルして
  「例外を出したストアの番地レジスタが，直前の呼出しで壊れていないか」を
  見るのが早い。
- **PMP を 1 つも設定しないと U モードへ移れない。** 「項目が無い = 全許可」
  なのは M モードだけで，U モードは全拒否になる。QEMU 7.2 ではこれが
  `mret` の不正命令 (mcause 2) として現れるため，原因が mret 自体に
  見えて紛らわしい (docs/stage012-os.md 5.1)。
- **cc へ直接与えるソースに `/* */` コメントは書けない。** コメントを空白へ
  置き換えるのは pp の役割で，cc 単体が処理するのは `//` のみである
  ([stage009-pp.md](stage009-pp.md) 3.1)。pp を通さずにコンパイルする
  テストソースは `//` で書く。誤った場合は構文エラー (1) だけが報告され，
  原因がコメントであることを特定しにくい。
- **ゲスト内のビルド記述でも「どの世代の cc で作るか」を守る。** OS の上に
  移った cc は最新世代 (cc10l) なので，何も考えずにそれで作ると **動く物は
  出来るが記録どおりの成果物にならない**。pp は Stage 8 の cc で作る決まり
  なので ([plan.md](plan.md) 2.1)，ゲスト内でも `cc8.o` を `'E'` でリンクした
  cc8 を使う必要がある。症状は「SHA-256 が合わない」だけで，動作は正常に
  見える (docs/stage013-tools.md 9.5)。
- **cc の 1 関数のフレーム総サイズは 2040 バイトまでである。** 関数の
  プロローグが `addi sp, sp, -fnf` の 1 命令であり，RISC-V の即値が
  12 ビット符号付きだからである (stage010/cc12.sc の `fnf > 2040`)。
  超えると **領域超過 (終了コード 6)** で止まる。局所変数・スピル・
  退避レジスタの合計なので，`char buf[2048];` を 1 本置くだけで超える。
  作業領域が要るなら **大域に置く** (処理系自身・カーネル・OS 上の道具は
  みなそうしている)。症状は「コンパイルが 6 で落ちる」だけで，どの
  関数が原因かは出ない。6 は他の上限 (記号表・IR・文字列プール) とも
  共用なので，まず大きな局所配列を疑うのが早い。
- **標準入力を親子で分け合えるのは，stdio が無バッファだからである。**
  シェルから起動したプログラム (ed など) は，シェルと同じ UART の続きを
  読む。これが成り立つのは stdio が 1 バイトずつ read するからで
  ([stage012-os.md](stage012-os.md) 6.4)，「速度のために」バッファを
  入れると**シェルが先読みした入力が子に渡らず消える**。壊れ方は
  「子が最初の数行を読み飛ばす」で，原因はバッファ側にあるため遠い。
  バッファを入れるときは，行単位で読む経路 (fgets) を別に用意するか，
  子を起こす前に読み戻す必要がある。
  [tests/stage013](../tests/stage013/test.sh) の「ed とシェルの同居」が
  この性質を固定している。
- **「仕様が揃った」は目次を追うだけでは確かめられない。** Stage 10 は C89 の
  文法を章立てで網羅したが，字句の細部 (文字エスケープ) に実装漏れが残っていた。
  見つかったのは Stage 11 の libc を書き始めて `isspace` が `\f` `\r` `\v` を
  必要としたときである。**実装漏れは最初の実際の利用で顕在化する。** 利用側の
  コードを書くまでは「揃った」と言い切らないほうがよい。
  なお，利用側 (libc) で数値を直書きして回避してはいけない。処理系の実装漏れ
  への対処を利用側に求めることになり，しかも理由が読む側に伝わらない。

- **`tools/env.sh` のホスト実行パッチも「走らせている最中に外さない」。**
  commit の前に `git checkout tools/env.sh` で戻すのが習慣になっているが，
  ビルドが走っている最中にやると，途中から `exec: host: not found` で
  止まる (ビルド自体は成功扱いで終わることもあり，紛らわしい)。
  戻すのはビルドとテストが完了してからにする。
- **`tools/build.sh` は全 Stage のスタンプの入力である。** 少しでも書き換えると
  全 Stage が作り直しになる (数十分)。まとめて直してから 1 回走らせること。
- **`run_stage` の成果物宣言に足し忘れると，その生成物は作られない。**
  新しい世代 (cc14f・ld14 など) をビルド手順に足しても，`do_stageNNN` の
  成果物一覧に挙げ忘れると，スタンプの照合はそれらの不在に気づかないため
  「入力が変わっていない」と判断して Stage 全体が省かれる。**手順と宣言は
  必ず一組で直す。**
- **同じ名前を持つ大域バッファは，再入する解析関数の間で壊れる。**
  cc の `ptype()` はタグ名を大域 `snam` に置いたまま `strudef()` を呼んで
  いたため，メンバの型に `struct X` が現れると入れ子の `ptype()` が
  上書きし，戻った先の `sfind2()` が内側の struct を引いていた
  ([stage014-external.md](stage014-external.md) 13.2)。**症状は「その
  typedef 名で書いたメンバ参照だけが型エラー」** という遠い形で出る。
  タグ形で書けば通る，という非対称に気づけたら大域バッファを疑う。
- **表のスロット幅を変えるときは，読む側と書く側を一組で変える。** pp の
  名前スロットを 32 -> 64 バイトへ広げた際，参照の添字だけを直して割付けの
  進み (`mpp = mpp + 32`) を残したため，**1 個目の仮引数だけ正しく動く**
  という壊れ方をした (位置 0 は幅に依らず一致するため)。
  症状は「関数形式マクロの 2 個目以降の引数が展開されない」。
- **世代は「直した数」ではなく「まとまった能力」で刻む。** 世代を 1 つ
  足すと，固定点の確認・SHA の記録・検査の配線で 30 分以上かかるうえ，
  **鎖が恒久的に伸びる** —— 以後のすべての通しビルドがその世代を再演する。
  Stage 15 は cc だけで 14 世代あり，CI のビルドが 10 分近いのは主にこれが
  理由である。
  調べている最中の修正は `tmp/` の**封をしていない複製**に当てて測り，
  まとまってから 1 世代として封をする (SHA を .md に記録し配線する)。
  第 6 部では 21 件を cc15m にまとめた一方，cc15n は 1 件で切ってしまった。
  効果を測るだけなら封は要らなかったので，これは判断の誤りである。
- **ビルド手順は Stage ごとのファイルに分ける。** 以前は
  `tools/build.sh` 1 枚に全 Stage の手順があり，それが全 Stage のスタンプの
  入力だったため，**どの Stage を触っても鎖の全段が作り直し**になった。
  Stage 15 で世代が増えたとき CI がジョブの時間上限 30 分を超え，
  **失敗ではなく cancelled** という形で現れた (GitHub Actions は
  timeout-minutes 超過を cancelled として report する)。
  手順を `tools/build/<stage>.sh` へ分け，各 Stage のスタンプの入力を
  その 1 ファイルだけにした。駆動側 (`tools/build.sh` の run_stage) は
  入力に含めていないので，**その意味を変える改訂をしたときは
  `STONE_FORCE_BUILD=1` で作り直す**こと。
