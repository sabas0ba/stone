# Stage 10: C89 言語完成 設計文書

## 1. 目的と位置づけ

### 1.1 目的

Stage 9 までで道具立て (分割コンパイル・リンカ・プリプロセッサ) は揃った。
残るのは言語そのものである。現在の cc が受け付けるのは
[stage005-sc.md](stage005-sc.md) 2 章の sc 言語 —— `int` / `char` /
ポインタ / 1 次元配列 / 構造体，`if` / `while` / `return`,
二項演算と単項 `- ! * &` —— に限られる。

Stage 10 の目的は，これを **C89 の言語仕様** まで引き上げることである。
[roadmap.md](roadmap.md) Phase A の 3 段目であり，これが済めば
「他人の書いた C」を読み始める Phase C の前提が整う。

### 1.2 分割

Stage 10 の作業量は 1 つの変更に収まらない。依存関係で分ける。

| 部 | 内容 |
|---|---|
| 第 1 部 | 文と式: `for` `do` `switch`/`case`/`default` `break` `continue` `goto`/ラベル，`?:`，複合代入，`++`/`--`，カンマ演算子，`sizeof`，キャスト |
| 第 2 部の 1 | 型 (前半): `typedef`，`enum`，`union`，`const`/`volatile`，`void`，識別子の大文字 |
| 第 2 部の 2 | 宣言: 関数プロトタイプ，`extern`，`static` (受理のみ)，ブロック内宣言 |
| 第 2 部の 3 | 識別子と配列: 識別子長 31，多次元配列 |
| 第 2 部の 4 | 整数型: `unsigned`/`signed`/`short`/`long` |
| 第 2 部の 5 | 関数ポインタ，`static` のリンケージ (13 章) |
| 第 3 部の 1 | 初期化子 (15 章) |
| 第 3 部の 2 | 可変長引数 (16 章) |
| 第 3 部の 3 | 構造体の値 (17 章) |
| 第 3 部の 4 | 構造体の返却 (18 章) |

第 2 部を割ったのは，**どこまで踏み込むか** で線が引けるからである。
第 2 部の 1 (9 章) は宣言の構文と字句だけを広げ，コード生成規則を変えない。
第 2 部の 2 (10 章) は宣言の形を広げ，フレームの割付け方だけを変える。
第 2 部の 3 (11 章) は字句と型表現を広げるが，コード生成規則は変えない。
第 2 部の 4 (12 章) は整数型の幅と符号が入るため，ロード・ストアの幅選択や
除算・シフト・比較の符号つき / 符号なしの選択が必要になり，
**コード生成規則そのものが変わる最初の段** である。

第 1 部を先に置く理由は 2 つある。

1. **自己完結している。** 構文解析と IR 構築だけで閉じ，ABI にも
   オブジェクト形式にも触れない。第 2 部の 2 の型システム変更や第 3 部の
   第 3 部のデータ配置の変更に比べて影響範囲が狭く，独立に検証できる
2. **後続が書きやすくなる。** 第 2 部・第 3 部のコンパイラは第 1 部の
   コンパイラでビルドされる。つまり第 1 部が済んだ時点から
   `for` / `switch` / `break` / `++` / 複合代入を使ってコンパイラ自身を
   書けるようになる。sc の制約 (途中脱出はフラグ，添字は `i = i + 1`) の
   下で型システムを書くのは苦しい

**本文書の 3〜7 章は第 1 部，9 章は第 2 部の 1，10 章は第 2 部の 2，
11 章は第 2 部の 3，12 章は第 2 部の 4，13 章は第 2 部の 5，
15 章は第 3 部の 1，16 章は第 3 部の 2，17 章は第 3 部の 3，
18 章は第 3 部の 4 の設計である。** これで全部が揃った。

### 1.3 非目標 (Stage 10 全体を通して)

- 浮動小数点 (`float` / `double`)。C89 の一部だが，実行環境が RV32I**M** で

- ビットフィールド
- `volatile` の意味論 (構文としては受け付けるが最適化の抑止は行わない)
- ワイド文字 (`wchar_t` / `L"..."`)
- C99 以降の機能

このほか，非目標には挙げていないが Stage 10 完了の時点で **未対応のまま
残った** ものが 3 点ある (18.4 の「揃った」はこれらを除いた範囲である)。
**いずれも Stage 14 のコンパイラ世代で解消した** ので，現在の最前線

### 2.2 記述言語の制約

`stage010/cc.sc` は **cc8 がコンパイルできる範囲**，すなわち sc 言語で書く。
自分が実装する機能を自分の記述には使えない。これはブートストラップの
常であり，Stage 6 (scc)・Stage 7 (occ) でも同じだった。

```
cc8(stage010/cc.sc)  -> cc10a0.bin          # ブートストラップ 1 段目
cc10a0(stage010/cc.sc) -> cc10a.bin         # 正本
cc10a(stage010/cc.sc)  -> ... == cc10a.bin  # 固定点 (B2 == B3)
```

なお cc10a0 と cc10a は「同じソースを異なるコンパイラでコンパイルしたもの」で
あり，コード生成を変えていなければバイト単位で一致する。第 1 部は
コード生成規則を変えないので **cc10a0.bin == cc10a.bin** が成り立つ。これは
セルフホストの健全性を示す強い検査になるので，テストに含める。

各部のソースはその部のコンパイラを前提に書く。第 1 部の `cc.sc` は cc8 が
コンパイルできる範囲 (sc 言語) で，第 2 部の `cc2.sc` は cc10a が
コンパイルできる範囲で書く。自分が実装する機能を自分の記述には使えない，
というのはブートストラップの常である。

## 3. 第 1 部の設計: 文

### 3.1 反復と分岐の飛び先

IR は既にラベルと `jmp` / `bz` / `bnz` を持ち，飛び先はラベル番号で表す
(実アドレスの解決は出力段の仕事)。したがって新しい制御構造の追加は
「どのラベルをどの順で置くか」を決めるだけで済み，IR にも出力段にも
変更は要らない。

#### `for (init; cond; step) body`

```
        init
   L0:  cond -> bz L2
        body
   L1:  step                (continue の飛び先)
        jmp L0
   L2:                      (break の飛び先)
```

`cond` の省略は「常に真」とする (`bz` を出さない)。`init` と `step` の
省略はその位置に何も出さない。

#### `do body while (cond);`

```
   L0:  body
   L1:  cond -> bnz L0      (continue の飛び先)
   L2:                      (break の飛び先)
```

#### `while (cond) body`

既存の形に `continue` の飛び先 (条件評価の直前) と `break` の飛び先
(ループの直後) を加えるだけである。

### 3.2 `break` / `continue`

飛び先はスタックで持つ。`break` は反復と `switch` の両方が受けるが，
`continue` は反復だけが受ける。そこで **2 本のスタックに分ける**。

```
brkl[]  break の飛び先ラベル   … while / do / for / switch が積む
conl[]  continue の飛び先ラベル … while / do / for が積む
```

`switch` の中の `continue` が外側のループへ抜けるのは，`switch` が
`conl` を積まないことで自然に実現される。

対応する構文の外に置かれた `break` / `continue` はエラー 1 とする。

### 3.3 `switch` / `case` / `default`

単一走査で組み立てるため，**本体を先に，振分けを後に** 出す。

```
        v = cond
        v を隠しスロット s へ格納
        jmp Ldisp
        body                 … case K: は「ラベル Lk を置き (K, Lk) を控える」
                               default: は「ラベル Ld を置き Ld を控える」
        jmp Lend
  Ldisp:                     … 控えた組を順に照合する
        s を読み，K と比較 -> bnz Lk     (控えた数だけ繰り返す)
        jmp Ld               … default があれば
  Lend:                      (break の飛び先)
```

こうすると，本体を読み終える前に `case` の一覧を知る必要がない。
`switch` の値を隠しスロットに置くのは，`&&` / `||` / `?:` と同じ理由で
ある (この IR は値を「定義した命令番号」で指すので，本体を跨いで
レジスタ上の値を生かしておけない)。

`case` のラベルは整数定数と文字定数 (先頭の `-` を許す) に限る。
`enum` 定数や定数式は第 2 部の 2 で扱う予定だったが **未履行のまま残った**
(1.3 の表。Stage 14 の cc14g で解消)。
フォールスルーは C と同じく既定の動作である (`case` は単なるラベル)。

### 3.4 `goto` とラベル

関数ごとにラベル表を持つ。

| 配列 | 内容 |
|---|---|
| `glname` | ラベル名 (16 バイトスロット) |
| `gllab` | 対応する IR ラベル番号 |
| `gldef` | 1 = 定義済み (`名前:` が現れた) |

`goto` が先に現れた場合は未定義のまま登録し，`名前:` が現れた時点で
定義済みにする。関数の終わりで未定義のラベルが残っていればエラー 2 とする。

文の位置で識別子が現れたとき，それがラベルなのか式の始まりなのかは
1 トークン先読みしないと判らない (`x:` と `x = 1`)。字句解析器は
1 トークン先読みしか持たないので，**読取り位置とトークンを退避して
読み直す** 方式を採る (`lsave` / `lrest`)。入力全体が `src` にあるので
巻き戻しは位置の代入だけで済む。

## 4. 第 1 部の設計: 式

### 4.1 優先順位の更新

```
15: ,                      カンマ演算子 (左結合)
14: = += -= *= /= %= &= |= ^= <<= >>=   代入 (右結合)
13: ?:                     条件演算子 (右結合)
12〜3: || && | ^ & ==/!= 関係 シフト +/- */%      (既存)
2: 単項 - ! * & ++ -- sizeof (型)キャスト
1: 後置 [] () . -> ++ --
```

C の文法どおり，**関数呼出しの実引数は代入式** (カンマ演算子を含まない)
とする。これに伴い既存の `expr()` を `assign()` に改名し，カンマ演算子を
扱う新しい `expr()` を最上位に置く。

### 4.2 複合代入と `++` / `--`

左辺は **一度だけ** 評価しなければならない (`*p++ += 1`)。
この IR は左辺値をアドレスの値番号で持つので，同じ値番号を
2 度参照すれば「一度だけ評価して 2 回使う」が自然に書ける。

```
a op= b   ->   addr = 左辺 (左辺値)
               cur  = load addr
               r    = 右辺
               res  = cur op r
               store addr, res
               値は res
```

`++` / `--` は `+= 1` / `-= 1` と同じ形で，後置は `cur` を，前置は `res` を
式の値とする。ポインタに対しては指し先の大きさでスケールする
(`+=` `-=` `++` `--` のみ。他の複合代入をポインタに適用するのはエラー 5)。

### 4.3 `?:`

`&&` / `||` と同じく隠しスロットを使う。

```
        cond -> bz L1
        then を評価してスロットへ格納
        jmp L2
   L1:  else を評価してスロットへ格納
   L2:  スロットを読む
```

結果の型は then 側の型とする (C の通常の算術変換・ポインタの合成は
第 2 部の 2 の型システムと合わせて扱う)。

### 4.4 `sizeof`

`sizeof (型)` と `sizeof 単項式` の両方を受ける。`(` の次が型名かどうかで
判別するため，ここでも `lsave` / `lrest` で 1 トークン先を覗く。

式形式では **コードを出してはならない** (C は被演算子を評価しない)。
IR は配列と個数で持っているので，解析前に `icnt` などを控えておき，
型を得た後に巻き戻す。

配列に対する `sizeof` が配列全体の大きさを返すよう，記号表に
バイト数を持たせる (`lsz` / `gsz` / `msz`)。式が配列オブジェクトを
指しているかは `earr` で伝える。`earr` は一次式で立ち，演算子を通ると
落ちる (配列は式の中でポインタへ退化するため)。

### 4.5 キャスト

`( 型 ) 単項式`。すべての値が 32 bit セルであり，`char` へのキャストも
値を切り詰めない現状では，キャストは **型の付け替え** だけを行う。
生成されるコードは無い。第 2 部の 2 で `unsigned` と幅の異なる整数型が
入った時点で，切詰めと符号拡張をここに足す。

## 5. エラー

Stage 8 の cc から変更しない ([stage005-sc.md](stage005-sc.md) 2.8)。
第 1 部で増える条件は次のとおり。

| 終了コード | 追加される条件 |
|---|---|
| 1 | 反復・`switch` の外の `break` / `continue`，`case` / `default` が `switch` の外，`case` のラベルが定数でない |
| 2 | 定義されていないラベルへの `goto` |
| 5 | ポインタに対する `*=` などの不正な複合代入 |
| 6 | ラベル数・`case` 数の上限超過 |

引数個数の検査 (エラー 5) には sc と同じ穴がそのまま残っている
([stage005-sc.md](stage005-sc.md) 2.5)。**前方参照の呼出しは個数未検査**で，
呼出しの時点で個数が未知の関数は検査を省き，定義時にも過去の呼出し位置を
遡って再検査しない (遡って検査されるのは「前方参照の呼出しの後で可変長と
判った」場合だけで，これはエラー 5 になる)。個数不一致の前方参照呼出しは
データスタックが不均衡な誤ったコードになる。この挙動は cc12 以降
(cc14g まで) 同じである。

## 7. 検証計画 (tests/stage010)

1. **ビルド再現**: `cc10a.bin` の SHA-256 が `stage010/cc.md` の記載値と一致する
2. **セルフホストの健全性**: `cc10a0.bin == cc10a.bin`。第 1 部はコード生成
   規則を変えないので，cc8 が作った 1 段目 (`cc10a0`) と，それが自分自身を
   再コンパイルしたもの (`cc10a`) はバイト単位で一致しなければならない
3. **固定点**: `cc.bin` で `stage010/cc.sc` を再コンパイルした結果が
   `cc.bin` と一致する (B2 == B3)
4. **同値性**: Stage 5 の仕様スイートと Stage 8 の分割コンパイル例が
   新しい cc でも同じ結果になる (退行がないこと)
5. **新機能**: `for` / `do` / `switch` (フォールスルー・`default`・入れ子)
   / `break` / `continue` / `goto` / `?:` / 複合代入 / `++` `--` (前置・後置・
   ポインタ) / カンマ / `sizeof` / キャストを，実行結果で確かめる
6. **エラー系**: 反復外の `break` → 1，未定義ラベルへの `goto` → 2
7. **構造体の値**: 4 バイトを超える構造体だけを使い，先頭以外のメンバの値を
   必ず出力に混ぜる。呼ばれた側で書き換えても呼んだ側に響かないこと
   (値渡しであること) まで見る。返却は入れ子の呼出しと 6 語の構造体で
   確かめ，繰り返してもデータスタックが減らないことまで含める
8. **可変長引数**: `include/stdarg.h` を pp で取り込み，個数の違う呼出しを
   混ぜて実行する。同じ可変長呼出しを 200 回繰り返してもデータスタックが
   減らないこと (後始末の検査) まで含める
9. **配置の検証**: 初期値を持つ大域が `.text` (節 1)，持たない大域が
   `.bss` (節 2)，`static` がローカルシンボルとして出ることを readelf で
   確かめる。値の一致だけでは置き場が設計どおりかを確かめられない
   (readelf は検証層でだけ使う。ビルド経路には既存の道具を入れない)

## 9. 第 2 部の 1 の設計: 型

### 9.1 型を増やさずに済むもの

`enum` と `typedef` は，一見すると型システムの拡張に見えるが，
**型を増やす必要がない**。

- `enum` の定数は「名前 -> 値」の対応にすぎず，型は `int` である。
  タグ (`enum color` の `color`) は型の区別を生まないので，読み捨ててよい
- `typedef` は「名前 -> 既存の型」の対応にすぎない

したがってどちらも表を 1 つ足すだけで済む。既存の型表現
(`ポインタの深さ << 16 | 基底`) には手を触れない。

### 9.2 `union` は構造体表を共有する

`struct` と `union` の違いはメンバの配置だけで，参照する側の扱いは同じで
ある (`.` と `->` はオフセットを足すだけ)。そこで同じ表に入れ，
`sunion` フラグで配置を分ける。

| | メンバの位置 | 全体の大きさ |
|---|---|---|
| `struct` | 直前の末尾を整列した位置 | 最後のメンバの末尾 (4 の倍数へ切り上げ) |
| `union` | すべて 0 | メンバの最大値 (同上) |

タグの名前空間も共有する。`struct s` と `union s` を同時に定義することは
できないが，実害は小さい。

### 9.3 `typedef` 名は構文を文脈依存にする

`x * y;` が宣言なのか式なのかは，`x` が `typedef` 名かどうかで決まる。
C の構文が文脈自由でない有名な箇所で，字句だけでは判断できない。
本実装では `istype()` が `typedef` 表を引いて決める。この判定は

- 局所宣言の並びの終わり (`while (istype()) plocal();`)
- キャストと括弧式の見分け (`( 型 )` か `( 式 )` か)
- `sizeof (型)` と `sizeof (式)` の見分け

の 3 箇所で使う。

### 9.4 無名の `struct` / `union`

`typedef struct { ... } T;` は実際の C で頻出する。タグが無いだけで
構造は同じなので，**内部で `$0` `$1` … というタグを振る**。先頭を `$` に
すると識別子の字句規則では作れない名前になるので，利用者の書いたタグと
衝突しない。

### 9.5 識別子の大文字

sc の識別子は英小文字と `_` に限っていた。しかし `enum` 定数も
`typedef` 名も大文字が慣習であり，取り込む外部の C も大文字を使う。
ここで解除する。予約語はすべて小文字なので，大文字を許しても衝突しない。

識別子の長さの上限 (15 バイト) は据え置く。C89 は内部識別子について
31 文字を要求しており，記号表のスロットを 16 バイトから 32 バイトへ
広げる必要がある。字句と記号表の両方に触れるので第 2 部の 2 で扱う。

## 10. 第 2 部の 2 の設計: 宣言

### 10.1 ヘッダを「宣言を共有する場所」にする

Stage 9 の申し送り ([stage009-pp.md](stage009-pp.md) 7 章) はここで解消する。
`#include` はあってもヘッダに書けるのはマクロと型定義だけだった。関数の
宣言 (プロトタイプ) と変数の宣言 (`extern`) が入って初めて，ヘッダが
本来の役割を果たす。

```c
/* util.h */
extern int shared;
int addup(int a, int b);
```

### 10.2 プロトタイプと定義の見分け

仮引数を読み終えた時点で `;` ならプロトタイプ，`{` なら定義である。
1 トークン先読みは要らない。プロトタイプは引数の個数と返却型だけを控え，
記号は未定義のままにしておく。

- 仮引数の名前は省略できる (`int f(int, char *);`)
- `(void)` は「引数なし」の明示である。`(void *p)` と紛らわしいので
  1 トークン先を覗いて見分ける
- プロトタイプの後に定義が来たとき，引数の個数が違えばエラー 5

### 10.3 `extern`

変数の `extern` 宣言では `.bss` を取らない。未定義シンボルとして出し，
リンカが他の翻訳単位の定義へ解決する。参照は既存の HI20 / LO12 再配置
そのままで，コンパイラ側に新しい仕掛けは要らない。

先に `extern` で宣言してから同じ翻訳単位で定義するのも正しい。記号を
探して未定義なら「定義への昇格」として扱う。

### 10.4 `static` は受理するにとどめる

`static` を本当に実装するには，ELF のローカルシンボルとして出し，リンカが
翻訳単位内で解決する必要がある。リンカは Stage 8 で凍結してあるので，
ここでは **受理して読み飛ばす** にとどめ，記号は大域のまま出す。

したがって 2 つの翻訳単位が同じ名前の `static` 関数を持つと，リンカが
多重定義とみなす。局所の `static` 変数 (記憶域が静的になるもの) は
意味が変わってしまうので，黙って自動変数として扱わず構文エラーとする。
本当のリンケージは第 2 部の 3 でリンカと合わせて扱う。

### 10.5 ブロック内宣言とフレームの割付け

隠しスロット (`&&` / `||` / `?:` / `switch` が使う) は，局所変数領域の
直後から取っていた。ブロック内宣言があると本体の解析中に局所変数が
増えるので，この 2 つが同じ領域を奪い合う。

そこで **隠しスロットも局所変数と同じ割付けポインタから取る**。
どちらも「フレーム上の 1 語」であり，区別する理由はもともと無かった。

複文を抜けると割付けポインタを戻すので，兄弟の複文は同じ領域を使い回す。
ただしフレームの大きさは戻した後の値ではなく **最大値** で決まるので，
高水位標 (`cmax`) を別に持つ。

この変更で，関数によってはフレームの大きさが前世代と数語異なる。
IR の命令種別・ABI・出力形式は変えていないが，**ブートストラップ 1 段目と
正本は一致しない**。正本が自分自身を再生成する固定点 (B2 == B3) は
従来どおり成り立つ。

## 11. 第 2 部の 3 の設計: 識別子と配列

### 11.1 識別子の長さ

C89 は内部識別子について 31 文字を有効とすることを要求している。
記号表の名前スロットを 16 バイトから 32 バイトへ広げる。字句解析器の
上限と，名前を複写する箇所と，スロットの添字計算がすべて連動する。

コード生成には一切影響しないので，ブートストラップ 1 段目と正本が
一致することでその点を確かめられる。

広げたのは **コンパイラの記号表だけ** であることに注意。リンカ
([../stage008/ld.sc](../stage008/ld.sc)。ld13 まで同じ) の大域シンボル表は
16 バイト固定スロットのままで，登録時に名前を 15 バイトへ黙って切り詰める。
定義側だけが切り詰められ，参照側の全文比較と一致しなくなるため，16 バイト
以上の外部名は **翻訳単位を跨ぐ参照だけが未定義シンボル (ld の終了コード 2)
になる** (同一翻訳単位内の参照は節内オフセットで解決されるため通る)。
C89 が保証する外部識別子 6 文字は満たす。この制限は Stage 14 の
[ld14](../stage014/ld14.md) がスロットを 32 バイトへ広げて解消した。

### 11.2 配列型

これまでの型は「ポインタの深さ << 16 | 基底」という平坦な表現で，
基底は `char` / `int` / 構造体 / `void` しか無かった。1 次元配列は
「配列かどうか」の旗と大きさを記号表に持たせるだけで済んでいたが，
多次元配列は **型から型を作る** ので平坦には表せない。

基底の 1024 番以降を配列型の表の添字に割り当て，要素型と要素数を持たせる。
`int a[3][4]` の型は `array(3, array(4, int))` になる。宣言子の `[n]` は
再帰で読むと自然にこの順で組み立てられる。

```
pdims(b): '[' が無ければ b。あれば n を読み，atype(pdims(b), n) を返す
```

### 11.3 退化 (decay)

配列は式の中では常に「先頭要素へのポインタ」になる。要素がさらに配列なら
「配列へのポインタ」になり，添字を 1 つ進めるたびに 1 段ずつ剥がれる。

| 式 | 型 |
|---|---|
| `a` | `int (*)[4]` |
| `a[i]` | `int *` |
| `a[i][j]` | `int` (左辺値) |

添字の計算はもともと「要素の大きさで掛ける」形なので，要素が配列でも
そのまま働く。`a[i]` は `a + i * 16` になる。

退化が起きるのは 3 箇所 —— 識別子・メンバの参照，添字の後，単項 `*` の後。
仮引数の配列も宣言の時点でポインタへ退化させる (C の規則)。

### 11.4 大きさの切り上げ

`sizeof` が正しい値を返すよう，記号表の大きさは **本当の大きさ** を持つ。
4 バイト境界への切り上げは `.bss` とフレームの割付けのときだけ行う。
`char cm[2][5]` の `sizeof` は 10 であって 12 ではない。

## 12. 第 2 部の 4 の設計: 整数型

### 12.1 幅と符号

| 型 | 幅 | 符号 |
|---|---|---|
| `char` | 1 | **なし** |
| `signed char` | 1 | あり |
| `short` / `unsigned short` | 2 | あり / なし |
| `int` / `long` | 4 | あり |
| `unsigned int` / `unsigned long` | 4 | なし |

素の `char` を符号なしとするのは，C が処理系定義としており，sc の時代から
`lbu` で読んできた挙動を引き継ぐためである。`long` は `int` と同じ 4 バイト
とする (`long long` は非目標)。

### 12.2 整数の格上げが効いて，符号の扱いが 1 箇所に集まる

`char` と `short` は算術の中で `int` へ格上げされる。`int` がその全ての値を
表せるので，`unsigned char` / `unsigned short` も **符号つき int** になる。
したがって **演算が符号なしになるのは `unsigned int` のときだけ** である。

ロードの時点で 32 bit へ拡張してあるので，格上げに命令は要らない。
型を付け替えるだけで済む。この性質のおかげで，符号の判定は
「どちらかの被演算子が `unsigned int` か」という 1 行で書ける。

### 12.3 命令の選択

| 対象 | 追加した命令 |
|---|---|
| ロード | `lb` (signed char) / `lh` (short) / `lhu` (unsigned short) |
| ストア | `sh` |
| 除算・剰余 | `divu` `remu` |
| 右シフト | `sra` (符号つき。符号なしは従来の `srl`) |
| 大小比較 | `sltu` |

比較は `slt` を基本形とし，`>` `<=` は被演算子を入れ替え，`<=` `>=` は
結果を `xori 1` で反転する形をそのまま使う。符号なしは基本形を
`sltu` へ差し替えるだけで済む。

IR には新しいロード・ストアの命令種別を足した。二項演算の起点 (`c_bin`)
より前の番号に入れる必要があるので，起点をずらしている。
**新しい命令種別は，出力段だけでなく dce とレジスタ割付けの
「どの被演算子を使うか」の表にも足さなければならない。**
片方だけ直すと，命令は出るのに被演算子にレジスタが割り当てられず，
生成物が静かに壊れる。

### 12.4 キャストの切詰め

幅の狭い型へのキャストは，左シフトの後に右シフトで戻す。符号つきなら
算術右シフト (符号拡張)，符号なしなら論理右シフト (0 拡張) である。

### 12.5 定数畳み込みの落とし穴

`>>` の意味が「論理シフト」から「符号つきなら算術シフト」へ変わったので，
**コンパイラ自身が定数を畳むときの `>>` も変わる**。この段のコンパイラは
前段でビルドされるが，その前段は「自分の書いたソースを新しい意味で読む」
わけではない —— 前段が作った 1 段目の *振舞い* は新しい意味に従う。
したがって畳み込みの結果が世代で食い違いうる。

論理右シフトの畳み込みは，上位に伸びた符号ビットを明示的に落とす形へ
書き改めた。新旧どちらの意味で解釈しても同じ値になる書き方である。
符号なし除算・剰余と算術右シフトは畳み込まない (このコンパイラ自身が
符号つきでしか計算できず，負の値で答えが食い違うため)。

## 13. 第 2 部の 5 の設計: 関数ポインタと static のリンケージ

### 13.1 関数型

型の表に関数型を足す。配列型と同じ考え方で，基底の 2048 番以降を関数型の
表の添字に割り当て，返却型を持たせる。仮引数の型までは持たない
(呼出しの検査は名前つきの関数と違って個数も見ない)。

式に現れるのは常に「関数へのポインタ」なので，型としては
`(1 << 16) | (2048 + k)` になる。**関数を参照はがししても関数のままで，
式の中では再びポインタへ戻る** と決めると，C の次の等価性が自然に出る。

```
p(x)  と  (*p)(x)          f  と  &f
```

### 13.2 呼出しが 2 通りになる

| 形 | 出力 |
|---|---|
| 記号を直接呼ぶ | `jal` + JAL 再配置 (従来) |
| 値を呼ぶ | `jalr` |

引数の積み方と返却値の受取りは同じである。IR には「値を呼ぶ」命令を
1 つ足す。**IR に命令を足したら，出力段・dce・レジスタ割付けの
「被演算子の表」と「値を定義する命令の表」の 4 箇所すべてに足す。**
最後の 1 つを忘れると，呼出しの結果にレジスタが割り当てられず，
別の値が返るという形で静かに壊れる。

### 13.3 宣言子

`T (*名前)(仮引数)` の形だけを受ける。`(` の次が `*` かどうかで
通常の宣言子と見分ける (1 トークン先読み)。仮引数は型を持たないので
括弧の対応だけ数えて読み飛ばす。

`T (*f[3])(int)` のような入れ子の宣言子は受けない。C の宣言子を一般に
解くには再帰的な組立てが要り，得られるものに対して複雑すぎる。
`typedef` を挟めば同じことが書ける。

### 13.4 `static` はリンカに手を入れずに済む

ld は既に次の作りになっている。

- 大域シンボルの収集を `sh_info` (最初の非ローカルの番号) から始める
- 再配置の解決を `st_shndx` で行い，1 (`.text`) / 2 (`.bss`) なら
  そのオブジェクト内で解く

つまり **リンカは最初からローカルシンボルを正しく扱えていた**
(文字列リテラルがそうだったため)。したがって cc が `static` の記号を
ローカル領域へ並べ替え，`sh_info` を正しく書くだけで翻訳単位に閉じる。

ELF は「ローカルが先，大域が後」で並べる決まりなので，シンボル表を

```
[0] 空 | 文字列リテラル | static | 非 static
```

の順に組み立て，大域記号から ELF シンボル番号への対応表を先に作ってから
再配置を書く。

## 14. 第 3 部への接続

第 2 部を終えた時点で，C89 の型と宣言が揃った。残るのは

- **初期化子**。`int a[] = {1, 2, 3};` `char *s = "x";`
- **可変長引数** (`stdarg.h` 相当)
- **構造体の値渡し・返却**

である。これが第 3 部で，Phase A の完了になる。

初期化子を先に置くのは，可変長引数の検証に文字列と書式が要るからである
(`prf("[%d]", n)` のような骨格を書くのに初期化済みのデータが要る)。

## 15. 第 3 部の 1 の設計: 初期化子

### 15.1 初期値のある大域を `.text` に置く

初期値を持つデータの置き場として，普通のコンパイラは `.data` 節を作る。
ここでは作らず，**`.text` の中に置く**。理由は次の 3 つ。

- 対象がベアメタルで MMU が無く，像はフラットに読み込まれる。
  節の保護属性 (実行可能か・書込み可能か) に意味が無い
- オブジェクト形式もリンカも変えずに済む。節が増えれば節ヘッダの番号が
  ずれ，`st_shndx` を見る ld の再配置解決にも手が入る
- データの中のポインタ (`char *p = "abc";` `int *q = &g;`) が
  **既存の `.rela.text` の `R_RISCV_32` でそのまま解ける**

`.bss` 節はそのまま残る。初期値を持たない大域はこれまでどおり `.bss` に
割り付ける。したがって記号ごとに置き場が 2 通りになり，ELF シンボルの
`st_shndx` を 1 (`.text`) と 2 (`.bss`) で書き分けることになる。

| 宣言 | 置き場 | `st_shndx` |
|---|---|---|
| `int g;` | `.bss` | 2 |
| `int g = 1;` | `.text` | 1 |
| `extern int g;` | 無し (未定義) | 0 |

### 15.2 文字列リテラルの実体は初期化子の後ろへ回す

`char *p = "abc";` は 2 つのものを `.text` へ置く。

1. `p` の実体 = 4 バイトのポインタ語 (中身は再配置で埋まる)
2. `"abc"` の実体 = 4 バイトの文字列

素朴に書くと，初期化子を読みながら文字列に出会った時点で文字列の実体を
出してしまう。すると `p` の実体はその後ろへずれ，先に確定させた
記号の値 `gval[p]` が文字列の先頭を指す。`p` を読むと文字列の中身が
ポインタとして読める，という壊れ方をする。

そこで **文字列は予約だけして，実体は初期化子を書き終えてから出す**。
予約の時点でローカルシンボルの番号を確保し，`.text` 内オフセット
(`lsoff`) は実体を出す段になってから埋める。再配置は番号を指すので，
オフセットが後で決まっても構わない。

```
int a[] = {1, 2};      -> [1][2]
char *p = "abc";       -> [ptr][a][b][c][\0]
char *n[] = {"x","y"}; -> [ptr][ptr][x][\0][pad][pad][y][\0][pad][pad]
```

この仕組みは関数本体の文字列プール (`spool`) とまったく同じものである。
関数の中の文字列も「本体を出し終えてからまとめて後ろへ置く」ので，
プールをそのまま使い回し，出し方 (再配置の種別) だけを変えている。

| 場所 | 再配置 | 意味 |
|---|---|---|
| 関数本体 | `R_RISCV_HI20` + `R_RISCV_LO12_I` | `lui`+`addi` の 2 語にアドレスを作る |
| 大域初期化子 | `R_RISCV_32` | 1 語にアドレスをそのまま書く |

### 15.3 要素数は初期化子から決まる

`int a[] = {1, 2, 3};` は要素数を初期化子の個数から決める。読み終えて
から `gty` と `gsz` を書き直す。`char s[] = "abc";` は終端の NUL を
含めて 4 バイトになる。

要素数を書いた場合 (`int a[5] = {9, 8};`) は足りない分を 0 で埋め，
多すぎれば領域超過 (6) とする。

多次元配列は **平らに並べる**。`int m[2][3] = {1,2,3,4,5,6};` のように
書き，入れ子の波括弧 `{{1,2,3},{4,5,6}}` は受けない。要素型が配列で
なくなるまで畳んで要素数を掛け合わせれば，あとは 1 次元と同じ処理で済む。
畳んだ場合は型も大きさも宣言で決まっているので，読み終えた後に
書き直してはならない (1 次元で要素数を省略した場合だけ書き直す)。

### 15.4 局所の初期化子は代入である

局所変数の実体は毎回フレーム上に作られるので，初期値は
**宣言のある位置で実行する代入** になる。

- スカラ (`int a = 5;`) は `a = 5;` と同じ IR を出す
- 配列 (`int t[4] = {7, 8};` `char s[6] = "hi";`) は要素ごとの store を
  並べる。書かれていない要素には 0 を書く

宣言の位置で IR を出す以上，**関数の IR を初期化するのは仮引数と局所
宣言を読むより前でなければならない**。第 2 部までは宣言の処理に IR が
関わらなかったので，本体に入る直前で初期化していた。ここで順序が変わる。

### 15.5 初期化子に書けるもの

大域の初期化子は，リンクの時点で値が決まるものに限る。

| 形 | 出力 |
|---|---|
| 定数・負の定数・文字定数・列挙定数 | 型の幅ぶんの語 |
| 文字列リテラル | 予約したローカルシンボルへの `R_RISCV_32` |
| `&g` (大域のアドレス) | その記号への `R_RISCV_32` |
| 配列名・関数名 | 同上 (アドレスへ退化する) |

定数式 (`1 + 2` や `sizeof(int) * 3`) は受けない。式の評価器は IR を
組み立てる作りになっており，初期化子の文脈では IR が使えないためである。
必要になれば定数畳み込み専用の評価器を足すことになる。

`extern int x = 1;` は「他の翻訳単位に実体がある」と「ここに実体を置く」が
両立しないので構文エラー (1) とする。

## 16. 第 3 部の 2 の設計: 可変長引数

### 16.1 いまの引数の受渡し

引数はデータスタック (`x9`) 経由で渡す。`x9` は下へ伸びる。

| 側 | 動作 |
|---|---|
| 呼ぶ側 | 実引数を左から 1 語ずつ積む (`addi x9,x9,-4` + `sw`) |
| 呼ばれた側 | プロローグで後ろから 1 語ずつ取り出し，フレームの `[8]` 以降へ移す |
| 呼ばれた側 | 返却値を 1 語積む |
| 呼ぶ側 | 返却値を 1 語取り出す |

呼ばれた側が取り出す個数は **仮引数の個数** で決まっている。素直に
左から積むと，可変長の呼出しでは余分な実引数が最後に積まれてスタックの
一番上に来る。プロローグはそれを名前つき引数だと思って取り出してしまう。

### 16.2 積む順序を変えるだけで解く

`va_arg` のためにレジスタ渡しの引数をフレームへ書き戻す (register save
area) といった仕掛けは要らない。もともと全部スタック渡しだからである。
必要なのは **可変部と名前つきの並び順** だけで，それは呼ぶ側で決められる。

そこで **可変部を逆順に先に積み，名前つきを後から順に積む**。
名前つきの個数を k，実引数の個数を n とすると

```
積む順:      arg[n-1] ... arg[k]   arg[0] arg[1] ... arg[k-1]
x9 から上へ: arg[k-1] ... arg[0]   arg[k] arg[k+1] ... arg[n-1]
                名前つき (逆順)      可変部 (昇順)
```

呼ばれた側のプロローグは 1 命令も変わらない。名前つきを後ろから
取り出す既存の動きがそのまま正しく，**取り出し終えた時点の `x9` が
可変部の先頭を指す**。あとはその値をどこかに残せばよい。

実引数の *評価* は左から順に行い，`ARG` 命令を出す順序だけを入れ替える。
IR は値を命令番号で指すので，計算と使用の間が離れても構わない
(レジスタ割付けが生存区間に基づいて処理する)。

### 16.3 `va_start` を「隠しローカルからの代入」にする

可変長引数を取る関数には，コンパイラが `__va_ptr` という名前の
ローカル変数 (`char *`) を勝手に 1 個作る。プロローグの末尾で，
名前つきを取り出し終えた `x9` をここへ書く。

利用者から見ると `__va_ptr` はただのローカル変数なので，

```c
#define va_start(ap, last) ((ap) = __va_ptr)
```

で済む。**式の構文をひとつも増やさずに済む** のがこの形の利点である。
`va_arg` も，可変部が 4 バイト単位で昇順に並ぶ以上，

```c
#define va_arg(ap, type) (*(type *)(((ap) += 4) - 4))
```

でよい。進み幅が `sizeof(type)` でなく 4 なのは，可変部へ渡る値が
既定の実引数拡張で `int` まで格上げされ，どの型でも 1 語を占めるため
である。`va_list` は `char *` の `typedef` にすぎない。

これらは `include/stdarg.h` に置く。コンパイラ側は `__va_ptr` を
用意するだけで，`va_start` / `va_arg` を知らない。

### 16.4 余分に積んだぶんは呼んだ側が捨てる

呼ばれた側は名前つきしか取り出さないので，可変部はスタックに残る。
残したまま次の呼出しをすると積み上がり，繰り返すうちに底を突く。

捨てられるのは **個数を知っている呼ぶ側** だけである。返却値を取り出す
`addi x9,x9,4` の即値を `4 + 4 * (n - k)` にすれば，命令は 1 つも
増えない。

このため **可変長関数の呼出しには，呼出しより前に宣言が要る**。
宣言が無いと呼ぶ側は k を知らず，積む順序も捨てる語数も決められない。
個数が判らないまま呼出しを出した後で可変長と判った場合は型エラー (5) と
する。同じ理由で，関数ポインタ経由の呼出しは可変長にできない
(ポインタの型が名前つきの個数を持たない)。

### 16.5 `...` の字句

`.` を読んだ直後にもう 1 つ `.` があれば 3 つ目まで揃っていなければ
ならない。C に `..` という字句は無いので，揃わなければ構文エラー (1)。
`...` の前には名前つき引数が 1 個以上要る (C89 の規則)。

## 17. 第 3 部の 3 の設計: 構造体の値

### 17.1 直すのは「静かに壊れていた」ところ

第 3 部の 2 までの構造体は，**ポインタ経由でしか正しく扱えなかった**。

| 書けるもの | 実際の動き |
|---|---|
| `struct S *p; p->a` | 正しい |
| `struct S g;` (大域) | 正しい |
| `struct S s;` (局所) | 型エラー (5) |
| `struct A { struct B b; };` | 型エラー (5) |
| `a = b;` (構造体どうし) | **先頭 4 バイトだけ複写する** |
| `f(s);` (値渡し) | **先頭 4 バイトだけ積む** |

下の 2 つが問題である。コンパイルは通り，先頭メンバだけ合っていて，
残りが呼出し時のスタックの残骸になる。エラーが出ないぶん，型エラーとして
検出されるより悪い。

### 17.2 構造体の値はアドレスで持ち回る

式の値は 1 語 (レジスタ 1 本) に載るという前提で IR を組んでいる。
構造体はそこに載らない。そこで **構造体型の式の値はその実体のアドレス**
とし，`rv()` で読み出さないことにした。

配列の退化と同じ考え方だが，**型は構造体のままにしておく**。ここが配列と
違う点で，型を保つのはメンバ参照がオフセットを足せるようにするためである。

```
配列:   値 = 先頭要素のアドレス，型 = 要素へのポインタ (退化する)
構造体: 値 = 実体のアドレス，    型 = 構造体のまま     (退化しない)
```

この規則ひとつで，代入も値渡しも「アドレスから語単位で複写する」形に揃う。

### 17.3 複写は IR の段で展開する

複写に専用の命令を足すこともできるが，足すと出力段・dce・レジスタ割付けの
4 箇所を触ることになる (12 章・13 章で 2 度遭遇した落とし穴)。そこで
**IR の段で語ごとの load / store に展開する**。

```
scopy(d, s, n):  for k = 0, 4, 8, ... < n:  st32(d + k, ld32(s + k))
```

構造体の大きさは登録時に 4 の倍数へ丸めてあるので，語の複写だけで足りる。
既存の命令しか使わないので，畳込みも dce もレジスタ割付けもそのまま働く。
代わりに大きな構造体では IR が長くなるので，上限を設けて超えたら
領域超過 (6) とする。

### 17.4 実引数は「語数」で数える

構造体の実引数は `ceil(大きさ/4)` 語を占める。積む順序は **語 0 から順**。
呼ばれた側は後ろから 1 語ずつ取り出してフレームへ移すので，こうすると

```
記憶域:      [語0][語1][語2]
積む順:      語0 -> 語1 -> 語2
x9 から上へ: 語2 語1 語0
取り出し:    語2 が最も高いスロットへ … 語0 が最も低いスロットへ
フレーム:    [語0][語1][語2]     ← 元の並びと一致
```

となり，**仮引数の構造体はふつうの局所の構造体変数と同じ形** になる。
メンバ参照は何も変えずに動き，呼ばれた側のプロローグも 1 命令も変わらない。

このため引数の個数 `cna` は「語数」を数えることにした。呼ぶ側も語数で
数えるので，個数の検査 (プロトタイプとの照合) はそのまま働く。

可変長引数の可変部に構造体は置けない。可変部は逆順に積む (16.2) ので，
語数と実引数の個数がずれると並べ替えられないためである。名前つきの側は
順に積むので置ける。

### 17.5 返却は次の部へ回す

返却値の受渡しも 1 語である。複数語を返すには，呼ばれた側が複数語を積み，
呼んだ側がそれを自分のフレームへ引き取ってからスタックを戻す，という
後始末の変更が要る。引数と違って **呼出し命令の直後に出力段で埋め込む**
必要があり (x9 は IR から触れない)，IR に側情報を持たせることになる。

分量が違うので第 3 部の 4 に分ける。それまでは，返却型が構造体の関数を
**型エラー (5) として拒否する**。拒否せずに通すと先頭メンバ以外が壊れる形で
静かに動いてしまい，17.1 で修正したのと同じ問題を残すことになる。

## 18. 第 3 部の 4 の設計: 構造体の返却

### 18.1 返却もデータスタックで受け渡す

返却値の受渡しはこれまで 1 語だった。構造体は複数語なので，引数と同じく
**データスタックに積んで返す**。

| 側 | 動作 |
|---|---|
| 呼ばれた側 | 語 k-1 … 語 0 の順に積む (語 0 が最後 = x9 に近い側) |
| 呼ばれた側 | 続いて従来どおり 1 語の返却値を積む (中身は使わない) |
| 呼んだ側 | 呼出しの直後に語をフレームの一時領域へ引き取る |
| 呼んだ側 | 1 + k 語ぶん x9 を戻す |

1 語の返却値を残したのは，**呼出し規約をひとつに保つため** である。
これがあるので `c_ret` も呼出し側の受取りも従来の形のままでよく，
構造体の場合だけ引取りと後始末が足される。

### 18.2 引取りは出力段でしか書けない

引数は IR で積める (`ARG` は値を 1 つ取る命令である)。しかし引取りは
IR では書けない。**x9 が IR から触れない** ためである。IR が知っているのは
「フレーム上の位置 (`LADDR`)」と「値番号」だけで，データスタックの上を
読む操作を組み立てる手段がない。

方法は 2 つある。

1. IR に「返却された構造体を引き取る」命令を足す
2. 呼出し命令に側情報を持たせ，出力段が呼出しの直後に複写を出す

**2 を選んだ。** 1 だと出力段・dce・レジスタ割付けの被演算子の表・
レジスタ割付けの値を定義する命令の表の 4 箇所を触ることになり，
12 章・13 章で 2 度遭遇した落とし穴を再び作り込むことになる。

側情報は `iret` (引取り先のフレームオフセット) の 1 つだけで足りる。
語数は呼出し先の記号から返却型が判るので持たなくてよい。0 を「構造体を
返さない」印にできるのは，フレームオフセットが必ず 8 以上だからである。

### 18.3 返却値は左辺値ではない

`mk().x` は取れる。構造体の値はどれも実体のアドレスで表しているので、
メンバはオフセットを足すだけで届く。第 3 部の 3 まで `.` が左辺値を
要求していたのは，構造体の右辺値が存在しなかったからにすぎない。

一方 `mk().x = 5` は C では誤りである。実体は呼んだ側の一時領域なので，
書いても捨てられる。**`elv` (左辺値) だけでは区別できない** —— メンバは
アドレスを持ち，読めるので `elv` は 1 になる。そこで「一時領域にある」
ことを別の印 `erv` で持ち，代入の左辺に来たら型エラー (5) とする。

左辺値かどうかと，アドレスがあるかどうかは別である，という一般則の例に
なっている。

### 18.4 Phase A の完了

これで C89 の言語仕様が揃った。文と式，型と宣言，整数型，関数ポインタと
リンケージ，初期化子，可変長引数，構造体の値と返却 —— [roadmap.md](roadmap.md)
の Phase A はここで終わりである。

ただし「揃った」には 1.3 末尾の表に挙げた残課題 (局所 `static`・`case` の
定数式・初期化子の定数式と入れ子) が含まれない。これらは非目標ではなく
未履行であり，Stage 14 の世代 (cc14b / cc14c / cc14g) で解消した。

残る非目標は 1.3 に挙げたとおり浮動小数点・ビットフィールド・ワイド文字で，
いずれも実行環境か libc の課題として Phase B 以降に属する。

## 19. 補遺: 文字エスケープ

### 19.1 「揃った」の取りこぼし

18 章で C89 の言語仕様が揃ったとしたが，**字句の側に実装漏れが残っていた**。
エスケープが 6 種 (`\n` `\t` `\0` `\\` `\'` `\"`) しかなく，C89 7.1.3 が
定める `\a` `\b` `\f` `\r` `\v` `\?` と，8 進・16 進のエスケープが
無かった。

見つかったのは Stage 11 の libc を書き始めたときである。`isspace` は
空白・改ページ・改行・復帰・水平タブ・垂直タブの 6 種を真とするので，
`\f` `\r` `\v` が要る。**最初の実際の利用で実装漏れが顕在化した** ことになる。

libc 側で `c == 12 || c == 13` と数値で書けば通る。しかしそれは処理系の
実装漏れへの対処を利用側に求めることであり，しかも「なぜ数値なのか」が
読む側に伝わらない。処理系を修正するのが正しい。

### 19.2 消費の責任を移す

数値エスケープは桁数ぶん読み進める。それまでの `escv` は「逆斜線の次の
1 文字」を受け取って値を返すだけで，読取り位置を進めるのは呼ぶ側だった。
この形だと桁数が可変のものを扱えない。

そこで **`escv` 自身が読取り位置を進め，呼ぶ側は進めない** ことにした。
文字リテラルと文字列リテラルの両方が同じ関数を通るので，直すのは一箇所で
済む。

| 綴り | 値 |
|---|---|
| `\a` `\b` `\f` `\r` `\v` `\?` | 7, 8, 12, 13, 11, 63 |
| `\101` | 8 進，最大 3 桁 (`\0` もここで扱う) |
| `\x41` | 16 進，桁数の制限は無く 1 バイトへ切り詰める |

3 文字表記 (trigraph) は入れない。C89 にはあるが実用されておらず，
`\?` を入れたのは綴りの完全性のためである。

### 19.3 考察

**「仕様が揃った」は，仕様書の目次を追うだけでは確かめられない。**
文法 (構文) は章立てで確認できるが，字句の細部は確認しにくい。実際に
使う側のコードを書いて初めて実装漏れが見つかる。Phase B の libc は，
その意味で Stage 10 に対する最初の検査になっている。

## 20. 補遺 2: 配列への単項 `&`

### 20.1 offsetof が配列メンバに適用できない

19 章の直後，Stage 11 の stddef.h でも実装漏れが見つかった。offsetof は

```c
#define offsetof(t, m) ((size_t)&(((t *)0)->m))
```

と書くが，メンバ m が配列だとこの `&` がエラー 5 になる。原因は退化
(11.3) にある。式の中の配列は「先頭要素へのポインタ」へ変換され，変換後の
式は左辺値でなくなる。`&` は左辺値 (と関数) にしか適用できないため，
`&a` が一律にエラーとなっていた。C89 では `&a` は合法で，値は先頭要素の
アドレスと同じ，型が「配列へのポインタ」(`int (*)[4]` など) になる。

配列へのポインタは本実装の型表現でそのまま表せる。配列型は既に基底 1024 番
以降の表として保持しており (11.2)，その 1 段ポインタは
「深さ 1 << 16 | 配列基底」だからである。多次元配列の退化が生成する型と
同じ形式であり，新しい型表現は不要である。

### 20.2 修正: 退化前の配列型を保存する

必要なのは「退化する前の配列型」である。退化は 5 箇所 (局所・大域・
メンバの参照，添字の後，単項 `*` の後) で起きるが，いずれの箇所でも
退化前の型を参照できるため，`esz` (配列全体の大きさ。sizeof が使う) と
並べて **`eaty` へ保存する**。

単項 `&` には分岐を 1 つ追加する。被演算子が退化した配列 (`earr`) の
場合，値はそのまま (配列のアドレスは先頭要素のアドレスに等しい)，型を
`eaty + 65536` に置き換えて返す。

```
&a + 1        配列 1 個ぶん進む   (ポインタ演算の係数 tsize(配列型) が全体の大きさを返す)
sizeof(*&a)   配列全体の大きさ    (間接参照が配列型に戻し，退化が earr / esz を設定する)
```

どちらも既存の処理がそのまま適用される。コード生成規則は変更して
いないので，ブートストラップ 1 段目と正本は一致する。

### 20.3 考察

19.3 と同様である。libc という実際の利用側のコードが，仕様書の目次からは
確認できない実装漏れを順に検出している。offsetof の慣用的な定義
(3.1 [stage011-libc.md](stage011-libc.md)) のような広く使われる書き方は，
言語機能の組合せ (キャスト・メンバ参照・`&`・配列) を一度に使用するため，
検査としての網羅性が高い。
