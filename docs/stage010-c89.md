# Stage 10: C89 言語完成 設計文書

## 1. 目的と位置づけ

### 1.1 目的

Stage 9 までで道具立て (分割コンパイル・リンカ・プリプロセッサ) は揃った。
残るのは言語そのものである。現在の cc が受け付けるのは
[stage005-sc.md](stage005-sc.md) 2 章の sc 言語 —— `int` / `char` /
ポインタ / 1 次元配列 / 構造体，`if` / `while` / `return`,
二項演算と単項 `- ! * &` —— に限られる。

Stage 10 の目的は，これを **C89 の言語仕様** まで引き上げることである。
[roadmap.md](roadmap.md) Phase A の 3 段目であり，これが済めば
「他人の書いた C」を読み始める Phase C の前提が整う。

### 1.2 分割

Stage 10 の作業量は 1 つの変更に収まらない。依存関係で分ける。

| 部 | 内容 |
|---|---|
| 第 1 部 | 文と式: `for` `do` `switch`/`case`/`default` `break` `continue` `goto`/ラベル，`?:`，複合代入，`++`/`--`，カンマ演算子，`sizeof`，キャスト |
| 第 2 部の 1 | 型 (前半): `typedef`，`enum`，`union`，`const`/`volatile`，`void`，識別子の大文字 |
| 第 2 部の 2 | 宣言: 関数プロトタイプ，`extern`，`static` (受理のみ)，ブロック内宣言 |
| 第 2 部の 3 | 識別子と配列: 識別子長 31，多次元配列 |
| 第 2 部の 4 | 整数型と関数ポインタ: `unsigned`/`signed`/`short`/`long`，関数ポインタ，`static` のリンケージ |
| 第 3 部 | 初期化子 (`.data` セクション)，可変長引数 (`stdarg` 相当)，構造体の値渡し・返却 |

第 2 部を割ったのは，**どこまで踏み込むか** で線が引けるからである。
第 2 部の 1 (9 章) は宣言の構文と字句だけを広げ，コード生成規則を変えない。
第 2 部の 2 (10 章) は宣言の形を広げ，フレームの割付け方だけを変える。
第 2 部の 3 (11 章) は字句と型表現を広げるが，コード生成規則は変えない。
第 2 部の 4 は整数型の幅と符号が入るため，ロード・ストアの幅選択や
除算・シフト・比較の符号つき / 符号なしの選択が必要になり，
コード生成規則そのものが変わる。

第 1 部を先に置く理由は 2 つある。

1. **自己完結している。** 構文解析と IR 構築だけで閉じ，ABI にも
   オブジェクト形式にも触れない。第 2 部の 2 の型システム変更や第 3 部の
   `.data` 追加に比べて影響範囲が狭く，独立に検証できる
2. **後続が書きやすくなる。** 第 2 部・第 3 部のコンパイラは第 1 部の
   コンパイラでビルドされる。つまり第 1 部が済んだ時点から
   `for` / `switch` / `break` / `++` / 複合代入を使ってコンパイラ自身を
   書けるようになる。sc の制約 (途中脱出はフラグ，添字は `i = i + 1`) の
   下で型システムを書くのは苦しい

**本文書の 3〜7 章は第 1 部，9 章は第 2 部の 1，10 章は第 2 部の 2，
11 章は第 2 部の 3 の設計である。** 残りは着手時に追記する。

### 1.3 非目標 (Stage 10 全体を通して)

- 浮動小数点 (`float` / `double`)。C89 の一部だが，実行環境が RV32I**M** で
  FPU を持たず，ソフトウェア浮動小数点の実装は Stage 11 の libc の課題である
- ビットフィールド
- `volatile` の意味論 (構文としては受け付けるが最適化の抑止は行わない)
- ワイド文字 (`wchar_t` / `L"..."`)
- C99 以降の機能

## 2. ブートストラップと命名の約束

### 2.1 世代の呼び分け

Stage 10 のコンパイラは Stage 8 の `cc` の後継である。ソースは
`stage008/cc.sc` を出発点とする新しいファイル `stage010/cc.sc` とする。
前段のソースを凍結しておかないと，チェーンを hex0 から再現できなくなるため
既存ファイルには手を入れない ([plan.md](plan.md) 2.1)。

同じ名前の道具が 2 世代あるので，生成物の名前で呼び分ける。

| 生成物 | 由来 | 位置づけ |
|---|---|---|
| `tmp/build/cc8.bin` | stage008/cc.sc | Stage 8 の C コンパイラ。Stage 9 と Stage 10 のブートストラップに使う |
| `tmp/build/cc10a.bin` | stage010/cc.sc | 第 1 部 (文と式) |
| `tmp/build/cc10b.bin` | stage010/cc2.sc | 第 2 部の 1 (型) |
| `tmp/build/cc10c.bin` | stage010/cc3.sc | 第 2 部の 2 (宣言) |
| `tmp/build/cc10d.bin` | stage010/cc4.sc | 第 2 部の 3 (識別子と配列) |
| `tmp/build/cc.bin` | — | **現行の C コンパイラ**。最新世代の別名 (複製) |

各部のソースは凍結し，次の部はその 1 つ前の部のコンパイラでビルドする。

```
cc8   -> cc10a0 -> cc10a      (第 1 部。cc10a0 == cc10a)
cc10a -> cc10b                (第 2 部の 1)
cc10b -> cc10c0 -> cc10c      (第 2 部の 2)
cc10c -> cc10d0 -> cc10d      (第 2 部の 3。cc10d0 == cc10d)
```

こうすると，各段が次の段を書きやすくする。第 2 部のソースは第 1 部で
実装した `for` / `switch` / `++` / 複合代入を使って書けるし，第 3 部の
ソースは第 2 部の `typedef` / `enum` / `union` を使って書ける。

Stage 9 の `pp.bin` は従来どおり `cc8.bin` でビルドする。各 Stage の成果物は
前段の成果物のみでビルドするという約束を守るためで，`pp.bin` の SHA-256 は
Stage 10 の前後で変わらない。

### 2.2 記述言語の制約

`stage010/cc.sc` は **cc8 がコンパイルできる範囲**，すなわち sc 言語で書く。
自分が実装する機能を自分の記述には使えない。これはブートストラップの
常であり，Stage 6 (scc)・Stage 7 (occ) でも同じだった。

```
cc8(stage010/cc.sc)  -> cc10a0.bin          # ブートストラップ 1 段目
cc10a0(stage010/cc.sc) -> cc10a.bin         # 正本
cc10a(stage010/cc.sc)  -> ... == cc10a.bin  # 固定点 (B2 == B3)
```

なお cc10a0 と cc10a は「同じソースを異なるコンパイラでコンパイルしたもの」で
あり，コード生成を変えていなければバイト単位で一致する。第 1 部は
コード生成規則を変えないので **cc10a0.bin == cc10a.bin** が成り立つ。これは
セルフホストの健全性を示す強い検査になるので，テストに含める。

各部のソースはその部のコンパイラを前提に書く。第 1 部の `cc.sc` は cc8 が
コンパイルできる範囲 (sc 言語) で，第 2 部の `cc2.sc` は cc10a が
コンパイルできる範囲で書く。自分が実装する機能を自分の記述には使えない，
というのはブートストラップの常である。

## 3. 第 1 部の設計: 文

### 3.1 反復と分岐の飛び先

IR は既にラベルと `jmp` / `bz` / `bnz` を持ち，飛び先はラベル番号で表す
(実アドレスの解決は出力段の仕事)。したがって新しい制御構造の追加は
「どのラベルをどの順で置くか」を決めるだけで済み，IR にも出力段にも
変更は要らない。

#### `for (init; cond; step) body`

```
        init
   L0:  cond -> bz L2
        body
   L1:  step                (continue の飛び先)
        jmp L0
   L2:                      (break の飛び先)
```

`cond` の省略は「常に真」とする (`bz` を出さない)。`init` と `step` の
省略はその位置に何も出さない。

#### `do body while (cond);`

```
   L0:  body
   L1:  cond -> bnz L0      (continue の飛び先)
   L2:                      (break の飛び先)
```

#### `while (cond) body`

既存の形に `continue` の飛び先 (条件評価の直前) と `break` の飛び先
(ループの直後) を加えるだけである。

### 3.2 `break` / `continue`

飛び先はスタックで持つ。`break` は反復と `switch` の両方が受けるが，
`continue` は反復だけが受ける。そこで **2 本のスタックに分ける**。

```
brkl[]  break の飛び先ラベル   … while / do / for / switch が積む
conl[]  continue の飛び先ラベル … while / do / for が積む
```

`switch` の中の `continue` が外側のループへ抜けるのは，`switch` が
`conl` を積まないことで自然に実現される。

対応する構文の外に置かれた `break` / `continue` はエラー 1 とする。

### 3.3 `switch` / `case` / `default`

単一走査で組み立てるため，**本体を先に，振分けを後に** 出す。

```
        v = cond
        v を隠しスロット s へ格納
        jmp Ldisp
        body                 … case K: は「ラベル Lk を置き (K, Lk) を控える」
                               default: は「ラベル Ld を置き Ld を控える」
        jmp Lend
  Ldisp:                     … 控えた組を順に照合する
        s を読み，K と比較 -> bnz Lk     (控えた数だけ繰り返す)
        jmp Ld               … default があれば
  Lend:                      (break の飛び先)
```

こうすると，本体を読み終える前に `case` の一覧を知る必要がない。
`switch` の値を隠しスロットに置くのは，`&&` / `||` / `?:` と同じ理由で
ある (この IR は値を「定義した命令番号」で指すので，本体を跨いで
レジスタ上の値を生かしておけない)。

`case` のラベルは整数定数と文字定数 (先頭の `-` を許す) に限る。
`enum` 定数や定数式は第 2 部の 2 で定数式の評価と一緒に扱う。
フォールスルーは C と同じく既定の動作である (`case` は単なるラベル)。

### 3.4 `goto` とラベル

関数ごとにラベル表を持つ。

| 配列 | 内容 |
|---|---|
| `glname` | ラベル名 (16 バイトスロット) |
| `gllab` | 対応する IR ラベル番号 |
| `gldef` | 1 = 定義済み (`名前:` が現れた) |

`goto` が先に現れた場合は未定義のまま登録し，`名前:` が現れた時点で
定義済みにする。関数の終わりで未定義のラベルが残っていればエラー 2 とする。

文の位置で識別子が現れたとき，それがラベルなのか式の始まりなのかは
1 トークン先読みしないと判らない (`x:` と `x = 1`)。字句解析器は
1 トークン先読みしか持たないので，**読取り位置とトークンを退避して
読み直す** 方式を採る (`lsave` / `lrest`)。入力全体が `src` にあるので
巻き戻しは位置の代入だけで済む。

## 4. 第 1 部の設計: 式

### 4.1 優先順位の更新

```
15: ,                      カンマ演算子 (左結合)
14: = += -= *= /= %= &= |= ^= <<= >>=   代入 (右結合)
13: ?:                     条件演算子 (右結合)
12〜3: || && | ^ & ==/!= 関係 シフト +/- */%      (既存)
2: 単項 - ! * & ++ -- sizeof (型)キャスト
1: 後置 [] () . -> ++ --
```

C の文法どおり，**関数呼出しの実引数は代入式** (カンマ演算子を含まない)
とする。これに伴い既存の `expr()` を `assign()` に改名し，カンマ演算子を
扱う新しい `expr()` を最上位に置く。

### 4.2 複合代入と `++` / `--`

左辺は **一度だけ** 評価しなければならない (`*p++ += 1`)。
この IR は左辺値をアドレスの値番号で持つので，同じ値番号を
2 度参照すれば「一度だけ評価して 2 回使う」が自然に書ける。

```
a op= b   ->   addr = 左辺 (左辺値)
               cur  = load addr
               r    = 右辺
               res  = cur op r
               store addr, res
               値は res
```

`++` / `--` は `+= 1` / `-= 1` と同じ形で，後置は `cur` を，前置は `res` を
式の値とする。ポインタに対しては指し先の大きさでスケールする
(`+=` `-=` `++` `--` のみ。他の複合代入をポインタに適用するのはエラー 5)。

### 4.3 `?:`

`&&` / `||` と同じく隠しスロットを使う。

```
        cond -> bz L1
        then を評価してスロットへ格納
        jmp L2
   L1:  else を評価してスロットへ格納
   L2:  スロットを読む
```

結果の型は then 側の型とする (C の通常の算術変換・ポインタの合成は
第 2 部の 2 の型システムと合わせて扱う)。

### 4.4 `sizeof`

`sizeof (型)` と `sizeof 単項式` の両方を受ける。`(` の次が型名かどうかで
判別するため，ここでも `lsave` / `lrest` で 1 トークン先を覗く。

式形式では **コードを出してはならない** (C は被演算子を評価しない)。
IR は配列と個数で持っているので，解析前に `icnt` などを控えておき，
型を得た後に巻き戻す。

配列に対する `sizeof` が配列全体の大きさを返すよう，記号表に
バイト数を持たせる (`lsz` / `gsz` / `msz`)。式が配列オブジェクトを
指しているかは `earr` で伝える。`earr` は一次式で立ち，演算子を通ると
落ちる (配列は式の中でポインタへ退化するため)。

### 4.5 キャスト

`( 型 ) 単項式`。すべての値が 32 bit セルであり，`char` へのキャストも
値を切り詰めない現状では，キャストは **型の付け替え** だけを行う。
生成されるコードは無い。第 2 部の 2 で `unsigned` と幅の異なる整数型が
入った時点で，切詰めと符号拡張をここに足す。

## 9. 第 2 部の 1 の設計: 型

### 9.1 型を増やさずに済むもの

`enum` と `typedef` は，一見すると型システムの拡張に見えるが，
**型を増やす必要がない**。

- `enum` の定数は「名前 -> 値」の対応にすぎず，型は `int` である。
  タグ (`enum color` の `color`) は型の区別を生まないので，読み捨ててよい
- `typedef` は「名前 -> 既存の型」の対応にすぎない

したがってどちらも表を 1 つ足すだけで済む。既存の型表現
(`ポインタの深さ << 16 | 基底`) には手を触れない。

### 9.2 `union` は構造体表を共有する

`struct` と `union` の違いはメンバの配置だけで，参照する側の扱いは同じで
ある (`.` と `->` はオフセットを足すだけ)。そこで同じ表に入れ，
`sunion` フラグで配置を分ける。

| | メンバの位置 | 全体の大きさ |
|---|---|---|
| `struct` | 直前の末尾を整列した位置 | 最後のメンバの末尾 (4 の倍数へ切り上げ) |
| `union` | すべて 0 | メンバの最大値 (同上) |

タグの名前空間も共有する。`struct s` と `union s` を同時に定義することは
できないが，実害は小さい。

### 9.3 `typedef` 名は構文を文脈依存にする

`x * y;` が宣言なのか式なのかは，`x` が `typedef` 名かどうかで決まる。
C の構文が文脈自由でない有名な箇所で，字句だけでは判断できない。
本実装では `istype()` が `typedef` 表を引いて決める。この判定は

- 局所宣言の並びの終わり (`while (istype()) plocal();`)
- キャストと括弧式の見分け (`( 型 )` か `( 式 )` か)
- `sizeof (型)` と `sizeof (式)` の見分け

の 3 箇所で使う。

### 9.4 無名の `struct` / `union`

`typedef struct { ... } T;` は実際の C で頻出する。タグが無いだけで
構造は同じなので，**内部で `$0` `$1` … というタグを振る**。先頭を `$` に
すると識別子の字句規則では作れない名前になるので，利用者の書いたタグと
衝突しない。

### 9.5 識別子の大文字

sc の識別子は英小文字と `_` に限っていた。しかし `enum` 定数も
`typedef` 名も大文字が慣習であり，取り込む外部の C も大文字を使う。
ここで解除する。予約語はすべて小文字なので，大文字を許しても衝突しない。

識別子の長さの上限 (15 バイト) は据え置く。C89 は内部識別子について
31 文字を要求しており，記号表のスロットを 16 バイトから 32 バイトへ
広げる必要がある。字句と記号表の両方に触れるので第 2 部の 2 で扱う。

## 10. 第 2 部の 2 の設計: 宣言

### 10.1 ヘッダを「宣言を共有する場所」にする

Stage 9 の申し送り ([stage009-pp.md](stage009-pp.md) 7 章) はここで解消する。
`#include` はあってもヘッダに書けるのはマクロと型定義だけだった。関数の
宣言 (プロトタイプ) と変数の宣言 (`extern`) が入って初めて，ヘッダが
本来の役割を果たす。

```c
/* util.h */
extern int shared;
int addup(int a, int b);
```

### 10.2 プロトタイプと定義の見分け

仮引数を読み終えた時点で `;` ならプロトタイプ，`{` なら定義である。
1 トークン先読みは要らない。プロトタイプは引数の個数と返却型だけを控え，
記号は未定義のままにしておく。

- 仮引数の名前は省略できる (`int f(int, char *);`)
- `(void)` は「引数なし」の明示である。`(void *p)` と紛らわしいので
  1 トークン先を覗いて見分ける
- プロトタイプの後に定義が来たとき，引数の個数が違えばエラー 5

### 10.3 `extern`

変数の `extern` 宣言では `.bss` を取らない。未定義シンボルとして出し，
リンカが他の翻訳単位の定義へ解決する。参照は既存の HI20 / LO12 再配置
そのままで，コンパイラ側に新しい仕掛けは要らない。

先に `extern` で宣言してから同じ翻訳単位で定義するのも正しい。記号を
探して未定義なら「定義への昇格」として扱う。

### 10.4 `static` は受理するにとどめる

`static` を本当に実装するには，ELF のローカルシンボルとして出し，リンカが
翻訳単位内で解決する必要がある。リンカは Stage 8 で凍結してあるので，
ここでは **受理して読み飛ばす** にとどめ，記号は大域のまま出す。

したがって 2 つの翻訳単位が同じ名前の `static` 関数を持つと，リンカが
多重定義とみなす。局所の `static` 変数 (記憶域が静的になるもの) は
意味が変わってしまうので，黙って自動変数として扱わず構文エラーとする。
本当のリンケージは第 2 部の 3 でリンカと合わせて扱う。

### 10.5 ブロック内宣言とフレームの割付け

隠しスロット (`&&` / `||` / `?:` / `switch` が使う) は，局所変数領域の
直後から取っていた。ブロック内宣言があると本体の解析中に局所変数が
増えるので，この 2 つが同じ領域を奪い合う。

そこで **隠しスロットも局所変数と同じ割付けポインタから取る**。
どちらも「フレーム上の 1 語」であり，区別する理由はもともと無かった。

複文を抜けると割付けポインタを戻すので，兄弟の複文は同じ領域を使い回す。
ただしフレームの大きさは戻した後の値ではなく **最大値** で決まるので，
高水位標 (`cmax`) を別に持つ。

この変更で，関数によってはフレームの大きさが前世代と数語異なる。
IR の命令種別・ABI・出力形式は変えていないが，**ブートストラップ 1 段目と
正本は一致しない**。正本が自分自身を再生成する固定点 (B2 == B3) は
従来どおり成り立つ。

## 11. 第 2 部の 3 の設計: 識別子と配列

### 11.1 識別子の長さ

C89 は内部識別子について 31 文字を有効とすることを要求している。
記号表の名前スロットを 16 バイトから 32 バイトへ広げる。字句解析器の
上限と，名前を複写する箇所と，スロットの添字計算がすべて連動する。

コード生成には一切影響しないので，ブートストラップ 1 段目と正本が
一致することでその点を確かめられる。

### 11.2 配列型

これまでの型は「ポインタの深さ << 16 | 基底」という平坦な表現で，
基底は `char` / `int` / 構造体 / `void` しか無かった。1 次元配列は
「配列かどうか」の旗と大きさを記号表に持たせるだけで済んでいたが，
多次元配列は **型から型を作る** ので平坦には表せない。

基底の 1024 番以降を配列型の表の添字に割り当て，要素型と要素数を持たせる。
`int a[3][4]` の型は `array(3, array(4, int))` になる。宣言子の `[n]` は
再帰で読むと自然にこの順で組み立てられる。

```
pdims(b): '[' が無ければ b。あれば n を読み，atype(pdims(b), n) を返す
```

### 11.3 退化 (decay)

配列は式の中では常に「先頭要素へのポインタ」になる。要素がさらに配列なら
「配列へのポインタ」になり，添字を 1 つ進めるたびに 1 段ずつ剥がれる。

| 式 | 型 |
|---|---|
| `a` | `int (*)[4]` |
| `a[i]` | `int *` |
| `a[i][j]` | `int` (左辺値) |

添字の計算はもともと「要素の大きさで掛ける」形なので，要素が配列でも
そのまま働く。`a[i]` は `a + i * 16` になる。

退化が起きるのは 3 箇所 —— 識別子・メンバの参照，添字の後，単項 `*` の後。
仮引数の配列も宣言の時点でポインタへ退化させる (C の規則)。

### 11.4 大きさの切り上げ

`sizeof` が正しい値を返すよう，記号表の大きさは **本当の大きさ** を持つ。
4 バイト境界への切り上げは `.bss` とフレームの割付けのときだけ行う。
`char cm[2][5]` の `sizeof` は 10 であって 12 ではない。

## 12. 第 2 部の 4・第 3 部への接続

第 2 部の 3 を終えた時点で，識別子の長さと多次元配列が C89 に追いついた。
残るのは

- **整数型の幅と符号** (`unsigned` / `signed` / `short` / `long`)。
  ロード・ストアの幅選択と，除算・シフト・比較の符号つき / 符号なしの
  選択が要る。**コード生成規則が変わる最初の変更になる**
- **関数ポインタ**。配列型と同じく型の表を足すが，呼出しの側も
  「記号番号ではなく値を呼ぶ」形が要るので IR に手が入る
- **`static` の本当のリンケージ**。ELF のローカルシンボルとして出し，
  リンカが翻訳単位内で解決する。リンカ側の変更を伴う

である。これが第 2 部の 4 になる。
