# 中期計画 (Stage 8 以降)

[plan.md](plan.md) の段階計画 (Stage 0〜7) は完了した。本書はその先，
**既存の C 資産をコンパイルできる処理系** へ到達するための中期計画である。

長期目標は 2 つ:

- **L1**: GCC 自体をコンパイルできること
- **L2**: Linux カーネルをコンパイルできること

## 1. 現在地と目標の差

Stage 7 の occ は「自分自身を書ける」水準であって，「他人の書いた C を読める」
水準ではない。差は言語機能だけではなく，道具立てと実行環境の全域にわたる。

| 領域 | 現状 (occ) | 既存資産のビルドに必要なもの |
|---|---|---|
| 翻訳単位 | 1 本のみ。出力はフラットバイナリ | 分割コンパイル，オブジェクトファイル，リンカ，アーカイブ (ar) |
| プリプロセッサ | なし | `#include` `#define` (関数形式マクロ含む) `#if` 系，`#pragma` の無視 |
| 型 | int, char, ポインタ, 1 次元配列, 構造体 | unsigned/signed, short/long/long long, enum, union, typedef, const/volatile, 関数ポインタ, 多次元配列, ビットフィールド, (浮動小数点) |
| 式・文 | 二項/単項演算, if/else, while, return | for, do-while, switch/case, break, continue, goto, 三項演算子, 複合代入, ++/--, カンマ演算子, sizeof, キャスト, 初期化子 |
| 関数 | 固定個数の引数，値は 1 語 | 可変長引数, 構造体の値渡し・返却, 関数プロトタイプ, static/extern リンケージ |
| ライブラリ | なし (getc/putc/exit のみ) | freestanding libc (string, stdlib) → hosted libc (stdio, ファイル I/O) |
| 実行環境 | ベアメタル QEMU virt，UART のみ | ファイルシステム，プロセス，環境変数。すなわち OS |
| ビルド駆動 | sh スクリプト (ホスト側) | 自立した make / シェル / ar |
| 互換性 | 独自 ABI，独自バイナリ形式 | ELF，System V ABI，GNU C 拡張 |

## 2. 戦略上の分岐点 (先に共有すべき問題)

### 2.1 GCC と RISC-V のバージョン断絶

L1 には構造的な障害がある。

- GCC の RISC-V バックエンドが入ったのは **GCC 7** (2017) である
- GCC が実装言語を C++ へ移したのは **GCC 4.8** 以降である
  (C コンパイラだけでビルドできる最後の版は **GCC 4.7.4**)

つまり **「C だけでビルドでき，かつ RISC-V を扱える GCC」は存在しない**。
L1 に到達するには次のいずれかを選ぶ必要がある。

| 案 | 内容 | 規模 | 得失 |
|---|---|---|---|
| A | C++ サブセット処理系を作り GCC 7 系をビルドする | 特大 | RISC-V を維持できる。C++ は C より桁違いに大きい |
| B | x86-64 バックエンドを追加し，GCC 4.7 → 新しい GCC と登る | 大 | 実績のある経路。ただし RISC-V が主対象でなくなる |
| C | GCC 4.7 に RISC-V バックエンドを自作して載せる | 大 | GCC 本体の fork を保守することになる |

**この判断は Phase C (Stage 14 以降) まで保留してよい。** Stage 8〜13 で行う
作業 (リンカ・プリプロセッサ・C 言語完成・libc・実行環境) はどの案でも
等しく必要であり，クリティカルパスは共通だからである。分岐点に到達した時点で，
その時の実装体力を見て決める。

### 2.2 実行環境をどうするか

GCC のビルドには数千のファイルの読み書き，数百 MB のメモリ，プロセス起動が要る。
UART しかないベアメタルでは成立しない。選択肢は 2 つ。

- **案 X**: Linux ユーザランドを実行環境とする (syscall を叩く側になる)。
  現実的で，L2 の「Linux をビルドする」とも整合する
- **案 Y**: 自前の OS を作る。プロジェクトの純度は保たれるが，
  ファイルシステム・プロセス・メモリ管理を自作することになり L1 が遠のく

**案 Y に決定した** ([stage012-os.md](stage012-os.md) 2 章)。L1 / L2 は
処理系を鍛えるベンチマーク指標としての目標であり，外部のソースや生成物を
stone の世代成果物 (実行環境を含む) に混ぜないことを優先する。自作の
簡易 OS と POSIX 風環境を作り，ホストとのファイル交換は QEMU 起動時の
イメージ注入 (memory-backend-file) で行う。syscall ABI は RV32 Linux
互換とし，L2 への経路 (同じバイナリが実 Linux でも動くこと) は保つ。
ベアメタル環境と既存 Stage の生成物は凍結して残す。

### 2.3 純度ポリシーの扱い

[plan.md](plan.md) 2.1 は「既存の as / ld を使わない」と定めている。
本計画はこれを維持する。ただし Phase C 以降で外部のソース (tcc, GCC, Linux) を
**入力として** 読むことは，ポリシー上の「既存成果物の流用」には当たらない。
それらをビルドできることこそが目標だからである。区別を明確にしておく:

- ビルド経路に他者のバイナリ・ツールを差し込むことは，引き続き禁止する
- 他者のソースコードを我々の処理系への入力として与えることは，目標そのものである

## 3. 段階計画

### Phase A: 言語と道具立ての近代化 (Stage 8〜10)

現状の処理系を「普通の C コンパイラ」に引き上げる。

| Stage | 成果物 | 完了条件 |
|---|---|---|
| 8 | ELF リロケータブルオブジェクト出力 + リンカ (ld) | 複数の翻訳単位に分割したプログラムが，個別コンパイル → リンクで動作する。自身も分割ビルドで固定点を維持する |
| 9 | プリプロセッサ (pp) | `#include` `#define` (関数形式マクロ・可変長マクロ) `#if/#ifdef/#elif/#else/#endif` `#undef` `##` `#` が動作し，ヘッダを共有した分割ソースがビルドできる |
| 10 | C89 言語完成 | 型 (unsigned/short/long/enum/union/typedef/関数ポインタ/多次元配列)・文 (for/do/switch/break/continue/goto)・式 (三項/複合代入/++/--/sizeof/キャスト)・初期化子・可変長引数・構造体の値渡しを実装し，C89 の言語仕様に対するテストスイートが通る |

### Phase B: 自立した開発環境 (Stage 11〜13)

処理系が自身の実行環境と開発道具を自前で備えるようにする。

| Stage | 成果物 | 完了条件 |
|---|---|---|
| 11 | freestanding libc | string.h / stdlib.h 相当 (memcpy, strlen, malloc, qsort 等) を自作の C で実装し，静的リンクで使える |
| 12 | 実行環境の移行 (syscall 層) | 2.2 の案を決定し，ファイル I/O・メモリ確保・プロセス終了を syscall 経由で行えるようにする。stdio.h 相当が動く |
| 13 | ビルド道具立て | ar (アーカイブ)，make 相当，シェル相当を自作し，ホスト側の sh スクリプトなしでチェーン全体を再ビルドできる |

### Phase C: 外部資産の取り込み (Stage 14〜16)

「他人の C」を読み始める。ここまでの各段階は自作コードのみを入力にしてきたので，
現実の C との差 (未実装の拡張・想定外の書き方) がここで一気に露呈する。
小さいものから順に当てて潰す。

| Stage | 成果物 | 完了条件 |
|---|---|---|
| 14 | 外部の小規模 C プログラムのビルド | 無改変の外部ソース (例: bzip2, sqlite3 のような単一ファイル規模) をビルドし，正しく動作する |
| 15 | tcc のセルフホスト | tcc (C99, 自己ホスト可能) を我々の処理系でビルドし，その tcc が自分自身をビルドできる |
| 16 | GCC | 2.1 の案を決定・実行し，GCC をビルドする (**L1**) |

### Phase D: Linux (Stage 17 以降)

| Stage | 成果物 | 完了条件 |
|---|---|---|
| 17 | GNU C 拡張の実装 | inline asm, `__attribute__`, statement expression, builtin 群など，カーネルが要求する拡張に対応する |
| 18 | Linux カーネルのビルド | カーネルをビルドし，QEMU 上で起動する (**L2**) |

## 4. 進め方の原則

前半 7 段で確立した以下の作法は，Stage 8 以降も維持する。

- **各 Stage の成果物は前段の成果物のみでビルドする。** 純度ポリシーを保つ
- **各 Stage に設計文書を残す** (`docs/stageNNN-*.md`)
- **固定点検証を維持する。** セルフホスト以降，コード生成を変えるたびに
  `B2 == B3` を確認する ([stage006-scc.md](stage006-scc.md) 1.2)
- **SHA-256 をビルド再現の基準とし，CI がコンテナ上で照合する**
- 手順・落とし穴は [dev-notes.md](dev-notes.md) に追記する

規模が大きくなるため，1 Stage が 1 PR に収まらない場合は
「設計文書 → 実装 → テスト」を分けて出す。

## 5. 現実的な見通し

Stage 8〜10 (Phase A) は，やることが明確で見通しが立つ。
Stage 11〜13 (Phase B) は実行環境の決定 (2.2) が支配的で，そこで規模が変わる。
Phase C 以降は「未知の C との遭遇」が主戦場になり，見積りの精度は落ちる。

L1 (GCC) と L2 (Linux) は，ここから見れば遠い。しかし途中の各段階
(リンカ・プリプロセッサ・C89 完成・libc) はそれぞれ単独で意味のある到達点であり，
順に積めば必ず近づく性質の目標である。

Stage 10 は 7 つに分ける。第 1 部が文と式，第 2 部の 1 が型
(`typedef` / `enum` / `union` / `const` / `void`)，第 2 部の 2 が宣言
(プロトタイプ・`extern`・ブロック内宣言)，第 2 部の 3 が識別子長 31 と
多次元配列，第 2 部の 4 が整数型の幅と符号，第 2 部の 5 が関数ポインタと
`static` のリンケージ，第 3 部が初期化子・可変長引数・構造体の値渡しである。
第 3 部の 4 (構造体の返却) をもって Stage 10 は完了し，**Phase A が終わった**。
次は Phase B (Stage 11 フリースタンディング libc，Stage 12 実行環境，Stage 13 ビルド道具) である。
Stage 11 の設計は [stage011-libc.md](stage011-libc.md)。着手時に文字エスケープの
実装漏れが見つかったため，Stage 10 に補遺 (19 章 / cc10k) を追加してから進めた。
第 1 部の着手時には，さらに配列への単項 `&` が未実装である (offsetof を配列
メンバに適用できない) ことが判明し，補遺 2 (20 章 / cc10l) を追加した。
第 1 部はこれらの修正を経て完了した。
第 2 部 (記憶域: malloc / free / calloc / realloc) は，ヒープを `.bss` 上の
固定領域に置く K&R 型のフリーリストとして完了した (7 章)。供給源は内部関数
morecore に集約してあり，Stage 12 で brk へ差し替える。
第 3 部 (整列と探索・数値変換: qsort / bsearch / atoi / strtol / abs / div)
も完了し (8 章)，**Stage 11 は完了した**。OS を要さない範囲の標準ライブラリが
揃った。
Stage 12 は設計を終えた ([stage012-os.md](stage012-os.md))。実行環境は
案 Y (自作の簡易 OS + POSIX 風環境) に決定した。カーネルは M モード，
ユーザプロセスは U モードの ELF 実行形式で，syscall ABI は RV32 Linux
互換。ホストとのファイル交換は memory-backend-file による sfs イメージの
注入で行う。cc と言語・ABI は変えず，特権命令と ecall の実体はリンカの
新世代 (ld12) の前置部に閉じる。libc は純粋部と環境部に分ける。
第 1 部 (共有領域と sfs) は完了した: sfs のバイト配置を確定し
(stage012-os.md 4.3)，ホスト側の変換道具 (tools/sfs.sh) と
memory-backend-file による注入・回収 (tools/run-qemu.sh の
STONE_QEMU_RAMFILE) を実装，ベアメタルのゲストプログラムによる
読み書きまで検証した。
第 2 部 (ld12 とカーネル) も完了した: リンカの新世代 ld12 が 'F' (従来)・
'K' (カーネル)・'E' (ELF 実行形式) の 3 形式を出し，自作 C で書いた
カーネルが sfs から ELF を読んで U モードで走らせ，syscall を処理する。
'F' の出力は stage008 の ld とバイト一致し，既存 Stage は影響を受けない。
第 3 部 (libc 環境部) も完了した: 生の syscall スタブ (sys_*) を POSIX の
名前で包んで errno を導入し，malloc の供給源 (morecore) を翻訳単位ごと
差し替えられるようにした。OS の上で純粋部 (string / stdlib) が無改変で
動き，malloc がベアメタルの固定領域 1 MiB を超えて 3 MB を確保できる。
次は第 4 部 (stdio: FILE / fopen 系 / printf 最小) である。
