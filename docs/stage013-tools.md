# Stage 13: ビルド道具立て 設計文書

## 1. 目的と位置づけ

### 1.1 目的

Stage 12 で「ファイルを開き，読み書きし，引数を受け取り，終了コードを
返す」コマンドが OS の上で書けるようになった
([stage012-os.md](stage012-os.md) 9 章)。しかしコマンドを **起動する**
手段はまだ無い。起動できるのは sfs 内の固定名 `boot` に書いた 1 本だけで，
複数のコマンドを続けて走らせるにはホスト側で QEMU を起動し直すしかない。

Stage 13 の目的は **ゲスト内で開発が完結する道具立てを揃える** ことである。

- プログラムからのプログラム起動 (spawn)。シェルとビルド駆動の前提
- シェル相当。コマンド行の解釈と入出力のつなぎ替え (リダイレクト)
- テキストエディタ。ゲスト内でソースを直す手段
- cc / ld / pp の OS 側への移住。ホスト側の sh スクリプトなしで
  チェーン全体を再ビルドできるようにする

[roadmap.md](roadmap.md) Phase B の最終段である。

### 1.2 非目標

- マルチタスク・並行実行。プロセスは引き続き一度に 1 つで，起動は
  「子の終わりを待つ」逐次実行に限る (パイプは作らない。中間結果は
  ファイルで受け渡す)
- アドレス変換。子の実行中，親の像は退避領域へ複写して守る (3.2)
- 環境変数・カレントディレクトリ。名前空間はフラットのまま
  ([stage012-os.md](stage012-os.md) 4.2)
- 対話編集 (スクリーンエディタ)。エディタは ed 風の行エディタから始める
- ベアメタル環境と既存 Stage の生成物・テストは一切変えない (凍結。
  [artifacts.md](artifacts.md))

## 3. 第 1 部: spawn とシェル

### 3.1 syscall の増設は前置部を変えずに済ませる (sys_ecall)

Stage 12 の 'E' 前置部は syscall ごとに専用スタブ (sys_read / sys_write /
sys_openat / sys_close / sys_brk) を機械語で持つ
([stage012-os.md](stage012-os.md) 6.3)。この形のまま syscall を足すと，
**足すたびにリンカの新世代が要る**。それは避けたい。

そこでリンカの新世代 ld13 の 'E' 前置部に **汎用スタブを 1 本だけ** 足す。

```
int sys_ecall(int n, int a, int b, int c);   /* a7=n, a0..a2=a,b,c で ecall */
```

以降の syscall の増設は libc の環境部 (C で書ける層) が sys_ecall を包む
だけで済み，前置部 (機械語) は二度と変えなくてよい。既存の専用スタブは
互換のためそのまま残す。

### 3.2 spawn: 逐次実行のプロセス起動

#### 意味

```
int spawn(char *path, char **argv, char *in, char *out);
```

path の ELF 実行形式を起動し，**その終わりを待って** 子の終了コード
(0..255) を返す。失敗は -1 (errno)。fork / exec のような分離はしない。
プロセスは一度に 1 つという Stage 12 の実行モデル (逐次実行) を保ったまま，
「起動して待つ」だけを提供する。

- argv は NULL 終端のポインタ列。NULL なら {path, NULL} 相当
- in / out は標準入出力のつなぎ替え (3.3)。NULL なら親と同じ先を継ぐ
- 子は fd 3 以降をすべて閉じた状態で始まる。親の開いていたファイルと
  fd 表は子の終了後に復元される

#### カーネルの実装 (退避と復帰)

アドレス変換が無いので，子も親と同じ固定位置 (0x8600_0000) へ配置される。
親の像は spawn の間 **退避領域へ複写して守る**。

```
0x8100_0000 .. 0x8370_0000   退避領域 (カーネルとトラップフレームの間)
```

退避するのは (1) トラップフレーム (33 語)，(2) fd 表とつなぎ替えの状態，
(3) ubrk と sp，(4) ユーザ像 [0x8600_0000, ubrk)，(5) フレームスタック
[sp, 0x8700_0000) である。子が exit したら逆順に書き戻し，親の a0 へ
子の終了コードを入れて再開する。入れ子は 8 段まで，退避領域が尽きたら
-ENOMEM。起動するファイルが無ければ何も壊さず -ENOENT を返す
(ELF でなければ -ENOEXEC。この検査は親の像を上書きする前に行う)。

argv の文字列は親の像の中にあるので，**親を退避する前にカーネル側の
buffer へ写す** (子の像を配置した時点で親の memory は読めなくなるため)。

#### syscall 番号は独自の範囲に置く

syscall ABI は RV32 Linux 互換だが ([stage012-os.md](stage012-os.md) 2.1)，
Linux に「起動して待つ」1 本の syscall は無い (clone + execve + wait4 の
合成になる)。Linux の番号に別の意味を与えると互換が壊れるので，
**Linux が使わない番号 500 を SPAWN に割り当てる**。

- Linux の番号 (0..463 付近) は今後も Linux の意味でだけ使う。独自の
  拡張は 500 番台に置き，両者を混ぜない
- 可搬性は libc の層で保つ: `spawn` の API は，実 Linux の上では
  clone / execve / wait4 で実装できる。ユーザプログラムは spawn を
  呼ぶ限り無改変で両方の環境に通じる

### 3.3 標準入出力のつなぎ替え (リダイレクト)

dup2 と fd の継承をカーネルに持ち込む代わりに，**spawn の引数で子の
fd 0 / fd 1 の結び先 (ファイル名) を指定する** 形にする。

- カーネルはプロセスごとに「fd 0 / fd 1 の結び先」を持つ。既定は UART。
  in が与えられれば fd 0 をその sfs ファイルへ (無ければ -ENOENT)，
  out が与えられれば fd 1 をその sfs ファイルへ (無ければ作成，あれば
  切詰め) 結んで子を始める。NULL なら親の結び先と位置を引き継ぐ
- fd 2 は常に UART。診断はリダイレクトに巻き込まれない
- cc / ld / pp は「標準入力を読み標準出力へ書くフィルタ」なので，
  この仕組みだけで第 3 部の移住に足りる

### 3.4 fd 0 の read はブロックする (kernel12 からの変更)

kernel12 の read は UART に用意が無ければその場で 0 (EOF) を返した。
シェルがスクリプトを標準入力から読む形 (QEMU への パイプ) では，これは
「まだ届いていない」と「終わった」を区別できず，成立しない。

kernel13 では fd 0 の read を **最初の 1 バイトが届くまで待ち，届いて
いる分だけ返す** 形に変える。入力の終わりは従来からの約束どおり
**EOT (0x04)** で表す ([dev-notes.md](dev-notes.md) 4 章)。シェルは
EOT を読んだら終了する。fd 0 がファイルへ結ばれている場合は従来どおり
末尾で 0 (EOF) を返す。

ベアメタルの鎖が「getc はブロックし，終端は約束 (EOT / `.`) で表す」で
来たのと同じ形であり，挙動の先例に合わせる変更である。kernel12 とその
テストは凍結されたまま変わらない。

### 3.5 boot 行は引数まで解釈する

sfs 内の固定名 `boot` の 1 行を空白で区切り，argc / argv として起動する
プログラムへ渡す (kernel12 は名前 1 語だけだった)。シェルを介さず
1 本のコマンドを引数付きで走らせる検査がこれで書ける。

### 3.6 シェル (sh)

自作 C (C89 + libc) で書く行指向の最小シェル。

- 1 行読み (fgets)，空白 (SP / TAB) で語に分割。空行は読み飛ばす
- `< name` / `> name` を取り出して spawn の in / out に渡す
- 最初の語をコマンド名 (= sfs 内のファイル名) として spawn する
- 組込みは 2 つ: `exit [n]` (シェルを終える。n 省略時 0)，
  `echo ...` (語を空白 1 つで繋いで出す。分割の検査に使う)
- プロンプト `$ ` を stdout へ出す。子の終了コードが 0 以外なら
  `? N` を 1 行で出す (検査がそのまま照合できる)
- spawn の失敗は `sh: <名前>: errno <E>` を出して次の行へ進む
- fgets が EOF (EOT または結び先ファイルの末尾) を返したら終了コード 0

パイプ・変数・引用符・グロブは作らない。必要になった部で足す。

### 3.7 libc は第 13 世代へ複製する

シェルの入力になる libc は世代ごとに凍結する ([artifacts.md](artifacts.md))。
`stage012/libc` を `stage013/libc` へ全文複製し，環境部 (posix/sys.c) に
spawn の包みを足す。純粋部は触らない。

## 5. 第 2 部: テキストエディタ (ed)

### 5.1 なぜ行エディタから始めるのか

ゲスト内で開発を完結させるには，ソースを直す手段が要る。第 1 部までの
道具では，ファイルを作れるのはプログラムの出力としてだけである。

最初のエディタを **行エディタ (ed 風)** にするのは，端末に何も要求しない
からである。スクリーンエディタは画面制御 (カーソル移動・消去) を要し，
それは端末の種類ごとに異なる約束 (エスケープ列) を前提にする。本計画の
実行環境は 16550 互換 UART の素の文字流であり，端末の能力を仮定できる
段階にない。行エディタなら「1 行読んで，1 行出す」だけで成り立ち，
**対話でもスクリプトでも同じように動く**。テストが書けるという実利も
大きい (6 章)。

スクリーンエディタは，端末の扱いを決めてから改めて考える。

### 5.2 コマンド

ed の作法にならう。アドレスは `.` `$` 数 と，それらに続く `+N` / `-N`
(N の既定は 1)。範囲は `a,b`，`,` だけなら `1,$`。省略時は現在行。

| コマンド | 内容 |
|---|---|
| (アドレスのみ) | その行へ移り，出す。空行なら次の行 |
| `a` / `i` / `c` | 追加 / 挿入 / 置換え。`.` だけの行で入力を終える |
| `d` | 消す |
| `p` / `n` | 出す / 行番号を付けて出す |
| `=` | 行番号を出す (アドレス省略時は最終行) |
| `s/古/新/[g]` | 置換 (5.3) |
| `w [名前]` | 書き出し，バイト数を出す。名前の省略時は開いた名前 |
| `r [名前]` | 読み込み，アドレスの後ろへ入れる |
| `q` / `Q` | 終える。`q` は未書き出しの変更があると 1 度だけ拒む |

- 起動時の引数はファイル名で，読み込んでバイト数を出す
- **誤りはすべて `?` の 1 行で表す。** 理由は出さない (ed の作法)。
  この割り切りは，実行環境に文字列資源を持たない段階では実利もある
- 入力の終わり (EOT / EOF) は，コマンド待ちでも入力モードでも終了

### 5.3 置換は正規表現ではない

`s` の探索は **文字列そのままの一致** である。正規表現エンジンは，
処理系にとって独立した規模の部品であり，第 2 部の目的 (ソースを直せる
ようにする) には要らない。必要になった段階で足す。

区切りは `s` の次の 1 文字とする (`s/a/b/` でも `s,a,b,` でもよい)。
これは置換する文字列に `/` を含む場合の逃げ道である。

### 5.4 行の持ち方

行ごとに malloc した文字列を，行番号順の表 (`char *buf[4096]`) で持つ。
挿入・削除は表をずらす。1 行は 511 バイトまで。

大きなファイルを扱う工夫 (ギャップバッファ・一時ファイル) はしない。
第 3 部で扱う自分自身のソースが数千行の規模であり，この形で足りる。
足りなくなったら，そのときの実測をもって作り直す。

## 7. 第 3 部: cc / ld / pp の OS 側への移住

### 7.1 ソースは 1 行も要らない

cc・pp・ld は，どれも **「標準入力を読み標準出力へ書くフィルタ」** と
して書かれている。ベアメタルではその読み書きが UART だった。OS の上では
`'E'` 前置部の getc / putc が read(0) / write(1) の 1 バイト版なので
([stage012-os.md](stage012-os.md) 5.5)，**同じオブジェクトを `'E'` で
リンクし直すだけで OS 上のコマンドになる**。

```
{ printf 'E'; cat cc10l.o; printf '\0'; } | ld13 > cc
```

3 つとも凍結された世代であり，1 行も書き換えない。「実行環境が提供する
ものは前置部が実体を持つ」という Stage 8 からの作法
([stage008-elf-ld.md](stage008-elf-ld.md) 2.2) が，ここで配当を返す。

移った先で，入出力の結び替えはシェルが行う (3.3)。

```
pp < hi.b > hi.i
cc < hi.i > hi.o
ld < hi.ld > hi
```

### 7.2 足りないのは「入力を組み立てる側」だった

ホスト側では，フィルタへ渡す入力をシェルスクリプトが組み立てていた。

| ホスト | 何をしていたか |
|---|---|
| `tools/bundle.sh` | 複数のソースを束ね形式にして末尾へ EOT を置く |
| `{ cat src.sc; printf '\004'; }` | 束ねを通さないソースの末尾へ EOT を置く |
| `{ printf 'E'; cat *.o; printf '\0'; }` | 形式の 1 バイトとオブジェクト列を連結する |

移住で本当に要ったのは，この 3 つのゲスト版である。

- `bundle file...` — 束ねを作る。**末尾の EOT が要である。** OS の上では
  入力の終わりで read が 0 を返すが，pp と cc は EOT でしか読取りを
  止めない (`while (c != eot)`)。どちらも凍結された世代なので，
  EOT を置くのは束ねを作る側の役目になる
- `eot` — 標準入力を写して末尾へ EOT を置くフィルタ。**処理系自身の
  ソース (`cc12.sc` / `pp.sc` / `ld13.sc`) は指令を含まないので束ねを
  通さない。** その経路にはこちらが要る
- `ldin {F|K|E} obj...` — リンカへの入力を組み立てる。ld は先頭バイトが
  ELF のマジックでなくなったところで止まるので，OS の上では末尾の 0 が
  無くても止まる。それでも置くのは，同じファイルがホスト側の経路でも
  そのまま通るようにするためである

pp の出力は末尾が EOT なので (`pp | cc` と繋げる前提。
[stage009-pp.md](stage009-pp.md))，cc へ渡す側には手当てが要らない。

3 つとも「入力を組み立てる」だけの小さなフィルタである。**処理系の側は
1 行も変えずに済んだ**という事実が，第 3 部でいちばん報告する値打ちの
ある結果である。

### 7.3 これで何ができるようになったか

ゲスト内で「書く → 束ねる → 前処理 → コンパイル → リンク → 実行」が
続けられるようになった。

```
$ ed hi.c            (第 2 部)
$ bundle hi.c > hi.b
$ pp < hi.b > hi.i
$ cc < hi.i > hi.o
$ ldin E hi.o > hi.ld
$ ld < hi.ld > hi
$ hi
```

ホスト側に残るのは「イメージの注入と回収」と「QEMU の起動」だけである。
この手順を 1 本の記述で駆動すること (make 相当) が第 4 部になる。

### 7.4 処理系は OS の上で自分自身を作り直せる

移住が本物かどうかは，**いちばん大きな入力**で決まる。そこで cc 自身の
ソース (`stage010/cc12.sc`，151636 バイト) をゲスト内で通した。

```
$ eot < cc12.sc > cc12.in
$ cc < cc12.in > cc12.o
$ ldin F cc12.o > cc12.ld
$ ld < cc12.ld > cc10l.bin
```

出来た `cc10l.bin` は，**チェーンの成果物 `tmp/build/cc10l.bin` と
バイト一致した** (QEMU 上で 3.5 秒)。処理系が，自分で作った OS の上で，
自分自身を作り直せている。

同じ形で `stage013/ed.c` (10196 バイト，ヘッダ 5 本を束ねる経路) も通し，
`.o` がホスト経路と一致することを確かめた。

### 7.5 判明した制限 (第 4 部への申し送り)

| 制限 | 由来 | 影響 |
|---|---|---|
| 引数は 8 個まで | kernel13 の `kargc < 8` (3.2) | `bundle` に並べられるファイルが 7 本まで。libc のヘッダを全部並べる形は取れない |
| cc のフレームは 2040 バイト | cc のプロローグが `addi sp, sp, -fnf` の 1 命令 ([dev-notes.md](dev-notes.md) 4 章) | OS 上の道具は大きな作業領域を大域に置く |

データスタックが `'E'` では 256 KiB しかない (ベアメタルの `'F'` は
7 MiB) 点は懸念していたが，cc が cc 自身を通せたので **足りている**。

残る 2 つはカーネル・リンカの世代を改めれば外れるが，**外す必要が実際に
生じてから改める。** 第 4 部でチェーン全体をゲスト内で再ビルドするときに，
どちらが本当に問題になるかが判る。

## 8. 検証計画 (第 3 部)

| 検査 | 内容 |
|---|---|
| ビルド再現 | bundle / ldin / eot / pp / cc / ld (コマンド版) の SHA-256 が各 .md 記載値と一致 |
| ゲスト内ビルド | シェルから `bundle` → `pp` → `cc` → `ldin` → `ld` を順に走らせ，出来た実行形式をその場で起動して出力と終了コードを照合する |
| **同一性** | 各段の生成物 (束ね・`.i`・`.o`・実行形式) が，ホスト経路の同じ段の生成物と **バイト一致する** |
| **自己再生成** | ゲスト内で `eot` → `cc` → `ldin` → `ld` を通し，cc 自身のソースから `cc10l.bin` を作る。チェーンの成果物と **バイト一致する** |

後半 2 つが第 3 部の核心である。移したのが「同じ処理系」であることを，
生成物のバイト列で示す。1 バイトでも違えば，前置部の入出力かゲスト側の
組み立てのどちらかが元の経路と食い違っている。

## 9. Stage 14 への接続

第 4 部まで終えると，ホスト側の関与は「sfs イメージの注入と回収」と
「QEMU の起動」だけになり，ビルドと開発の主体はゲスト内へ移る。
Stage 14 (外部の小規模 C プログラムのビルド) は，この環境に外部ソースを
注入して「他人の C」との差を潰していく段になる。
