# Stage 15: tcc のセルフホスト 設計文書

## 1. 目的と位置づけ

Stage 14 で，処理系は**他人が書いた C** を無改変でビルドできるように
なった (bzip2 と zlib。[stage014-external.md](stage014-external.md))。
ただし当てた素材はいずれも「ライブラリ 1 本」の規模であり，
使う言語機能も C89 の範囲に収まっていた。

Stage 15 の完了条件は [roadmap.md](roadmap.md) のとおり
**「tcc を我々の処理系でビルドし，その tcc が自分自身をビルドできる」**
である。これまでと質的に違う点が 3 つある。

1. **規模が変わる。** bzip2 は約 5 千行，zlib は約 2 万行。tcc は
   ヘッダを含めて約 6 万行で，かつ 1 つの翻訳単位が大きい
2. **言語の要求が変わる。** tcc は自身がコンパイラなので，64 bit 整数
   演算と浮動小数点定数の扱いを避けて通れない。台帳に残した gap が
   そのまま効く (4 章)
3. **正しさの基準が変わる。** これまでは「動いた」で足りたが，
   本 Stage は**生成したコンパイラがさらに正しいコードを吐くこと**まで
   問われる。処理系の誤りは「tcc が動かない」ではなく「tcc が作った
   ものが動かない」という一段遠い形で出る

## 2. 完了条件の定め方

ブートストラップ鎖でずっと使ってきた固定点の考え方
([dev-notes.md](dev-notes.md) 3.1) をそのまま持ち込む。

| 記号 | 作り方 |
|---|---|
| T1 | **我々の処理系** (pp + cc + ld) が tcc のソースから作った tcc |
| T2 | **T1** が tcc のソースから作った tcc |
| T3 | **T2** が tcc のソースから作った tcc |

完了条件は **T2 == T3** (バイト一致) とする。

> **第 1 部の実測を受けた補足 (8 章)。** tcc には RV32 の backend が
> 無いため，この条件は**我々が `riscv32-gen.c` を書いて初めて成立する**
> (第 5 部)。条件そのものは変えない。

- **T1 == T2 は期待しない。** T1 を作ったのは我々のコード生成，T2 を
  作ったのは tcc のコード生成であり，同じバイト列になる理由がない
- T2 == T3 が成り立てば，「T1 は自分自身を再生産できる tcc を作れた」
  ことになる。これは T1 の生成コードが**少なくとも tcc を走らせる範囲で
  正しい**ことの，かなり強い証拠である
- 併せて，T1 と T2 が同じ入力から**同じ .o を作る**ことも見る。
  T2 == T3 だけでは，T1 が「たまたま自分の複製だけは作れる」場合を
  排除できない

## 3. 対象の版と取得

**開発枝 (mob) を commit で固定して対象とする。**

当初はリリース版 0.9.27 を選んだ。理由は「開発版は日々動くので記録が
固定できない」ことだったが，**git の commit で固定すれば記録は同じだけ
固く決まる**。そして第 1 部の実測 (8 章) で，版の選択が作業量を大きく
変えることが判った。

| | 0.9.27 (リリース) | mob (commit 固定) |
|---|---|---|
| RISC-V の backend | **無い** | `riscv64-gen.c` (1496 行) がある |
| RISC-V の再配置 | **無い** | `riscv64-link.c` に `R_RISCV_*` が 111 件 |
| ELF の対象種別 | RISC-V 無し | `EM_RISCV` あり |
| 32 bit 対象の仕組み | あり (i386 / arm は `PTR_SIZE 4`) | 同じ |

第 6 部で書く `riscv32-gen.c` は，**RV64 版を RV32 へ移す作業**になる。
ゼロから書くのに比べて手本があり，再配置と ELF の対象種別も既にある。
リリース版を選ぶと，これらをすべて自前で用意することになる。

したがって版の選択を改める。**記録の固さは commit で担保する**ので，
当初の理由は失わない。

取得は Stage 14 で作った仕組み ([../tools/fetch.sh](../tools/fetch.sh))
に載せる。実体は `docs/external/` に置き repo には取り込まない。

**取得は書庫ではなく git で行う。** savannah の配布ファイルは要求ごとに
別のミラーへ 302 で転送し (mirror.accum.se / mirror.rabisu.com …)，
転送先が一定しないため取得元を固定できない。git なら取得元が 1 つに
決まり，**commit が木の内容ハッシュとして印になる** (git 自身が取得時に
検証する)。記録は [SOURCES.md](SOURCES.md)。

| 項目 | 値 |
|---|---|
| 取得元 | https://github.com/TinyCC/tinycc |
| 枝 | mob |
| commit | 2ba12e83b3599ca8f5d50c179fe5138fe956f0c9 (2026-08-04) |

取得は**枝の先頭ではなく commit を直接取りに行く**。開発枝は日々動くので，
枝で取ると動いた瞬間に照合が壊れて取得できなくなる。枝の名前は記録の
ためだけに持つ。

書庫の SHA-256 と違い，**git の commit は SHA-1 である**。素材の同一性の
印としては書庫の SHA-256 のほうが強い。ここでは「取得元が固定できる」
ことと「RISC-V の手本がある」ことを優先したが，この差は意識しておく。

## 4. 現状と tcc の距離

台帳 ([../tests/stage014/ledger.txt](../tests/stage014/ledger.txt)) に
残る 3 件は，いずれも tcc では避けられないと**予想している**。

| 台帳 | 現状 | tcc での必要性 (予想) |
|---|---|---|
| llwidth | `long long` を拒む (終了コード 2) | **必須。** コンパイラは対象機械の整数定数を扱うため 64 bit 演算を持つ |
| floatv | `float` / `double` を拒む (終了コード 2) | **必須。** 浮動小数点定数の解析と出力に要る |
| emptyproto | 空の引数リストへ実引数を渡すと拒む | 未知。古い書き方が残っていれば要る |

加えて libc の不足 (`setjmp` / `longjmp`，`stdio` の未実装部，
`sys/stat` など) が出ると見ている。

**これらは「予想」であって「実測」ではない。** 素材を取得したら
Stage 14 第 1 部と同じやり方で**実測して台帳に落とす**のが第 1 部の
仕事である。予想で実装を始めると，要らないものを作り，要るものを
見落とす。

## 6. 第 2 部の見通し: 64 bit 整数

対象は RV32IM で，レジスタは 32 bit である。64 bit の値は**レジスタ 2 本の
組**で表し，演算を合成する。

| 演算 | 合成の仕方 |
|---|---|
| `+` / `-` | 下位を足し，桁上げ (`sltu` で検出) を上位へ運ぶ |
| `<<` / `>>` | 桁数が 32 未満か以上かで場合分けする |
| `*` | 32x32 の部分積 4 本 (`mul` / `mulhu`) を組む |
| `/` / `%` | 命令が無いので**ソフトウェアで割る** (libc 側の関数呼出しにする) |
| 比較 | 上位を比べ，等しければ下位を比べる |

**IR の 4 箇所ルール** ([dev-notes.md](dev-notes.md) 4 章) が効くため，
命令種別を増やす設計は避けたい。「値 1 個 = レジスタ 1 本」という
現在の前提をどう緩めるかが設計の中心になる。案は 2 つある。

1. **型で幅を持たせ，割付けを 2 本組にする。** 素直だが，割付け・
   スピル・呼出し規約のすべてに手が入る
2. **64 bit を「上位・下位の 2 値」に分解して既存の IR に載せる。**
   前段 (構文解析) で分解し，コード生成は 32 bit のままにする。
   IR を触らずに済むが，分解の規則が式の全域に散る

### 6.1 案 2 を採る

**案 2 (前段で上位・下位へ分解する) を採る。** 理由は 3 つある。

1. **IR とコード生成と割付けに手が入らない。** 4 箇所ルールを踏むのは
   64x64 の乗算に要る `mulhu` の 1 個だけで済む
2. **この処理系の作法に合う。** 式の付随情報は既に大域変数
   (`ety` / `elv` / `earr` / `esz` / `ebfw` …) で受け渡している。
   上位語の値番号を持つ `ehi` を 1 本足すのは，その並びに素直に載る
3. **段階的に進められる。** 実装した演算だけを通し，未実装は拒む
   (終了コード 5) 形にできる。**黙って 32 bit で計算して値を壊す**
   のが最悪であり，それを構造的に避けられる

案 1 (割付けを 2 本組にする) は，スピル・呼出し規約・生存区間の全てに
同時に手を入れることになり，途中で止められない。

### 6.2 変更の内訳

| # | 変更 | 備考 |
|---|---|---|
| 1 | 型 `t_llong` / `t_ullong` を足し `tsize` を 8 にする | `long long` を拒む分岐 (`lng > 1`) を外す |
| 2 | 記憶域を 8 バイトで取る | 局所・大域・構造体メンバ・配列要素 |
| 3 | 64 bit の定数を読む | cc 自身の int は 32 bit なので `tval` に上位語 `tvalhi` を添える。接尾辞 `LL` / `ULL` |
| 4 | 式の付随情報 `ehi` を足す | 0 = 32 bit の式。左辺値なら上位語のアドレスは +4 |
| 5 | 読み書き | `ldval` / `stval` を 2 語に分ける |
| 6 | 加減・ビット演算・比較 | 桁上げは `sltu`，比較は上位を見て等しければ下位 |
| 7 | シフト | 桁数が 32 未満か以上かで分ける |
| 8 | 乗算 | `mulhu` (新しい二項演算 1 個) と部分積 |
| 9 | 除算・剰余 | libc のソフトウェア除算を呼ぶ |
| 10 | 型変換 | int -> 64 は符号/ゼロ拡張，64 -> int は下位語 |
| 11 | 引数と返却 | データスタックに 2 語積む |
| 12 | libc の `printf` の `%lld` | 第 4 部と重なる |

**1〜7 と 10 を先に通し，8・9・11 は後続にする**のが安全である。
未実装の演算は拒む (終了コード 5) ので，途中の世代でも「通るが誤り」を
作らない。台帳はこの区切りごとに更新する。

### 6.3 第 2 部の結果

12 項目を 5 つの世代に分けて入れた。**IR に足した命令種別は `mulhu` の
1 つだけ**で，それ以外はすべて既存の 32 bit の演算の組合せである。

| 世代 | 入れたもの |
|---|---|
| [cc15a](../stage015/cc15a.md) | 型・記憶域・リテラル・代入 (1〜5) |
| [cc15b](../stage015/cc15b.md) | 加減・ビット演算・比較・シフト・型変換 (6・7・10) |
| [cc15c](../stage015/cc15c.md) | 実引数 (11 の前半) |
| [cc15d](../stage015/cc15d.md) | 返却と乗算 (11 の後半・8) |
| [cc15e](../stage015/cc15e.md) | 除算・剰余 (9)。実体は [rt64.c](../stage015/rt64.c) |

段階を分けた狙いは「**黙って値を壊さない**」ことだった。左辺値を値へ
変える関数を `rvany` (64 bit 可) と `rv` (32 bit 専用) に分けてあるので，
まだ教えていない経路は自動的に拒まれる。実際，各世代の台帳は
「通るが誤り」が 0 件のまま進んだ。

残る制限は 2 つ。可変長引数の**可変部**に置く 64 bit (逆順に積むので
語数がずれると並べ替えられない。構造体と同じ制約) と，64 bit と
ポインタの加減算である。どちらも tcc が要求した時点で入れる。

なお `long long` の実際の使われ方 (全域か定数の保持だけか) は第 1 部の
実測が決めるが，**上の内訳は使われ方に依らない**。素材の取得を待つ間に
進めてよい部分である。

## 7. 見積りと撤退条件

Stage 15 はこれまでで最も大きい。**途中で「別の道のほうが早い」と
判ることも十分ありうる**ので，判断できる形にしておく。

- 第 1 部の実測で「tcc が要求する機能が Stage 3 つ分を超える」と
  判ったら，roadmap の Phase C の順序そのものを見直す。具体的には
  **tcc より小さい自己ホスト可能なコンパイラ**を先に当てる案がある
- 撤退の判断材料は第 1 部の実測結果であり，第 2 部以降の途中経過では
  ない。**始めてしまったものを惜しんで続けない**

## 8. 第 1 部の実測 (2026-08-11)

素材を取得して実測した。**設計の前提を 1 つ覆す事実が出た。**

### 8.1 tcc には RV32 の backend が無い

tcc 0.9.27 が持つコード生成は次のとおりで，**RISC-V が 1 つも無い**。

```
arm-gen.c  arm64-gen.c  c67-gen.c  i386-gen.c  il-gen.c  x86_64-gen.c
```

現行の開発枝 (mob) には `riscv64-gen.c` があるが，**RV64 であって RV32
ではない**。本計画の鎖は Stage 1 から一貫して RV32 である。

したがって **2 章で定めた完了条件 (T2 == T3) は，上流の tcc を無改変で
使う限り達成できない。** 我々が作った tcc は RV32 の上で動くが，
RV32 のコードを吐けないので，自分自身を作り直せない。

これは 7 章に書いた撤退条件そのものである。**判断は素材を取得した
時点で行う**と決めてあった。

### 8.2 言語の要求 (予想は当たっていた)

| 要求 | 実測 |
|---|---|
| `long long` | **中核。** 定数の表現 `CValue` が `uint64_t i` を持ち，全域で使う (tccgen.c だけで 96 箇所) |
| 浮動小数点 | **中核。** 同じ `CValue` に `float` / `double` / `long double` が入る |
| `long double` | **対象依存。** i386 は 12 バイト，ARM は 8 バイト (double と同じ)。対象の選び方で重さが変わる |

### 8.3 libc の要求

`setjmp` / `longjmp` (エラー処理の骨格)，`snprintf` (25 箇所)，`qsort`，
`realloc`，`memmove`，`strtoul`，`strtod`，`time`，`getcwd`，
`math.h` / `fcntl.h` / `errno.h`。第 4 部の範囲である。

### 8.4 取りうる道

| 案 | 内容 | 見積り |
|---|---|---|
| A | tcc に **RV32 の backend を書き足す** (`riscv32-gen.c`)。上流は無改変のまま，新しいファイルを足す形 | 大きい。ただし tcc の backend 境界は明確で，既存の `*-gen.c` が手本になる |
| B | 完了条件を**交差compile**へ変える。tcc を RV32 の上で動かし，i386 や arm 向けのコードを吐かせる。正しさはホストの tcc と出力を突き合わせて見る | 中くらい。自己ホストは諦めるが，tcc 本体を通す価値は残る |
| C | **別のコンパイラ**を当てる。ただし RV32 を対象にできる自己ホスト可能な C コンパイラは少ない | 調査が要る |
| D | 鎖を **RV64 へ広げる** | 非常に大きい。Stage 1 まで遡る |

いずれの案でも **第 2 部 (64 bit 整数) と第 3 部 (浮動小数点) は必要**で
あり，先に進めておいて無駄にならない。

### 8.5 採る道: 案 A (RV32 の backend を書く)

**自己ホスト (2 章の T2 == T3) を Stage 15 の目標として維持する。**
そのために `riscv32-gen.c` を書く。案 B (交差コンパイルで完了とする) は
採らない。自己ホストこそが Phase C の山であり，そこを外すと
「我々の処理系が本物のコンパイラを作れた」ことの証拠が弱くなる。

**backend の作業は第 2〜4 部と並行できる。** ここが要点である。

- `riscv32-gen.c` の開発と検証には**我々の処理系は要らない**。ホストで
  ビルドした tcc (RV32 を対象にした交差コンパイラ) が RV32 のコードを
  吐き，それを我々の QEMU と OS の上で走らせれば正しさを確かめられる
- つまり「tcc が RV32 のコードを吐けるか」と「我々の処理系が tcc を
  ビルドできるか」は**別々に進めて，最後に合流させられる**
- 合流したときに初めて T1 が作れ，T2 == T3 を見られる

交差コンパイルは**目標ではなく道具**として使う。backend の検証と，
第 6 部で我々の tcc の出力を突き合わせる基準の両方に効く。

> **その 1 の実測による訂正 ([stage015-riscv32.md](stage015-riscv32.md) 8 章)。**
> ここに「上流の tcc は無改変である。足すのは新しいファイルと設定で
> あり，既存のソースは書き換えない」と書いたが，**これは守れない**。
> コンパイラに対象を足す作業は，性質上，対象を選ぶ仕掛けと backend 本体に
> 手が入る。改変は patch 1 枚
> ([../stage015/tcc/riscv32.patch](../stage015/tcc/riscv32.patch)) に閉じ，
> repo に置いて読めるようにする。**我々の処理系が扱う C の側 (第 2〜4 部)
> では tcc のソースを 1 行も書き換えない**という線は守る。

## 9. 検証

各部の検証は Stage 14 と同じ枠組みに載せる。

- 言語機能は**台帳** (probe + 期待出力) に落とし，実測と表の食い違いを
  検査で捕まえる
- 世代を足したら**固定点** (B2 == B3) と**回帰** (既存ソースが同じ .o に
  なる) を必ず見る
- 素材に依存する検査は**素材があるときだけ走らせる**
  ([stage014-external.md](stage014-external.md) 2.2)
