## 3. 3 案を，いま判っていることに当てる

### 3.1 変わらない事実 (roadmap 2.1 の前提)

- GCC の RISC-V backend が入ったのは **GCC 7**
- C だけでビルドできる最後の GCC は **4.7.4** (4.8 以降は C++)

この 2 つが交わらないことが，そもそもの障害である。

### 3.2 「我々の OS の上で走る GCC」に何が要るか

**GCC が我々の OS の上で走り，かつ我々の OS 向けのコードを吐く**には，
RISC-V backend を持つ GCC (= 7 以降) が要る。7 以降は C++ で書かれて
いるので，**それを訳せる C++ 処理系が要る**。

ここで tcc は助けにならない。**tcc は C の処理系であって C++ ではない。**

### 3.3 案 B (x86-64) が落ちる理由

GCC 4.7 は C なので tcc で訳せる。訳せば **我々の OS の上で走る GCC
4.7** が手に入る。ところがその GCC 4.7 が吐けるのは 4.7 が持つ対象
(x86 / ARM / …) だけで，**RISC-V は無い**。

つまり案 B で登っても，出来上がるものは我々の OS の上では走らない。
**RV32 を主対象から降ろす**という判断とセットでなければ成立しない。

### 3.4 案 C が案 A への近道になりうる

GCC 4.7 の木には **C++ の前端 (`cc1plus`) も入っている**。4.7 の
ソースは C なので，前端ごと tcc で訳せる。

したがって案 C —— GCC 4.7 に RISC-V backend を載せる —— を採ると，
副産物として **RV32 を吐く `g++` が手に入る**。その `g++` で GCC 7 を
訳せば，案 A の目的 (RISC-V を持つ GCC) に，C++ 処理系を自作せずに
届く。

```
tcc ──(C)──> GCC 4.7 + 我々の RISC-V backend
                   ├─ cc1    : RV32 を吐く C
                   └─ cc1plus: RV32 を吐く C++   ──> GCC 7 ──> …
```

**我々は同じ種類の仕事を既に一度している。** tcc に RV32 backend を
書き足した (`stage015/tcc/riscv32.patch`)。GCC の backend は機械記述
(`.md`) が主で書き方は違うが，「対象を 1 つ足す」という仕事の形は同じ
である。しかも RISC-V の記述は GCC 7 以降に**実在する**ので，
まったくの白紙ではない。

### 3.5 したがって現時点の見立て

**案 C を採り，その `g++` で案 A の目的地 (GCC 7) へ登る**のが、
いま判っている範囲では最も短い。案 A を単独で採る (C++ 処理系を
自作する) 理由は，「GCC 4.7 を fork したくない」以外に見当たらない。

**これは推奨であって決定ではない。** 下の 4 章が埋まっていない。

## 4. まだ測れていないこと

**この 3 つを測るまで，上の見立ては見立てのままである。**

### 4.1 GCC 4.7 が tcc で訳せるか

上流の live-bootstrap 系の経路では通っているとされるが，**我々は
測っていない**。tcc の版も我々の RV32 backend も我々のものなので，
他所で通ったことは我々で通ることを意味しない。

### 4.2 GCC 4.7 の `configure` と `Makefile` が我々の OS で回るか

Stage 16 の教訓は「**律速はコンパイラではなく OS だった**」である
(stage016-os.md 1〜4 章)。tcc の `configure` は通ったが、GCC の
`configure` は桁が違う。我々の `sh2` は POSIX の部分集合で，道具は
10 個，`awk` は無い。

**tcc のときと同じ測り方ができる。** 上流の `configure` と `Makefile`
が何を要求するかを静的に数え，足りないものを表にする
(stage016-os.md 11 章・[stage017-cc.md](stage017-cc.md) 15 章・22 章と
同じ手順)。

### 4.3 GCC 4.7 の backend を 1 つ足す仕事の大きさ

`.md` の行数・対応が要る hook の数を数えれば見積もれる。

### 4.4 いまこの環境では測れない

**GCC の素材が取れない。** この作業環境の網は `ftp.gnu.org` を
policy で拒む。

```
$ curl -fsSI https://ftp.gnu.org/gnu/gcc/gcc-4.7.4/gcc-4.7.4.tar.bz2
curl: (22) The requested URL returned error: 403
    "gateway answered 403 to CONNECT (policy denial or upstream failure)"
```

`tools/fetch.sh` が今持っているのは `bzip2` / `zlib` / `tcc` の 3 つで，
どれも取得先が別である。GCC を足すには**取得先を許された網の中に
見つける**必要がある。

## 5. どの案でも等しく要るもの

判断を待つ間に進められるものを分けておく。Stage 16・第 1 部と同じ
考え方である。

### 5.1 我々の OS の `cc` を tcc にする

いま OS の上の `cc` は `cc19` (駆動役) + `cc15q` (器) で，言語は
**C89 の部分集合**である。tcc は C99 を相当に受ける。GCC 4.7 だろうと
GCC 7 だろうと，あるいは C++ 処理系を自作するのだろうと，**その入口に
立つには我々の OS の上に強い C 処理系が要る**。

材料は揃っている —— tcc は我々の OS の上で組め，走り，`libtcc1.a` も
持っている。残るのは「`cc` と打ったら tcc が動く」ように据えることと，
その状態で鎖が回ることを確かめることである。

**着手した。** tcc に**結合まで**任せられることを確かめた ——
入口 (`stage017/crt1.S` + `crt1c.c`) を tcc 自身に組ませ，
`tcc -static -Wl,-Ttext=0x86000000` で結合した実行形式が我々の OS の上で
走り，返り値・`argc`・`argv` が届く ([stage017-cc.md](stage017-cc.md) 30 章)。

**残るのは tcc の世界の libc である。** 我々の `libc20` は `cc15k` が
組んだもので，引数をデータスタック (x9) で渡す我々の規約に従う。tcc は
標準の RISC-V ABI を使うので**この 2 つは互いに呼べない** (30.6)。
`libc20` のソースを tcc に訳し直すのが 5.1 の後半である。

### 5.2 OS の側の不足を先に数える

4.2 の測り方は GCC の素材が無くてもできない —— が，**tcc より一段
大きい実物**なら手元にある。`zlib` と `bzip2` は既に取れる
(`tools/fetch.sh`)。この 2 つを **tcc で，我々の OS の上で** ビルド
すれば，`cc19` + `cc15q` では届かなかった範囲が測れる。

Stage 14 では我々の cc でこの 2 つを訳した。**同じものを tcc で訳し
直す**のは退行の検査にもなる。
