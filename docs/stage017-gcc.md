## 3. 3 案を，いま判っていることに当てる

### 3.1 変わらない事実 (roadmap 2.1 の前提)

- GCC の RISC-V backend が入ったのは **GCC 7**
- C だけでビルドできる最後の GCC は **4.7.4** (4.8 以降は C++)

この 2 つが交わらないことが，そもそもの障害である。

### 3.2 3 案は「我々が何を獲得するか」である

| 案 | **我々が獲得するもの** | 得失 |
|---|---|---|
| A | **C++ の部分集合を訳せる器** | RISC-V を維持できる。C++ は C より桁違いに大きい |
| B | **我々の器の x86-64 backend** | 実績のある経路。ただし RV32 が主対象でなくなる |
| C | **GCC 4.7 に載せる RISC-V backend** (我々が書く) | GCC 本体の fork を保守することになる |

**どの案でも，GCC を訳すのは我々の器である。** 案 C で「GCC 4.7 は C
だから訳しやすい」と言えるのは，**我々の器が C を訳せるから**であって，
他所に C 処理系があるからではない。

**持ち主の判断は案 A である** (6 章)。以下 3.3〜3.4 は判断の材料として
残す。

### 3.3 したがって，いちばん先に測るべきことが変わる

初版は「GCC 4.7 が tcc で訳せるか」を 4.1 に置いていた。**それは我々の
指標ではない。** 置くべきはこれである。

> **我々の器 (`cc19` + `cc15u`) が GCC 4.7 の C を訳せるか。**

tcc を訳せたことは足場になる。tcc は C99 を相当に使う実物で，それを
訳せたのだから，GCC 4.7 の C も「まったく手が届かない」わけではない。
**しかし tcc と GCC 4.7 は桁が違う** —— そこを数えるのが 4 章である。

### 3.4 案 C の副産物についての訂正

初版は「案 C を採ると副産物として RV32 を吐く `g++` が手に入り，それで
GCC 7 を訳せば案 A の目的に C++ 処理系を自作せずに届く」と書いた。

**筋としては成り立つ** —— GCC 4.7 の木には `cc1plus` が入っており，
それも C で書かれているので，**我々の器が訳せれば**我々の鎖の成果物に
なる。tcc を経由する必要はない。

ただし前提が 2 つある。

1. **我々の器が GCC 4.7 の C を訳せること** (3.3)
2. **C++ の実行時** (`libstdc++` / `libsupc++`) をどうするか (4.4)

2 は案 A を採っても消えない，3 案に共通の未測項である。

## 4. 案Aを進めるために測ること

案Aの選択後も、GCC規模のsource tree、build system、C++ runtimeに対する未測定項目が残っている。4.5の取得と容量測定は完了した。

### 4.1 我々の器が GCC 4.7 の C を訳せるか

**これが最初の 1 つである。** tcc のときと同じ測り方ができる ——
ソースを読ませ，**通らなかった単位とその理由を数える**。tcc では
それが「C 適合の誤り 4 つ + libc の穴 6 つ」という表になった
(31〜33 章)。GCC 4.7 でも同じ形の表が出るはずで，**その表の長さが
案 C の見積りそのもの**になる。

### 4.2 GCC 4.7 の `configure` と `Makefile` が我々の OS で回るか

Stage 16 の教訓は「**律速はコンパイラではなく OS だった**」である。
tcc の `configure` は通ったが，GCC の `configure` は桁が違う。我々の
`sh2` は POSIX の部分集合で，道具は 10 個，`awk` は無い。

上流の `configure` と `Makefile` が何を要求するかを静的に数え，
足りないものを表にする (stage016-os.md 11 章・21 章と同じ手順)。

### 4.3 backend を 1 つ足す仕事の大きさ

`.md` の行数・対応が要る hook の数を数えれば見積もれる。案 B と案 C の
どちらでもこの数が効く。

### 4.4 C++ の実行時をどうするか

案 A でも案 C でも，C++ を訳せる器が出来ただけでは `g++` は使えない。
対象の側の `libstdc++` / `libsupc++` とそのヘッダが要る。我々の OS に
あるのは C の libc だけである。

道は 2 つあり，**どちらも測っていない**。

| | 中身 | 大きさの見当 |
|---|---|---|
| 実行時を移す | `libstdc++-v3` を我々の OS 向けに組む | `configure` が大きく，libc に要求するものも多い |
| 要らないことを示す | GCC 7 の bootstrap が実行時のどこまでを使うかを数える | 静的に数えられる。4.2 と同じ手順 |

後者から測るのが順である。GCC 自身は例外も RTTI も使わない方針で
書かれているので `libsupc++` の一部で足りる見込みはあるが，
**見込みは測りではない**。

### 4.5 GCC 4.7.4の取得と容量測定 — 完了

GNU公式配布元の`https://ftp.gnu.org/gnu/gcc/gcc-4.7.4/gcc-4.7.4.tar.bz2`を取得し、SHA-256 `92e61c6dc3a0a449e62d72a38185fda550168a86702dea07125ebd3ec3996282`で固定した。取得と照合は`sh tools/fetch.sh gcc47`、容量測定は`sh tools/gcc17.sh measure`で再現できる。

|---|---:|
| file | 76,693 |
| directory | 4,663 (rootを含む) |
| symbolic link | 0 |
| その他のsfs3未対応entry | 0 |
| hard linkを持つfile path | 0 |
| file内容の合計 | 467,486,875 bytes |
| sfs3のtableと4-byte alignmentを含む最小image | 473,459,336 bytes |

`sfs3.sh pack`が表現できないsymbolic linkその他のentryは、公式archiveと展開後のtreeのどちらにも無かった。hard linkも無い。`gcc17.sh measure`はこれらを明示的に数え、未対応entryが1つでもあれば最小image容量とkernel24への収容可否を`unknown`とする。したがって、黙って欠落させたtreeの容量を全treeの容量として扱うことはない。

## 5. どの案でも等しく要るもの

判断を待つ間に進められるもの。**どれも主語は我々の器である。**

### 5.1 実物を，我々の器で，我々の OS の上で組む —— **済**

`zlib` 1.3.1 (15 単位) と `bzip2` 1.0.8 (7 単位) を，**我々の OS の上で
我々の器が**訳し，**我々の `ar` が書庫にまとめ**，**我々の `ld` が繋ぎ**，
**走らせて往復させた**。手順は `tools/ext17.sh run`。

**初版はここを「tcc で組む」と書いていた。撤回した** —— それでは tcc の
成熟度を測ることになり，我々の値が出ない (34 章)。外部のソースは素材で
あって，道具ではない。

```
cc19 -c z/deflate.c -o z/deflate.o -I z    ... 22 単位
ar rcs z/libz.a z/*.o                       我々の ar17
cc19 -o zt z/zt.c z/libz.a -I z             我々の cc19 + ld
zt                                          我々の kernel24 の上で走る
```

駆動 (`tests/stage017/ext/zt.c` / `bzt.c`) は**我々が書いたもの**である。
`compress2` / `uncompress` / `crc32` / `adler32` と
`BZ2_bzBuffToBuffCompress` / `Decompress` を呼び，元に戻ることを見る。

#### zlib 自身の検査も通した

**我々が書いた駆動は，我々が思いついた道しか通らない。** `zlib` は
自分の検査 (`test/example.c`) を持っているので，それも**入力として
読ませ**，我々の器で組んで走らせた。

`gzopen` / `gzputs` / `gzprintf` / `gzread` / `gzseek` / `gztell` /
`gzgetc` / `gzungetc` / `gzgets` / `deflateSetDictionary` /
`inflateSync` / 辞書つき伸長まで通る。**`gz*` の系統はファイルを開いて
読み書きするので，`libc` のファイル層まで一緒に測れる。**

```
zlib version 1.3.1 = 0x1310, compile flags = 0x55   ← 我々 (RV32)
uncompress(): hello, hello!
gzread(): hello, hello!
gzgets() after gzseek:  hello!
inflate(): hello, hello!
large_inflate(): OK
after inflateSync(): hello, hello!
inflate with dictionary: hello, hello!
```

**ホストで同じソースを組んだものと，1 行ずつ一致した。** 唯一違うのは
`compile flags` で，これは `uInt` / `uLong` / `voidpf` / `z_off_t` の
大きさを畳んだ値なので RV32 (`0x55`) と x86-64 (`0xa9`) で必ず違う ——
**違ってよい理由が言える 1 行だけが違う**。

#### 出た表

| 出たもの | 中身 | 直し |
|---|---|---|
| C 適合の穴 | 型修飾子が宣言指定子の列の**途中**に来る形 (`unsigned const char`) を拒む。C89 6.5 は順序を縛らない | `cc15t` |
| **C 適合の誤り** | **複合代入 (`a op= b`) が符号を見ていない。** `unsigned` の `%=` が符号つき剰余に，`int` の `>>=` が論理シフトになる | `cc15u` |
| libc の穴 | `libc21` を **`.o` にしていなかった** —— ヘッダだけ足して満足していたので，新しく実装したもの (`signal` / `memchr` / `strerror`，`fopen(path,"a")` の直し) はどこにも無かった | `l21_*` を組む |
| 道具の穴 | **`ld` が落ちた理由を言わない。** 未定義シンボルを `exit(2)` で拒むだけで，`cc19` に出るのは "cc: link failed" の 1 行 | `ld17` |
| /lib の組合せ | `ctype` を置いていなかった (tcc の作業場では要らなかった)。`bzlib.c` が `isdigit` を呼ぶ | `ext17.sh` |

**`ld17` は足した直後に効いた。** `bzip2` の結合が落ちたとき，`ld16` は
黙って `exit(2)` するので判るのは「どれかが足りない」まで。`ld17` は
`ld: undefined symbol: isdigit` と言った。**測る道具に目が無いと，
測定そのものが止まる。**

#### 往復するだけでは足りなかった

いちばん大きい収穫は `cc15u` で，**それは往復の検査では捕まらなかった**。
往路と復路で同じ誤りが起きれば，中身が違っても元に戻る。

捕まえたのは**外の物差しとの突き合わせ**である。ホストの gcc に
**同じソースと同じ駆動**を組ませ，値を並べた。

```
        crc32     adler32     level 1/5/9 の長さ
我々    282d245a  43dc7153    3042 / 1537 / 1537
ホスト  282d245a  459e7153    3042 / 1537 / 1537
```

`crc32` も圧縮長も一致するのに `adler32` だけ違い，しかも**下位 16 bit
は合っていて上位だけ**違う。adler32 の下位は最大 142 万，上位は約 39 億
—— **上位だけが 2^31 を超える**。出方がそのまま原因 (符号つき剰余) を
指していた。

**この突き合わせは `tools/ext17.sh run` に入れてある。** 期待値は
ホストの gcc と Python の `zlib` (別実装) で同じになることを確かめた。

#### 4.1 の予行として

出た表は 4.1 と同じ形である。**GCC の素材が無くても予行になる**と
書いたとおりになった —— 22 単位という tcc より一段小さい的でも，
C 適合の誤りが 1 つ・穴が 1 つ・libc と道具の穴が 3 つ出た。

### 5.2 我々の器の C 適合を，測って埋め続ける

tcc を読ませて 4 つ出た (25 / 28 / 31 / 33 章)。`zlib` / `bzip2` を
読ませて 2 つ出た (`cc15t` / `cc15u`)。GCC 4.7 を読ませれば，同じように
出る。**台帳 (`tests/stage015` / `tests/stage014`) に載せて埋める**のが，
どの案でも要る仕事である。

`cc15u` が示したのは，**自分自身を組む限り永久に表に出ない誤りがある**
ということである。我々のソースは `>>=` / `/=` / `%=` を 1 つも使って
いない。固定点も再現性もバイト一致も，この誤りを 1 つも捕まえなかった。
**外を的として読ませる以外に見つける道が無い。** ベンチマークを置く
理由がこれである。

#### 台帳の期待値は我々が書いている

`cc15u` を捕まえたのは「ホストの gcc に同じソースを組ませて値を並べた」
という**1 回限りの手作業**だった。それを仕組みにしたのが
`tools/diff17.sh` である。

```
sh tools/diff17.sh          プローブ全部
sh tools/diff17.sh <名前>   1 つだけ
```

同じソースを我々の鎖とホストの処理系の両方に訳させ，走らせて標準出力を
突き合わせる。**我々が拒む形**については，
`gcc -std=c89 -pedantic-errors` が**エラーにするか**を見る ——
台帳の `gap` が「未対応」ではなく「誤った入力を正しく拒む」だと名乗る
には，**その入力が本当に誤っていることを我々以外が言っている**必要が
あるからである。

**警告の数を数えるのでは弱い。** gcc は正しいソースにも
`-Wmissing-braces` のような書き方の助言を出す。制約違反にしか出ない
判定が要る。

##### 仕掛けた初回に 2 つ出た

| | 中身 | 直し |
|---|---|---|
| **我々の誤り** | スカラの初期化子を波括弧で囲んだうえ中身が 2 つ以上ある形 (`int a[2][2] = {1,{2,3},4}`) を黙って通し，溢れを隣へ入れていた | `cc15v` |
| **検査の誤り** | `probe/qualorder.c` が `const` の付いた対象へ**代入**していた。C89 6.3.16 の制約違反で，我々が修飾子を検査に使わないから通っていただけ | プローブを直した |

1 つ目は，`stage015/cc15s.md` の表に**「正」と書いてあった**ものである。
我々が出した値を我々が正しいと決めていた。ホストは診断を 2 つ出したうえで
別の値 (`1 2 4 0`) にしており，**制約違反に黙って値を作っていたのは我々
だけ**だった。

2 つ目は，**差分試験を入れなければ「同じソース」と言えなかった**ことを
意味する。ホストで訳せないプローブは，そもそも比べる相手になっていない。

##### ホストは万能の物差しではない

飛ばすものは**名前と理由を必ず出す** —— 黙って飛ばすと「全部合った」に
見える。

| 飛ばす | 理由 |
|---|---|
| `strsizeof` / `layout` | 語長・構造体配置が RV32 の規則。ホストは x86-64 |
| `lldiv` | 0 除算を見る。C が定義していない (ホストは SIGFPE) |
| `fpsoft` | 鎖の内部の名前 (`__dadd` …) を直に呼ぶ |
| `hyg16` | 前処理器の検査。訳して走らせるものではない |
| `layout-oracle` | `main` を持たない断片 |

`strtod` もここにあった —— 「libc を繋いで OS の上で走らせる形。
**次に広げるならここ**」。**その行を消したのが 5.3 である。**

いまは 22 一致 / 0 食い違い / 6 飛ばし。走行は 90 秒ほどである。

### 5.3 差分試験を libc まで広げた —— OS の上で走らせる側

5.2 が「次に広げるならここ」と書いた形を作った。`strtod` を飛ばして
いたのは，**前置部だけで走る形では libc が繋がらない**からである。
繋げるには我々の OS の上で走らせるしかない。

#### 何をしたか

`tools/diff17.sh` を 2 系統に分けた。

```
sh tools/diff17.sh bare   前置部だけで走る側 (Stage 15 の器の適合)
sh tools/diff17.sh os     libc を繋いで OS の上で走らせる側
```

`os` は，同じソースを

- 我々の側では `pp16` -> `cc15v` -> `ld17` で組み，libc の `.o` を
  繋いで `'E'` にし，`kernel24` の上で走らせる
- ホストの側では `gcc` に組ませて走らせる

両者の標準出力を突き合わせる。**起動は 1 回だけ**である —— プローブ
ごとに QEMU を上げ下げすると，測るものより待つ時間のほうが長くなる。
1 つの像に全部詰め，我々のシェル (`sh2`) に順に起動させ，`@@名前` の
行で切り分ける。**終わりの印 (`@@end`) が出ていなければ落とす** ——
途中で止まったのに，出た分だけを見て「合っていた」と言わないためで
ある。

測る libc の世代は `STONE_DIFF_LIBCGEN` で差し替えられる。**直す前の
世代を後から測り直せないと，直した記録が我々の言い分だけになる。**

#### 4.1 に対して何が言えるようになったか

4.1 は「GCC 4.7 の C を訳せるか」を，通らなかった単位とその理由の表で
測ると書いた。**その表には必ず libc の行が入る** —— tcc のときは 6 行
入った (32.3)。ここまでは，その libc の行を**組めるか (結合が通るか)**
でしか測れていなかった。組めた後に**値が合っているか**は，実物を走らせ
なければ出ない。

今回出た 9 件は，どれも**結合は通る**。`%o` を知らない `printf` は
リンクできるし，`strtoul` は値を返す。**動くが違う**という，台帳で
`bad` と呼ぶ状態である。GCC の生成物 (`genattrtab` などのビルド時
プログラム) は書式出力を大量に使うので，ここが違えば**生成されるソース
が静かに壊れる**。

走行は 80 秒ほどである (5 本を組むのが大半で，起動は 1 回)。

### 5.4 ファイル層まで広げた —— libc と OS が一緒に効く場所

5.3 のプローブは 1 本もファイルを開かない。**そこは libc だけの話で
あって，我々の OS は測られていない。** 5.1 で `zlib` の `example.c` を
通したとき「`gz*` の系統はファイルを開いて読み書きするので libc の
ファイル層まで一緒に測れる」と書いた部分を，正面から測る。

GCC に向けてここを先に測る理由がある。`configure` も生成器
(`genattrtab` など) も**テキストを行で読む**。行の読み方が違うと，
落ちるのではなく**読めたつもりで別のものを読む**。

| | 中身 |
|---|---|
| `filex` | `fgets` の縁 (改行つき / 終端で切れた行 / 容れ物が足りない / `n == 1`)，`fread` の半端 (員の数で数える)，`ftell` / `fseek` / `ungetc` の位置，追記，`remove`，`feof` が `fseek` で落ちること |

#### 出た表 (第 21 世代) —— 1 行だけだった

| | ホスト | 我々 (libc21) |
|---|---|---|
| `fgets(b, 1, f)` | `[]` (空の文字列を返す) | `(null)` |

**これは我々の OS の側の結果でもある。** 位置と追記と削除はカーネルの

NULL を返していた。`n == 1` のときは 1 バイトも要求されていないので

`libc22` で分けた。

### 5.5 正規表現と `sed` —— `configure` の正面の壁

**我々の OS には正規表現が 1 つも無かった。** `sh2` の `grep` は固定
文字列としてしか探さず (stage016/sh2.c の註)，`sed` は存在しない。

これは 4.2 (GCC の `configure` が我々の OS で回るか) の正面の壁である。
autoconf が作る `configure` は，変数の展開・条件の判定・`config.status`
の生成まで**ほぼすべてを sed でやる**。Stage 16 で tcc の `configure`
が通ったのは，**それが手書きで sed をほとんど使わない**からで，
autoconf の側は測れていなかった。

#### 何を作ったか

[stage017/sed1.c](../stage017/sed1.c)。2 つを持つ。

1. POSIX BRE の部分集合を解する正規表現機構 (節の配列へ組んでから
   後戻りで照合する)
2. その上に立つ `sed`

| | 受ける形 |
|---|---|
| 正規表現 | `^ $ . *` `[...]` `[^...]` `[a-z]` `\( \)` `\1`〜`\9` `\+` `\?` `\.` `\\` `\n` `\t` |
| 命令 | `s/re/rep/[gp数]` `y/../../` `p d q = n N D P b : ! { }` |
| 番地 | 行番号 / `$` / `/re/` / `addr1,addr2` / 番地の後の `!` |
| 引数 | `-n` `-e` `-f` `--` / 最初の非オプションが台本 |
| 置換 | `&` `\1`〜`\9` `\&` `\\` `\n` |

受けないものは**名指しで拒む** (`\{n,m\}` の区間量指定子・GNU の
`\|`・行を足す `a i c r w`)。黙って読み飛ばすと，台本の意図と違う
出力が静かに出る。

#### 物差しはホストの `sed` である

`sed` の値は「我々が正しいと思う値」では測れない。POSIX の文言は短く，
**実際の振舞いは実物と突き合わせないと決まらない** —— 空に合う置換の
進み方，組の控え方，範囲の閉じ方。5.3 で libc に対してやったのと同じ
筋である。

`tools/diffsed.sh` が，同じ台本と同じ入力を我々とホストの `sed` の
両方に食わせ，出力と終了コードを突き合わせる。台本は**我々のソースが
使う形ではなく，autoconf の `configure` が使う形**を選んである。

**41 件のうち 2 件が食い違った。** どちらも「読めば正しそうに見える」
実装だった。

| | ホスト | 我々 (初版) |
|---|---|---|
| `s/x*/-/g` を `x` に当てる | `-` | `--` |
| `n;d` を 5 行に当てる | 最後の行が 1 度 | **2 度出る** |

1 つ目は，**空に合う形が直前の合致の直後に来たときは飛ばす**という
POSIX の規則である。`x` を置いた後の行末でも `x*` は空に合うので，
飛ばさないと置換後の字が 2 つ出る。

2 つ目は `n` が入力の終わりに当たったときで，`n` は自分で自動出力を
済ませてから次の行を読む。次が無ければそこで終わるが，呼び手の側でも
う一度出していた。**どちらも「落ちる」のではなく「値が違う」形**で
ある。

直して 41 件とも一致した。

#### 我々の OS の上でも一致した

ホストで組んだものが合うことは，**我々の器が同じものを作れることを
意味しない**。`cc15aa` が訳し，`libc22` を繋ぎ，`ld17` が組み，
`kernel24` の上で走らせた `sed` で測り直した。

```
sh tools/diffsed.sh os
diffsed (os): 一致 40 / 食い違い 0
```

台本はファイル (`-f`) で渡す。**引用の差を測ってしまわないため**である
—— 我々のシェルとホストのシェルで `;` や `{` の扱いが違えば，`sed` の
差ではないものが差として出る。

#### 4.2 に対して何が言えるようになったか

4.2 は「上流の `configure` と `Makefile` が何を要求するかを静的に数え，
足りないものを表にする」と書いた。**その表の 1 行目が消えた** ——
`sed` が無いことは，数えるまでもなく最初から判っていた壁である。

残るのは `awk`・`tr`・`expr`・`sort`・`basename` などで，どれも
`sed` より小さい。**`grep` を正規表現へ引き上げる**のも，機構ができた
今は写すだけである。

### 5.6 機構を分け合い，道具を揃える (`re1` / `sed2` / `sh3`)

5.5 で作った正規表現機構は `sed` の中にあった。**`grep` も同じものを
使う**ので，そのままだと写しが 2 つになる —— この鎖が何度も踏んだ
「同じ規則を書く場所が 2 つある」形である
([stage018-ext.md](stage018-ext.md) 3.2 / 5.1)。

そこで 3 つに分けた。

| | 中身 |
|---|---|
| [stage017/re1.c](../stage017/re1.c) | 正規表現機構。**組む側で `exit` しない** (道具が診断の出し方を決められるように，-1 と理由を返す) |
| [stage017/sed2.c](../stage017/sed2.c) | `sed1` から機構を抜いたもの。受ける形は同じ |
| [stage017/sh3.c](../stage017/sh3.c) | シェルの第 3 世代。`grep` を正規表現へ引き上げ，`configure` が使う道具を足した |

#### `grep` は「静かに違う答」を返していた

`sh2` の `grep` は**固定文字列としてしか探さない**。`configure` は
`grep '^ac_cv_'` のような形を渡すので，そのままでは合うはずの行が
合わない —— **落ちるのではなく，空の結果を掴んで進む**。

`sh3` の `grep` は `re1` を使う。**`-E` (拡張正規表現) は名指しで
拒む** —— BRE として読むと `+` や `|` の意味が変わり，やはり静かに
違う答になるからである。

#### 足した道具

`tr` / `expr` / `basename` / `dirname` / `wc` / `sort` / `touch` /
`chmod`。どれも autoconf の `configure` が使う。

**組込みは `curout` / `curin` を見なければならない。** 我々のカーネル
には `dup2` が無いので，シェルはリダイレクトを「ファイル名の持ち回り」
で実現している。`printf` や `getchar()` を直に呼ぶと `> f` が素通しに
なり，`< f` は端末を待って**止まる**。最初 `tr` がそれで固まった。

#### 突き合わせ (`tools/difftool.sh`)

**28 件とも一致した。** 我々の OS の上で `sh3` に走らせ，同じ命令を

```

ok   15  expr abcdef : a\(b*\)c
```

### 5.7 機構を組み直す (`re2` / `sed3` / `sh4`)

`awk` に着手するには機構を作り直す必要があった。**awk が使うのは
ERE** で，`re1` は BRE 専用だったからである。作り直すにあたって
`re1` を測り直したところ，ERE 以外に 3 つ穴が出た。

| 台本 | `re1` (第 1 世代) | 正しい答 |
|---|---|---|
| `s/\(a*\)ab/[\1]/` を `aab` に | `aab` (**合わない**) | `[a]` |
| `s/[[:digit:]]/#/g` を `abc123` に | `abc123` (**合わない**) | `abc###` |
| `s/a\{2\}/X/` | **無限ループ** | `X`(b) |
| `s/ac\|ac_cv/X/` | **無限ループ** | 最長の `ac_cv` に合う |

上 2 つは**黙って違う答**である。`configure` の中で起きればそのまま
通り過ぎる —— 5.5 で `sed` を作った理由そのものが，ここでもう一度
出た形になる。

下 2 つは輪をかけて悪い。`re1` は `\{` と `\|` を「名指しで拒む」と
書いてあったが，**拒む処理が原文の位置を進めていなかった**ので，
診断を出さずに回り続けていた。「拒む」と書いてあることと，拒めて
いることは別である。

#### なぜ木ではなく命令列にしたか

`re1` は正規表現を節の木に組み，木を辿って照合していた。この形では
**組の中へ後戻りできない** —— `mgrp1()` が組を 1 回照合して到達点を
1 つ返す作りなので，続きが外れたときに「組の取り方を変えてやり直す」
道が無い。1 行目の穴はこれである。

[stage017/re2.c](../stage017/re2.c) は命令列
(CHAR / ANY / SET / SPLIT / JMP / SAVE / BREF / MARK / REP / MATCH) に
組んでから辿る。後戻りは**続きを引数に取った再帰**そのものになり，
組の中も外も同じ 1 つの仕組みで済む。選択 (`|`) は SPLIT がそのまま
担う。

受ける形も増えた —— ERE，`\{n,m\}` / `{n,m}`，`[[:alpha:]]` の類，
`\|`。逆に **`\<` `\>` `\b` `\w` `\s` は名指しで拒む**。GNU の
拡張で，字そのものとして通すと黙って違う答になる。今度は原文の位置を
進めずに戻る道が無いことを確かめてある。

#### 段数と手数を抑える 2 つの工夫

命令列を素直に辿ると `a*` のような形で**入力の長さぶんの再帰**が積む。
8 KiB の行で 8000 段になると危ない。そこで **1 文字の節の繰返しだけは
`I_REP` という 1 命令に畳んだ**。回数を数える繰返しは再帰しないので，
段数が入力に比例するのは組の繰返し (`\(ab\)*`) だけになる。

POSIX は**最左最長**を要求するが，後戻りは最左・貪欲である。両者が
分かれるのは選択があるときなので (`ac\|ac_cv`)，**選択を含む形だけ
全探索して最長を採る**。含まない形は最初に合った形で止める —— 全探索
は行長の 2 乗の手数になるので，必要な形だけに限る。

手数には上限を置き，当たったら `re_overrun()` で外へ伝える。道具の側
(`sed3` / `sh4` / `awk1`) はそれを見て止まる。**「判らなかった」を
「合わなかった」として通さない。**

#### 組の番号を組み直しごとに戻す

`re1` は `ngrp` を `re_reset()` でしか戻していなかった。sed の台本が

```
s/\(a\)\(b\)/[\2\1]/
s/\([0-9]\)/{\1}/
```

のように**組を 2 度使う**と，2 つめの命令の組が 3 番になり，`\1` は
1 番を指したままになる。`re2` は組むたびに 1 から数え直す。

#### 測り直した

`tools/diffsed.sh` に 19 件足して 59 件にした。足したのは上の表の形と，
`\{n,m\}`・字種・`\+`・`\?`・選択の最長一致である。

```
diffsed (host): 一致 59 / 食い違い 0
diffsed (os):   一致 59 / 食い違い 0
difftool:       一致 34 / 食い違い 0
```

`tools/difftool.sh` にも 6 件足して 34 件にした。`grep -E` と `egrep`，
それに `expr aabcd : a*abc` —— 最後のは**組の中への後戻り**で，
`re1` は 0 を返していた。

`sh4` では **`grep -E` を受けるようになった** (`egrep` も同じ)。
`sh3` が名指しで拒んでいたのは BRE しか無かったからで，理由が消えた。

### 5.8 `awk` (`awk1`)

`configure` が使う道具のうち最後に残っていたものである。autoconf の
`config.status` は awk 無しでは 1 行も書き出せない。

[stage017/awk1.c](../stage017/awk1.c) は POSIX awk の部分集合で，
字句 → 構文木 → 木を歩く の 3 段。これは `sh2` や `cc15` と同じ形で
ある。正規表現は持たず `re2` を使う —— **`re2` に ERE を入れたのは
そもそもこのためである**。

| 持つもの | |
|---|---|
| 規則 | `BEGIN` / `END` / 式 / 正規表現 / 範囲 (`p1, p2`) / 既定動作 |
| 式 | 代入 (7 種) / 三項 / `\|\|` `&&` / `in` / `~` `!~` / 比較 / 連結 / 四則 / `^` / 単項 / `++` `--` / `$` |
| 文 | `if` `while` `do` `for` `for(k in a)` `break` `continue` `next` `exit` `return` `delete` `print` `printf` |
| 組込み | `length` `substr` `index` `split` `sub` `gsub` `match` `sprintf` `toupper` `tolower` `int` `close` `srand` `rand` |
| 変数 | `NR` `NF` `FNR` `FS` `OFS` `ORS` `RS` `FILENAME` `SUBSEP` `RSTART` `RLENGTH` `CONVFMT` `OFMT` |
| その他 | 利用者定義関数 (再帰・配列の参照渡し・余った仮引数は局所) / `getline` (主入力とファイル) / `print > file` / `-f` `-v` `-F` / `var=value` の引数 |

持たないもの: パイプ (`cmd | getline` / `print | cmd`)，`system()`,
段落単位の `RS`，数学関数 (`libm` が無い。`int()` は持つ)，`ENVIRON`。
どれもカーネルか libc の側の話で，awk の側の手抜きではない。

#### 値が 2 つの顔を持つことを型で持つ

awk の値は文字列でも数でもある。**入力から来た値は「数に見えるなら数
として比べる」** (strnum)。この規則を落とすと `$1 == 0` の類が黙って
違う答になるので，型を 4 つ (未設定・数・文字列・数に見える文字列)
持って区別している。

#### 数を字にする形は自前で持った

CONVFMT / OFMT の既定は `%.6g` である。**libc22 の printf は `%g` を
`%f` と同じに扱っている** ——「動くが違う」である。awk の出力はほとんど
がこの変換を通るので，`%e` / `%f` / `%g` を awk の側で書いた。

libc の穴は libc の世代で直すべきもので，ここで測るものではない。
**libc23 の課題として記録する** (6.3)。

丸めで 1 か所詰まった。`printf "%.1f", 2.45` はホストでは `2.5` に
なる —— 2.45 は 2 進では 2.45 より僅かに大きいからである。ところが
`2.45 * 10` を素直に計算すると丁度 `24.5` に丸まり，「半端」に見えて
偶数丸めで `2.4` になる。**桁寄せの積を Dekker の手で正確に求めて**
半端かどうかを判定している。

#### 物差しはホストの awk である

[tools/diffawk.sh](../tools/diffawk.sh) に 85 件。**awk は言語ひとつ
ぶんあるので，我々が期待値を書くと我々の読み違いがそのまま期待値に
なる。**

```
diffawk (host): 一致 85 / 食い違い 0
diffawk (os):   一致 85 / 食い違い 0
```

順序の決まらない形 (`for (k in a)` の巡回順) は置いていない。POSIX が
実装ごとに違ってよいと定めているので，差ではないものが差として出る。

85 件のうち 1 件は**数を字にする形をまとめて測る**もので，19 個の値 ×
10 通りの書式 = 190 の変換を 1 件で突き合わせている。桁寄せの丸めは
ここでしか出ない。

#### ホストと分かれた 1 件

`substr(s, m, n)` の `m` が 1 未満のとき，POSIX の文言と gawk は
「位置 `m`〜`m+n-1` のうち在るものだけ」を返すので
`substr("hello", 0, 3)` は `he` になる。**mawk は `m` を 1 に切り上げて
から `n` 文字取る**ので `hel` になる。

我々は POSIX に合わせた。差分試験には置かず，値を
`tests/stage017/test.sh` に直に書いてある —— 5.2 で書いた
「ホストは万能の物差しではない」の 2 例目である。

#### 器の上限に当たった —— 関数の枠は 65528 バイトまで

最初に組んだとき，`cc15aa` が終了コード 6 で止まった。**`awk1.c` の
中で何が上限に当たったのかは，診断からは判らない** (終了コードだけ
である)。`cc15aa` の中の `exit(6)` を数え上げて絞り込んだところ，
`fnf > 65528` —— **1 つの関数の枠の大きさ**だった。

`char out[LINEMAX]` (64 KiB) を積んだ関数が 2 つあり，そのうち 1 つは
2 本積んでいた。**行ほどの大きさの入れ物を関数の枠に積まない**形に
直した (入れ子にならない使い方なので，場所を分けて静的に持つ)。
`LINEMAX` も 32 KiB に下げた。

我々の OS では枠の領域は 16 MiB あるので走ってはいたが，**器の上限は
器の上限である**。上限そのものを上げるのは cc の次の世代の仕事で，
ここで無理に押し込む話ではない。

同時に数と書式を [stage017/awkfmt1.c](../stage017/awkfmt1.c) へ分けた。
これは上限とは別で，**書式の仕事が「数と字を並べる」で閉じている**
からである。libc23 (6.3) がそのまま下敷きにできる形にもなる。

#### 見つかった穴 (自分の側)

差分試験を回して出たものを記録する。**どれも「動くが違う」形**である。

| | 何が起きたか |
|---|---|
| `$1 = $1` | 欄を解放してから複製していた (`setfield`)。解放済みの領域を読んで文字化けした。`$1 = $1` は **autoconf の生成する awk に実際に現れる**。同じ誤りが配列の要素 (`a[k] = a[k]`) にもあり，こちらは差分試験に件を足して初めて出た |
| `printf "%.0f", 2.5` | 半端を切り上げていた。ホストの printf は偶数へ丸める |
| `print 2 ^ 62` | 整数として出す境を `1e18` に切っていたので，`4611686018427387904` が `4.61169e+18` になった |

### 5.9 経路展開 (`sh5`)

4.2 の道具の表で最後に残っていたものである。

`sh2` は **経路展開 (glob) を持たない**と決めていた
([stage016-os.md](stage016-os.md) 10.1) —— tcc の `configure` では
`*` が `case` のパターンとパラメータ展開にしか出なかったからである。
GCC の `Makefile` と `configure` は `*.c` を使う。**無いと落ちるのでは
なく，語がそのまま残って進む** —— この鎖が何度も踏んだ形である。

#### 引用の印が 1 文字ごとに残っている

`sh2` は語を展開するとき，**どの文字が引用の中から来たか**を 1 文字
ごとに控えている (`eqf`)。これは `IFS` で切る位置を決めるために要る
ものだったが，そのまま経路展開にも効く —— `"*.txt"` と `\*.txt` の
`*` は引用されているので展開しない，と正しく決められる。

照合器は `case` 用の `patmatch` とは別に持った。引用されたメタ文字を
逆斜線で守った形で渡すので，**逆斜線を読む必要がある**からである
(`case` のパターンは引用がすでに落ちている)。

#### 出来上がった経路は実在しなければならない

最初に組んだとき `<星>/y.c` が

```
a.txt/y.c ab.c/y.c b.txt/y.c g.sh/y.c sub/y.c
```

を返した。メタ文字のある成分は一覧を通るが，**メタ文字の無い成分は
通らずに積んでいた**からである。POSIX の経路展開は「在る経路に合わせ
る」ものなので，出来上がった経路を最後に確かめる形へ直した。実在の
確認は `open` して閉じるだけで行う —— 我々の libc に `stat` は無く，
ディレクトリも開くことはできる。

#### 物差しはホストのシェルである

[tools/diffglob.sh](../tools/diffglob.sh) に 24 件。**同じ台本を両方の
シェルに食わせて**出力を比べる。

```
diffglob (host): 一致 24 / 食い違い 0
diffglob (os):   一致 24 / 食い違い 0
```

`echo *` は「その場に在るもの」を並べるので，**両方に同じ中身の
ディレクトリを見せなければ差ではないものが差として出る**。1 つ調整が
要った —— 我々のカーネルは像に入っていない `dev/null` を一覧に見せる
ので，ホスト側にも同じものを置いてある。これはシェルの差ではなく OS の
差である。

先頭が `.` の名前は測っていない。**我々の `readdir` は `.` と `..` を
返さない** (`dirent.h`。sfs に実体が無く，POSIX も未規定としている)
ので，やはりシェルの差ではないものが出る。

ので，その間は 5 章 (どの案でも等しく要るもの) を進める。5.3 は

([stage018-ext.md](stage018-ext.md))。GCC 4.7 の C 自身が C89 では
書かれていないので，4 に進んだ瞬間に要るものである。しかも GNU 拡張は
ホストの `gcc` が実装しているから，**差分試験がそのまま物差しになる**
—— 我々が期待値を書かずに済む。

### 6.2 sfsと差分build

`sfs3`はmtimeをnanosecond単位で保持し、`mk20`はその値からdependencyの更新を判定できる。この機能は既存testで確認済みであり、差分buildの判定ロジック自体に変更は不要である。

一方、前版の「項目数とimage sizeは`pack`の引数なので拡張できる」という記述は不正確だった。host側の`pack`は値を受け取れるが、kernel24がsfsに割り当てるaddress spaceは`0x84000000`から`0x86000000`までの32 MiBに限られる。GCC 4.7.4の配布木が必要とする最小imageは473,459,336 bytesであり、`pack`の引数だけでは解決しない。

したがって、差分build機能を作り直す必要はないが、GCCのbuildに進む前にsfs formatとkernel memory mapの世代更新が必要である。少なくともcomponentを50 bytes以上保持し、測定用source treeとbuild outputを同時に置ける容量を定義する。

**この結論に対する実装が7章である。** 差分buildの判定は1行も変えていない。

### 6.3 libc23 --- 浮動小数点の変換 (**済**)

`awk1` を書く途中で libc22 の穴が出た。**awk の側で回避したが，直す
場所は libc である。**

| | libc22 |
|---|---|
| `printf` の `%g` / `%e` | `%f` と同じ扱い。`%.6g` が `3.141590` になる |
| `printf` の `%E` / `%G` / `%F` | 変換として認識せず，**可変部を取り出さないまま次へ進む** |
| `printf` の丸め | 半端を 0 から遠い側へ倒す (`%.0f` の `2.5` が `3`)。ホストは偶数側 |
| `#` 旗・幅 | 浮動小数点に効かない |

[stage017/libc23](../stage017/libc23) で埋めた。`awk1` が持っていた
変換がそのまま下敷きになっている ([libc23.md](../stage017/libc23.md))。

#### 測った

[tests/stage017/probe/fltfmt.c](../tests/stage017/probe/fltfmt.c) を
差分試験に足した。33 個の値 × 11 通りの書式で，**我々の OS の上で
275 行が一致**する。

```
diff17 (os): 一致 8 / 食い違い 0
```

#### 写しを 2 つ持たない

`libc23` が穴を埋めたので，**`awkfmt1` が浮動小数点を自前で持つ理由が
消えた**。`fmte` / `fmtf` / `fmtg` を libc の `sprintf` へ委ねる薄い
包みに替え，桁寄せと半端の判定は `libc23/posix/stdio.c` の 1 か所だけ
にした (`awkfmt1.c` は 553 行から 318 行になった)。同じ規則を書く場所が
2 つあると必ず片方だけ直す誤りが出る —— この鎖が何度も踏んだ形である。

#### 限界を書いておく

**2 進の値を十進へ正確に展開してはいない。** 有効 18 桁までしか数えない
ので，有効 17 桁を求める形と，`%f` で 18 桁を超える値はホストと分かれる。
実際の呼び手が使うのは `%.6g` や `%.2f` の類なので，正確な展開 (多倍長
の整数演算が要る) は必要になった世代で足す。詳細は
[libc23.md](../stage017/libc23.md) 4 章。

`%#g` で丸めが桁上がりする値 (`%#.6g` の `999999.5`) では **glibc の
ほうが規格から外れている** ——`#` は「末尾の 0 を落とさない」であって
「落とす」ではない。ここは物差しに合わせていない (5.2 / 5.8 と同じ形の
3 例目)。

## 7. sfs4 と kernel25 —— 長い名前と広い窓 (6.1 の 3)

4.5 の測定に対する答である。**変えたのは名前の枠と像の置き場だけ**で、
差分buildの判定も、syscallの並びも、userlandも1行も変えていない。

### 7.1 sfs4

| | sfs3 | sfs4 |
|---|---:|---:|
| 項目の幅 | 72 bytes | 128 bytes |
| 名前の枠 | 48 bytes | 104 bytes |
| 名前の上限 | 47 bytes | 103 bytes |
| 頭の32 bytes | magic / size / tbloff / count / cursor | 同じ |
| 名前より後ろの6語 | parent / dataoff / len / flags / mtlo / mthi | 同じ順 |

magicは`sfs4`。道具は[tools/sfs4.sh](../tools/sfs4.sh)で、`pack` / `unpack` /
`list`の引数はsfs3と同じである。

**なぜ103か。** 項目を128 bytes = 2の冪にすると、索引から位置を出す算術が
乗算ではなく左shiftで済む。128から後ろの6語 (24 bytes) を引くと名前の枠が
104 bytes、終端の分を除いて103 bytesになる。実測の92 bytesに11 bytesの余りが
残る。

**長すぎる名前は黙って切らずに拒む。** 切ると同名衝突が起き、別のfileを
上書きする。104 bytesのcomponentは`name too long`で名指しで落とす。

**深さ10以上でpackが落ちていたのを直した。** `pack`はdirectoryを浅い順に
並べてから作るが、深さの印を0詰めせずに並べると文字列として比べられ、
`"10"`が`"2"`より前に来る。親より先に子が出て`parent not found`で落ちる。
tccの木は深さ6だったので表に出ていなかったが、GCC 4.7.4は深さ12なので
1 fileも載らなかった。`tools/sfs2.sh` / `sfs3.sh`にも同じ誤りがあったので
同時に直した。深さ9までの木では並び順が変わらないので、既存のimageは
1 byteも変わらない。

### 7.2 kernel25

kernel24の写しに`#define`と起動時の検査を入れただけである。

```
                kernel24        kernel25
  SFSA          0x8400_0000  -> 0xa000_0000     sfs image
  窓の上端      0x8600_0000     0xc000_0000     (SFSTOPを新設)
  窓の大きさ    33,554,432   -> 536,870,912 bytes
  RAM           512 MiB      -> 1 GiB
  PATHMAX       63           -> 255 bytes         (statat / spawn)
```

**名前を広げただけでは足りない。** 名前1段が103 bytes持てても、経路を受ける
器が63 bytesなら、92 bytesの名前は**rootに置いてもstatできない**。`open`は
経路をそのまま辿るので`cat`だけでは表に出ず、`stat`で初めて出る。GCC 4.7.4の
木は最長の経路が131 bytes・深さ12なので、余りを足して255にした。`mk20`の差分
buildは`statat`を使うので、ここが塞がっていると測定用treeを置いてもbuildできない。

**なぜ上へ移したか。** `0x8600_0000`より下は1 byteも動かせない。trap frame
(`0x8370_0000`)・kernel stack (`0x8380_0000`)・user像のload先
(`0x8600_0000`) はld16の前置部に機械語として焼き込まれており、動かすと
linkerの世代が要る。kernel19が記憶域を広げたときと同じ制約である。
上へ伸ばすしかなく、`SAVETOP` (`0xa000_0000`) の先が唯一の空きだった。

`0x8400_0000`〜`0x8600_0000`の32 MiBが空いた。`0x8100_0000`〜`0x8370_0000`と
合わせ、当面は使わない。

**kernel24とsfs3はそのまま残す。** `tools/tcc17.sh`と`tools/ext17.sh`
(tcc・zlib・bzip2をbuildする道) は32 MiBで足りており、動かす理由が無い。
凍結した世代は凍結したまま再現できることが、この鎖の前提である
([artifacts.md](artifacts.md))。kernel25へ移すのは、移す必要が測定で出て
からにする。

**窓に入らないimageは載せない。** 頭の大きさの欄を見て、窓を超えるなら`S`を
出して止まる。黙って載せると、はみ出した先は何も無い番地なので、書いた中身が
消える。形の違うimage (sfs3) は`?`で止まる。

### 7.3 測り直した結果

| | 値 |
|---|---:|
| GCC 4.7.4の最小image | 478,015,272 bytes |
| kernel25の窓 | 536,870,912 bytes |
| 余り | 58,855,640 bytes |
| 103 bytesを超えるcomponent | 0 |

**全配布木が窓に収まる。** ただし余りは56 MiBしかなく、build outputを同じ像に
置く余地は小さい。6.1の4に進むときは、必要なtranslation unitだけを取り出した
測定用treeを使う。

### 7.4 何を検査しているか

`tests/stage017` 第5部。

| 検査 | 中身 |
|---|---|
| roundtrip | 92 bytesの名前を含む木がsfs4に載って戻る。時刻もnanosecondまで一致 |
| cap (対照) | 同じ木をsfs3は名指しで拒む —— だから世代を刻んだ |
| cap | 103 bytesは載り、104 bytesは`name too long`で拒む |
| cap | 容量の式がtools/sfs4.shとkernel25.cの実際の値を読んでいる (答の判っている小さな木で確かめる) |
| cap | 深さ12の木 (経路131 bytes) がsfs4に載って戻る |
| run | 92 bytesの名前と131 bytesの経路を、引き・読み・作り、statする |
| run | guestが作った長い名前が、走った後のimageをhostで開いても在る |
| run | 旧世代の窓 (32 MiB) の外に置いた中身が読める |
| run | sfs3のimageは`?`で拒む |
| run | 窓を超える大きさのimageは`S`で拒む |
| run | 2^31を超える大きさも`S`で拒む —— 符号つきで比べていたら通り抜ける |

**「載る」だけでは足りない。** hostで詰められてもkernelが引けなければ意味が
ないので、長い名前は必ずguestでも引かせる。同じ理由で、窓が広がったことは
「旧世代なら届かない位置のfileが読める」という形でしか確かめない。
