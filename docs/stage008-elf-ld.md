# Stage 8: ELF オブジェクト + リンカ 設計文書

## 1. 目的と位置づけ

### 1.1 目的

occ までの処理系は入力 1 本を受け取り，そのままフラットバイナリを吐く。
翻訳単位を分けられないため，ソースが大きくなると 1 ファイルに押し込むほかなく，
外部のライブラリと結合する手段もない。

Stage 8 の目的は **分割コンパイル** を可能にすることである。コンパイラは
リロケータブルオブジェクトを出力し，リンカが複数のオブジェクトを結合して
実行像を作る。これは [roadmap.md](roadmap.md) Phase A の最初の段であり，
以降のすべて (プリプロセッサ・libc・外部資産の取り込み) の前提になる。

### 1.2 オブジェクト形式に ELF を選ぶ理由

独自形式のほうが実装は小さくて済むが，長期目標 (GCC・Linux) は ELF を前提と
しており，いずれ捨てることになる。加えて ELF なら verify 層の `objdump` /
`readelf` で自作オブジェクトの妥当性を機械的に検査できる。
最小部分集合に限れば実装量の差も小さいので，最初から ELF を採る。

### 1.3 非目標

- 動的リンク・共有ライブラリ。静的リンクのみ扱う。
- アーカイブ (`ar`) と部分リンク (`ld -r`)。Stage 13 で扱う。
- セクションの整列指定・リンカスクリプト・ガベージコレクション。
- `.data` (初期値つき大域変数)。初期化子は Stage 10 の課題であり，
  現状の言語仕様には初期値つき宣言が存在しない。大域変数は `.bss` に置く。

## 2. 構成の変更

### 2.1 これまでとの違い

```
Stage 7 まで:  occ(prog.sc)                        -> prog.bin
Stage 8 から:  cc(a.sc) -> a.o                     (翻訳単位ごと)
               cc(b.sc) -> b.o
               ld(a.o b.o) -> prog.bin
```

`cc` は Stage 7 の occ にオブジェクト出力を加えたもの，`ld` は新規である。
両者とも sc 言語で記述し，occ でブートストラップする。

### 2.2 ランタイム前置部の移動

occ は生成物の先頭に 32 語のランタイム前置部 (レジスタ初期化・`main` 呼出し・
`getc`/`putc`/`exit`) を置いていた。分割コンパイルでは，どの翻訳単位が
先頭に来るか決まらないため，これはコンパイラの仕事ではない。
**前置部はリンカが出力する** (実質的に crt0 に相当する)。

これに伴い `getc` / `putc` / `exit` は「コンパイラが知っている固定アドレス」から
「リンカが提供する外部シンボル」へ変わる。`cc` はこれらを未定義シンボルへの
呼出しとして出力し，`ld` が前置部内の実体へ解決する。

### 2.3 入力の与え方

実行環境は UART のみで，複数ファイルを開く手段がない。リンカへは
**オブジェクトを連結して標準入力から与える**。ELF ヘッダから全体長を
算出できるので，連結したまま順に切り出せる。

```
cat a.o b.o | ld > prog.bin
```

## 3. ELF 部分集合の仕様

### 3.1 生成するオブジェクト (ET_REL, RV32, リトルエンディアン)

ファイル配置は次の順とする (整列は 4 バイト)。

| 位置 | 内容 |
|---|---|
| 0 | ELF ヘッダ (52 バイト) |
| | `.text` の内容 |
| | `.symtab` (16 バイト/エントリ) |
| | `.strtab` (シンボル名) |
| | `.rela.text` (12 バイト/エントリ) |
| | `.shstrtab` (セクション名) |
| | セクションヘッダ表 (40 バイト/エントリ × 7) |

セクション:

| 番号 | 名前 | 種別 | 用途 |
|---|---|---|---|
| 0 | (なし) | NULL | 規約上の空エントリ |
| 1 | `.text` | PROGBITS, AX | コードと文字列リテラル |
| 2 | `.bss` | NOBITS, WA | 大域変数 (サイズのみ) |
| 3 | `.symtab` | SYMTAB | シンボル表 |
| 4 | `.strtab` | STRTAB | シンボル名 |
| 5 | `.rela.text` | RELA | `.text` に対する再配置 |
| 6 | `.shstrtab` | STRTAB | セクション名 |

ELF ヘッダの主な値: `e_ident` = `\x7fELF` + ELFCLASS32(1) + ELFDATA2LSB(1) +
EV_CURRENT(1)，`e_type` = ET_REL(1)，`e_machine` = EM_RISCV(243)，
`e_version` = 1，`e_ehsize` = 52，`e_shentsize` = 40，`e_shnum` = 7，
`e_shstrndx` = 6。`e_phoff` / `e_phnum` は 0。

### 3.2 シンボル

セクションシンボルは作らない。大域変数も関数も，それぞれ固有のシンボルとして
登録し，再配置はシンボルを直接参照する。これによりリンカ側で
「セクション + オフセット」を解く処理が不要になる。

| 種類 | `st_shndx` | `st_value` | `st_info` |
|---|---|---|---|
| 関数 (定義) | 1 (`.text`) | `.text` 内オフセット | GLOBAL FUNC |
| 大域変数 (定義) | 2 (`.bss`) | `.bss` 内オフセット | GLOBAL OBJECT |
| 未定義 | 0 (`SHN_UNDEF`) | 0 | GLOBAL NOTYPE |

`st_size` は大域変数のみ設定する (リンカが `.bss` を配置するために使う)。
0 番エントリは規約どおり全 0 とする。

### 3.3 再配置 (RELA)

必要なのは 4 種類である。

| 種別 | 番号 | 対象 | 計算 |
|---|---|---|---|
| `R_RISCV_32` | 1 | データ語 | `S + A` |
| `R_RISCV_JAL` | 17 | `jal` の 20 bit 変位 | `S + A - P` |
| `R_RISCV_HI20` | 26 | `lui` の 20 bit | `((S + A + 0x800) >> 12) & 0xfffff` |
| `R_RISCV_LO12_I` | 27 | `addi` の 12 bit | `(S + A) & 0xfff` |

`S` は解決したシンボルのアドレス，`A` は加数 (`r_addend`)，`P` は再配置を
適用する位置のアドレス。HI20 と LO12_I はそれぞれが独立にシンボルと加数を持ち，
対にする必要はない (RISC-V ELF psABI の規定どおり)。

`r_info` は `(シンボル番号 << 8) | 種別`。

### 3.4 コンパイラ側の変更点

occ からの差分は次の 3 点に集約される。

1. **大域変数のアドレスをコンパイル時に決めない。** occ は `bssp` を
   0x8010_0000 から順に配ってリテラルとして埋め込んでいた。cc では
   `.bss` 内オフセットを割り当てるだけにし，参照は
   `lui` + `addi` + HI20/LO12_I 再配置として出す。
2. **関数呼出しを再配置にする。** occ は定義済みなら `jal` を直接埋め，
   未定義なら未解決リストに繋いでいた。cc では常に `jal` を 0 変位で出し，
   JAL 再配置を付ける。同一オブジェクト内で解決できる場合もリンカに委ねる
   (処理を 1 本化するため)。
3. **文字列リテラルは `.text` 内の自己参照。** アドレスはリンク時に決まるので，
   HI20/LO12_I 再配置を自分自身のセクション先頭シンボルではなく，
   **その翻訳単位の内部シンボル** に対して張る。内部シンボルは
   `.L.str.N` という名前で LOCAL として登録する。

### 3.5 リンカの動作

1. 標準入力を読み切り，ELF ヘッダを辿って各オブジェクトの範囲を求める
2. 第 1 走査: 各オブジェクトの `.text` と `.bss` に最終位置を割り当てる
   (前置部の直後から `.text` を連結し，その後ろに `.bss` を置く)
3. 大域シンボル表を作る。定義の重複はエラー，未定義の残存もエラー
4. 前置部 (32 語) を出力し，`main` への `jal` を埋める
5. 各オブジェクトの `.text` を順に出力する
6. 再配置を適用する
7. `.bss` は出力しない (NOBITS)。実行時に 0 で埋まっている前提は
   ベアメタルでは QEMU の初期状態に依存する。この前提は Stage 12 で
   実行環境を移す際に見直す

ロードアドレスは従来どおり 0x8000_0000 固定。

### 3.6 エラー

| 終了コード | 条件 |
|---|---|
| 0 | 正常終了 |
| 1 | 入力が ELF でない・想定した部分集合に合致しない |
| 2 | 未定義シンボルが残った |
| 3 | シンボルの多重定義 |
| 4 | 再配置の値が表現範囲を超えた |
| 5 | `main` が未定義 |
| 6 | 容量超過 (オブジェクト数・シンボル数・出力サイズ) |

## 4. 成果物

| ファイル | 内容 |
|---|---|
| stage008/cc.sc | ELF オブジェクトを出力する C サブセットコンパイラ |
| stage008/ld.sc | リンカ |
| stage008/cc.md, stage008/ld.md | 説明文書 (ビルド手順・SHA-256・構造表) |

ブートストラップの順序:

```
occ(ld.sc)  -> ld0.bin      # occ はフラット出力なので単体で動く
occ(cc.sc)  -> cc0.bin
cc0(cc.sc)  -> cc.o ; ld0(cc.o) -> cc.bin
cc0(ld.sc)  -> ld.o ; ld0(ld.o) -> ld.bin
```

以降の正本は `cc.bin` / `ld.bin` である。

## 5. 検証計画 (tests/stage008)

1. ビルド再現: `cc.bin` / `ld.bin` の SHA-256 が各 `.md` の記載値と一致する
2. 固定点: `cc.bin` で `cc.sc` をコンパイルし `ld.bin` でリンクした結果が
   `cc.bin` と一致する。`ld` についても同様
3. **分割コンパイル**: 2 つの翻訳単位に分けたプログラム (一方が他方の関数と
   大域変数を参照する) が，個別コンパイル → リンクで正しく動作する
4. 同値性: Stage 5 の仕様スイート (arith/fib/ptr/struct/upper) が
   単一翻訳単位のまま `cc` + `ld` で動作する
5. ELF 妥当性 (verify 層): 生成した `.o` を `readelf -a` / `objdump -dr` で
   読み，セクション・シンボル・再配置が意図どおりであることを照合する
6. エラー系: 未定義シンボル → 2，多重定義 → 3，`main` 未定義 → 5

## 6. Stage 9 への接続

分割コンパイルが可能になると，翻訳単位間で宣言を共有する手段が必要になる。
それがプリプロセッサ (Stage 9) である。本 Stage の時点では，各翻訳単位が
参照する外部関数は「未定義シンボルへの呼出し」として暗黙に扱われ，
大域変数は各ファイルで再宣言する必要がある。この不便は Stage 9 の
`#include` で解消する。
