# Stage 18: C89 の外側 (C99 と GNU 拡張)

[roadmap.md](roadmap.md) の Stage 18 は「GNU C 拡張の実装」で，完了条件を
「カーネルが要求する拡張に対応する」と置いている。本書はその段の設計と
実測を残す。

## 1. なぜ今か

Stage 17 の 6.1 は 4 (GCC 4.7.4 の C を我々の器に読ませる) を次の手と
しているが，**これには配布木が要る**。取得と容量測定は済んでおり
SHA-256 も固定してあるが ([stage017-gcc.md](stage017-gcc.md) 4.5)，
実体は `docs/external/` (git ignore) に置く約束なので，取得元へ到達
できない環境では手元に無い。

**待つ間に，どの案でも等しく要るものを進める** —— これは 5 章の方針
そのものである。Stage 18 はその筆頭で，理由が 2 つある。

- **GCC 4.7 の C 自身が C89 では書かれていない。** `__attribute__`・
  `__extension__`・`__inline__`・文の後ろの宣言・指示つき初期化子を
  当たり前に使う。6.1 の 4 に進んだ瞬間に要るものである
- **測る物差しがある。** これらは GNU C とホストの `gcc` が実装して
  いるので，差分試験 (`tools/diff17.sh`) がそのまま使える。我々が
  期待値を書く必要が無い

## 2. 何を実装するか (順序)

**要るものから並べる。** 実物のソースに出る頻度と，実装の重さで決めた。

| | 中身 | 重さ | 状態 |
|---|---|---|---|
| 1 | GNU の別綴り (`__extension__` / `__inline__` / `__const__` / `__volatile__` / `__signed__` / `__restrict__` / `restrict`) | 軽 | **済** (`cc15w`) |
| 2 | 文の後ろの宣言 (C99 6.8.2) | 軽 | **済** (`cc15w`) |
| 3 | `for` の初期化での宣言 (C99 6.8.5.3) | 軽 | **済** (`cc15w`) |
| 4 | 指示つき初期化子 (`.f = v` / `[k] = v`。C99 6.7.8) | 中 | 未 |
| 5 | 文式 (`({ ... })`) | 中 | 未 |
| 6 | `typeof` / `__typeof__` | 中 | 未 |
| 7 | `__builtin_expect` / `__builtin_constant_p` / `__builtin_offsetof` | 中 | 未 |
| 8 | `case a ... b:` (範囲つき case) | 軽 | 未 |
| 9 | インライン asm (`__asm__ volatile`) | 重 | 未 |

`__attribute__` は Stage 14 の時点で既に落としてある (字句の段で丸ごと
捨てる)。`inline` の素の綴りも既に読み捨てている。

**9 (インライン asm) は最後でよい。** カーネル (L2) には要るが，GCC の
C をビルドする道には出てこない —— 出てくるのは `libgcc` の一部で，
そこは我々の実行時支援 (`rt64` / `rtfp`) が既に埋めている領域である。

## 3. 第 1 陣 (`cc15w`) —— 1〜3

[stage015/cc15w.md](../stage015/cc15w.md) に世代の記録がある。ここには
設計の判断だけを書く。

### 3.1 別綴りは字句の段で片付ける

綴りが違うだけで意味は同じなので，構文の側を触る理由が無い。
`streq` の並びに足して同じトークンを返す。

`__extension__` だけは扱いが違う。これは「この先で拡張を使う。診断を
出すな」という**印**であって型でも修飾子でもないので，`__attribute__`
と同じ場所で落とす。**我々は診断を出さないので，落とすだけで意味が
合う。**

`restrict` は C99 の予約語で「この経路でしか触らない」という約束だが，
我々は最適化の判断に使っていない。`const` / `volatile` と同じく
**読み飛ばす修飾子**として扱えば意味は変わらない。

### 3.2 宣言と文の環は 2 か所ある

C89 は複文の先頭に宣言をまとめることを要求する。C99 は混ざってよい。
我々の器は環を 2 か所に持っていた ——

- `stmt()` の複文 (`{` … `}`)
- **関数本体の最外**。ここは `stmt()` を通らず自前で回している

片方だけ直すと「関数の途中では書けるが，本体の直下では書けない」と
いう妙な処理系になる。**最初に複文だけ直して試し，それで落ちたので
気づいた** —— 2 か所あることは，直して測るまで判らなかった。

関数本体の側では，制御構造の状態 (`brkn` / `conn` / `swn` …) の初期化を
環より前へ移した。文がいつ来てもよい状態にしてから入る必要がある。

### 3.3 `for` の初期化での宣言

複文と同じに `lcnt` / `cloff` / `lblk` を退避して戻す。`for` を抜けた
後に同じ名前を使い直せることまで含めて C99 の規則である。

**戻す場所は 2 つある** —— 歩進の無い `for` と，ある `for` で出口が
分かれているためで，片方だけ戻すとフレームが伸びたまま残る。

### 3.4 残る穴: `typedef` 名と同じ名前の変数

宣言か文かの見分けは `istype()` ただ 1 つで，これは名前が `typedef` 名
かどうかしか見ない。同じ名前の局所変数を作ると取り違える。

**新しく生じた穴ではない。** 先頭にまとめる書き方でも，複文の先頭で
`foo = 1;` と書けば同じことが起きた。当たる場所が増えただけである。
解くには宣言子の先読みが要るので，実物がこの形を使うことが判ってから
にする。

## 4. 測り方 —— C89 の外側は「拒む」が言い訳にならない

差分試験は，我々が拒んだときに `gcc -std=c89 -pedantic-errors` へ
「その入力は本当に誤りか」を訊く形になっている
([stage017-gcc.md](stage017-gcc.md) 5.2)。

**この裏取りは C89 の外側では素通しになる。** C99 や GNU の書き方は
C89 モードのホストなら当たり前に拒むので，*我々が実装できていない
だけの拒否*が「拒むのが正しい」に化ける。実際，`c99decl` を最初に
走らせたときはこう出た。

```
ok   c99decl        我々は拒む (rc=1)。C89 として誤り
                    (error: 'for' loop initial declarations are only allowed in C99 mode)
```

**我々の器はこのプローブを通すために書いたのに，通らないまま緑に
なった。** そこで `tools/diff17.sh` に `beyond_c89` の名簿を置き，
載っているプローブは**拒んだ時点で落とす**ようにした。

これは 5.2 の「台帳の期待値は我々が書いている」と同じ筋の話である ——
**裏取りの仕組み自体が，測る対象によっては嘘をつく。**

## 5. 次

4 (指示つき初期化子) が次である。GCC 4.7 の C も Linux も当たり前に
使い，どちらも「無いと書き換えるしかない」形である。実装は `ginit` /
`ginit1` / `linit` の対象選択に指示子を足す形になる。
