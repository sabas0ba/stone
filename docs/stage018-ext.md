# Stage 18: C89 の外側 (C99 と GNU 拡張)

[roadmap.md](roadmap.md) の Stage 18 は「GNU C 拡張の実装」で，完了条件を
「カーネルが要求する拡張に対応する」と置いている。本書はその段の設計と
実測を残す。

## 1. なぜ今か

Stage 17 の 6.1 は 4 (GCC 4.7.4 の C を我々の器に読ませる) を次の手と
しているが，**これには配布木が要る**。取得と容量測定は済んでおり
SHA-256 も固定してあるが ([stage017-gcc.md](stage017-gcc.md) 4.5)，
実体は `docs/external/` (git ignore) に置く約束なので，取得元へ到達
できない環境では手元に無い。

**待つ間に，どの案でも等しく要るものを進める** —— これは 5 章の方針
そのものである。Stage 18 はその筆頭で，理由が 2 つある。

- **GCC 4.7 の C 自身が C89 では書かれていない。** `__attribute__`・
  `__extension__`・`__inline__`・文の後ろの宣言・指示つき初期化子を
  当たり前に使う。6.1 の 4 に進んだ瞬間に要るものである
- **測る物差しがある。** これらは GNU C とホストの `gcc` が実装して
  いるので，差分試験 (`tools/diff17.sh`) がそのまま使える。我々が
  期待値を書く必要が無い

## 2. 何を実装するか (順序)

**要るものから並べる。** 実物のソースに出る頻度と，実装の重さで決めた。

| | 中身 | 重さ | 状態 |
|---|---|---|---|
| 1 | GNU の別綴り (`__extension__` / `__inline__` / `__const__` / `__volatile__` / `__signed__` / `__restrict__` / `restrict`) | 軽 | **済** (`cc15w`) |
| 2 | 文の後ろの宣言 (C99 6.8.2) | 軽 | **済** (`cc15w`) |
| 3 | `for` の初期化での宣言 (C99 6.8.5.3) | 軽 | **済** (`cc15w`) |
| 4 | 指示つき初期化子 (`.f = v` / `[k] = v`。C99 6.7.8) | 中 | **済** (`cc15x`) |
| 5 | 文式 (`({ ... })`) | 中 | **済** (`cc15y`) |
| 6 | `typeof` / `__typeof__` | 中 | **済** (`cc15z`) |
| 7 | `__builtin_expect` / `__builtin_constant_p` / `__builtin_offsetof` | 中 | 未 |
| 8 | `case a ... b:` (範囲つき case) | 軽 | **済** (`cc15aa`) |
| 9 | インライン asm (`__asm__ volatile`) | 重 | 未 |

`__attribute__` は Stage 14 の時点で既に落としてある (字句の段で丸ごと
捨てる)。`inline` の素の綴りも既に読み捨てている。

**9 (インライン asm) は最後でよい。** カーネル (L2) には要るが，GCC の
C をビルドする道には出てこない —— 出てくるのは `libgcc` の一部で，
そこは我々の実行時支援 (`rt64` / `rtfp`) が既に埋めている領域である。

## 3. 第 1 陣 (`cc15w`) —— 1〜3

[stage015/cc15w.md](../stage015/cc15w.md) に世代の記録がある。ここには
設計の判断だけを書く。

### 3.1 別綴りは字句の段で片付ける

綴りが違うだけで意味は同じなので，構文の側を触る理由が無い。
`streq` の並びに足して同じトークンを返す。

`__extension__` だけは扱いが違う。これは「この先で拡張を使う。診断を
出すな」という**印**であって型でも修飾子でもないので，`__attribute__`
と同じ場所で落とす。**我々は診断を出さないので，落とすだけで意味が
合う。**

`restrict` は C99 の予約語で「この経路でしか触らない」という約束だが，
我々は最適化の判断に使っていない。`const` / `volatile` と同じく
**読み飛ばす修飾子**として扱えば意味は変わらない。

### 3.2 宣言と文の環は 2 か所ある

C89 は複文の先頭に宣言をまとめることを要求する。C99 は混ざってよい。
我々の器は環を 2 か所に持っていた ——

- `stmt()` の複文 (`{` … `}`)
- **関数本体の最外**。ここは `stmt()` を通らず自前で回している

片方だけ直すと「関数の途中では書けるが，本体の直下では書けない」と
いう妙な処理系になる。**最初に複文だけ直して試し，それで落ちたので
気づいた** —— 2 か所あることは，直して測るまで判らなかった。

関数本体の側では，制御構造の状態 (`brkn` / `conn` / `swn` …) の初期化を
環より前へ移した。文がいつ来てもよい状態にしてから入る必要がある。

### 3.3 `for` の初期化での宣言

複文と同じに `lcnt` / `cloff` / `lblk` を退避して戻す。`for` を抜けた
後に同じ名前を使い直せることまで含めて C99 の規則である。

**戻す場所は 2 つある** —— 歩進の無い `for` と，ある `for` で出口が
分かれているためで，片方だけ戻すとフレームが伸びたまま残る。

### 3.4 残る穴: `typedef` 名と同じ名前の変数

宣言か文かの見分けは `istype()` ただ 1 つで，これは名前が `typedef` 名
かどうかしか見ない。同じ名前の局所変数を作ると取り違える。

**新しく生じた穴ではない。** 先頭にまとめる書き方でも，複文の先頭で
`foo = 1;` と書けば同じことが起きた。当たる場所が増えただけである。
解くには宣言子の先読みが要るので，実物がこの形を使うことが判ってから
にする。

## 4. 測り方 —— C89 の外側は「拒む」が言い訳にならない

差分試験は，我々が拒んだときに `gcc -std=c89 -pedantic-errors` へ
「その入力は本当に誤りか」を訊く形になっている
([stage017-gcc.md](stage017-gcc.md) 5.2)。

**この裏取りは C89 の外側では素通しになる。** C99 や GNU の書き方は
C89 モードのホストなら当たり前に拒むので，*我々が実装できていない
だけの拒否*が「拒むのが正しい」に化ける。実際，`c99decl` を最初に
走らせたときはこう出た。

```
ok   c99decl        我々は拒む (rc=1)。C89 として誤り
                    (error: 'for' loop initial declarations are only allowed in C99 mode)
```

**我々の器はこのプローブを通すために書いたのに，通らないまま緑に
なった。** そこで `tools/diff17.sh` に `beyond_c89` の名簿を置き，
載っているプローブは**拒んだ時点で落とす**ようにした。

これは 5.2 の「台帳の期待値は我々が書いている」と同じ筋の話である ——
**裏取りの仕組み自体が，測る対象によっては嘘をつく。**

## 5. 第 2 陣 (`cc15x`) —— 4

[stage015/cc15x.md](../stage015/cc15x.md) に世代の記録がある。ここには
設計の判断だけを書く。

### 5.1 初期化子を読む道は 4 本ある

`ginit` (大域の配列の最外)・`ginit1` (大域の入れ子)・`linit` の構造体・
`linit` の配列。**4 本とも直さないと，同じ書き方が場所によって通ったり
通らなかったりする。** 実際，最初に `ginit1` だけを直したときは
`static struct S g = { .b = 2 };` は通ったが
`static int a[5] = { [4] = 5 };` が落ちた —— 最外の配列は `ginit` が
自前で読んでいるからである。

3.2 の「環は 2 か所ある」と同じ形の見落としで，**どちらも
「直して測る」まで判らなかった。**

### 5.2 大域と局所で仕組みが違う

大域は `.text` へバイトを順に書くので，指示子は「書く位置を移す」
ことになる。局所は先に全体を 0 で埋めてから代入を出すので，
「代入先を選ぶ」だけで済む。

### 5.3 触れなかった場所は 0 である —— 戻るときに詰めてはいけない

跳ぶたびに隙間を埋めるが，**埋めてよいのは「まだ誰も書いていない
場所」だけ**である。書いた最後尾 (`hw`) より手前には既に値があるので，
戻るときは位置を移すだけにする。

最初はここを数え落とし，戻るときも詰める道を通していた。
`{ .b = 2, .a = 1, .c = 3 }` の `b` が 0 に戻り，和が 6 でなく 4 に
なる —— **落ちるのではなく値が違う**という，いちばん見つけにくい形で
ある。プローブが値の食い違いとして出した。

### 5.4 受けないもの

連ねた指示子 (`.a.b = v` / `[k].f = v` / `[i][j] = v`) は `exit(5)` で
拒む。**黙って別の場所を埋めるより拒むほうがよい。** 実装は「指示子の
並びを辿って位置と型を出す」形になるので，要ることが判ってから足す。

## 7. 第 3 陣 (`cc15y`) —— 5

[stage015/cc15y.md](../stage015/cc15y.md) に世代の記録がある。

**文式はマクロの中に出る。** GCC とカーネルのヘッダは，引数を 1 度
だけ評価する `max` / `min` をこの形で書く —— つまり**呼ぶ側のソースを
直しても避けられない**。ここまでの 4 つ (別綴り・宣言の位置・指示つき
初期化子) は「書き換えれば避けられる」ものだったが，これは違う。

### 7.1 見分けは 1 文字

一次式の `(` を読んだ直後が `{` なら文式である。キャストは `(` の次が
型名なので既に別の道へ入っており，ここへは来ない。

### 7.2 中身は複文の環に「値を控える」を足したもの

文の環を回しながら，式文に当たるたびに値と型を覚え，`}` に来た時点の
最後のものを返す。**右辺値にしてから控える** —— 左辺値のまま返すと，
呼び手はアドレスを値として使う。

環の中では宣言・文・式文の 3 通りが来る。宣言は `istype()`，文は先頭の
トークンで見分けるが，**ラベル (`名前 :`) だけは 1 つ先を見ないと式と
区別がつかない**。`stmt()` が使っているのと同じ手を使う。

### 7.3 最後が式文でなければ拒む

GNU C は「その場合の値は void」と定める。我々がここへ来るのは値の要る
場所だけなので，黙って前の式の値を返すより `exit(5)` で拒む。

## 9. 第 4 陣 (`cc15z`) —— 6

[stage015/cc15z.md](../stage015/cc15z.md) に世代の記録がある。

**`typeof` は文式と組で使う。** カーネルのヘッダの `container_of` /
`min` / `max` はどれもその形で，片方だけでは足りない。だから 5 の次に
置いた。

### 9.1 コードを出さずに式を読む

**我々の器は読みながら出す。** 型だけが要る場所では出したものを捨てる
—— IR (`icnt`)・ラベル (`labcnt`)・文字列 (`spcnt`) の位置を控えて
戻す。

**式そのものは普通に読む。** 型付けの規則を「式の道」と「型だけの道」で
2 つ持つと，必ず片方だけ直す誤りが出る。3.2 と 5.1 で 2 度出た
「同じ規則を書く場所が 2 つある」の予防である。

### 9.2 配列は退化させない

`typeof(a)` の `a` が配列なら型も配列である。式の側は配列を先頭要素へ
のポインタへ退化させるので，退化前の型を使う。

## 11. 第 5 陣 (`cc15aa`) —— 8

[stage015/cc15aa.md](../stage015/cc15aa.md) に世代の記録がある。

`case` の値の表と対に**上端の表**を持ち，普通の `case` では両方に同じ
値を入れる。振分けの側は「上端 == 下端なら等値で，違えば
`lo <= v && v <= hi` で」比べる。空の範囲 (`case 20 ... 19:`) は
その形のまま偽になるので特別扱いが要らない。

**世代の名前が英字を使い切った。** `cc15a` 〜 `cc15z` の次は `cc15aa`
とする。置き場は `stage015/` のままである。

## 12. 差分試験をコンパイラ側へ広げた (`cc15ab`)

C89 の外側 (Stage 18 の本題) とは別に，**C89 の内側にも穴が残っていた**。
配布木を待つあいだに，器そのものの差分試験を広げて 5 つ見つけた。

### 12.1 足したプローブ

[tests/stage015/probe](../tests/stage015/probe) に 4 本。どれも同じ
ソースをホストの処理系にも走らせて出力を突き合わせる形で，**我々が
期待値を書いていない**。

| | 何を測るか | なぜ要るか |
|---|---|---|
| `bitfld` | ビットフィールドの並び・出し入れ・初期化子 | **GCC 自身がビットフィールドの塊である** (`tree` の旗) |
| `funcptr` | 関数ポインタの配列・構造体の中・引数・返却 | GCC は hooks の表で出来ている |
| `intconv` | 整数の格上げ・符号・けた移動・割り算・複合代入 | `cc15u` と同じ場所。**動くが違う**しか起きない |
| `aggr` | 構造体の値渡し・共用体・入れ子の初期化子 | 表の添字が静かにずれる |

### 12.2 物差しに的の約束を伝える

2 か所で「器の誤りでない差」が出たので，測り方の側を直した。

- **`char` の符号。** 素の `char` が符号つきかは処理系定義で，RV32
  (我々の的) は符号なし，x86-64 のホストは符号つきである。ホストを
  `-funsigned-char` で組む —— `-std=c89` を伝えるのと同じ筋で，我々に
  合わせているのではない
- **語長。** ポインタを含む構造体の `sizeof` と `long` の最小値は
  ILP32 と LP64 で必ず違う。プローブの側からその形を外した

### 12.3 出た 5 つ

| | 何が起きていたか | 種別 |
|---|---|---|
| 無名のビットフィールド (`unsigned : 5;` / `unsigned : 0;`) | 名前が無い時点で拒む | gap |
| 関数ポインタの配列 (`int (*tab[3])(int, int)`) | 名前の直後の `[n]` を読まない | gap |
| 逆向きの添字 (`3[p]`) | 左がポインタであることを要求する | gap |
| **静的な初期化子のビットフィールド** | メンバごとに記憶単位を書くので 2 つめ以降が別の語へ行く。`{1,0,5,200}` が `{1,0,0,0}` になる | **bad** |
| **関数ポインタ越しの 64 bit 返却** | 上位語を引き取らず，データスタックからも捨てない | **bad** |

下 2 つは**通ったうえで値が違う**。しかも**我々のソースが使っていない
形**である —— ビットフィールドを静的に初期化する場所も，`double` を
返す関数ポインタを呼ぶ場所も鎖の中に無い。固定点もバイト一致も捕まえ
ない誤りで，`cc15u` と同じ構図である。

### 12.4 いちばん悪かった 1 つ

関数ポインタ越しの `double` の返却は，値が違うだけでは済まない。

```
d = dbl;  pn((long)(d(2.5, 4.0) * 100.0));   ホスト 1000 / 我々 400
```

`400` は `4.0 * 100` である。呼出しは下位語しか引き取らず `ehi` を
触らずに戻るので，**直前の式 (最後の引数 4.0) の上位語が残って混ざる**。
`10.0` の下位語は 0 なので，`4.0` の上位語と組んで丁度 `4.0` になった。

さらに悪いことに，上位語をデータスタックから捨てていない。**呼ぶたびに
スタックが 1 語ずれる。** 名前つきの呼出し (`c_call`) には引取りが
あったが，値を呼ぶ側 (`c_calli`) に無かった —— 同じ規則を書く場所が
2 つある形である。

### 12.5 受けない形を 1 つ残した

関数ポインタを**返す**関数を直に書く形 (`int (*pick(int))(int, int)`)
は受けない。宣言子の途中で「これは関数定義である」と判る形になり，
宣言の読み方そのものを組み直すことになる。typedef を挟めば書けるので，
実物が要求してから直す。

```
diff17 (bare): 一致 31 / 食い違い 0 / 飛ばした 6
```

## 13. 次

7 (`__builtin_*`) と 9 (インライン asm) が残る。

**7 はどれが要るかが配布木を読むまで決まらない**ので，4.1 の表が出て
からにする —— 先回りで実装すると，また我々の思い込みが期待値になる
(5.2 と同じ筋)。9 は L2 (Linux) の段で要る。

ここまでで **C89 の外側のうち「書き換えでは避けられないもの」は
出揃った** —— 文式と `typeof` はマクロの中に出るので，呼ぶ側を直しても
逃げられない。残りはどちらも「実物が要求してから」で足りる。
