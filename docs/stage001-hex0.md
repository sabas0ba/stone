# Stage 1: hex0 設計文書

## 1. 目的と位置づけ

### 1.1 目的

Stage 0 までの成果物にバイナリを生成する手段はなく，実行物は人手エンコードした
生バイナリを直接 git 管理するほかない。この方式は監査性は高いが，
1 バイトの修正でもバイナリ全体の差し替えとなり，開発の反復に耐えない。

hex0 の目的は，「人手で管理する生バイナリ」を hex0 自身の 1 個で打ち止めにすることである。
hex0 が導入されると，以降のプログラムは hex テキスト (注釈・コメント付きで diff 可能な
ソース形式) として記述・管理し，バイナリはビルドで再生成できるようになる。
これは docs/plan.md 2.1 の純度ポリシーを保ったまま，開発対象を
「バイナリの直接管理」から「ソースの管理」へ移行させる最初の段階である。

### 1.2 用途

- Stage 2 (hex1: ラベル対応) のソースは hex0 言語で記述し，hex0 でビルドする。
  hex0 の唯一の実運用上の用途はこれである。
- 副次的な用途として，人手エンコードの検証がある。listing から起こした hex テキストを
  hex0 に通した出力と管理下のバイナリを比較することで，転記誤りを機械的に検出できる
  (6 章のテストはこの形をとる)。

使用形態はホスト側から見ると通常のフィルタと同じである:

```
sh tools/env.sh qemu stage001/hex0.bin < stage002/hex1.hex > tmp/hex1.bin
```

### 1.3 非目標

- 人間が大規模なプログラムを hex0 言語で書き続けることは想定しない。
  ラベルもアドレス計算もないため，分岐オフセットの手計算は Stage 1 までで終わりにし，
  その解消は Stage 2 (hex1) が担う。
- hex0 自身の機能拡張は行わない。改良はすべて後継 Stage で行い，
  hex0.bin は完成後凍結する (7 章)。

hex0 自体は人手で命令エンコードした生バイナリとして git 管理する (docs/plan.md 2.1)。
hex0 のバイナリ生成に変換ツールは使用しない。

## 2. 入力言語仕様 (hex0 言語)

### 2.1 文法

```
input    := element* end
element  := byte | comment | ws
byte     := hexdig hexdig     ; 2 桁で 1 バイト。桁間に他の文字を挟めない
hexdig   := '0'..'9' | 'a'..'f'
comment  := '#' (LF 以外の任意バイト)*
ws       := SP | TAB | CR | LF
end      := '.'
```

- `byte` は読み取り完了と同時に 1 バイトとして即時出力する。
- `comment` は `#` から行末 (LF) の直前までを読み飛ばす。LF 自体は `ws` として扱う。
- `end` (`.`) を読むと正常終了する。以降の入力は読まない。

### 2.2 文字集合

- 16 進数字は小文字のみ許可する。大文字 (`A`..`F`) はエラーとする。
  最小実装を優先し，表記の揺れを仕様側で排除するためである。
- 入力は ASCII を前提とする。コメント内に限り任意バイトを許容する。

### 2.3 エラー

| 終了コード | 条件 |
|---|---|
| 0 | `end` により正常終了 |
| 1 | 許可されない文字を読んだ (`byte`/`comment`/`ws`/`end` のいずれにも該当しない，または桁間への他文字の混入) |
| 2 | 16 進数字が 1 桁の状態で `end` を読んだ |

エラー検出時は即時に異常終了し，以降の入力を処理しない。
入力が `end` を含まない場合，hex0 は入力を待ち続ける (タイムアウトは持たない)。
実行の打切りとテストでの時間制限はホスト側の責務とする。

## 3. 実行環境インタフェース

| 項目 | 内容 |
|---|---|
| ロード | フラットバイナリを 0x8000_0000 に配置 (QEMU virt, `-bios`) |
| UART | 16550 互換 @ 0x1000_0000。RBR/THR (offset 0), LSR (offset 5) のみ使用 |
| 受信 | LSR bit0 (Data Ready) をポーリングし，RBR を読む |
| 送信 | LSR bit5 (THR Empty) をポーリングし，THR へ書く |
| 終了 | test finisher @ 0x0010_0000。正常: 0x5555，異常: (code << 16) \| 0x3333 |

割込みは使用しない。DRAM のデータ領域も使用しない (状態はレジスタのみで保持する)。

## 4. 実装方針

- RV32I のみ使用 (M 拡張不使用)。サブルーチンなしの単一ループで実装し，
  スタックも使用しない。
- 状態はレジスタのみで保持する:

| レジスタ | 役割 |
|---|---|
| x5 | UART base (0x1000_0000) |
| x6 | test finisher base (0x0010_0000) |
| x7 | 受信文字 |
| x8 | 組立て中のバイト値 |
| x9 | 桁状態 (0: 上位桁待ち, 1: 下位桁待ち) |
| x10-x15 | 比較用定数・一時値 |

- 16 進数字の値化は範囲比較 2 回 (`0`..`9`, `a`..`f`) で行う。変換表は持たない。
- 規模の見積りは 40〜60 命令 (160〜240 バイト)。

## 5. 成果物と管理形態

| ファイル | 内容 |
|---|---|
| stage001/hex0.bin | 生バイナリ (人手エンコード)。これが唯一の実行成果物 |
| stage001/hex0.md | 説明文書: 仕様参照，SHA-256，全命令の注釈付き listing |
| stage001/hex0.hex | hex0 言語で書いた hex0 自身のソース表現。検証入力であり，ビルドには使用しない |

hex0.hex は hex0.md の listing と同一のバイト列を機械可読形式で保持する。
両者の整合はテストで検証する (6 章)。

## 6. 検証計画 (tests/stage001)

1. 完全性: hex0.bin が hex0.md 記載の SHA-256 と一致すること
2. 自己再生成: `hex0(hex0.hex) == hex0.bin` (ビット一致)。完了条件 (docs/plan.md 4 章)
3. 交差検証: `hex0(hello.hex) == tests/stage000/hello.bin`。hello の listing を
   hex0 言語で記述した検証入力を用意する
4. エラー系: 不正文字で終了コード 1，奇数桁 + `end` で終了コード 2
5. verify 層: hex0.bin を objdump で逆アセンブルし，hex0.md の listing と照合する
   (手順とスクリプトは verify/ 配下)

## 7. Stage 2 への接続

Stage 2 (ラベル対応 hex1) のソースは hex0 言語で記述し，hex0 でビルドする。
以降 hex0.bin を再エンコードすることはなく，機能追加はすべて後継の Stage で行う。
