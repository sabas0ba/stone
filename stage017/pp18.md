# pp18 説明文書

pp18 は C プリプロセッサの第 18 世代である。[pp17.sc](pp17.sc) の
**全文複製**に，**展開の結果に現れた `defined` を評価する**ことだけを
足した。器も，`-I` の探し方も，出力の 1 バイトも変えていない。

ソース [pp18.sc](pp18.sc) が正本である。

## ビルド

```
sh tools/build.sh stage017
# cc15p(pp18.sc) -> pp18.o -> ld16 'E' -> pp18
```

SHA-256: 08052d462181a62ebeb780e60ac8e750d8d0aa1b109e466c921422442ff7790e

## なぜ要ったか

GCC 4.7.4 の **libcpp 13 単位すべてが，1 つの形で止まっていた**
([docs/stage017-gcc.md](../docs/stage017-gcc.md) 8.4)。

`libcpp/system.h` 379 行がこう定義する。

```c
#define HAVE_DESIGNATED_INITIALIZERS \\
  (!defined(__cplusplus) \\
   && ((GCC_VERSION >= 2007) || (__STDC_VERSION__ >= 199901L)))
```

そして `libcpp/internal.h` 577 行が `#if HAVE_DESIGNATED_INITIALIZERS`
と書く。

**`defined` は本来，展開より先に潰す。** C89 がそう定めており，pp16 から
`dodefined()` がそうしている。その規定は pp18 でも変えていない。

問題は**マクロの本体に `defined` が書いてある**ときである。
`dodefined()` が走る時点で式は `HAVE_DESIGNATED_INITIALIZERS` の 1 語
しかない。展開してはじめて `defined(__cplusplus)` が現れるが，そのときには
`dodefined()` は終わっている。pp17 までは残った `defined` を識別子として
0 に潰し，続く `(` で構文が壊れて **4 (条件指令の誤り)** で止まっていた。

## 規格の上では拒むのが正しい

**C89 6.8.1 はこの形を未定義動作としている。** ホストの
`gcc -std=c89 -pedantic-errors` も
`this use of "defined" may not be portable` で拒む。pp17 が 4 で止まるのは
**誤りではない**。

**それでも通す。** GCC 4.7.4 の libcpp は自分自身がこの形を受けることを
前提に書かれており，ここを通さなければ 1 単位も訳せない。GCC を組むのが
目的である以上，選ぶ余地は無い。ホストの cpp も clang も評価する側に
倒しており，**倒す先は 1 つしかない**。

## 何を足したか

3 つだけである。

| | 中身 |
|---|---|
| `ebuf[64]` | `#if` の式の中で読んだ識別子。**`nbuf` とは別に持つ** —— 同じ枠を貸し借りすると「どちらがいつ使うか」を追わなければ読めなくなる |
| `ename()` | `eb` から識別子を読む。63 バイトで切る (下記) |
| `edefined()` | `defined X` と `defined ( X )` を読んで 1 / 0 を返す |

`enext()` は識別子を読んだあと，それが `defined` なら `edefined()` を
呼ぶ。そうでなければこれまでどおり値 0 の数として扱う。

**名前を 63 バイトで切ってよい理由。** この名前は `defined` の判定にしか
使わず，63 バイトを超える名前はマクロの表が持つ枠 (64 バイト) にそもそも
入らない。切った名前は必ず「定義されていない」になる。

## 書いておく限界

**`defined` の operand が定義済みマクロのときは，pp18 も 4 で拒む。**

```c
#define X 1
#define M (defined(X))
#if M                    /* pp18 も 4 で止まる */
```

展開のときに operand の `X` 自身が `1` へ展開されるので，`edefined()` が
見るときには名前が消えている。**黙って違う答を出すのではなく拒む。**
正しく直すには展開器の側で `defined` の operand を展開しないようにする
必要があり，それは `scan1()` の抑止の印 (`c == 1`) を使う別の仕事である。

**この限界は GCC 4.7.4 には当たらない。** libiberty と libcpp の閉包で
マクロ本体に `defined` が現れるのは `system.h` の 1 箇所だけで，その
operand は `__cplusplus` —— 我々の pp が定義しない名前である。

## 検査

`tests/stage017` 第 6 部。上の 3 つの形を**stone の OS の上で**通す。

| | 中身 |
|---|---|
| a | GCC の原文をそのまま。pp17 は 4 で拒み，pp18 は通して正しい枝を選ぶ |
| b | operand が未定義の名前。pp18 が 0 を出す |
| c | operand が定義済みマクロ。**pp18 も 4 で拒む** (上の限界を固定する) |

**原文をそのまま置く。** 縮めて書くと「縮めた形では通る」ことしか
言えない。
