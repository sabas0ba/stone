# cc15q 説明文書

cc15q は C コンパイラの Stage 15 第 6 部の世代である。
[cc15p.sc](cc15p.sc) を出発点に，**静的な器の初期化子に文字列リテラルが
出てくると値が壊れる誤り**を直した。差は 2 か所 (補助の関数 1 つを
含めて計 27 行) である。

ソース [cc15q.sc](cc15q.sc) が正本である。

## 何が壊れていたか

同じ根から 2 つの形で出る。どちらも **翻訳は成功し，実行もでき，値だけが
違う** —— 台帳で `bad` と呼ぶ，いちばん悪い状態である。

### その 1: 関数内 `static` がポインタで受けるとき

```c
static void f(void) { static char *p = "hello"; printf("[%s]", p); }
```

`[hello]` ではなく `[L]` が出た。

文字列プールの flush は 2 系統ある。関数本体側は `spfn` の分だけ，
`gstrflush()` は `gspn` の分だけ `lsoff` を埋める。ところが
`gstrflush()` は呼び出し 3 か所すべてが `if (!ginfn)` で守られているので，
関数内 `static` のときは一度も呼ばれない。**任せた先が受け取っていな
かった。**

直しは本体側の flush の後ろで `gspn` の分も埋めるだけである。静的の
文字列は `plocal()` で先に積まれるので同じプールの中にあり，`gspofs` は
そのまま使える。

### その 2: 構造体の中の char 配列で受けるとき

```c
static const struct { char name[16]; char size[10]; } h = { "/", "2636" };
```

`h.name` に `"/"` ではなく**文字列の実体のアドレス**が入っていた。

`ginit1()` が対象の型を見ずに `t_str` をポインタとして扱っていた。
`ginit()` は最上位の `char s[] = "abc"` を実体として並べるが，構造体の
メンバへ降りる道 (`ginit1`) には同じ判断が無かった。関数内かどうかに
関係なく，大域の静的でも同じに壊れる。

直しは `ginit1()` に「対象が**文字型の**配列なら実体を並べる」を
`t_str` の分岐より前に置くだけである。並べ方は `ginit()` と同じで，
宣言した幅ぶん並べ，残りを 0 で埋める。

**「配列か」だけで見てはいけない。** 最初はそう書いたが，それだと

```c
static struct { char *p[1]; int n; } s = { "A", 5 };
```

の `p` にも並べてしまい，ポインタの枠に字が入る。参照先が不正になるので
値が違うでは済まず**落ちる**。文字列リテラルが実体として並ぶのは
**文字型の配列だけ**である (C89 3.5.7)。`ischararr()` で見分ける。

詳細は [../docs/stage017-cc.md](../docs/stage017-cc.md) 24〜25 章 (その 1)
と 27〜28 章 (その 2)。

## まだ直っていない形

```c
static char s[3][8] = { "ab", "cd" };
```

`ginit()` が多次元を平らに畳んだ後は要素型が `char` になっていて，
「配列」として見えなくなる。tcc は使っていないので世代を刻んでいない。
台帳 (`tests/stage015/probe/staticstr.c`) には測った結果を載せてある。

## なぜ気づかなかったか

**我々自身がどちらの形も使っていない。** 鎖のソース全体を探して 0 件
だった。tcc の `tccgen.c` (その 1) と `tcctools.c` の `arhdr_init`
(その 2) が使っており，そこで初めて表に出た。適合台帳の `staticinit` は
整数の初期化子しか見ていなかったので漏れた。`staticstr` を足してある。

**その 2 は，その 1 を直した後で見落としに気づいたものである。**
「関数内 `static` で，かつポインタのときだけ壊れる」と読んだのが狭
すぎた。`static char c[] = "xyz"` が正しく動くのを確かめて「配列は無事」
と一般化したのが誤りで，構造体の中に入ると別の道を通る。

```
sh tools/build.sh stage015

# cc15q0(cc15q.sc) -> cc15q     (正本。以降は固定点)
```

- 対象: RV32IM，リトルエンディアン
- ロードアドレス: 0x8000_0000 (QEMU virt, `-bios`)

## 鎖の成果物は変わらない

既存のソースはどちらの形も使っていないので，出るコードは変わらない。
`stage013/sh.c` `ed.c` `mk.c` の `.o` が cc15p のものと**バイト一致**
することを確かめた。固定点 (B2 == B3) も成立する。

## どこで使うか

鎖のプログラムは今までどおり cc15p で組む。cc15q を使うのは
**tcc の作業場だけ** である (`tools/tcc17.sh`)。cc19 が器の位置を
`/bin/cc15p` と焼き込んでおり，cc19 は凍結世代なのでその名前は変え
られないので，作業場では**名前を `cc15p` のままにして中身に cc15q を
置く** (`cmdlink cc15qcmd cc15q`)。
