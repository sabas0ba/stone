# cc15g 説明文書

cc15g は C コンパイラの Stage 15 第 3 部の 2 番目の世代である。
[cc15f.sc](cc15f.sc) を出発点に，**再配置の表を 8192 件から 16384 件に
広げた**。それだけの世代である。

ソース [cc15g.sc](cc15g.sc) が正本である。

## ビルド

```
sh tools/build.sh stage015
# cc15f(cc15g.sc) -> cc15g0     (1 段目)
# cc15g0(cc15g.sc) -> cc15g     (正本。以降は固定点)
```

SHA-256: 4f9ea5f323b2abb4489d569ef24ce989f7dd051d1a25262f808fedbec6bf6f3a

- 対象: RV32IM，リトルエンディアン
- ロードアドレス: 0x8000_0000 (QEMU virt, `-bios`)

## なぜ容量だけの世代を挟むのか

次の世代 (cc15h。浮動小数点の型) のソースを cc15f に食わせると，
再配置が 8191 件を超えて終了コード 6 で止まる。**cc15f 自身のソースが
既に上限の 200 件以内まで来ていた。**

拡張を cc15h に入れても解決しない。cc15h.sc をコンパイルするのは
**前の世代**であり，前の世代の表が小さいままだからである。だから
「表を広げるだけの世代」を先に挟む。cc14f が IR の配列を 8192 から
16384 に広げたときと同じ形である (dev-notes 1.3 の考え方)。

診断の手掛かり: 素の cc15f.sc に「呼出しを 200 個含む関数」を 1 つ
足すだけで再現した (呼出し 1 つが再配置 1 件になる)。

## 検証

- 固定点: cc15g(cc15g.sc) == cc15g0(cc15g.sc)
- 回帰: 表の幅は生成コードに影響しないので，既存ソースの `.o` は
  1 バイトも変わらない
