# cc15s --- C コンパイラ 第 15 世代 その 19

`cc15r` との差は `ginit()` と `ginit1()`。ソースは `stage015/cc15s.sc`。
経緯は [docs/stage017-cc.md](../docs/stage017-cc.md) 33 章。

## 直したもの: 多次元の char 配列を文字列で初期化する形

```c
static char m[2][8] = { "ab", "cd" };
```

が**通ってしまうが値が違う**状態だった。台帳 (`tests/stage015/ledger.txt`)
に `staticstr2 bad` として載せてあったもので，**`cc15q` から残っていた
最後の 1 つ**である。

`ginit()` は多次元を平らに畳んでから要素を読む。畳んだ後の要素型は
`char` であって配列ではないので，`cc15q` が `ginit1()` に入れた
「対象が配列なら実体を並べる」が効かない。要素 1 つに 4 バイトの再配置が
書かれ，配列の中身がアドレスになっていた。

## 直し: 畳んでよいかを，初期化子の書かれ方で決める

平らに畳むのは `int a[2][2] = {1,2,3,4}` のような書き方のための近道
である。`{"ab","cd"}` の波括弧の中の 1 つ 1 つは **行 (`char[8]`) を
初期化する**のであって，畳んだ後の要素 (`char`) を初期化するのではない。

見分け方は「`{` の次が `{` か文字列か」。そうなら下位の対象そのものを
初期化しているので**畳まない**。そうでなければ平らな並びなので今までどおり
畳む。**畳む道のバイト列は 1 バイトも変わらない。**

畳まなくなった分，`ginit1()` に**配列を波括弧で受ける道**が要る。要素型で
読み，宣言した幅に足りない分を 0 で埋める。`{ "ab" }` の形は波括弧が無い
ときと同じに実体を並べる (C89 6.5.7)。

**決めるのは要素ごとである。** 初期化子の先頭 1 回で全体を決めると，
C が許す**波括弧の省略** (`int a[2][2] = {{1,2}, 3, 4}`) を拒む。
宣言どおりの要素型 (`esd`) と最後まで畳んだスカラ型 (`es`) の**両方を
持ち**，`{` か「文字型配列に対する文字列」なら `esd` で，そうでなければ
`es` で読む。数え上げは要素数ではなく**バイト**で行う —— 1 つの要素が
1 / 2 / 4 バイトとは限らなくなったためである。

ついでに 2 つ。

- 埋める量を「要素の大きさぶん」に直した。1 / 2 / 4 を並べる書き方だと
  `char[8]` のような要素で 4 バイトしか埋まらない。**1 / 2 / 4 のときの
  出るバイト列は前と同じ**である
- `char a[8] = { "ab" }` も通るようにした

## 族を 16 の形でまとめて測った

| | 形 | `cc15r` | `cc15s` |
|---|---|---|---|
| 1 | `char m[2][8] = {"ab","cd"}` | **誤** | 正 |
| 2 | `char m[][8] = {"ab","cd","ef"}` | **拒む** | 正 |
| 3 | `char m[3][8] = {"ab","cd"}` (埋め) | **誤** | 正 |
| 4 | `char m[2][8] = {{'a','b'},{'c'}}` | **誤** | 正 |
| 5 | `char b[8] = { "ab" }` | **誤** | 正 |
| 6 | `char p[8] = "ab"` | 正 | 正 |
| 7 | `int a[2][2] = {1,2,3,4}` (畳む道) | 正 | 正 |
| 8 | `int a[2][2] = {{1,2},{3,4}}` | 正 | 正 |
| 9 | `struct { char a[8]; } s = {"xy"}` | 正 | 正 |
| 10 | `char *p[2] = {"gh","ij"}` | 正 | 正 |
| 11 | `int a[2][2] = {{1,2}, 3, 4}` | 正 | 正 |
| 12 | `int a[2][2] = {1, {2,3}, 4}` | 正 | 正 |
| 13 | `char m[2][8] = {"ab", {'c','d'}}` | **誤** | 正 |
| 14 | `int a[][2] = {{1,2}, 3, 4, 5}` | **拒む** | 正 |
| 15 | `char a[8] = { "ab", }` (末尾のコンマ) | **誤** | 正 |
| 16 | `char m[2][8] = { "ab", "cd", }` | **誤** | 正 |

**11〜16 はレビューで指摘を受けて足した。** 最初の直しは「`{` の次が
`{` か文字列か」を**初期化子の先頭 1 回だけ**見ていたので，C が許す
**波括弧の省略** (C89 6.5.7) を拒んでいた —— `cc15r` が通す形を壊して
いたことになる。要素ごとに決める形へ直した。

**1 つの形で確かめて族ぜんぶが無事だと思ったのが 3 度の誤りの元だった**
([docs/stage017-cc.md](../docs/stage017-cc.md) 27.4 / 31.4)。4 度目は
測ってから書いたが，**測る形を自分で選んでいた** —— 直した道は測り，
**直しが通り道を変えるほうの道**を測っていなかった。検査は
`tests/stage015/probe/staticstr2.c` がこの 14 を一度に見る。

## 鎖は変わらない。**tcc は変わる** (訂正)

既存のソースには多次元の char 配列を文字列で初期化する形は無い。
stage017 まで作り直しても全段が cached である。

**tcc は変わった。** 最初「tcc にも無い (探して 0 件)」と書いたが，
**探し方が誤っていた** —— `char 名前[..][..]` の形で探したので

```c
static char const ab_month_name[12][4] = {       /* tccpp.c 3384 行 */
    "Jan", "Feb", "Mar", ... };
```

の `const` が間に入る形を見落としていた。組み直したら `tccpp.o` が
151,220 → 150,752 バイト，`tcc` が 974,204 → 974,156 バイトになった。

**これは `cc15s` が tcc の潜在的な誤りを直したということである。**
`cc15r` までは，この 12 個の要素に**文字の実体ではなく再配置**が
書かれていた。つまり我々が組んだ tcc の `__DATE__` は月名として
別の場所を読んでいた。我々のビルドが `__DATE__` を使わないので
表に出ていなかっただけである。

21 章・29 章の突き合わせ (`Makefile` から出た tcc と命令を直に並べた
tcc) は両方を組み直せば成り立つ。再測して一致を確認した
(`tcc == tcc-mk`，974,156 バイト)。
