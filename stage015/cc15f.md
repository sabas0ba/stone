# cc15f 説明文書

cc15f は C コンパイラの Stage 15 第 3 部の最初の世代である。
[cc15e.sc](cc15e.sc) を出発点に，**第 2 部で埋め残した穴 3 つ**を
直した。浮動小数点はまだ入っていない。設計は
[stage015-tcc.md](../docs/stage015-tcc.md) 10.5。

ソース [cc15f.sc](cc15f.sc) が正本である。

## ビルド

```
sh tools/build.sh stage015
# cc15e(cc15f.sc) -> cc15f0     (1 段目)
# cc15f0(cc15f.sc) -> cc15f     (正本。以降は固定点)
```

SHA-256: f35ed358a96f5348138c38890da46fa1fe0ea0ed86fde7e0295b54928785836f

- 対象: RV32IM，リトルエンディアン，182924 バイト
- ロードアドレス: 0x8000_0000 (QEMU virt, `-bios`)

## 直した穴 3 つ

いずれも浮動小数点の実行時支援 ([rtfp.c](rtfp.c)) を第 2 部の cc に
通したときに出た ([stage015-tcc.md](../docs/stage015-tcc.md) 10.5)。

### 1. 64 bit の静的初期化 (通るが誤りだった)

`unsigned long long a[] = { 0x1122334455667788ULL };` が**下位語しか
書かなかった**。読む側は 8 バイト刻みなので，要素どうしがずれて
まったく別の値になる。拒まれもしないので，台帳でいう
「通るが誤り (bad)」。3 つの中でいちばん悪い。

直し: 定数式の畳込み評価器に上位語の側路 (`cchi` / `ccll`) を足し，
`ginit1` が幅 8 のときに下位語・上位語の順で 2 語書く。32 bit の値は
符号拡張する (`unsigned long long x = -1` が全 bit 1 になる C の規則)。

64 bit リテラルを**含む二項の定数式** (`0x100000000ULL + 5` など) は
まだ畳めないので拒む (終了コード 5)。黙って 32 bit で畳むと同じ穴を
別の場所に作ることになる。

### 2. 64 bit の値を条件に使えない (拒んでいた)

`if (x)` や `while (h)` の x が 64 bit だと終了コード 5 で拒んでいた。
上位語だけが立つ値 (`0x100000000ULL`) が偽になってはならないので，
下位語だけ見る形では通せなかったためである。

直し: 「条件の値」への変換 `rvc()` を足した。64 bit なら上下の語を
or して 1 語にする (条件は 0 かどうかしか見ないのでこれで足りる)。
`if` / `while` / `do` / `for` / `&&` / `||` / `!` の 7 箇所を `rv` から
`rvc` に替えた。

### 3. 実引数の幅が宣言と揃わない (拒んでいた)

`f(unsigned long long)` へ `f(7)` と int を渡すと語数が合わず拒んで
いた。C では実引数は仮引数の型へ変換されるので，これでは実際の C が
通らない (rtfp.c は `0ULL` と書いて避けた)。

直し: 記号表に**仮引数の 64 bit 位置のビット表** (`gllm`) を足した。
呼出しの際に宣言と突き合わせ，32 bit の実引数は符号に応じて上位語を
作って格上げし (`ext32`。既存の関数)，64 bit の実引数を 32 bit の
仮引数へ渡すときは下位語に切り詰める。

- 宣言が判らないとき (前方参照・関数ポインタ) は何もしない (従来どおり)
- 可変長引数の**可変部**も触らない (C の既定の格上げのまま)
- プロトタイプと定義でビット表が食い違えば拒む (個数の検査と同じ扱い)
- ビット表は 32 語ぶんしかないので，それより深い位置に 64 bit の
  仮引数が来る宣言は拒む (終了コード 6)

## 台帳

3 つの穴に対応する検査 `llinit` / `llcond` / `llargp` を足した。
いずれも ok。既存の 7 件と合わせて 10 件が通る。

## 検証

- 固定点: cc15f(cc15f.sc) == cc15f0(cc15f.sc) (B2 == B3)
- 回帰: sh / ed / mk のソースが cc10l と同じ `.o` になる (32 bit の
  コード生成は変えていない)
- rtfp.c / rt64.c が引き続き同じ `.o` になる
