# cc15an --- C コンパイラ 第 15 世代 その 40

`cc15am` との差は単項演算子の 3 か所と，幅 32 のビットフィールドである (註を除く)。ソースは `stage015/cc15an.sc`。
経緯は [docs/stage017-gcc.md](../docs/stage017-gcc.md) 8.15。

GCC の cc1 が要る libdecnumber・GMP を測る準備で見つけた。

## 直したもの 1: 符号なしの `-` と `~` の型 —— cc15am 以前からの不具合

単項の `-` と `~` の結果の型は，オペランドを格上げした型である (C89 6.3.3.3)。`cc15am` までは結果を一律に int にしていた。命令は同じでも型が違うので，**後に続く比較・割り算・右シフトの種類が変わる**。

| 式 | 正しい値 | `cc15am` |
|---|---|---|
| `~0U >> 1` | 2147483647 | 4294967295 (算術シフト) |
| `-1U >> 28` | 15 | 4294967295 |
| `(-1U) / 2` | 2147483647 | 0 (符号つきの割り算) |
| `~0U > 5` | 1 | 0 (符号つきの比較) |
| `-1U > 5` | 1 | 0 |

unsigned int はそのまま，それより狭い型 (unsigned char / unsigned short) は int にする。GMP は `~(mp_limb_t) 0` や `-(mp_limb_t) x` を至る所で使い，gcc/ にも `~(unsigned) 0 >> 1` の形がある。定数式の評価器は `cc15al` から符号の有無を持っているので，この誤りは式の中だけにあった。

## 直したもの 2: 単項の `+`

式の中の `+x` を受けていなかった (定数式の評価器は受けていた)。libdecnumber の decNumber.c が `result=+1;` と書く。値は格上げしたオペランドそのものである。

## 直したもの 3: 幅 32 のビットフィールド

幅は型の幅以下であればよい (C89 6.5.2.1)。`cc15am` までは 31 を超える幅を 2 で拒んでいた。GMP の gmp-impl.h が `gmp_uint_least32_t manl:32;` と書く。

幅のマスクを `(1 << bw) - 1` で作ると，32 ではシフトが 32 を法として 0 になり，マスクが 0 になる。`bfmask()` が語全体 (-1) を返す。

## ビルドチェーンは変わらない

`sh` / `ed` / `mk` を訳した `.o` は `cc10l` のものと 1 バイトも変わらない。符号なしの値に単項の `-` / `~` を掛けた結果を比較・割り算・右シフトへ渡す形と，単項の `+` と，幅 32 のビットフィールドは，既存のソースに無い。

## 測り方

`tests/stage015/probe/unaryu.c` は単項の結果をそのまま比較・割り算・右シフトへ渡し，unsigned char / unsigned short が int に格上げされることも見る。`tests/stage015/probe/bigarg.c` に幅 32 のビットフィールドを足した。

| | `cc15am` | `cc15an` |
|---|---|---|
| `tools/diff17.sh unaryu` | **我々だけが拒む** (単項の `+`)。`+` を外すと **値が違う** | 値が一致 |
| `tools/diff17.sh bigarg` | **我々だけが拒む** (幅 32) | 値が一致 |
