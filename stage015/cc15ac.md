# cc15ac --- C コンパイラ 第 15 世代 その 29

`cc15ab` との差は 5 か所 (註を除く)。ソースは `stage015/cc15ac.sc`。
経緯は [docs/stage017-gcc.md](../docs/stage017-gcc.md) 8.8。

**どれも [PR #93](https://github.com/sabas0ba/stone/pull/93) の branch が
見つけたもので、世代名の衝突のため取り込めていなかった** ——
あちらの `cc15ab` にある実装を、main の `cc15ab` の上へ derive し直した。

## 見つけ方 —— 差分試験をコンパイラ側へ広げた

これまでの差分試験 (`tools/diff17.sh`) は 64 bit 整数・浮動小数点・
文字列リテラルなど、**問題に遭遇してから足した**プローブの集まりだった。
ここでは逆に、GCC が要求する形から先に引いて 4 本を足している。

| プローブ | 何を測るか |
|---|---|
| `bitfld` | ビットフィールドの並び・出し入れ・初期化子 |
| `funcptr` | 関数ポインタの配列・構造体の中・引数・返却 |
| `intconv` | 整数の格上げ・符号・けた移動・割り算・複合代入 |
| `aggr` | 構造体の値渡し・共用体・入れ子の初期化子 |

**GCC 自身がビットフィールドと関数ポインタを多用している。** langhooks /
target hooks / gimple の walk はどれも「構造体に関数ポインタを並べ、
初期化子で埋め、添字で呼ぶ」形で書かれている。

期待値は書いていない。同じソースをホストの `gcc` にも走らせて出力を
突き合わせる。

## 直したもの

### 拒むだけのもの (`gap`) —— 3 つ

| 形 | `cc15ab` | `cc15ac` |
|---|---|---|
| `unsigned : 5;` / `unsigned : 0;` (無名のビットフィールド) | **1 で拒む** | 通る |
| `int (*tab[3])(int, int)` (関数ポインタの配列) | **1 で拒む** | 通る |
| `3[p]` (逆向きの添字) | **5 で拒む** | 通る |

1. **無名のビットフィールド** は C89 6.5.2.1 が定める詰め物の形である。
   幅 0 は「次の記憶単位へ送る」の意で、名前は付けられない。
   `memb()` が名前の無い時点で拒んでいた。無名のメンバは**引けない名前**
   (空文字) で表に入れる —— 名前で探す側と一致しないので、重複の検査から
   自然に対象外になる
2. **関数ポインタの配列** は、宣言子を内側から読めば「関数へのポインタの
   配列」である。`typedef` を挟めば前から通っていたが、直に書く形を
   `fnpdec1()` が拒んでいた。名前の直後の `[n]` を読み、`pdims()` と同じ
   順 (内側の次元から) で型を組む
3. **逆向きの添字** は `E1[E2]` が `*(E1 + E2)` だからである
   (C89 6.3.2.1)。足し算に順序は無い。`epost()` が左をポインタと
   決めつけていたので、両辺の型を見て入れ替えるようにした

### 通ったうえで値が違うもの (`bad`) —— 2 つ

**`cc15u` と同じ種類の不具合である。** 固定点もバイト一致も往復検査も検出しない。

| 形 | `cc15ab` が出す値 | 正しい値 |
|---|---|---|
| `static struct a g = {1,0,5,200};` (ビットフィールド 4 つ) | `{1,0,0,0}` | `{1,0,5,200}` |
| `d = dbl; d(2.5, 4.0) * 100` (関数ポインタ越しの `double`) | `400` | `1000` |

4. **静的な初期化子のビットフィールド。** `ginit1()` がメンバごとに記憶
   単位を書いていたので、同じ単位を共有する 2 つめ以降が**隣を 0 で上書きして
   いた**。記憶単位へ溜めてから書くように変え、単位が変わるところと
   普通のメンバの手前、そして構造体の終わりで書き出す
5. **関数ポインタ越しの 64 bit 返却。** 名前つきの呼出し (`ecall` /
   `c_call`) にある上位語の引取りが `ecalli` / `c_calli` に無かった。
   `ehi` を触らずに戻るので**直前の式の上位語が残り**、返却値の下位語と
   混ざる。さらに出力段が 1 語しか捨てないので**データスタックが 1 語
   ずれる** —— 値が違うだけでなく、その後の呼出しも狂う

`d(2.5, 4.0) * 100` が 400 になるのは、最後の引数 `4.0` の上位語が
残っていて、返ってきた `10.0` の下位語と組んだ結果である。

## 受けない形を 1 つ残した

関数ポインタを**返す**関数を直に書く形である。

```c
int (*pick(int k))(int, int);       /* 受けない */
typedef int (*binop)(int, int);
binop pick(int k);                  /* 通る */
```

宣言子の途中で「これは関数定義である」と判る形になり、宣言の読み方その
ものを組み直すことになる。`typedef` を挟めば書けるので、次の世代へ回す。

## ビルドチェーンは変わらない

既存のソースはどの形も使っていない。**使っていないからこそ、自分自身を
組む限り永久に表に出ない** —— 外部のソースをビルド対象として読ませるか、ホストと突き合わせる
以外に見つける方法が無い。`sh` / `ed` / `mk` を訳した `.o` は `cc10l` の
ものと 1 バイトも変わらない (`tests/stage015/test.sh` が見る)。

## 測り方

- `tools/diff17.sh` がホストの `gcc` と突き合わせる。ホストも
  `-std=c89 -pedantic-errors` と `-funsigned-char` で通す ——
  素の `char` が符号つきかは処理系定義で、RV32 (stone のターゲット) は符号なし、
  x86-64 のホストは符号つきである。**比較に使う処理系にはターゲットの規約を伝える**
- 語長に依存する形はプローブから外してある。ポインタを含む構造体の
  `sizeof` と `long` の最小値は ILP32 と LP64 で必ず違う
- `cc15ab` で同じプローブを走らせると `bitfld` / `funcptr` / `intconv` の
  3 本が食い違う (`STONE_DIFF_CC=tmp/build/cc15ab.bin`)。**直す前を
  再現できる**ようにしてある
