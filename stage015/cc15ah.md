# cc15ah --- C コンパイラ 第 15 世代 その 34

`cc15ag` との差は型の基底番号の初期値だけである (註を除く)。ソースは `stage015/cc15ah.sc`。
経緯は [docs/stage017-gcc.md](../docs/stage017-gcc.md) 8.12。

## 直したもの: 型の基底番号の範囲が重なっていた

型番号は「ポインタの深さ << 16 | 基底」で，基底の範囲が型の種類を表す。
`isstru()` / `isarr()` / `isfn()` はそれぞれ自分の範囲だけを見るので，
範囲が重なると 1 つの番号が 2 つの種類に同時に当たる。

| 基底 | `cc15ag` | `cc15ah` |
|---|---|---|
| char / int | 0 / 1 | 0 / 1 |
| 構造体表 (2048 個) | 2..2049 | 2..2049 |
| void と算術型 | **300..308** | 4096..4104 |
| 配列型表 (4096 個) | **1024..5119** | 8192..12287 |
| 関数型表 (1024 個) | **2048..3071** | 12288..13311 |

表の大きさを増やしたときに起点を動かしていなかった。`t_void` の註には
「構造体の 2..257 と離した値」とあり，構造体表が 256 個だった頃の配置の
ままである。

| 条件 | `cc15ag` で起きること |
|---|---|
| 構造体が 298 個を超える | void / signed char / short / unsigned int などが構造体と判定される |
| 構造体が 1022 個を超える | 配列型が構造体と判定される |
| 配列型が 1024 個を超える | 関数型が配列型と判定される |

**GCC の gcc/ の単位は構造体を 300 個以上宣言する。** `vec.h` の

```c
VEC_BASE(*vec_)->prefix.num = size_;      /* num は unsigned int */
```

の左辺が構造体と判定され，右辺と型が違うとして構造体の代入の検査
(`assign()`) で 5 になっていた。同じ番号の取り違えは，ビットフィールドの型
(`memb()`)，構造体の返却型 (`return`)，関数ポインタの呼出しでも起きる。

`cc15ah` は起点を 4096 / 8192 / 12288 へ移した。いずれも 65536 未満なので，
ポインタの段の符号化 (1 段ごとに 65536) は変わらない。

## どうやって見つけたか

`cc15ag` と同じく各 `exit(5)` を別々の値へ置き換えた調査用の版を組み
(`tmp/` の中だけ)，gcc/ の 75 単位が同じ箇所で止まることを確かめた。
`gcc/tree-mudflap` の `.i` の止まる位置は `vec.h` の `safe_grow` の
展開で，同じ関数はそれ以前の VEC 型では通っていた。違いは，その時点で
登録済みの構造体の数である。

小さな再現は次のとおり (`tests/stage015/probe/manystru.c`)。

```c
struct s0 { int a; }; ... struct s299 { int a; };   /* 300 個 */
struct p { unsigned int num; };
int main(void) { struct p x; x.num = 5; return x.num; }
```

## ビルドチェーンは変わらない

既存のソースは構造体を 298 個も宣言しない。`sh` / `ed` / `mk` を訳した `.o` は
`cc10l` のものと 1 バイトも変わらない。
