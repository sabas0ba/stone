# 適合台帳 (Stage 15。docs/stage015-tcc.md)
#
# 形式は Stage 14 の台帳と同じ (tests/stage014/ledger.txt)。
#
#   ok    <出力>   コンパイル・実行が通り，標準出力がその文字列になる
#   gap   <cc の終了コード>  cc がその終了コードで拒む。2 通りある ——
#                            (a) 未対応 (いずれ ok になる)
#                            (b) **誤った入力を正しく拒む** (ずっと gap のまま)
#                            どちらかは probe の註に書く
#   bad   <出力>   通ってしまうが結果が誤っている (**いちばん悪い状態**)
#
# 第 2 部は段階的に進める。実装した演算だけを通し，未実装は拒む
# (docs/stage015-tcc.md 6.1)。gap が ok に変わったら表を直す。
#
# 欄は空白で区切るので，期待する出力に空白を含めない (プローブ側で
# ':' を使う)。Stage 14 の台帳と同じ制約である。

# ---- 静的な初期化子の中の文字列リテラル (cc15q / cc15s で直した) ----
#
# Stage 14 の台帳には cc14g で測った bad が載っている。あちらは
# その世代の記録なので据え置き，こちらが最前線の姿である。
#
# staticstr  … cc15q で直した形 (関数内 static のポインタ・構造体の中の
#               char 配列・大域の static)
# staticstr2 … cc15s で直した形 (多次元の char 配列)。**族を 20 の形で
#               まとめて測る** —— 畳む道と，直しで壊していないことも
#               含めて見る。1 つの形で確かめて族ぜんぶが無事だと思った
#               のが 3 度の誤りの元だった (docs/stage017-cc.md 27.4)
#
# **行は分けたままにする。** 1 行にまとめると，どちらかが bad へ戻った
# ときにどちらか判らなくなる
staticstr    ok   y\n
staticstr2   ok   y\n
# staticstr3 … **拒むのが正しい形** (上の (b))。入れ子の初期化子が
#               その対象の幅を超える。外側に余りがあると総量の検査を
#               素通りし，溢れた分が**別の行に入る** (33.6)
# staticstr4 … 同じく**拒むのが正しい形**。スカラの初期化子を波括弧で
#               囲んだうえ中身が 2 つ以上ある (C89 6.5.7 の制約違反)。
#               cc15u まで黙って通し，溢れた分を隣へ入れていた。
#               **差分試験 (tools/diff17.sh) が見つけた** ——
#               staticstr2 の 12 番として ok で載せてあった (5.2)
staticstr3   gap   6
staticstr4   gap   6

# ---- 第 5 部の 2 で見つけた誤り (cc15r で直した) ----
#
# 文字列リテラルの sizeof が「ポインタの大きさ」になっていた形。
# 上の staticstr と**同じ根**で，あちらは初期化子の側，こちらは式の側
# である (docs/stage017-cc.md 31.4)。
strsizeof    ok   y\n

# ---- 5.1 (zlib / bzip2 を我々の器で訳す) で見つけた穴 (cc15t で直した) ----
#
# 型修飾子が宣言指定子の列の**途中**に来る形 (unsigned const char)。
# C89 6.5 は順序を縛らないが，ptype() は列の先頭と末尾でしか
# const / volatile を読んでいなかった。**拒む**ので bad ではないが，
# C89 が許す形を拒むのは穴である (docs/stage017-gcc.md 5.1)。
qualorder    ok   y\n

# ---- 5.1 の突き合わせで見つけた誤り (cc15u で直した) ----
#
# 複合代入 (a op= b) が符号を見ていなかった。a = a op b と同じ意味な
# のに，除算・剰余・右シフトの命令をトークンの並び (符号つき側) のまま
# 選んでいた。**二項の道は前から符号を見ていた** —— 片方だけ直っている
# 状態が Stage 10 から残っていた。
#
# **通ってしまうが値が違う** (bad) —— zlib の adler32 が誤った値を返す
# 形で表に出た。我々のソースは >>= / /= / %= を 1 つも使っていないので，
# **自分自身を組む限り永久に表に出ない**誤りだった。
asnsign      ok   y\n

# ---- 仮引数並びの抽象宣言子 (cc15w) ----
#
# プロトタイプでは仮引数の名前を省ける (C89 6.5.4)。関数ポインタも
# 例外ではないが，cc15v までは「( * 名前 ) ( 仮引数 )」の形でしか
# 読まず，名前の位置に ')' が来ると 1 で止まっていた。GCC 4.7.4 の
# include/obstack.h 193 行がこの形で，libcpp の 12 単位を塞いでいた
# (docs/stage017-gcc.md 8.3 の 4)。**読めるだけでは足りない**ので，
# 抽象宣言子で宣言した関数を実際に呼んで値を見る
fnpabs       ok   y\n

# ---- 型名の中の関数ポインタ (cc15x) ----
#
# cast の型名も識別子を含まない (C89 6.5.5)。宣言子は fnpabs と同じ
# だが**通る道が別**で，cc15w は仮引数並びの側だけを直していた。
# GCC の libcpp/symtab.c 65 行が obstack へ確保子を渡すときにこの
# cast を使い，3 単位が止まっていた (docs/stage017-gcc.md 8.3 の 9)。
# cast した関数ポインタを実際に呼び，呼び先が変わることまで見る
fnpcast      ok   y\n

# ---- 条件演算子と空ポインタ定数 (cc15y) ----
#
# C89 6.3.15 は「一方の被演算子が空ポインタ定数であれば，結果は他方の
# 型を持つ」と書いており，順序に依存しない。cc15x までは結果の型を
# then 側からだけ取っていたので (k ? 0 : p)->f が 5 になり，
# (k ? p : 0)->f だけがたまたま通っていた。代入や返却では左辺の型へ
# 変換する道を通るので隠れる。GCC の include/line-map.h 518 行が
# この形で，line-map.c がそのまま -> で辿る
# (docs/stage017-gcc.md 8.3 の 12)。**値まで見る**
condnull     ok   y\n

# ---- 括弧の中の宣言子の型修飾子 (cc15z) ----
#
# C89 6.5.4.1 の pointer は「* type-qualifier-list_opt」なので
# int (*const f)(int) は妥当である。括弧の外は pstars() が既に
# 読み飛ばしており，括弧の中の宣言子 (fnpdec1) だけが持っていなかった。
# GCC の libcpp/charset.c 455 行がこの形で，1 単位が止まっていた
# (docs/stage017-gcc.md 8.3 の 11)。読み飛ばした先が正しく繋がること
# (仮引数の位置がずれていないこと) まで見る
fnpqual      ok   y\n
